# Идентичность канала: результаты четырёх раундов ревью, ограничения и открытые кандидаты

**Статус:** решение зафиксировано в `channel-identity-substrate.md` (редакция 4, финал): матчинг = точное равенство, семья = проекция имени, категория вне адресации.
**Дата:** 2026-08-17
**Связанные документы:** `channel-identity-substrate.md` (редакция 3, вердикт NO-GO; редакция 4 — финал), шесть планов в `client-requests/`
**Зачем этот файл:** зафиксировать проверенные по коду факты и причины отказа трёх дизайнов, чтобы следующий заход
начинал с ограничений, а не с чистого листа.

---

## 1. Проблема

Находка идентифицируется парой `(ruleName, violationCode)`, обе половины — строки с точками. Четыре подсистемы
независимо решают вопрос «выбирает ли эта пользовательская строка эту находку», и все четыре используют один
матчер с семантикой `exact ∨ startsWith(pattern + '.')`:

| Подсистема                                    | Что матчит                | Файл                                                          |
| --------------------------------------------- | ------------------------- | ------------------------------------------------------------- |
| подавление `@qmx-ignore`                      | только `violationCode`    | `Policy/Inline/Contract/Suppression/Suppression.php:48`       |
| override порога `@qmx-threshold`              | только `ruleName`         | `Finding/Contract/Threshold/ThresholdOverride.php:51`         |
| выбор правил (`only_rules`, `--disable-rule`) | обе половины, дизъюнкцией | `Finding/Contract/Rule/RuleSelector.php:193-195`              |
| фильтры исключений по категории               | `ruleName`                | `Finding/Contract/Filter/{Namespace,Path}ExclusionFilter.php` |

### Четыре конкретных следствия

**1.1. Новый канал, названный точечным потомком существующего, молча попадает под все селекторы предка.**
`RuleMatcher::matches('architecture.coverage', 'architecture.coverage.source') === true` (проверено исполняемо).
Пользователь, заглушивший шумный канал покрытия, включает новый гейт и получает зелёную сборку без гейта.
Это заблокировало клиентский запрос `architecture-coverage-source-scope`.

**1.2. Две директивы принимают разные словари.** Отчёт печатает `coupling.cbo.class`; вставленное в
`@qmx-threshold`, это имя не матчится ни с одним правилом (`ThresholdOverride` смотрит `ruleName`, а правило
называется `coupling.cbo`) и уходит в тихий no-op. Это клиентский запрос `threshold-override-exact-matching`.

**1.3. Поддерживает ли правило override порога — недоступно снаружи.** Признак — реализует ли класс опций
`ThresholdAwareOptionsInterface` и вызывает ли правило `getEffectiveOptions()`. Отсюда невозможно построить
подсказку «вы имели в виду…»: нет обратного отображения «код → адресуемая единица». `computed.*` не поддерживает
override вовсе, и это тоже невидимо.

**1.4. «Можно ли принять находку в baseline» закодировано наличием/отсутствием объекта декларации.** Два
следствия, оба реальны:
- диагностики о директивах (`annotation.*`) эмитятся напрямую из `AnalysisPipeline`, владельца-правила у них нет,
  поэтому объявить форму — а с ней настраиваемую severity — негде;
- четыре архитектурные диагностики (`architecture.coverage`, `.unreachable-layer`, `.potential-shadow`,
  `.empty-template`) декларации имеют и потому **могут быть приняты в baseline как обычный долг кода**, хотя
  ADR 0017 строка 25 прямо требует обратного: «configuration diagnostics are not baselineable». В текущем
  `qmx-baseline.json` таких записей нет — дефект латентный.

## 2. Ограничения, установленные по коду

Это главная ценность файла: любой будущий дизайн обязан им удовлетворять. Все проверены прямым чтением кода или
исполняемой командой; там, где проверка косвенная, это сказано.

**2.1. Точечная иерархия — не соглашение, а протестированный инвариант.**
`ChannelDeclarationFixtureDriftTest::everyDeclaredViolationCodeEqualsOrIsPrefixedByItsRuleName` требует, чтобы код
канала был равен имени правила либо начинался с `имя_правила.`. Любой дизайн, объявляющий группировку свободной,
конфликтует с этим тестом.

**2.2. Имя не разрешается в единственный уровень.** 38 из 51 объявленного канала имеют `violationCode ===
ruleName` (посчитано по `declared.txt`). Для них одна строка одновременно называет производителя, семью и канал.
Схема «имя → ровно одна сущность» требует необъявленного приоритета уровней.

**2.3. Потребители различаются половиной пары, а не уровнем.** См. таблицу §1. Практическое следствие:
`@qmx-ignore architecture.layer-violation` сегодня гасит **один** канал (тот, чей код равен строке) и не трогает
четыре диагностики того же правила. Любое введение адресации по производителю расширит этот захват до пяти.

**2.4. У открытых семей произвольная глубина префикса.** Грамматика имени вычисляемой метрики —
`prefix.identifier(.identifier)*`, то есть `computed.team.quality.score` легально
(`ComputedMetricDefinition.php:73-97`). Проверено исполняемо: `matches('computed', 'computed.team.quality.score')
=== true`. Такой канал сегодня адресуется четырьмя разными глубинами префикса.

**2.5. Категория объявлена, но расходится с префиксом имени.** `ComputedMetricRule::getCategory()` возвращает
`RuleCategory::Maintainability` при `NAME = 'computed.health'`. Сегодня `Maintainability->matches('computed.health')`
даёт `false` (матчинг префиксный); при переходе на объявленное членство даст `true`. То есть «транскрипция текущего
поведения» на уровне категории невозможна без изменения захвата.

**2.6. Реальное использование в репозитории узкое.** Пятнадцать живых `@qmx-ignore`: восемь `health.cohesion`, по
несколько `design.data-class`, плюс единичные `design.god-class`, `coupling.instability`,
`code-smell.empty-catch`, `code-smell.boolean-argument`. **Категорийных подавлений ноль.** Тридцать четыре живых
`@qmx-threshold` — все с точными именами правил. Следствие для любого плана: корпус собственного кода **не может**
служить оракулом совместимости для категорийного, префиксного и wildcard-матчинга — таких кейсов в нём нет, и
тест на нём будет зелёным при сломанной семантике.

**2.7. Строка идентичности — внешний контракт в пяти местах.** `ruleId` в SARIF, `check_name` в GitLab, `source`
в Checkstyle, поля `code` и `channel` в JSON. Любое переименование канала — breaking для потребителей отчётов.

**2.8. Эмиссия находки имеет три разные формы, и статический охранник видит две.**
- прямо в классе правила;
- декларация в абстрактном предке через позднее статическое связывание (`static::NAME`) — 12 правил
  (9 наследников `AbstractCodeSmellRule`, 3 наследника `AbstractSecurityPatternRule`);
- конструирование в отдельном классе-коллабораторе: `CodeSmellFinding`, `SecurityPatternFinding`,
  `ComputedMetricFindingBuilder` — это `final readonly` классы **вне цепочки наследования правила**.

`ChannelEmissionStaticGuardTest` обходит правило и его предков, поэтому **третью форму не видит**. Утверждение
«дрейф идентичности уже ловится машинно» верно для правил первой и второй формы и неверно для двенадцати правил
третьей.

**2.9. Потребителей идентичности больше, чем в перечислении.** Помимо пятнадцати call-site'ов общего матчера в
шести файлах есть точечные читатели по литералам: `RemediationTimeRegistry.php:123-124` сравнивает `ruleName` со
списком литералов и отдельно с `'computed.health'`; `RuleNameValidator.php:59-61` содержит собственную копию
трёхсторонней логики матчера; `BaselineConfiguredThresholds::axisOf` отрезает префикс. Перечисление,
построенное только вокруг общего матчера, их не видит.

## 3. Три отвергнутых дизайна и причина отказа

| Редакция | Дизайн                                                 | Почему отказал                                                                                                                                                                                 |
| -------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | объявленные семьи + белый список режимов у потребителя | «Семья» осталась строковым префиксом, то есть §1.1 не решался вообще; режим выбирался в точке вызова, а для двухрежимного потребителя не выбирался ничем                                       |
| 2        | один режим на потребителя                              | Фактический режим override — префикс по именам правил; объявление «адресует канал» противоречило коду, а обещание «поведение не меняется» — самому объявлению                                  |
| 3        | три объявленных уровня + единое разрешение имени       | Нарушает 2.2 (имя неоднозначно у 38 из 51 канала), 2.3 (ось не та), 2.4 (глубина произвольна), 2.5 (категория не транскрибируется). Обоснование опиралось на несуществующую аннотацию — см. §5 |

Общая причина всех трёх: попытка заменить словарь адресации целиком там, где заблокирован был один сценарий
(§1.1). Каждая редакция расширяла поверхность изменения и ломалась в новом месте.

## 4. Открытые кандидаты

### 4.1. Узкий инвариант столкновения имён (не проверен)

Формулировка: **код канала не может быть точечным потомком кода другого объявленного канала, если их производитель
не объявил их одной семьёй.** Проверяется на этапе объявления, как существующие структурные инварианты.

Что закрывает: §1.1 — единственный сценарий, который реально заблокировал клиентский план.
Чего не трогает: ни один существующий селектор, ни один пользовательский конфиг, внешний контракт §2.7.

Что надо проверить, прежде чем принимать:
- нет ли сегодня легальных пар, нарушающих инвариант (то есть не покраснеет ли он на текущем дереве);
- как он взаимодействует с открытыми семьями §2.4, где имена появляются в рантайме;
- достаточно ли «объявили одной семьёй» как разрешающего условия, или нужна явная декларация «этот канал
  сознательно вложен в тот».

### 4.2. Три независимые починки

Не зависят от адресации и могут исполняться по отдельности:

- **свести два реестра идентичности в один авторитет с узкими представлениями.** Сейчас
  `ChannelDeclarationRegistryInterface` (какая форма) и `RuleChannelRegistryInterface` (кто производит) разделены
  по задаваемому вопросу, наполняются из одного источника и обслуживают непересекающиеся множества потребителей;
- **объявить адресуемость override** вместо вывода из наличия интерфейса у класса опций, и добавить обратное
  отображение «код → производитель» для подсказки (§1.3);
- **расщепить форму и принимаемость** (§1.4). Сужение, вытекающее из ревью: «не принимается ратчетом; принимается
  только явным объявлением намерения в конфигурации» — потому что `pending: true` на слое и `coverage: ignore`
  уже являются легальными способами принять конфигурационную ошибку. Плюс `ConfigurationError` обязан влечь
  эффективную severity не ниже `Warning`: иначе для каналов с дефолтом `Info` подложка убирает единственный гейт
  (пробитие baseline), не добавив обязательного.

## 5. Ошибки процесса, стоившие раундов

Перечисление в этой области ломается тихо. За сессию четыре ошибки:

1. Артефакт объявил `excluded.txt` отсутствующим; второй артефакт его в это же время цитировал. **Расхождение
   двух артефактов между собой — самый дешёвый детектор**, и никто его не применял.
2. «Конкатенация — 3 правила» → 7 → фактически 4: одно вхождение оказалось построением имени спана профайлера.
3. Направление обратного матчинга описано наоборот. Источник — противоречивый докблок `RuleMatcher::anyReverseMatches`:
   первая строка описывает реализацию верно, вторая фраза — обратное. Докблок надо исправить независимо от судьбы плана.
4. **Обоснование редакции 3 опиралось на несуществующий факт.** В плане было записано «в `src/` живёт реальная
   аннотация `@qmx-ignore complexity`». Единственное вхождение — экранированный бэктиками пример формата в
   докблоке `Suppression.php:15`; парсер такие области вырезает (правило 8 в `CLAUDE.md`). Категорийных подавлений
   в репозитории нет. Поймано тремя рецензентами независимо.

Отсюда два практических правила для следующего захода:
- разбивку по множеству правил генерировать скриптом, а не писать в прозе, и печатать слепую зону скрипта;
- перед тем как строить решение на конкретной аннотации или конфигурационном ключе, проверять, что он живой:
  экранированные примеры в докблоках выглядят в grep идентично реальным директивам.

## 6. Что проверено и что нет

**Проверено исполняемо:** префиксный захват `architecture.coverage` → `.source`; захват открытой семьи `health` →
`health.cohesion` и `computed` → `computed.team.quality.score`; направление `anyReverseMatches`; 38 из 51 канала с
совпадающими половинами; 41 конкретное правило; 51 объявленный канал; пять путей ветвления по отсутствию
декларации в `Policy/Baseline/**`; отсутствие категорийных подавлений; `getCategory()` у `ComputedMetricRule`;
`architecture:check` краснеет на незарегистрированном документе.

**Проверено чтением:** оба структурных инварианта drift-теста; пустой skip-лист охранника эмиссии; норма ADR 0017
строка 25; формы эмиссии §2.8; отсутствие `qmx-suppressions.txt` в репозитории (единственное вхождение строки —
в клиентском threshold-плане, который ссылается на него как на существующий механизм).

**Не проверено:** тела четырёх сборочных проходов; миграторы формата baseline; влияние на сериализуемую нагрузку
границы воркеров; поведение `mode: suppress` из ADR 0017 относительно небазлайнимых каналов; полнота правок
документации по ~62 файлам.

## 8. Как вести следующий заход

**Артефакты перечислений держать в рабочем дереве.** Артефакты этой сессии лежали в session-скоупном scratchpad
(`/private/tmp/...`) и до следующей сессии не доживут. Хуже: песочница Qwen блокирует доступ за пределы рабочей
директории, поэтому межартефактную сверку он выполнить не смог и честно об этом сообщил — задание оказалось
частично неисполнимым не по его вине.

**Перечисления добывать заново, а не наследовать.** Это не противоречит предыдущему пункту: сохранять надо
**метод** (скрипт ниже) и **названные слепые зоны**, а не результат. Унаследованная таблица опаснее отсутствующей
— она выглядит выполненной работой. За эту сессию перечисления ошиблись четырежды (§5).

**Что писать в бриф рецензенту**, чтобы не получить пересказ уже закрытого: ссылку на §7.1 и §7.2 этого файла с
явным «эти пункты установлены, повторный отчёт о них не нужен», и на §7.3 с «эти гипотезы проверены и отклонены».

**Особенности прогонов, замеченные за сессию:** обёртка Codex дважды вернула код `141` (SIGPIPE) **после** того,
как полный ответ был записан — вывод при этом целый, отказом это не является; DeepSeek в одном прогоне вернул
пустой ответ с кодом `3`, застряв на повторных попытках прочитать недоступные пути, и заработал после явного
указания их не читать; Qwen требует сохранять отчёт в файл и читать обратно, потому что `-p` обрезает вывод до
последнего сообщения.

**Полезность рецензентов на плановом материале** (в отличие от кода): native `comprehensive` даёт наибольшую
глубину и единственный запускает реальные гейты — он и обнаружил, что `architecture:check` краснеет из-за
незарегистрированного файла плана; Codex сильнее всех на когерентности контрактной поверхности; DeepSeek дешёвый и
ценен списком отклонённых гипотез; Qwen лучше всех структурирует отчёт и честно отделяет проверенное от
непроверенного.

## Приложение A. Классификация способов построения идентичности

Скрипт держать здесь, а не в scratchpad: он воспроизводит таблицу за секунду и печатает свою слепую зону.

```bash
#!/usr/bin/env bash
# Классифицирует способ построения violationCode по каждому конкретному правилу.
# СЛЕПЫЕ ЗОНЫ (важнее самой таблицы):
#  - делегирование абстрактному предку не разворачивается: бакет delegated-to-base
#    смешивает LSB-объявление в предке и эмиссию в классе-коллабораторе;
#  - косвенность через локальную переменную попадает в бакет other (см. CboRule);
#  - регексы гоняются по всему файлу, поэтому строка из channelDeclarations()
#    может определить метку эмиссии;
#  - эмиссия через инжектированный коллаборатор не видна вообще.
set -euo pipefail
cd "${1:?repo root required}"
for f in $(find src -name '*Rule.php' ! -name '*Interface.php' | sort); do
  grep -q '^abstract class' "$f" && continue
  base=$(basename "$f" .php)
  em=$(grep -c 'violationCode:' "$f" || true)
  if [ "$em" -eq 0 ]; then
    parent=$(grep -oE 'extends [A-Za-z]+' "$f" | head -1 | awk '{print $2}')
    echo "delegated-to-base|$base|${parent:-?}"
  elif grep -qE "violationCode: *match" "$f"; then echo "match-literals|$base|-"
  elif grep -qE "violationCode: *self::NAME \. '" "$f"; then echo "concat|$base|-"
  elif grep -qE "violationCode: *self::(COVERAGE|UNREACHABLE|POTENTIAL|EMPTY)[A-Z_]*" "$f"; then echo "sibling-const|$base|-"
  elif grep -qE 'violationCode: *(self::NAME|\$this->getName\(\)),' "$f"; then echo "equals-name|$base|-"
  else echo "other|$base|-"; fi
done
```
