## 0. Зафиксированное решение: что считается ухудшением (читается отдельно от плана)

**Решение принято 2026-07-28: вариант C (гибрид). Развилка закрыта — ниже входное условие
плана, а не предмет выбора.**

Гейт валит сборку на трёх и только на трёх вещах:

1. **новое нарушение** — ключа не было в базе (`Absent`);
2. **рост severity** или **рост кратности** по существующему ключу (`Escalated`, `Surplus`);
3. **ухудшение метрики из фиксированного списка §0.2** (`Worsened`).

Всё остальное — в том числе ухудшение символьных метрик уровня метода и класса (CCN,
LCOM, CBO и подобные) — подаётся **информационно**, отдельной секцией, и на exit-код не
влияет (§4.7, §8.4).

### 0.1 Почему не A и не B

**A** («только новые нарушения, метрики не смотрим») сознательно пропускает класс реальных
деградаций: нарушение уже было, severity та же, а покрытие слоёв упало 98 → 60 %, цикл
вырос с 3 до 12 классов, health неймспейса упал 61 → 11. Для персоны «CI Pipeline» из
PRODUCT_VISION («Did this PR make things worse?») этого мало.

**B** («гейтим ухудшение любой метрики») покупает полноту ценой доверия к гейту: значение
метрики шумно на per-symbol уровне — CCN метода меняется при извлечении хелпера и переносе
соседнего кода, — а гейт, падающий на «+1 CCN» в чужом методе, приучает команду к
`--fail-on=none`, то есть отключает и полезную часть. Плюс требует метаданных направления
у всех ~40 правил.

**C** ставит границу ровно там, где проходит граница шума: агрегатные метрики низкой
кардинальности гейтуют, символьные — показываются. Аргумент про шум верен для CCN метода и
неверен для покрытия слоёв: 98 → 60 не бывает побочным следствием рефакторинга, это
удаление слоя или массовое перемещение классов.

### 0.2 Фиксированный список гейтируемых метрик

| 1   | Покрытие слоёв — `ruleName = violationCode = architecture.coverage` (`LayerViolationRule::COVERAGE_DIAGNOSTIC_NAME`), % классов, попавших хотя бы в один объявленный слой | Project            | меньше | abs 1.0 п.п., rel 0          |

**Правило значимости:** ухудшение учитывается, только если превышены **оба** допуска:
`|Δ| > abs` **и** `|Δ| / |base| > rel`. Допуск `0` означает «любое ухудшение значимо».

**Настройка:** секция `comparison.tolerances.<metric-id>.{abs,rel}` в `qmx.yaml`
(константы в `ConfigSchema`, см. П9). Идентификаторы метрик — те же, что в первой колонке.
Допуски входят в `EffectiveRuntimeConfiguration` и, следовательно, в отпечаток конфигурации
и ключ кэша базы (§5, §7.2).

**Явные исключения из списка:**

- пользовательские `computed.*` метрики (не `health.*`) **не гейтуются**: их множество
  задаёт пользователь, оно неограничено, а «перечислимый список» с неограниченной частью
  перестаёт быть списком;
- `architecture.layer-violation`, `architecture.unreachable-layer`, `architecture.empty-template`,
  `architecture.potential-shadow` метрики не несут — их изменения ловятся facets (§4.2);
- любые символьные метрики (`complexity.*`, `coupling.*`, `cohesion.*`, `design.*`,
  `size.*`) — только информационно (§4.7).

> **Замечание по реализации (проверено по коду).** У записей 2 и 3 `metricValue` уже
> заполняется (`CircularDependencyRule:106`, `CodeDuplicationRule:103`). У записи 1 —
> **нет**: диагностика покрытия печатает счётчики в `message` и не ставит `metricValue`
> (`LayerViolationRule:620-640`). Поэтому П6 обязан добавить `metricValue` покрытию —
> долю классов, попавших хотя бы в один объявленный слой, в процентах (0–100, один знак).
> Если общее число классов в этой точке правила недоступно, агент **останавливается и
> сообщает оркестратору**, а не подменяет носитель счётчиком незакрытых классов: смена
> носителя переворачивает направление «хуже» и расходится с документацией и каталогом.

### 0.3 Почему шум не проблема для каждой из четырёх

Это несущий аргумент варианта C, поэтому он зафиксирован по каждой записи отдельно.

**1. Покрытие слоёв.** Кардинальность — ровно одно значение на проект. Величина меняется
только когда классы входят в объявленные слои или выходят из них; рефакторинг внутри слоя
не двигает её вообще, а вывод класса из-под критерия членства — это и есть содержательное
изменение архитектуры. Ложное срабатывание физически не может дать вал: одна строка отчёта
на прогон, объяснимая за один взгляд.

**2. Размер цикла.** Величина целочисленная и дискретная, циклов в здоровом проекте
единицы. Рост SCC невозможно получить форматированием или переносом кода — он требует
именно нового ребра зависимости. Извлечение класса может только разбить SCC; если
извлечение втянуло в цикл новый класс — это ровно та регрессия, ради которой правило
существует. Поэтому допуск 0: шум отсутствует по построению.

**3. Размер блока дублирования.** Кардинальность — число обнаруженных блоков, единицы-
десятки на проект. Рост блока означает, что копипасту дописали, — прямая цель правила.
Единственный источник шума, переформатирование внутри блока, сдвигает счётчик строк на
единицы и поглощается допуском (5 строк **и** 10 %).

**4. Health на Namespace/Project.** Это средневзвешенные агрегаты по десяткам-сотням
символов: per-symbol шум в них усредняется — ровно то свойство, которого нет у самих
символьных метрик. Дрожание CCN одного метода сдвигает health неймспейса на доли допуска.
Кардинальность — число неймспейсов (десятки), поэтому срабатывание адресно: называется
конкретный неймспейс и дельта, а не тысяча методов.

**Почему символьные исключены.** Их кардинальность — тысячи (каждый метод), каждое
значение индивидуально шумно при обычном рефакторинге, а срабатывание неатрибутируемо:
«CCN вырос у 40 методов» не говорит, что чинить. Это стена шума, а не сигнал.

### 0.4 Архитектурное ограничение: список живёт в одном месте

**Требование оркестратора, обязательное к исполнению.** Перечень гейтируемых метрик
существует в коде **ровно в одном месте** — `src/Baseline/Comparison/GatedMetricCatalog.php`,
— перечислим и покрыт тестом, который падает при любом его расползании.

Проверяемый DoD (пакет П9):

- Правила **не** объявляют направление «хуже» и не участвуют в решении о гейтировании.
  Никаких per-rule метаданных направления (это был механизм варианта B). Единственный
  источник истины — каталог.
- `GatedMetricCatalog::all()` возвращает детерминированный перечислимый список записей
  `GatedMetric` (id, `ruleName`, `violationCode` или множество кодов, применимые
  `SymbolType`, направление, дефолтные `abs`/`rel`).
- **Тест-пин инвентаря:** каталог сравнивается с литеральным списком, выписанным прямо в
  тесте (все поля каждой записи). Добавление, удаление, переименование или смена допуска
  валят тест.
- **Тест-потолок:** `count(GatedMetricCatalog::all()) === 4`. Рост требует поправки к
  ADR 0016, а не правки константы.
- **Архитектурный тест:** типы `GatedMetric` / `MetricDirection` не встречаются в `src/`
  нигде, кроме `GatedMetricCatalog` и `WorsenedDetector` (проверяется grep'ом; правила и
  коллекторы обязаны остаться незатронутыми).
- **Синхронность с документацией:** таблица гейтируемых метрик на сайте сверяется с
  каталогом тестом (DoD П10), чтобы обещание в документации не разошлось с кодом.

**Обоснование, которое обязано остаться в плане и в ADR.** Если список начнёт разрастаться
по правилам — сегодня добавили `complexity.cyclomatic`, завтра `coupling.cbo` — вариант C
выродится в вариант B, а заодно воспроизведёт **ровно ту продуктовую развилку, ради отказа
от которой пользователь отверг graph views в соседнем плане**: два расходящихся
представления одной реальности («что гейтует» и «что показывает»), границу между которыми
придётся объяснять всю оставшуюся жизнь продукта. Фиксированный, короткий, машинно
пинованный список — это цена того, чтобы обещание оставалось однострочным и проверяемым.

### 0.5 Формулировка обещания (единая для документации, `--help` и ADR)

Канонический текст (EN, репозиторный язык):

> `--new-since` reports findings that are absent from the base revision: violations that did
> not exist there, violations whose severity or count increased, and regressions in a fixed
> set of aggregate metrics (layer coverage, dependency-cycle size, duplicate-block size,
> namespace- and project-level health scores). Per-symbol metric changes, such as a method's
> cyclomatic complexity, are reported separately and never affect the exit code.

**Запрещённые формулировки** — «did not get worse», «не стало хуже», «no regressions»,
«see only the violations you introduced» — без непосредственно следующей за ними явной
границы. Проверяется машинно: grep по `website/docs/**` и по строкам `--help` в `src/`
на этот список даёт либо пусто, либо совпадения в абзацах, где рядом стоит перечисление
границ (DoD П10). Существующая формулировка «Focus — see only the violations you
introduced» у `--report` неверна уже сегодня и чинится тем же пакетом.

**Влияние на план:** пакет metric-aware regression policy **обязателен** (П9); нумерация
пакетов, волн и зависимостей в §14 это учитывает.

## 1. Резюме

`--report=git:REF` не сравнивает состояния — он строит индекс изменённых файлов и
оставляет нарушения, попавшие в этот индекс. В тронутом файле показывается весь
исторический долг (замер: 9 warning'ов, из них 7 предшествовали диапазону).

Предлагается **сравнение с базовой ревизией**: полный анализ снапшота базовой ревизии →
множество нарушений базы → вычитание из текущего множества.

Ключевые решения (звёздочкой отмечено изменённое относительно редакции 1):

| Вопрос                         | Решение                                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Как получить базу              | Материализация через `git worktree add --detach` + полный повторный анализ                                         |
| ★ Идентичность                 | **Отдельная** comparison identity: ключ правила + structured facets + content anchor. `ViolationHasher` не трогаем |
| ★ Конфигурация обоих прогонов  | `EffectiveRuntimeConfiguration` — снимок после всех CLI-мержей, включая `--rule-opt` и алиасы                      |
| ★ Изоляция базового прогона    | Свежий контейнер + **scoped save/restore статических холдеров** + per-run копия architecture registry              |
| ★ Мультимножество              | Детерминированный consumption-алгоритм с severity-упорядочиванием (см. §4.4)                                       |
| ★ Порядок фильтров             | `--new-since` **отключает** git-scope для гейтового множества                                                      |
| ★ Композиция с baseline-файлом | Baseline-файл — wildcard-исключение ключа, задокументировано; Surplus для таких ключей не работает                 |
| ★ Ключ кэша базы               | SHA + отпечаток **effective** конфигурации + нормализованные пути + suppression policy + версия схемы сравнения    |
| ★ Материализация снапшота      | Явная политика для partial clone / submodules / LFS; `git archive` fallback удалён                                 |
| ★ Уборка                       | Owned-manifest lease, не глобальный `git worktree prune`                                                           |
| ★ Стоимость                    | Числа не заявляются до замера. Контентный ключ AST-кэша сам по себе даёт мало (см. §7)                             |
| CLI                            | ★ `--new-since=<git-ref>` со **строго обязательным** значением                                                     |
| База недоступна                | Fail loudly, exit 3, ★ shallow — подсказка, а не причина отказа                                                    |
| ★ Что гейтует вердикт          | Новые ключи, рост severity/кратности и ухудшение **четырёх** метрик из `GatedMetricCatalog` (§0.2)                 |
| ★ Символьные метрики           | Информационная секция «metric drift», exit-код не трогает (§4.7, §8.4)                                             |
| ★ Границы обещания             | Канонический текст §0.5; «did not get worse» запрещено, проверяется grep'ом                                        |

## 3. Установленные факты о текущем коде

Проверено по коду на рабочем дереве от 2026-07-28 (дерево не чистое: в нём уже
приземлены `NamespaceExclusionFilter` в конвейере и настраиваемые severity диагностик
`LayerViolationRule`).

1. `ViolationFilterPipeline::filter()` — пять шагов: baseline-файл → suppression →
   path exclusion → **namespace exclusion** → git scope. `GitScopeFilter` создаётся
   локально (`new`), не инжектится.
2. `NamespaceExclusionFilter::shouldInclude()` пропускает все правила категории
   `architecture` мимо namespace-исключений (проверка по префиксу
   `RuleCategory::Architecture->value . '.'`).
3. `ViolationHasher::hash()` = `ruleName | namespace | type | member | violationCode`
   (+ `dependencyTarget->toCanonical()` и `dependencyType` при наличии). Намеренно
   исключены строка, параметры, сообщение, severity. Значение метрики и порог тоже
   не входят.
4. `Violation` **не имеет** поля для структурированных дискриминаторов. Данные о цикле
   существуют только внутри `message` и JSON внутри `recommendation`.
5. `BaselineGenerator` дедуплицирует по `canonical:hash`; `BaselineFilter` удаляет все
   экземпляры ключа. Формат v5 severity и кратность не хранит.
6. Проектные диагностики (`SymbolPath::forProject()`) имеют `Location::none()`
   (`pathString() === ''`) и namespace-sentinel `__PROJECT__`. `GitScopeFilter`
   отбрасывает их всегда, включая нестрогий режим. Признак для тестов —
   `SymbolPath::getType() === SymbolType::Project`.
7. `CacheKeyGenerator::generate()` = `hash('xxh128', realpath | mtime | size | cacheVersion)`.
   Для снапшота в другом каталоге ключи не совпадут ни по одному компоненту.
8. `FileProcessor::process()` использует кэш только для шага «parse». Обход коллекторов,
   извлечение метрик и два прохода `NodeFinder` (suppressions, threshold overrides)
   выполняются всегда.
9. `ConfigurationDocument` resolves root-bound values for each invocation;
   cache storage may remain warm without retaining a prior project's Composer path.
10. Project namespace discovery uses the invocation working directory's
    `composer.json` and falls back to source parsing. It has no configurable
    strategy or alternate Composer-path field.
11. Состояние, которое должно быть изолировано между прогонами: `ProfileSession`,
    каталог определений ComputedMetrics и owner-local PHPDoc configuration;
    `RuntimeConfigurator` сбрасывает их до разрешения нового документа.
    `WorkerBootstrap::$processor` живёт в
    worker-процессах, ключ мемоизации включает `projectRoot` и `cacheDir`).
12. `ArchitectureConfiguration` изменяем по факту: `registry()->bindGraph($graph)`
    в `ArchitectureProcessor::prepare()`. Объект достижим из `ConfigurationDocument->architecture`.
13. `AmphpParallelStrategy` создаёт `ContextWorkerPool` на прогон и гасит его в `finally`.
14. `ContainerFactory::create()` собирает и компилирует контейнер на лету, без дампа.
15. `OutputConfigurator` авторегистрирует `src/Baseline/*` целиком (exclude —
    `Baseline.php`, `BaselineEntry.php`, `Suppression/Suppression.php`) и вручную
    перечисляет аргументы `CheckCommand`.
16. Symfony `ArgvInput::addLongOption()` для опции с необязательным значением **забирает
    следующий токен**, если он не начинается с `-`. Значит `qmx check --new-since src/`
    при `VALUE_OPTIONAL` съест `src/` как значение опции, а не как анализируемый путь.
17. `ChangedFile` хранит `oldPath` для статусов `R`/`C` — данные для карты переименований
    файлов уже есть.
18. `vendor/` исключён из анализа по умолчанию; снапшот не требует `composer install`.

## 4. Целевая семантика: идентичность и новизна

### 4.1 Отдельная comparison identity (не baseline identity)

Baseline identity (`ViolationHasher`) намеренно груба: она обязана переживать рефакторинг
и смену порогов, а её выход попадает в версионируемый файл v5. Для сравнения ревизий
нужна **более точная** функция, и её нельзя получить ужесточением `ViolationHasher`:
любое изменение хеша сломает все существующие baseline-файлы.

Решение: `ComparisonKey` — новая, независимая функция идентичности. `ViolationHasher`,
`Baseline`, `BaselineEntry`, формат v5 остаются нетронутыми (проверяется DoD пакета).

`ComparisonKey` собирается из трёх уровней; каждый уровень применяется, если данные есть:

- **Уровень 1 — символьный ключ.** `ruleName | symbolPath->toCanonical() | violationCode`
  (+ `dependencyTarget->toCanonical()` и `dependencyType` при наличии). По сути то же,
  что даёт baseline, но считается независимо.
- **Уровень 2 — structured facets.** Упорядоченный набор пар `name => value`, который
  правило объявляет само (см. 4.2). Предназначен для случаев, где символьный ключ
  заведомо не различает разные нарушения.
- **Уровень 3 — content anchor.** Для нарушения с точной локацией (`Location::$precise`
  истинно и файл известен) — хеш нормализованной строки исходника, на которую указывает
  нарушение. Нормализация: обрезка ведущих/хвостовых пробелов, схлопывание
  последовательностей пробельных символов в один. Строка не входит в ключ, входит хеш
  её содержимого.

Content anchor — дешёвый универсальный дискриминатор occurrence-уровня. Он даёт то, чего
не может дать номер строки:

- перенос кода вверх/вниз ключ **не** меняет (номер строки в ключ не входит);
- замена одного захардкоженного пароля на другой ключ **меняет** → новое нарушение
  предъявляется, а не проезжает под видом «того же самого»;
- удаление одного `$_GET` и добавление другого в том же файле при неизменном count
  различается.

**Ограничения content anchor (документируются):** нарушение, у которого изменился только
форматирующий пробел внутри строки, ключ не меняет (нормализация); нарушение, у которого
изменилось имя переменной, — меняет и будет предъявлено как новое. Это осознанный
консервативный уклон: гейт скорее покажет лишнее, чем спрячет реальное.

**Инвариант реализации:** content anchor базовой стороны обязан вычисляться **внутри**
базового прогона, пока каталог снапшота существует. После `release()` строки базы
прочитать нельзя. Зафиксировано отдельным тестом (см. §13).

### 4.2 Structured facets по правилам

Носитель — новое необязательное поле `Violation::$comparisonFacets` (тип
`ComparisonFacets`, Core). Поле **не** участвует в `ViolationHasher`, в формате baseline
и в форматтерах — только в comparison identity. Значение по умолчанию — пустой набор,
поэтому все существующие правила и тесты продолжают работать без изменений.

| Правило                                   | Проблема сегодня                                                                     | Facets                                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `architecture.circular-dependency`        | `symbolPath = classes[0]`, `violationCode` — константа; смена состава цикла невидима | `cycle` = канонический состав (отсортированный список FQCN, хеш)                                            |
| `architecture.unreachable-layer`          | `project:` + константный код; разные слои неразличимы                                | `layer` = имя слоя                                                                                          |
| `architecture.empty-template`             | то же                                                                                | `template` = имя шаблона                                                                                    |
| `architecture.potential-shadow`           | то же; разные пары слоёв неразличимы                                                 | `shadowing` = упорядоченная пара `имя_слоя_1 → имя_слоя_2`                                                  |
| `architecture.coverage`                   | одна диагностика на проект — ключ и должен быть один                                 | facets не нужны; изменение уровня покрытия ловится как `Worsened` (§0.2, запись 1)                          |
| `duplication.code-duplication`            | ключ = файл первой копии; изменение состава копий невидимо                           | `block` = хеш канонического (отсортированного) набора участвующих путей. **Размер блока в facet не входит** |
| `security.*`, `code-smell.*` (occurrence) | несколько экземпляров на файл неразличимы                                            | facets не нужны — покрывается content anchor (уровень 3)                                                    |
| пороговые правила (`complexity.*` и др.)  | один экземпляр на символ — ключ уже точен                                            | facets не нужны                                                                                             |

**Канонизация состава цикла:** цикл — это SCC, множество; его строковое представление
зависит от точки входа обхода. В facet кладётся хеш **отсортированного** списка FQCN
участников, чтобы смена стартовой вершины между прогонами не порождала ложную новизну.

**Разделение «идентичность» и «величина» (следствие решения §0).** Facet отвечает на
вопрос «то же ли это нарушение», `metricValue` — на вопрос «насколько оно хуже». Величину
в facet класть нельзя: тогда любой рост величины меняет ключ, нарушение классифицируется
как `Absent`, и ветка `Worsened` становится мёртвым кодом. Поэтому у
`duplication.code-duplication` facet держит только состав путей, а число строк остаётся в
`metricValue`. У `architecture.circular-dependency` разделить нельзя — состав SCC и есть
его размер, поэтому для циклов вводится отдельное правило сопоставления по включению
(§4.7).

### 4.3 Определение новизны

Нарушение `v` из текущего прогона **новое**, если его не удалось сопоставить ни с одним
несопоставленным нарушением базы с тем же `ComparisonKey` по алгоритму 4.4. Причина
новизны — одна из:

- **Absent** — ключа нет в базе вовсе;
- **Escalated** — ключ есть, но все несопоставленные экземпляры базы имеют строго более
  низкую severity;
- **Surplus** — ключ есть, экземпляры подходящей severity были, но уже израсходованы
  другими текущими нарушениями (кратность выросла);
- **Worsened** — сопоставление состоялось, нарушение предсуществующее, но его метрика
  входит в `GatedMetricCatalog` (§0.2) и ухудшилась сверх допуска (механика — §4.7,
  пакет П9).

Ухудшение метрики, **не** входящей в каталог, новизной не является ни в каком смысле: оно
не попадает ни в `$new`, ни в exit-код, а уходит в информационный дрейф (§4.7).

### 4.4 Consumption-алгоритм (закрывает находку #5)

Задаёт однозначное соответствие между экземплярами базы и текущего прогона внутри одного
ключа. Порядок детерминирован и не зависит от порядка нарушений во входе.

```
для каждого ComparisonKey:
    base_slots  := экземпляры базы,   отсортированные по (severity desc, anchorHash asc)
    head_items  := экземпляры текущие, отсортированные по (severity desc, anchorHash asc)

    для каждого h из head_items (в порядке убывания severity):
        // best fit: самый низкий из подходящих, чтобы не тратить error-слот на warning
        slot := первый несопоставленный s из base_slots,
                у которого severity(s) >= severity(h),
                с минимальной severity(s) среди подходящих
        если slot найден:  пометить slot использованным; h — предсуществующее
        иначе:             h — новое, причина:
            Absent    если base_slots пуст
            Escalated если все base_slots имеют severity < severity(h)
            Surplus   иначе (подходящие были, но израсходованы)
    // ... implementation details
```

Проверка на кейсах:

| База                 | Текущий прогон       | Результат                                           |
| -------------------- | -------------------- | --------------------------------------------------- |
| `{}`                 | `{warning}`          | 1 новое, Absent                                     |
| `{error}`            | `{warning, warning}` | 1 новое, Surplus (первый warning сел на error-слот) |
| `{warning}`          | `{error}`            | 1 новое, Escalated                                  |
| `{error, warning}`   | `{error, warning}`   | 0 новых                                             |
| `{error, error}`     | `{error, warning}`   | 0 новых (понижение — не новизна)                    |
| `{warning, warning}` | `{warning}`          | 0 новых                                             |

Сортировка по `anchorHash` (а не по `(line, message)`, как в редакции 1) даёт
стабильность при сдвиге строк и переформулировке сообщений.

### 4.5 Границы устойчивости идентичности

| Изменение                                     | Ключ                                               | Поведение гейта                                   |
| --------------------------------------------- | -------------------------------------------------- | ------------------------------------------------- |
| Сдвиг строк в файле                           | не меняется                                        | не новое                                          |
| Переформулировка сообщения правила            | не меняется                                        | не новое                                          |
| Перемещение файла без переименования класса   | символьный — не меняется                           | не новое                                          |
| Перемещение файла, нарушение файлового уровня | меняется → **нормализуется через `FileRenameMap`** | не новое (см. ниже)                               |
| Переименование класса или метода              | меняется                                           | новое; документируется                            |
| Переименование namespace целиком              | меняется у всех вложенных                          | новое; документируется, эскейп — прогон без опции |
| Изменение содержимого строки нарушения        | anchor меняется                                    | новое (осознанный консервативный уклон)           |
| Изменение порога в конфиге между ревизиями    | невозможно                                         | оба прогона на текущей конфигурации               |

**`FileRenameMap`** — узкая компенсация файловых ключей. Строится из
`GitClient::getChangedFiles()` между базовой ревизией и HEAD: пары
`oldPath → path` для статусов `R`/`C` (поле `ChangedFile::$oldPath` уже существует).
Применяется **только** при нормализации файловой части ключей базовой стороны и только
к `SymbolType::File`. Символьные ключи через карту не прогоняются: там переименование —
это содержательное изменение, а не перемещение.

### 4.6 Какая конфигурация используется для обоих прогонов

**Всегда текущая (head).** Конфигурация базовой ревизии, включая `qmx.yaml` внутри
снапшота, игнорируется полностью.

1. Гейт отвечает на вопрос «стало ли хуже по *сегодняшним* правилам».
2. При ужесточении порога старый долг всплывает в обоих прогонах и взаимно сокращается.
3. Устраняется необходимость сравнивать две конфигурации.

Следствие: автодискавери конфигурации внутри каталога снапшота обязано быть отключено —
иначе `qmx.yaml` базовой ревизии подхватится. Проверяется тестом (снапшот с намеренно
ломающим `qmx.yaml`; результат обязан совпасть с прогоном без него).

**Важная поправка к редакции 1.** Тезис «ужесточение порога работает как храповик по мере
касания кода» **неверен** и удалён: ключ, всплывший в обоих прогонах, вычитается
независимо от того, трогали ли код. Ужесточение порога начинает влиять на гейт только
там, где меняется severity или появляется новый ключ.

### 4.7 Ухудшение метрики: гейт и информационный дрейф

Обе ветки работают **только по сопоставленным парам** (base-экземпляр ↔ head-экземпляр),
которые consumption-алгоритм §4.4 признал предсуществующими. Несопоставленные нарушения
уже классифицированы как новые и повторно не рассматриваются.

**Ветка 1 — гейт (`Worsened`).** Для пары, чей `(ruleName, violationCode, SymbolType)`
находится в `GatedMetricCatalog`:

1. берутся `metricValue` базы и head (в `BaseViolationSet` значение уже хранится);
2. знак ухудшения определяется направлением из каталога (`Lower` / `Higher` is worse);
3. значимость — по правилу «оба допуска превышены» (§0.2);
4. значимое ухудшение → нарушение попадает в `$new` с причиной `Worsened`, влияет на
   `--fail-on` и exit-код наравне с `Absent`.

Отсутствие `metricValue` хотя бы с одной стороны → пара молча не гейтуется, но пишется
в дрейф; отдельный тест фиксирует, что для четырёх каталожных метрик такого не бывает
(иначе гейт был бы тихо мёртвым — тот же класс дефекта, ради которого пишется весь план).

**Специальное правило для циклов.** Состав SCC входит в facet, поэтому выросший цикл
получает другой `ComparisonKey` и штатно классифицируется как `Absent`. Чтобы вердикт
сопровождался осмысленным текстом, `WorsenedDetector` делает второй проход по нарушениям
с причиной `Absent` у правила `architecture.circular-dependency`: если множество
участников head-цикла **строго содержит** множество участников какого-то несопоставленного
base-цикла, причина переклассифицируется `Absent → Worsened`, а в сообщение подставляется
«cycle grew: 3 → 12 classes». Вердикт при этом не меняется (обе причины гейтуют) —
меняется только диагностическая ценность строки. Каждый base-цикл расходуется не более
одного раза; порядок обхода детерминирован (по возрастанию размера base-цикла, затем по
каноническому хешу состава).

**Ветка 2 — информационный дрейф.** Для пары, которой в каталоге нет, но у обеих сторон
есть `metricValue` и он изменился в худшую сторону, порождается `MetricDriftEntry`
(символ, правило, значение базы, значение head, дельта). Это **не** `Violation`: запись
живёт в отдельной коллекции `NoveltyResult::$drift`, не попадает в `$result->violations`,
не доходит до `ExitCodeResolver` и не участвует в `--fail-on`. Направление «хуже» для
некаталожных правил берётся из знака отклонения от порога самого нарушения (значение
уходит дальше от порога), а не из отдельных метаданных: заводить их означало бы завести
второй источник истины и нарушить §0.4.

Дрейф считается по тем же парам, что и гейт, поэтому он не требует ни второго прохода по
метрикам, ни хранения всех метрик базы — только `metricValue` тех нарушений, которые в
базе были. Следствие, которое нужно честно назвать в документации: **дрейф виден только
там, где нарушение существовало в обеих ревизиях**. Рост CCN с 5 до 9 при пороге 10 не
показывается вообще — нарушения нет ни там, ни там.

## 5. Effective runtime configuration (закрывает находку #2)

Проблема: «тот же `ConfigurationDocument`» не воспроизводит эффективную конфигурацию.
Вне его остаются: `--rule-opt`, динамические CLI-алиасы правил, `--exclude-path`,
`--exclude-namespace`, а также состояние `RuleOptionsRegistry`
(трёхслойный мерж defaults → config file → CLI).

Решение: ввести **`EffectiveRuntimeConfiguration`** — иммутабельный снимок всего, что
влияет на результат анализа, формируемый **один раз**, после всех CLI-мержей, и
используемый:

1. головным прогоном,
2. базовым прогоном (с подменённым project root — см. 6.3),
3. отпечатком конфигурации для ключа кэша базы.

Состав снимка (полный, фиксируется явно, а не «и т. п.»):

- `ConfigurationDocument` целиком (paths, analysis, ruleOptions из файла, architecture,
  computedMetrics);
- **слитые** rule options после CLI (`array_replace_recursive(config, cli)` — тот же
  результат, что `RuntimeConfigurator` кладёт в `obsolete shared configuration carrier`);
- значения CLI-алиасов правил;
- список включённых правил после применения `--disable-rule` / `--only-rule` / presets;
- фильтрационная политика: `excludePaths`, `excludeNamespaces` (конфиг + CLI),
  `disableSuppression`, `baselinePath` (наличие, не содержимое);
- допуски гейтируемых метрик (`comparison.tolerances.*`, §0.2) — они влияют на вердикт,
  значит обязаны влиять и на отпечаток; поле добавляется пакетом П9;
- версия инструмента и версия схемы сравнения.

`ConfigurationFingerprint::of(EffectiveRuntimeConfiguration)` — стабильный хеш **всего**
снимка. Инвентарь полей фингерпринта фиксируется отражением/явным списком и покрывается
тестом «изменение любого поля снимка меняет отпечаток» (см. §13) — чтобы поле,
добавленное в будущем, не выпало из отпечатка молча.

`RuntimeConfigurator::configure()` начинает возвращать этот снимок (сейчас возвращает
`void`) — единственная точка, где он может быть построен корректно, потому что именно там
происходят все мержи.

## 6. Архитектура базового прогона

### 6.1 Материализация снапшота

**Единственный путь — `git worktree add --detach <tmpdir> <sha>`.**

`git archive` fallback редакции 1 **удалён**: он применяет `export-ignore` из
`.gitattributes` **того дерева, которое архивируется**, вложенные `.gitattributes` в
подкаталогах при этом тоже действуют, и проверить это по рабочей копии HEAD нельзя
(находка #16). Молча усечённая база порождает фантомные «новые» нарушения на весь
исключённый объём — это ровно тот класс тихой некорректности, ради устранения которого
делается механизм. Если `git worktree` недоступен — fail loudly с указанием причины.

Каталог снапшота — под системным temp, с уникальным префиксом инструмента и идентификатором
процесса (для CI-матрицы с параллельными прогонами в одном репозитории).

### 6.2 Изоляция двух прогонов в одном процессе (закрывает находку #10)

Отклонён вариант «дочерний процесс `bin/qmx check <snapshot>`»: воспроизведение
эффективной конфигурации через повтор argv требует переносить `--preset`, все
`--rule-opt`, все динамические алиасы, `--config`, `--disable-rule`/`--only-rule`,
`--exclude*`. Забытая опция не падает, а тихо меняет базис сравнения.

Принято: базовый прогон исполняется **в том же процессе, на свежем DI-контейнере**, с тем
же `EffectiveRuntimeConfiguration` (root подменён по 6.3). Но свежего контейнера
**недостаточно** — вводится явный **run scope**: объект, который на входе сохраняет
глобальное состояние, а в `finally` восстанавливает его побайтово.

| Состояние                            | Проблема                                                           | Мера в run scope                                                    |
| ------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------- |
| `ProfileSession`                     | Старые спаны могут попасть в следующий запуск                      | instance-owned `disable()`/`enable()` очищает сессию до запуска     |
| Architecture prepared state          | Граф одного запуска не должен удерживаться в следующем             | подготовка создаётся и сбрасывается владельцем политики             |
| ComputedMetrics definition catalog   | Конфигурация одного запуска не должна пережить следующий           | владелец сбрасывает каталог до разрешения нового документа          |
| DependencyModel PHPDoc configuration | Флаг PHPDoc не должен утечь в воркер следующего запуска            | immutable owner-local value передаётся только в текущий worker task |
| Console logger/progress adapters     | Режим базы не должен засорять вывод головного запуска              | локальная no-op конфигурация применяется на текущий запуск          |
| `CacheFactory` (DI, мемоизирует)     | Свежий контейнер → свежая фабрика                                  | Безопасно                                                           |
| `WorkerBootstrap::$processor`        | Живёт в worker-процессах; ключ включает `projectRoot` и `cacheDir` | Безопасно; покрыть тестом ключа                                     |
| `ContextWorkerPool`                  | Создаётся и гасится на прогон                                      | Безопасно                                                           |

**Порядок исполнения: базовый прогон первым, головной вторым.** Мотивация — память:
репозиторий метрик базы освобождается до старта головного прогона. Оговорка: аргумент
работает только при выполнении меры по architecture registry, иначе граф базы удерживается
до `prepare()` головного (это и была ошибка редакции 1).

Дополнительно к освобождению памяти: между прогонами должно быть явное разрушение
контейнера базы и вызов `gc_collect_cycles()`; пиковое потребление обязано измеряться в
DoD пакета, а не предполагаться.

### 6.3 Привязка путей при подмене корня (закрывает находку #9)

Вместо «`withProjectRoot()` и всё заработает» вводится явная **политика по каждому
root-зависимому полю**:

| Поле                                 | Политика для базового прогона                   | Почему                                                                                                 |
| ------------------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `projectRoot`                        | корень снапшота + относительный подпуть проекта | Проект может лежать в подкаталоге git-дерева                                                           |
| `paths` (анализируемые)              | пересчитываются относительно нового корня       | Иначе анализировался бы HEAD                                                                           |
| `composerJsonPath`                   | **пересчитывается** в снапшот                   | `Psr4NamespaceDetector` разрешает каталоги через `realpath` от него; иначе PSR-4-маппинг укажет в HEAD |
| `cacheDir`                           | **остаётся** привязан к HEAD                    | Общий тёплый AST-кэш — единственный способ переиспользования между прогонами                           |
| `excludePaths` / `excludeNamespaces` | без изменений (относительные шаблоны)           | Сопоставляются с project-relative путями                                                               |
| путь конфигурации                    | без изменений (конфигурация HEAD)               | §4.6                                                                                                   |
| автодискавери `qmx.yaml`             | **выключено** внутри снапшота                   | §4.6                                                                                                   |

**Проект в подкаталоге git-дерева.** Корень снапшота — это git-toplevel базовой ревизии.
Проектный корень внутри снапшота = корень снапшота + `relative(gitToplevel → projectRoot)`.
Эта относительная часть вычисляется на стороне HEAD один раз.

**Пути вне репозитория.** Если анализируемый путь не лежит под git-toplevel — отобразить
его в снапшот невозможно. Политика: fail loudly с перечислением таких путей. Тихо
анализировать их «из HEAD» нельзя — это смешает две ревизии в одном множестве.

### 6.4 Политика материализации: partial clone, submodules, LFS (закрывает находку #13)

| Ситуация             | Детекция                                                                                                            | Политика                                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Partial clone        | наличие promisor-remote в конфигурации; проверки объектов выполняются с запретом lazy fetch (`GIT_NO_LAZY_FETCH=1`) | Проверять **дерево и blob'ы** анализируемых путей, а не только корневое дерево. Не хватает объектов — fail loudly с командой дозагрузки                                    |
| Submodules           | наличие gitlink-записей в дереве базовой ревизии под анализируемыми путями                                          | `worktree add` их не инициализирует → пустой каталог → фантомная «новизна» на весь объём. Fail loudly с явным указанием, что submodule под анализом не поддерживается в v1 |
| Git LFS              | наличие `filter=lfs` в effective attributes дерева базы под анализируемыми путями                                   | Предупреждение + продолжение. Pointer-файл не парсится → попадает в parse errors, что видно в выводе; сеть при этом дёргает git, а не мы                                   |
| Ref есть, дерева нет | `cat-file -e` c запретом lazy fetch                                                                                 | Fail loudly (см. 6.5)                                                                                                                                                      |

Общий принцип: **«сеть не трогаем» — это требование, а не пожелание**, поэтому все
проверки объектов выполняются с явным запретом lazy fetch, иначе `cat-file` в partial
clone сам сходит в сеть и требование нарушится молча.

### 6.5 Поведение при недоступной базовой ревизии (закрывает находку #12)

**Fail loudly, exit 3 (`EXIT_CONFIG_ERROR`), без деградации.** Тихий откат к текущему
поведению воспроизводит ровно тот баг, ради устранения которого механизм делается, и
делает это невидимо.

Порядок проверок изменён: **сначала проверяется наличие нужных объектов, shallow — только
подсказка**.

| Кейс                      | Детекция                                                                                                | Сообщение                                                                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Не git-репозиторий        | `git rev-parse --is-inside-work-tree` (**не** `isRepository()` — тот ломается на проекте в подкаталоге) | `--new-since requires a git repository`                                                                                                                            |
| Ref не существует         | `rev-parse --verify <ref>^{commit}`                                                                     | Показать ref, предложить `git fetch origin <branch>`                                                                                                               |
| Объектов нет              | проверка дерева и blob'ов с запретом lazy fetch                                                         | Если репозиторий shallow — добавить подсказку `fetch-depth: 0` / `GIT_DEPTH: 0` / `git fetch --unshallow`; иначе — `git fetch --deepen` / отключить partial-фильтр |
| Нет merge-base (`A...B`)  | `merge-base` падает                                                                                     | Несвязанные истории — предложить `A..HEAD`                                                                                                                         |
| Force-push переписал базу | объекта нет                                                                                             | То же, что «объектов нет»                                                                                                                                          |
| База == head              | —                                                                                                       | Штатно: базовое множество == текущее → 0 новых                                                                                                                     |

Расширение `GitClient::isRepository()` не трогаем (у него есть существующие потребители) —
вводим отдельный метод проверки через `rev-parse`.

### 6.6 Уборка снапшота (закрывает находку #15)

Три уровня, ни один не полагается на исполнение кода после SIGKILL:

1. **Штатный** — `release()` в `finally`: `git worktree remove --force` + удаление каталога.
2. **Аварийный в том же процессе** — shutdown-хендлер (покрывает исключения и `exit`, но
   не SIGKILL).
3. **Между прогонами** — **owned manifest**: файл-lease в кэш-каталоге инструмента со
   списком созданных нами каталогов снапшотов и pid/временем создания. При старте
   `--new-since` читается манифест; каталоги, чьи lease протухли (процесс мёртв, время
   вышло), удаляются **по точному пути из манифеста**, затем вызывается
   `git worktree prune`. Глобальный prune без манифеста как основной механизм не
   используется — он не удалит запись, пока каталог существует, то есть после SIGKILL
   не помогает.

Никаких `rm -rf` по собранному из переменных пути: перед удалением проверяется, что путь
записан нами в манифест и лежит под ожидаемым temp-префиксом.

## 7. Стоимость (закрывает находку #14)

### 7.1 Числа не заявляются до замера

Редакция 1 обещала оверхед 10–30 % на основании контентного ключа AST-кэша. Обоснование
не выдерживает проверки: `FileProcessor::process()` кэшем закрывает только парсинг, а
обход коллекторов, извлечение метрик и два прохода `NodeFinder` (suppressions, threshold
overrides) выполняются всегда. Доля именно парсинга в фазе Collection неизвестна.

Порядок работ меняется:

1. **Сначала профилирование** (пакет П4): измерить долю `parse` внутри Collection на
   `src/` и на одном из бенчмарк-проектов, встроенным профайлером.
2. Контентный ключ AST-кэша делается в любом случае — он чинит существующее неудобство
   (`touch` и переключение веток инвалидируют кэш без изменения содержимого) и является
   **необходимым, но, возможно, недостаточным** условием переиспользования кэша между
   деревьями.
3. Если доля парсинга окажется малой, следующий рычаг — **кэш `FileProcessingResult`**
   (результат Collection на файл) по ключу `содержимое файла + отпечаток набора
   коллекторов + версия схемы`. Это выносится в отдельную задачу и в v1 не входит;
   в плане фиксируется как названный, а не гипотетический, следующий шаг.
4. Числа оверхеда попадают в документацию и ADR **только после замера** по протоколу
   из §13.

Контентный ключ: `hash_file('xxh128')` вместо `stat()`; путь и mtime из ключа удаляются;
поднимается версия схемы ключа, чтобы старые записи не читались. Корректность: AST не
содержит пути файла, поэтому одинаковое содержимое ⇒ одинаковый AST; совпадение ключей
для двух файлов с идентичным содержимым безопасно, из кэша десериализуется независимая
копия.

### 7.2 Кэш результата базового прогона (закрывает находку #3)

Значение: сериализованный `BaseViolationSet` (компактный — ключи, severity, кратности,
anchor-хеши). Хранится в существующем cache dir, запись атомарна (tmp + rename, правило 5
CLAUDE.md).

**Ключ (полный состав, каждый компонент обязателен):**

- полный object id базовой ревизии (длина не фиксируется — SHA-1 или SHA-256);
- `ConfigurationFingerprint::of(EffectiveRuntimeConfiguration)` — включает пути,
  фильтрационную политику и `--rule-opt` (см. §5);
- нормализованный набор анализируемых путей (project-relative, отсортированный,
  дедуплицированный) — отдельно, чтобы дефект был виден в ключе, а не спрятан в отпечатке;
- флаг `disableSuppression` — базовое множество строится после suppression;
- версия схемы сравнения (`ComparisonKey` + формат `BaseViolationSet`);
- версия инструмента.

Промах ключа — это полный базовый прогон, а не деградация вердикта, поэтому
консервативная избыточность ключа предпочтительна. Частный случай той же избыточности:
допуски метрик (§0.2) входят в отпечаток, хотя на состав `BaseViolationSet` они не
влияют, — правка допуска в `qmx.yaml` перепрогонит базу. Это осознанно: отдельный
«урезанный» отпечаток ради экономии одного прогона завёл бы второй источник истины о
том, что влияет на результат.

Что не делается в базовом прогоне: форматирование и репортинг, профилирование,
генерация baseline, прогресс-бар. Detection-фазы (duplication, circular) — **нужны**,
они порождают нарушения.

## 8. CLI и место в конвейере

### 8.1 CLI-поверхность

```
--new-since=<git-ref>    Report findings absent from the given base revision: new violations,
                         raised severity or count, and regressions in a fixed set of
                         aggregate metrics (see docs). Per-symbol metric changes are
                         reported separately and do not affect the exit code.
```

Текст `--help` выведён из канонической формулировки §0.5 и обязан оставаться её
сокращением: «did not get worse» / «no regressions» в нём не появляется (проверяется
grep'ом, DoD П10).

- **Значение обязательное** (`VALUE_REQUIRED`). Причина не стилистическая: Symfony
  `ArgvInput::addLongOption()` для опции с необязательным значением забирает следующий
  токен, если он не начинается с `-`. При `VALUE_OPTIONAL` команда
  `qmx check --new-since src/` съела бы `src/` как значение опции, оставив анализ без
  путей. Прецедент `--profile` в проекте страдает тем же — это отдельное наблюдение,
  не входящее в область плана.
- Вывод базы из `--report` (`git:main` → `main` и т. д.) **не делается**: он превращает
  одну неоднозначную композицию в две (см. 8.2) и требует необязательного значения.
  Пользователь пишет ref явно.
- Одна опция — одно имя, без алиасов-дублей (CLI_CONVENTIONS, правило 1).
- Семантика `--report` и `--report-strict` **не меняется**.

**Отвергнутые альтернативы:** менять семантику `--report` (breaking change, ломает
пайплайны молча — вывод станет меньше, а не упадёт); `--new-only` + `--new-since`
(два имени для одной функции); `--baseline=git:main` (перегрузка опции-пути даёт
невнятные ошибки при опечатке в ref).

### 8.2 Место в конвейере и взаимодействие с git-scope (закрывает находку #11)

Текущий конвейер:

```
baseline-файл → suppression → path exclusion → namespace exclusion → git scope
```

Новый шаг — **вместо** git-scope, а не после него:

```
--new-since задан:      baseline-файл → suppression → path exclusion → namespace exclusion → new-only
--new-since не задан:   без изменений (пять шагов как сегодня)
```

**Почему git-scope не применяется.** Он отбрасывает: (а) все проектные диагностики
(`pathString() === ''`, sentinel-namespace), (б) новые нарушения-побочные-эффекты в
нетронутых файлах — а именно они и есть самый ценный улов гейта (изменил интерфейс —
сломал метрики у десяти реализаций). Применять его до сравнения — значит сузить гейт
ровно там, где он полезнее всего.

**Почему не запрет сочетания** (прескрипция ревьюера отклонена): `--report=git:...` уже
стоит во множестве пайплайнов и хуков; добавление `--new-since` к работающей команде не
должно валить её с «options are mutually exclusive». Принято: при обоих заданных
`--new-since` **побеждает**, git-scope не применяется, а в вывод печатается
информационная строка «`--report` scope is not applied when `--new-since` is used».

Порядок относительно suppression **сохранён**: базовое множество строится **после**
suppression- и exclude-фильтров, то есть это ровно то, что инструмент **сообщил бы** на
базовой ревизии. Следствия: снятие `@qmx-ignore` в head → нарушение новое (намеренное
действие разработчика, гейт обязан показать); добавление `@qmx-ignore` в head → тишина
(разработчик явно принял ответственность и оставил след в коде с обязательным reason).
Обратный порядок означал бы «подавленное когда-то — подавлено навсегда». Отвергнуто.

Механика stale-записей (`getStaleKeys()`) к базовому множеству **не применяется**:
исчезновение символа между ревизиями нормально (файл удалён в PR).

### 8.3 Сочетание с baseline-файлом (закрывает находку #7)

Опции **композируются**, порядок — baseline-файл первым. Но у композиции есть
подтверждённое кодом ограничение, которое обязано быть названо, а не спрятано:

`BaselineFilter::shouldInclude()` удаляет **все** текущие экземпляры ключа, попавшего
в baseline, а формат v5 хранит один entry на ключ. Значит для ключа, принятого в
baseline, **Surplus не сработает никогда**: второй и последующий экземпляры не доживут
до сравнения.

Три варианта; выбран третий:

1. Запретить сочетание — ломает легитимный сценарий «легаси + PR-гейт».
2. Ввести multiset-aware формат v6 — миграция версионируемого артефакта ради
   вспомогательного сценария; цена несоразмерна.
3. **Принято:** объявить baseline-файл **сознательным wildcard-исключением ключа** —
   «этот ключ принят человеком целиком, во всех кратностях». Это согласуется с тем,
   чем baseline является по смыслу («решение человека»), в отличие от `--new-since`
   («факт истории»). Документируется в `baseline.md` явным абзацем; при одновременном
   задании обеих опций в verbose печатается, сколько ключей исключено wildcard'ом.

Baseline v10 создаётся отдельной командой `baseline:generate`, которая захватывает
измеряемый набор после suppression и exclusions; `--new-since` не должен менять
этот capture.

**Сочетание с `--fail-on`:** без изменений. Новый шаг только уменьшает множество,
доходящее до `ExitCodeResolver`. Комбинация `--new-since --fail-on=warning` и есть
целевой honest gate. Записи дрейфа (§4.7) до `ExitCodeResolver` не доходят вовсе.

### 8.4 Подача в выводе: гейтующее против информационного

Задача — сделать невозможной ситуацию, в которой пользователь путает то, что валит
сборку, с тем, что просто показано.

**Гейтующее.** `Worsened` печатается в общем списке нарушений, наравне с `Absent` и
`Escalated`, но с собственным маркером причины и текстом вида
`architecture.coverage: layer coverage 98.0% → 60.0% (worse than base, tolerance 1.0 pt)`.
Слово «violation» применимо, exit-код зависит.

**Информационное.** Дрейф печатается **отдельной секцией после списка нарушений и до
итоговой сводки**, с заголовком, который прямо снимает вопрос о вердикте:

```
Metric drift (informational — does not affect the exit code)
  App\Service\UserService::calculate   complexity.cyclomatic   12 → 20   (+8)
  … and 37 more (use --format=json for the full list)
```

Требования, каждое проверяется тестом (DoD П9):

- секция не содержит слов `violation`, `error`, `warning`, `failed` — только «changed» /
  «drift»; уровень severity в ней не печатается вовсе;
- секция не печатается, если дрейф пуст;
- в текстовом формате выводится не более N строк (N по умолчанию 10, сортировка по
  относительной дельте убывающе), остальное — счётчиком;
- exit-код с непустым дрейфом и без него **идентичен** при прочих равных — прямой тест;
- в машинных форматах, потребляемых гейтами (`checkstyle`, `sarif`, `gitlab`), дрейф
  **отсутствует** полностью: эти форматы читают CI-системы, и попадание туда сделало бы
  информационное неотличимым от гейтующего;
- в `--format=json` дрейф присутствует **отдельным** ключом верхнего уровня
  `metricDrift`, рядом с `violations`, но не внутри него;
- форматы `metrics` и `health` не меняются.

## 9. Размещение по неймспейсам и DI (закрывает находку #4)

Решение по фреймворку ADR 0010 / ADR 0012.

- **Вертикальный слайс `src/Diff/` не создаём.** Критерии ADR 0010 требуют
  «cross-layer-consuming rule И independent-lifecycle adapter». Правила здесь нет вообще:
  механизм — идентичность + фильтр + оркестрация, то есть cross-cutting инфраструктура,
  которая по таблице решений остаётся горизонтальным слоем.
- **Примитив facets → `src/Core/Violation/`** (`ComparisonFacets`, поле в `Violation`).
  Core, потому что заполняют его правила из разных доменов, а читает Baseline.
- **Идентичность и модель новизны → `src/Baseline/Comparison/`.** Соседство с
  `ViolationHasher` даёт namespace cohesion; слой `baseline` в `qmx.yaml` покрывает
  под-namespace префиксно.
- **Git-часть → `src/Infrastructure/Git/`** (слой `infra-git`).
- **Оркестрация базового прогона → `src/Infrastructure/Comparison/`** — новый слой
  `infra-comparison` в `qmx.yaml`. Обязана быть в Infrastructure, потому что строит
  DI-контейнер.
- **CLI → `src/Infrastructure/Console/`** (adapter-exclusion principle).

| #   | Кейс                                                                   | Ожидаемое поведение                                                                                   |
| --- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1   | Новое нарушение в изменённом файле                                     | Показано                                                                                              |
| 2   | Старое нарушение в изменённом файле                                    | Скрыто (цель механизма)                                                                               |
| 3   | Новое нарушение в **не**изменённом файле (побочный эффект)             | Показано **всегда**, в том числе при заданном `--report` (§8.2)                                       |
| 4   | Файл добавлен в PR                                                     | Все его нарушения новые                                                                               |
| 5   | Файл удалён в PR                                                       | Нарушения базы не находят пары — ничего не показывается, ошибок нет                                   |
| 6   | Файл перемещён, класс тот же — **символьное** нарушение                | Ключ не меняется → не новое                                                                           |

## 12. Решения по открытым вопросам редакции 1

1. **Имя и форма опции.** `--new-since=<git-ref>`, значение **обязательное**, вывод базы
   из `--report` не делается. Обоснование — факт 16 §3: при необязательном значении
   Symfony съест следующий позиционный путь. Альтернативы (`--new-from-rev`,
   `--compare-to`) отклонены: `--new-since` точнее описывает семантику («новое с момента»),
   а узнаваемость для пришедших из golangci-lint не перевешивает.

2. **Взаимодействие с `--report`.** `--new-since` **побеждает**: git-scope не
   применяется. Не запрет (ломает существующие вызовы) и не «new within changed files»
   (прячет самый ценный улов — побочные эффекты в нетронутых файлах и проектные
   диагностики). При обоих заданных печатается информационная строка.

3. **Fail loudly без опт-аута.** Опт-аут (`--new-since-on-missing=warn`) **не вводится**.
   Это ровно та лазейка, из-за которой гейт перестаёт быть гейтом: сборка зелёная,
   пользователь считает себя защищённым, а сравнение не выполнялось. Команде с shallow-
   пайплайном доступны два честных выхода: починить `fetch-depth` (одна строка в CI) или
   не передавать `--new-since` в этом пайплайне. Дополнительно: shallow сам по себе больше
   не является причиной отказа (§6.5), так что часть таких пайплайнов заработает без правок.

4. **Выдача «ухудшилось, но не ново».** Решено вариантом C (§0): `Worsened` гейтует
   четыре агрегатные метрики из `GatedMetricCatalog`, остальные ухудшения уходят в
   информационную секцию `metric drift` и вердикт не трогают. Отдельный флаг
   `--show-worsened` / `--show-drift` **не вводится**: секция печатается всегда, когда
   непуста, и подавляется в машинных форматах, читаемых гейтами (§8.4). Флаг здесь
   означал бы, что по умолчанию часть картины скрыта, — а её сокрытие и есть исходная
   проблема `--report`.

5. **`hook:install` и `--new-since`.** По умолчанию **не включаем**: удваивает время
   хука, а хук должен быть быстрым, иначе его отключают. Упоминаем в документации как
   опцию. Отдельная оговорка, найденная ревьюером: `--report=git:staged` анализирует
   рабочее дерево, поэтому staged-проверка и сегодня может приписать коммиту unstaged-
   изменения того же файла — это существующее свойство, документируем, но не чиним здесь.

6. **Будущее `--report`.** Семантику **не меняем даже в мажорной версии**. Дешёвый
   файловый scope и историческое сравнение — разные операции с разной стоимостью
   (второй полный анализ). Что чиним обязательно — вводящую в заблуждение формулировку
   «Focus — see only the violations you introduced» в `website/docs/usage/git-integration.md`:
   она неверна независимо от судьбы `--new-since`. Замена описывает механику, а не эффект:
   «`--report` filters the report down to violations located in the files touched by the
   given range — including violations that predate it».

7. **Границы обещания.** Зафиксированы §0.5 как единый источник текста для документации,
   `--help` и ADR. Запрет на «did not get worse» / «не стало хуже» / «no regressions» без
   тут же следующего перечисления границ — проверяемое требование, а не редакторское
   пожелание (grep-DoD в П10).

## 13. Тестовый план

Что тестируем (без самих тестов). Наименование методов — `itXxx` + `#[Test]` (CLAUDE.md §9).

**Unit — `Core\Violation`:**
- `ComparisonFacets`: нормализация порядка, пустой набор, детерминированность сериализации.
- `Violation` с facets: `ViolationHasher` даёт **тот же** хеш, что и без них
  (защита формата baseline v5 от протечки facets).

**Unit — `Baseline\Comparison` (идентичность):**
- Символьный ключ: те же кейсы, что у `ViolationHasher`, плюс `dependencyTarget`.
- Content anchor: сдвиг строк — ключ тот же; изменение содержимого строки — ключ другой;
  изменение отступа — ключ тот же; `Location::none()` — anchor отсутствует, ключ строится
  без него.
- Facets: цикл с той же длиной, но другим составом → разные ключи; тот же цикл с другой
  стартовой вершиной → одинаковые ключи; разные `unreachable-layer` → разные ключи;
  разные пары shadowing → разные ключи.
- `FileRenameMap`: файловый ключ базы нормализуется; символьный — не трогается.
- Тип символа определяется через `SymbolType::Project`, **не** через `namespace === null`
  (закрывает находку #17).

**Unit — `Baseline\Comparison` (новизна):**
- Четыре исхода Absent / Escalated / Surplus / предсуществующее.
- **Replacement при неизменной кратности** → новое (регресс на находку #1).
- Матрица mixed severity из таблицы §4.4 целиком, включая base `{1 error}` / head `{2 warning}`.
- Понижение severity и уменьшение кратности → не новое.
- Пустая база, пустой текущий набор.
- Детерминированность: перемешанный вход даёт тот же набор и те же причины.
- Агрегатные символы (`project:`, `ns:`) участвуют наравне.

**Unit — `Baseline\Comparison` (каталог гейтируемых метрик и ухудшение):**
- **Пин инвентаря:** `GatedMetricCatalog::all()` равен литеральному списку в тесте — id,
  `ruleName`, коды, уровни, направление, дефолтные `abs`/`rel`. Любая правка каталога
  валит тест.
- **Потолок:** ровно 4 записи; тест содержит комментарий, что рост требует поправки ADR 0016.
- **Ограничение области:** grep по `src/` показывает `GatedMetric` / `MetricDirection`
  только в каталоге и `WorsenedDetector`; ни одно правило и ни один коллектор их не
  упоминает (машинная проверка §0.4).
- `MetricTolerance`: значимо только при превышении **обоих** допусков; допуск 0 значим при
  любом ухудшении; улучшение метрики никогда не значимо.
- Каждая из четырёх метрик: ухудшение за допуском → `Worsened`; в пределах допуска →
  тишина; улучшение → тишина (кейсы 47, 50–53 §11).
- Направление: для покрытия и health хуже меньше, для размера цикла и блока — больше
  (тест на перепутанный знак).
- Циклы: head-состав строго содержит base-состав → `Absent` переклассифицируется в
  `Worsened` с дельтой размера; тот же размер и другой состав → остаётся `Absent`;
  один base-цикл не расходуется дважды; результат детерминирован на перемешанном входе.
- Некаталожная метрика ухудшилась → запись в `$drift`, `$new` не пополняется.
- Каталожная метрика без `metricValue` с одной стороны → в дрейф, не в гейт; отдельный
  тест на то, что для четырёх каталожных метрик такой случай не возникает на реальных
  фикстурах правил.
- Пользовательская `computed.*` (не `health.*`) не гейтуется.

**Unit — `Configuration`:**
- Допуски читаются из `comparison.tolerances.*`, дефолты применяются при отсутствии ключа,
  неизвестный id метрики в конфиге → ошибка валидации, а не тихое игнорирование.
- Изменение допуска меняет `ConfigurationFingerprint` (следовательно, и ключ кэша базы).
- `ConfigurationFingerprint`: изменение **каждого** поля снимка меняет отпечаток
  (тест ведётся по инвентарю полей, чтобы новое поле не выпало молча); одинаковые
  снимки → равный отпечаток.
- `EffectiveRuntimeConfiguration::forSnapshot()`: `composerJsonPath` переанкорен в
  снапшот, `cacheDir` остался на HEAD, `projectRoot` учитывает подкаталог проекта.

**Unit — `Infrastructure\Git`:**
- Типизированные причины `BaseRevisionUnavailableException` для каждого кейса §6.5.
- Shallow-репозиторий с доступным нужным commit'ом → **успех**, не ошибка.
- Пути вне репозитория → `PathsOutsideRepository`.

**Unit — `Infrastructure\Cache`:**
- Одинаковое содержимое по разным путям → одинаковый ключ.
- `touch` без изменения содержимого → ключ тот же; изменение на 1 байт → другой.
- Несуществующий файл; смена версии схемы ключа.

**Integration (реальный временный git-репозиторий):**
- Снапшот: содержимое совпадает с `git show <sha>:<path>`; после `release()`
  `git worktree list` не содержит записи, каталог удалён; удаление происходит и при
  брошенном исключении.
- Проект в подкаталоге git-дерева (переиспользовать фикстуры `GitScopeFilterProjectSubdirTest` /
  `GitSubdirScopeTest`).
- Submodule под анализируемым путём → fail loudly, а не пустой каталог.
- Partial clone с отсутствующими blob'ами → fail loudly без сетевых обращений
  (проверяется тем, что remote недоступен по адресу).
- Owned manifest: имитация SIGKILL (каталог и запись манифеста оставлены) → следующий
  запуск убирает их; чужой worktree того же репозитория остаётся на месте.
- `qmx.yaml` внутри снапшота игнорируется.
- **Anchor до release:** базовое множество, построенное `BaseRevisionAnalyzer`, содержит
  непустые anchor-хеши (доказывает, что чтение произошло до удаления каталога).

**Integration — изоляция прогонов:**
- `ProfileSession` после `analyze()` идентичен состоянию до вызова; при `--profile`
  в выводе головного прогона нет фаз базового.
- Architecture registry головного прогона не содержит граф базы: после базового прогона
  `prepare()` головного проходит без ошибок и даёт те же матчи, что и одиночный прогон.
- Два `--new-since` подряд в одном процессе дают идентичный результат.
- Ключ мемоизации `WorkerBootstrap` различает базовый и головной корни.

**Integration — эквивалентность (исправленный oracle, закрывает находку #18):**
- Результат базового прогона совпадает с результатом отдельного процесса
  `bin/qmx check <snapshot>`, **которому передана сериализованная
  `EffectiveRuntimeConfiguration` головного прогона** (через временный конфиг-файл),
  а не argv по умолчанию. Без этого сравнивались бы разные конфигурации.
- Отдельный кейс с непустыми `--rule-opt` и CLI-алиасом правила — прямая проверка
  находки #2.

**Integration — кэш базового результата:**
- Разные наборы анализируемых путей при том же SHA и конфигурации → разные ключи.
- `--no-suppression-annotations` не меняет ключ: это report-only флаг после baseline-измерения.
- `--rule-opt` меняет ключ.
- Второй вызов с тем же ключом не создаёт снапшот (проверяется спаем на
  `RevisionSnapshotFactoryInterface`, не по времени).
- Запись атомарна (tmp + rename).

**Functional (CLI, `tests/Functional/Console/Command/`):**
- Репозиторий с двумя коммитами: в базовом — класс с 3 нарушениями, в head — добавлено
  одно новое. `--report=git:HEAD~1..HEAD` показывает 4, `--new-since=HEAD~1` — 1.
  **Регрессионный тест на исходный баг: обязан падать на коммите до реализации** —
  проверяется явно, прогоном теста на предыдущем коммите (правило «verify the check itself»).
- `--new-since` показывает новое нарушение в нетронутом файле **и при заданном `--report`**;
  печатается информационная строка про неприменённый scope.
- Проектная диагностика (`architecture.*` на `project:`) при `--new-since` **видна**
  (сегодня `--report` скрывает её всегда).
- Комбинация с `--baseline` (проверяется сообщение про wildcard) и с `--fail-on=warning`
  (проверяется exit-код, не текст).
- Недоступная база → exit 3, текст содержит `fetch-depth`.
- `--new-since` без значения → ошибка парсинга опции; `qmx check --new-since src/`
  **не** съедает путь (регресс на факт 16).
- Снятый `@qmx-ignore` → нарушение показано.
- **Гейт по каталожной метрике:** покрытие слоёв упало за допуск → exit-код ненулевой при
  `--fail-on=warning`, строка в списке нарушений содержит `98.0% → 60.0%`.
- **Информационный дрейф не влияет на вердикт:** прогон, где единственное отличие —
  выросший CCN метода, даёт **exit 0** и печатает секцию `Metric drift`; тот же прогон
  без дрейфа даёт тот же exit-код (прямая проверка §8.4).
- Секция дрейфа не содержит слов `violation` / `error` / `warning` / `failed`
  (проверяется по тексту вывода) и не печатается, когда дрейф пуст.
- `--format=sarif`, `--format=checkstyle`, `--format=gitlab` не содержат записей дрейфа;
  `--format=json` содержит ключ `metricDrift` верхнего уровня, и `violations` в нём
  записей дрейфа не содержит.
- Текст `--help` для `--new-since` не содержит запрещённых §0.5 формулировок.

**Регрессионные / инвариантные:**
- **Документация не расходится с каталогом:** таблица гейтируемых метрик в

## 16. Соотношение с baseline-файлом

**Дополняет, не заменяет.**

| Сценарий                                                          | Инструмент           |
| ----------------------------------------------------------------- | -------------------- |
| Внедрение в легаси: зафиксировать долг и не падать на нём целиком | baseline-файл        |
| PR-гейт: новые нарушения + регрессии четырёх агрегатных метрик    | `--new-since`        |
| Осознанно принятый долг, который должен пережить любые сравнения  | baseline-файл        |
| Отслеживание погашения долга (`--show-resolved`)                  | baseline-файл        |
| Разовая проверка «что я внёс за 3 коммита»                        | `--new-since=HEAD~3` |
| Репозиторий без доступной истории / первый прогон на новой машине | baseline-файл        |

Baseline фиксирует *решение человека* («этот долг принят»), `--new-since` фиксирует
*факт истории* («этого раньше не было»). Их композиция осмысленна, с оговоркой §8.3.

Позиция проекта в догфудинге (baseline-файл не используется принципиально)
`--new-since` не противоречит: он не прячет долг, он отделяет чужой долг от своего.
