# План: исключить енумы из знаменателя абстрактности (нейтрально)

**Статус:** реализовано 2026-08-19
**Дата:** 2026-08-16 (факт кода сверен и обновлён 2026-08-19)
**Область:** `src/Analysis/Evidence/Coupling/AbstractnessCollector.php`, `src/Analysis/Evidence/Size/ClassCountCollector.php` и `ClassCountVisitor` (счётчик расщепляется там), `src/Analysis/Evidence/Measurement/Contract/MetricName.php` (новое имя метрики), доки метрики, бенчмарки

---

## 1. Предпосылки

Формула абстрактности (до изменения — `AbstractnessCollector::calculate()`):

```
A = (abstract-классы + интерфейсы) / (классы + енумы + трейты + интерфейсы)
```

Енумы попадают в знаменатель как «конкретика». Клиентский замер: порт с 16 классами +
7 енумами + 7 интерфейсов, `7/30 = 0.233` (замер даёт 0.24) → без енумов `7/23 = 0.304`.
Направление сдвига D = |A + I − 1| не монотонно по A: в «зоне боли» (A+I < 1) рост A
**уменьшает** D — то есть енумы действительно ложно поднимают distance, как заявлено;
в «зоне бесполезности» (A+I > 1) рост A **увеличивает** D. Вывод клиента верен для его
случая, но не как общее утверждение.

Предпосылка «енум меняется аддитивно и не ломает зависимых» **неверна и из плана убрана**:
добавление case'а ломает неисчерпывающий `match` (`\UnhandledMatchError`), а енум может нести
методы и реализовывать интерфейсы. Аргумент за исключение — не «не ломает», а
классификационный: енум — «другое обозначение строки/числа», не несущий сигнала
абстрактности/конкретики (см. §2).

Поиск по источникам: модель из whitepaper «OO Design Quality Metrics — An Analysis of
Dependencies» (R. C. Martin, 1994) оперирует только «abstract classes» и «interfaces»;
PDepend дословно повторяет формулу без енумов; ни PDepend, ни PHPMetrics не имеют
документированной спецобработки енумов (обе старше PHP 8.1 enums). Устоявшейся конвенции
нет — вопрос открытый, а не «другие уже решили».

**Отображение PHP на модель Мартина.** Текущая формула уже неявно адаптирует модель; план
делает её явной и меняет одну клетку:

| Модель Мартина (1994) | Конструкт PHP             | Текущая классификация    | Предлагаемая                |
| --------------------- | ------------------------- | ------------------------ | --------------------------- |
| abstract class        | abstract class, interface | абстрактное (числитель)  | без изменений               |
| concrete class        | class                     | конкретное (знаменатель) | без изменений               |
| — (не существует)     | trait                     | конкретное (знаменатель) | без изменений               |
| — (не существует)     | enum                      | конкретное (знаменатель) | **нейтральное (исключить)** |

## 2. Аргументы

**Почему нейтрально, а не в числитель.** Абстрактность в модели Мартина измеряет, сколько в пакете
точек, куда можно подставить другую реализацию. Енум не даёт ни одной: его нельзя расширить,
у него не бывает подтипов и реализаций. Методы на енуме — функции над фиксированным набором
литералов, а не точка расширения, поэтому их количество и сложность на классификацию не влияют.
Отсюда «нейтрально» следует напрямую, без апелляции к волатильности поведения — прежняя
редакция аргументировала именно ей, а этот довод работает против исключения (волатильность —
признак конкретики) и потому убран.

**Енум, реализующий интерфейс, — исключение: он идёт в знаменатель.** `enum X implements Y`
есть конкретная реализация объявленного контракта, то есть ровно та точка подстановки, которой
у голого перечисления литералов нет. Без этой оговорки неймспейс «один интерфейс плюс N
реализующих его енумов» давал бы `A = 1/1 = 1.0` — «полностью абстрактный» при том, что
реализация лежит рядом; при низкой нестабильности это разворот с `D ≈ 0.83` на `D ≈ 0`.
Данные для различения дешёвые: `ClassCountVisitor` уже разбирает узел `Enum_`, у которого есть
список `implements`.

**Про 0/0 — это не новый edge-case.** Неймспейс без единого класса (только функция или голый
`echo`) уже даёт `totalTypes === 0` → `computeAbstractness()` возвращает `0.0`. И он уже нейтрализован ниже по стеку: `DistanceRule` /
`InstabilityRule` / `CboRule` (namespace) гейтят по `minClassCount` (`SIZE_CLASS_COUNT`,
дефолт 3), а енумы считаются отдельным `SIZE_ENUM_COUNT`, не `SIZE_CLASS_COUNT`. То есть
enum-only неймспейс после исключения имеет `classCount = 0 < 3` и пропускается — ровно как
уже пропускается no-class неймспейс. Исключение енумов делает enum-only неймспейс «таким же»,
а не вводит новое деление на ноль.

**Метрическая политика: адаптация скоупа, а не смена формулы.** Форма формулы (абстрактное /
все типы) не меняется; меняется классификация одного PHP-конструкта, отсутствовавшего в
модели 1994 года. По Metrics Policy это «scope adaptation for PHP realities» (документируемое,
AGENTS.md:228), а не «changing the fundamental formula» (требующее переименования, :232).
Обоснование — таблица отображения в §1; без неё изменение было бы непрозрачным.

## 3. Решение

1. **Знаменатель определяется заново и явно:** `totalTypes = classCount + traitCount + interfaceCount
   + implementingEnumCount`. Это существенно для стража деления на ноль: он проверяет именно `totalTypes`,
   и при старом определении, включавшем все енумы, поведение при нуле было бы другим.

   Различать два вида енумов при подсчёте. Голое перечисление литералов — нейтрально,
   исключается из знаменателя. `enum X implements Y` — конкретная реализация, остаётся в
   знаменателе. Числитель не меняется.

   **Форма расщепления (решено при реализации).** `SIZE_ENUM_COUNT` (`enumCount`) сохранён
   без изменения смысла — это размерная метрика «сколько здесь енумов», она экспортируется
   наружу (`--format=metrics`, JSON/HTML, `scripts/collect-benchmark-data.php`) и не обязана
   знать про классификацию Мартина. Рядом добавлен `SIZE_IMPLEMENTING_ENUM_COUNT`
   (`implementingEnumCount`) — подмножество: енумы с явным `implements`. Голые енумы
   выводятся вычитанием и отдельного счётчика не получают. Отвергнута альтернатива
   «расщепить `enumCount` на два непересекающихся счётчика»: она молча меняет смысл уже
   экспортируемого имени метрики и ломает потребителей ради величины, которая выводится
   арифметикой. Знаменатель — `classCount + traitCount + interfaceCount + implementingEnumCount`;
   `requires()` читает `implementingEnumCount.sum` вместо `enumCount.sum`.

   Учитываются только явные `implements`: `UnitEnum` / `BackedEnum`, которым удовлетворяет
   любой енум, в AST в списке `implements` не появляются, и по смыслу это не авторское
   объявление контракта.
2. Поведение при `totalTypes === 0` (включая enum-only неймспейс) оставить: `A = 0.0`,
   downstream-правила и так пропускают его по `minClassCount`. (Альтернативу «хранить
   undefined и пропускать» — не делать, чтобы не менять уже существующее поведение no-class
   неймспейса; при необходимости — отдельным решением.)
3. Задокументировать как отклонение от оригинальной формулы: docblock +
   `!!! info "Deviation from original spec"` в `website/docs/rules/coupling.{md,ru.md}` +
   `> Note:` в `src/Analysis/Evidence/Coupling/README.md`.
4. Перекалибровать бенчмарк: `composer benchmark:check` / при необходимости
   `composer benchmark:update`, обновить golden-файлы и ожидаемые диапазоны health.

## 4. Последствия

- Код: `AbstractnessCollector::calculate()` и docblock формулы; `ClassCountVisitor`
  (ветка `Enum_` получает подсчёт `implements`), `ClassCountCollector` (`provides()`,
  `collect()`, `getNamespacesWithMetrics()`, `getMetricDefinitions()`), `MetricName`.
- Метрическая политика: изменение формулы = release-событие; CHANGELOG, docblock, доки EN+RU,
  бенчмарки.
- Потребители: прямые — `DistanceCollector` (считает `D = |A + I − 1|`) и `DistanceRule`
  (читает готовые `distance`/`abstractness`); косвенные — экспорт метрики наружу
  (metrics/JSON/HTML-формат, Martin-диаграмма) и `health.coupling` через distance.
  `enumCount` наружу не поменялся, добавился `implementingEnumCount`.
- Тесты: `AbstractnessCollectorTest` (случай с енумами в неймспейсе; `requires()` без
  `SIZE_ENUM_COUNT` и его тесты), golden-агрегация при наличии, `DistanceCollectorTest`
  (D = |A+I−1| вычисляется там, `DistanceCollector.php:82-84`, а не в DistanceRule; A растёт →
  D **уменьшается** на concrete+stable стороне, **увеличивается** на abstract+unstable стороне).
- Бенчмарк (факт 2026-08-19): `composer benchmark:check` зелёный до и после изменения, все
  15 проектов в прежних диапазонах, `benchmark:update` не потребовался. Причина — в корпусе
  почти нет енумов (0–3 на проект, ни одного с `implements`), поэтому корпус эту клетку
  практически не проверяет. Эффект измерен на самом qmx (одинаковая цель, два бинаря):
  31 из 166 неймспейсов сдвинулись, max |ΔA| = 0.167; у 29 D **уменьшился**, у 2 —
  увеличился, и это ровно те два, где A + I > 1. Направление совпадает с §1.
- Половина «readonly-VO без поведения» в этот план **не входит**: у неё нет точного
  определения «без поведения», отдельно и позже.
