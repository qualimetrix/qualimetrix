# Пакет A — вердикт директивы на выключенном правиле

Вторая редакция. Первая построила ответ на утверждении «авторитет включённости —
объект опций правила, спецслучаев нет»; три ревьюера независимо показали, что это
утверждение неверно дважды, и обе поправки меняют контракт, а не формулировку.
Что именно опровергнуто — в разделе «Чего стоила первая редакция», чтобы
следующий читатель не восстановил её из общих соображений.

## Дефект, измеренный

Стенд: класс с методом CCN 4 и директивой
`@qmx-threshold complexity.cyclomatic warning=1 error=2` на нём.

| конфигурация правила                               | вердикт                                                         | код возврата |
| -------------------------------------------------- | --------------------------------------------------------------- | ------------ |
| `enabled: false` (плоско)                          | `unmeasured: the producer of the addressed channel did not run` | 0            |
| `callable.enabled: false` + `class.enabled: false` | `inert: removing it changes nothing`                            | **2**        |
| `callable.enabled: false`, `class.enabled: true`   | `inert: removing it changes nothing`                            | **2**        |

Первая строка — верный ответ, вторая и третья — нет: правило не работало на том
уровне, к которому директива привязана, и причина в конфигурации, а не в
директиве. Код `2` требует от автора снять живую директиву.

Третья строка — вклад ревью: первая редакция плана считала дефектом только
полное выключение всех уровней и объявляла частичное «не дефектом».

## Почему это не «научить метод читать уровни»

`RuleOptionsRegistry::isRuleDisabledByOptions()` пере-выводит ответ из сырого
массива конфигурации: смотрит ключ `enabled` верхнего уровня. Научить его форме
`callable: {enabled: false}` — значит завести вторую копию семантики, которая
разъедется с первой; ровно этот класс дефектов заход и убирает.

Настоящий авторитет — объект опций, и он **уже построен**: `RuleOptionsCompilerPass`
регистрирует опции каждого продюсера отдельным DI-сервисом и связывает их с
правилом. Метод `RuleOptionsCompilerPass::optionsServiceId()` публичен именно
потому, что на тот же экземпляр уже ссылается другой потребитель.

## Решение

- Из `RuleConfigurationInterface` операция `isRuleDisabledByOptions()`
  **удаляется**: это не вопрос к хранилищу опций.
- Заводится сервис-владелец ответа в `Analysis\Finding`. Он **не строит** опции, а
  берёт их из service locator'а, собранного компилятор-пассом по тем же
  `optionsServiceId()`. Значит спрашивается буквально тот объект, которым
  пользуется правило.
- Ответ даётся с гранулярностью **уровней, достижимых директивой**, а не
  продюсера.

```
answer(producerName, reachableLevels):
    options = locator.get(producerName)          // тот же экземпляр, что у правила
    if options is not hierarchical:
        return options.isEnabled() ? NotDisabled : Disabled
    levels = reachableLevels ∩ options.getSupportedLevels()
    return every(levels, l => !options.isLevelEnabled(l)) ? Disabled : NotDisabled
    // ... implementation details
```

`HierarchicalRuleOptionsInterface` уже объявляет `isLevelEnabled(SymbolLevel)` и
`getSupportedLevels()` — заводить ничего не нужно.

### Почему locator, а не фабрика

`RuleOptionsFactory::create()` имеет побочные эффекты: пишет в
`RuleNamespaceExclusionProvider` и `RulePathExclusionProvider`
(`extractExcludeNamespaces()`, `extractExcludePaths()`), логирует неизвестные
ключи и валидирует числа с возможным исключением. Вызов по каждой директиве
переregистрировал бы исключения и дублировал диагностику, а `DirectiveUsage`
документирован как чистая функция без состояния прогона
(`src/Analysis/Policy/Inline/README.md`). Locator этого не делает: сервисы уже
построены один раз.

### Почему карта приходит компилятор-пассом

Прямая инъекция `RuleExecutionInterface` замыкает цикл: `DirectiveUsage` →
`RuleExecution` → все экземпляры правил, среди которых `UnusedDirectiveRule` →
`InlineDirectivePolicy` → `DirectiveUsage`. Сервисы опций от правил не зависят,
поэтому locator по ним цикла не создаёт.

### Контракты

```php
interface ProducerEnablementInterface   // имя — предмет решения на ревью
{
    /**
     * Выключен ли продюсер конфигурацией опций на всех уровнях,
     * достижимых директивой этого охвата.
     *
     * @param list<SymbolLevel> $reachableLevels
     * @throws LogicException если имя не зарегистрировано — см. краевой случай 1
     */
    public function isDisabledByOptions(string $producerName, array $reachableLevels): bool;
}
```

Из `RuleConfigurationInterface` уходит:

```php
public function isRuleDisabledByOptions(string $ruleName): bool;   // удаляется
```

## Шаг A0 — перечисление достижимых уровней (до реализации)

Множество существует в коде, поэтому перечисляется, а не выводится по ходу:
`ControlScope` имеет четыре значения (`Hook`, `Property`, `Callable`, `Class_`),
`SymbolLevel` — пять (`Callable`, `Class_`, `File`, `Namespace_`, `Project`), и
отображение между ними не тотально. Директива охвата `Class_` раскрывается
`FileProcessor` на содержащиеся объявления, то есть достаёт и до находок уровня
`Callable`; директива на методе — только до `Callable`.

Шаг A0 снимает таблицу «охват × достижимые уровни» скриптом по коду раскрытия
охватов и кладёт её рядом с `enumeration-producer-enablement.tsv`. Пока таблицы
нет, контракт `isDisabledByOptions()` не фиксируется: множество, о котором
утверждает сигнатура, не перечислено.

Отдельно таблица обязана назвать, откуда берётся набор уровней у второго
потребителя: `DirectiveUsage` судит по коду канала, а не по охвату, и связь
«канал → уровни» отвечает `ChannelIdentityInterface::levelsOf()`.

## Перечисление продюсеров

`enumeration-producer-enablement.tsv` (51 строка), снято
`enumeration-producer-enablement.php` по живому контейнеру.

| величина                                          | значение                                    |
| ------------------------------------------------- | ------------------------------------------- |
| имён-продюсеров                                   | 51                                          |
| классов правил в реестре                          | 45                                          |
| плоских / иерархических опций                     | 46 / 5                                      |
| продюсеров без собственного класса                | 6 (`health.*`, хост — `ComputedMetricRule`) |
| строк, где столбец `isEnabled_sites` равен `NONE` | **6** — те же шесть `health.*`              |

Шесть `NONE` — не дефект и не пробел: у этих имён нет своего класса, поэтому
токенизатору нечего было читать. Их включённость решается
`ComputedMetricProducerOptions::isEnabledFor()` в хосте. Первая редакция плана
писала в этой строке «0», противореча собственному артефакту; три ревьюера нашли
это независимо.

Иерархические пять: `complexity.cognitive`, `complexity.cyclomatic`,
`complexity.npath`, `coupling.cbo`, `coupling.instability`.

**Чем получено и чего этот способ не видит.** Имена и классы опций — из живого
контейнера (`RuleExecutionInterface::allRules()` отдаёт `RuleMetadata` с `name` и
`optionsClass`; классы правил — `RuleRegistryInterface::getClasses()`). Места
обращения к включённости — токенизатором по цепочке наследования класса правила
внутри `src/`. Способ **не видит**: обращение из коллаборатора, не являющегося
предком правила; динамическую диспетчеризацию; включённость, вычисляемую в обход
объекта опций. Третье слепое пятно сработало на практике — см. краевой случай 2.
Первая редакция искала точный идентификатор `isEnabled` и объявила семь правил
«никогда не спрашивающими», потому что семейство computed зовёт `isEnabledFor`.
Каналы ссылки, покрытые перечислением: прямой импорт, DI-реестр, метаданные
правила. Не покрыты конфигурация и рефлексия — для них утверждение сужено до
«locator отдаёт тот же экземпляр, что получает правило», и это проверяется
стражем тождества из тестового плана, а не перечислением.

## Краевые случаи

1. **Имени нет в locator'е — отказ, а не умолчание.** Оба потребителя передают
   имя, уже разрешённое вселенной каналов: `DirectiveUsage` — через
   `producerOf($code)`, `ThresholdDirectiveAudit` — после
   `addressability->problemWithThreshold()`, который отвечает `AlreadyRefused` на
   всё неадресуемое. Поэтому промах карты означает дефект проводки
   компилятор-пасса, а не опечатку автора, и молчаливое «не выключен» его бы
   замаскировало. Порядок «адресуемость раньше включённости» — инвариант, и он
   проверяется тестом, а не комментарием.
2. **У семейства computed есть второй путь выключения, и отвечать на него не
   надо.** Секция `computed_metrics` (и `--exclude-health`) снимает определение из
   каталога до всякого объекта опций: `ComputedMetricsConfigResolver::resolve()`
   либо удаляет определение, либо отправляет в `HealthFormulaExclusion`. Ревью
   предсказало здесь `Inert` и красный CI; **измерено — предсказание неверно**:
   выключение убирает канал из вселенной, и адресуемость отвечает раньше.
   Проверено на обеих половинах семейства:

| вход                                                                                            | вердикт                                                   | код |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------- | --- |
| `computed_metrics: {health.cohesion: {enabled: false}}` + `@qmx-ignore health.cohesion`         | `unmeasured` (`annotation.unresolved-directive` отвечает) | 0   |
| пользовательская `computed.branch-load` c `enabled: false` + `@qmx-ignore computed.branch-load` | `unmeasured`                                              | 0   |
| те же входы с включённой метрикой (контроль)                                                    | `effective`                                               | 0   |

   Сервис на этот путь не отвечает намеренно: ответ уже принадлежит другому
   вердикту, и вторая жалоба судила бы одну ошибку дважды.
3. **`rulePattern` — не образец.** Поле названо `rulePattern`, но
   `ThresholdOverride::matches()` сравнивает строгим равенством, а докблок поля
   говорит «exact rule name». Раскрытия образца не требуется.
4. **Цена.** Locator не строит ничего: сервисы опций уже созданы для правил.
   Ответ — обращение к контейнеру плюс `isLevelEnabled()`. Оценка первой редакции
   («~51 построение на прогон») относилась к отменённому дизайну и снята.

## Тестовый план

- **Страж тождества (вместо тавтологичного стража дрейфа).** Первая редакция
  предлагала сверять ответ сервиса с опциями, построенными фабрикой, — оба конца
  читали бы один источник. Вместо этого: для каждого из 51 имени объект, который
  отдаёт locator, — **тот же экземпляр**, что получил правило (сравнение по
  идентичности объекта, не по значению). Это проверяет проводку, которую
  перечисление не покрывает.
- **Поведенческие, сквозь продукт, а не через подставленные опции.** Три строки
  таблицы «Дефект, измеренный» становятся кейсами: полное выключение → тот же
  ответ, что и сегодня; оба частичных → `unmeasured / ProducerDisabled` и код 0.
  Правило, проверяемое подставленным состоянием, не проверяется вовсе.
- **Иерархические поимённо, все пять** — источник списка — TSV; выключение
  каждого уровня по отдельности и обоих сразу.
- **Плоские:** `enabled: false` и скалярное `false` — регрессия сегодняшнего
  поведения.
- **Computed:** выключение одного `health.*` через `rules:` не выключает соседей;
  выключение через `computed_metrics:` даёт `unmeasured` **не** через новый
  сервис (краевой случай 2).
- **Инвариант порядка:** имя, не прошедшее адресуемость, до сервиса не доходит;
  а незарегистрированное имя, поданное напрямую, даёт отказ.
- **Проверка самой проверки:** с откаченным исправлением обязаны краснеть
  поведенческие кейсы частичного выключения; проверяется снятием поштучно, а не
  «набор покраснел». Отдельно: мутация «locator отдаёт свежепостроенные опции
  вместо связанных с правилом» обязана краснить страж тождества.

## Definition of Done

1. `composer cs-check`.
2. `composer phpstan` — уровень 8, покрывает и `scripts/`.
3. `composer test` — в отчёте называется **число исполненных тестов**.
4. Декларации манифеста правятся руками (новый тип, новые потребители, снятие
   записей об удалённой операции), затем `composer architecture:generate`.
5. Новый путь получает пробу в `scripts/directive-audit-controls/Probes.php`, и
   `composer directives:controls` краснеет на ней.
6. Обновляются README: `src/Analysis/Finding/README.md` (новый сервис и его
   контракт), `src/Analysis/Policy/Inline/README.md` (утверждение о чистоте
   `DirectiveUsage` и его новая зависимость), `src/Infrastructure/README.md`
   (новый компилятор-пасс).
7. `composer check` целиком, с
   `QMX_MKDOCS=<основной checkout>/website/.venv/bin/mkdocs`.
8. `composer gate -- --reference=38ad58e9` — GREEN. **Чем это является и чем не
   является:** вывод команды `directives` в сравниваемые поверхности гейта не
   входит (`Surfaces::FORMATS` — одиннадцать форматов `check` плюс `rules`,
   `baseline:explain` и сгенерированный baseline). Поэтому гейт здесь
   свидетельствует «ничто другое не сдвинулось», а не «исправление работает».
   Свидетель самого исправления — поведенческие тесты и стенд.
9. `FOLLOWUPS.md`: запись «`isRuleDisabledByOptions()` не спускается в
   поуровневую конфигурацию» закрывается с указанием, чем именно; частичное
   выключение называется отдельно, потому что записью не покрывалось.
10. `CHANGELOG.md`: запись `Fixed`. **Не `Breaking`:** удаляемая операция
    принадлежит внутреннему контракту `RuleConfigurationInterface`, который
    политика обратной совместимости к внешней поверхности не относит (CLI, схема
    конфигурации, формат baseline, `RuleInterface`). Пользовательски видимое
    изменение здесь — вердикт и код возврата, и это исправление, а не слом.

Пакет не объявляется готовым по зелени одной группы: свидетельство — только
агрегат.

## Чего стоила первая редакция

Три ревьюера, девять + шесть + девять находок, из них по существу дизайна четыре,
и каждая — про решение планировщика:

- ответ давался с гранулярностью продюсера, а дефект имеет гранулярность уровня
  (найдено дважды независимо). Усугубляющий факт, которого я не проверил:
  агрегатный `isEnabled()` у всех пяти иерархических опций **не вызывается сегодня
  ни из одного места продакшена** — сервис стал бы первым потребителем величины,
  которой никто не пользуется, то есть формула «спрашиваем у авторитета» была бы
  ложной именно там, где важна;
- опции предлагалось строить фабрикой, у которой есть побочные эффекты (найдено
  дважды независимо), при том что готовые экземпляры уже зарегистрированы;
- сводная таблица противоречила собственному артефакту (найдено трижды);
- страж дрейфа был тавтологичен: оба конца читали фабрику (найдено дважды).

Опровергнута измерением одна находка — предсказание `Inert` и красного CI на
втором пути выключения computed. Механизм в ней назван верно, следствие — нет.
