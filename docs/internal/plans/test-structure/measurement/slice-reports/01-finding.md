# Test audit — slice `tests/Analysis/Finding/` (84 files)

A read-only audit. Nothing in the repository was changed; no state-changing
`composer`/PHPUnit/`bin/qmx`/git commands were run. The work was done by subdirectory (Unit — 4
groups via parallel subagents and directly, Integration and RuleConfiguration — separate groups),
every file read in full and checked against the corresponding `src/` code via `grep`/reading.

84 files = 62 unit tests + 15 integration tests (Integration, first half) + 12
integration/control tests (Integration, second half) + 3 RuleConfiguration/Unit tests + 4 Support
files (not tests). The table below contains exactly 84 rows.

## Duplicates and contradictions

1. **`FindingTest.php`: five twin fingerprint tests.**
   `itGetFingerprintFor{Method,Class,Namespace,File,GlobalFunction}` (lines 28–123) are named
   differently, but `Finding::getFingerprint()` never reads `symbolPath` at all — this is
   directly confirmed by the neighboring test
   `itUsesSubjectOccurrenceAndEdgeRatherThanLocationOrMessageForFingerprint` at line 245. There is
   one real regression guard, four are ballast disguised as coverage of five scenarios.

2. **`AnalysisContextThresholdTest.php` — the name lies about the content.**
   `itGetThresholdOverrideRespectsLineScope`, `itMethodLevelOverrideTakesPriorityOverClassLevel`,
   `itBoundedOverrideWinsOverUnbounded` (lines 78–192) describe a boundary by line number, but
   every call passes the same `subject` with no line number — the "inside/outside scope"
   comparison never actually varies.

3. **`RuleThresholdKeyGroupRegistryCompletenessTest.php` (793 lines) vs
   `RuleThresholdKeyGroupRegistryDriftTest.php` (513 lines)** — both run the AST parser over all
   of src/ to check the same `RuleThresholdKeyGroupRegistry`, with nearly identical method names
   (`itMakesEveryRegistryEntryCorrespondToARealCallSite` / `...RealThresholdParserCallSite`). The
   authors themselves explain the difference in the docblocks (literal arguments vs a behavioral
   probe) — not a blind duplicate, but the run cost is doubled; a merge candidate.

4. **`DECLARED_CHANNEL_COUNT = 58`** is hardcoded independently in
   `ChannelUniverseCoverageTest.php:65` and `ChannelPresentationCoverageTest.php:31`. The second
   one's docblock admits the numbers must match ("a divergence between the two counts would
   itself be a regression"), but nothing checks this programmatically — the divergence could go
   unnoticed if one file is fixed and the other forgotten.

5. **`LocationTest.php::itNoneCreatesLocationWithoutFile` ↔
   `LocationNullFileTest.php::itLocationNoneCarriesNullFile`** — both create `Location::none()`
   and check the same set of properties. `LocationNullFileTest` is a separate file under ADR 0015
   Phase 1a with 3 cases of its own, so not a pure duplicate, but the overlap is nearly complete —
   a merge candidate.

6. **`Support/FindingFactory.php` — the file is physically in the wrong place.** It lives in
   `tests/Analysis/Finding/Support/`, but no test in the `tests/Analysis/Finding/` directory uses
   it — all 8 consumers are in `tests/Analysis/Policy/Baseline/Unit/`. By the subject-cohesion
   rule this is a Baseline-domain file; the correct location is
   `tests/Analysis/Policy/Baseline/Support/FindingFactory.php` (next to the already-existing
   `tests/Analysis/Policy/Baseline/Fixtures/CeilingStageFixtures.php`).

7. **`RuleConfigurationIsolationTest.php`** partially overlaps by subject (resetting
   `RuleOptionsRegistry`) with two state-reset tests inside `RuleOptionsFactoryTest.php` — not a
   strict duplicate (different fields), but a merge candidate.

8. **`RuleNamespaceExclusionProviderTest.php`** — the first two tests actually check
   `RuleOptionsRegistry` (delegation), not the declared SUT `RuleNamespaceExclusionProvider` —
   mixing subjects in one file.

9. **`RuleDocsPageCoverageTest.php` ↔ `RuleRemediationMinutesCoverageTest.php`** — private
   helpers copied verbatim (`ruleClasses()`, the count `48`, `docsRoot()`) between two files using
   the same pattern for checking docs against the rule registry.

10. **The `ChannelLevelAssemblyTopologyTest`/`ChannelLevelDeclarationDriftTest`/
    `ChannelLevelRefusalTopologyTest` triad** — NOT duplicates: three different facets

No contradictions (two tests asserting incompatible things about the same behavior) were found in

## How this was checked and what this method cannot see

Method: reading each of the 84 files in full (Read/cat), matching the declared SUT against the
real `src/` code via `grep`/following `use` statements, analyzing structure
(`#[Test]`/`#[CoversClass]`/method names) and comparing neighboring files for duplicates. The
work ran in four parallel streams (subagents A/B/C + direct work on group D), each stream
checking the code independently but not seeing the other groups — coordinating duplicates
BETWEEN groups (e.g. between Unit and Integration) was done only at this final step, by a quick
comparison of the tables, not a repeated line-by-line reading.

What this method does NOT see and does NOT prove:

- **Not verified by execution.** No test was ever actually run; the
  "integration"/"functional"/"control" assessments rest on static analysis of imports and calls
  (`ContainerFactory`, `CommandTester`, real Options classes, `proc_open('bin/qmx ...')`), not on
  observing a real run or a real failure when a regression is introduced.
- **The control guards' bite has not been confirmed by mutation.** For the large
  control-invariant files (`OccurrenceKindFreezeGuardTest`, `RuleIdentifierLiteralGuardTest`,
  `ThresholdOverrideOwnRuleNameGuardTest`, etc.) the docblocks assert "it was measured, it bites"
  — this was taken on faith from the docblock text; not a single mutation was reproduced within
  this audit.
- **The 654- and 1105-line files were not read line by line in full**
  (`RuleIdentifierLiteralGuardTest.php`, `ThresholdOverrideOwnRuleNameGuardTest.php`) — the
  docblock, the full method structure (`grep`), and representative body fragments were read; the
  same for `RuleOptionsFactoryTest.php` (2194 lines) and `RuleExecutorTest.php` (1504 lines) in
  group A. Point defects in the unread middle sections/blocks could have been missed.
- **The "duplicate" assessment is limited to this slice.** Duplicates of SUT/assertions with
  tests OUTSIDE `tests/Analysis/Finding/` (e.g. the same SUT checked from `tests/Infrastructure/`
  or `tests/Functional/`) were not searched for — that's outside the scope of the assigned slice.
- **Use of `Support/*.php` outside the slice was established with `grep -rl` on the class name**
  — a reliable but syntactic method; for every match the context (a `use` statement and a real
  constructor call) was briefly confirmed, but not guaranteed exhaustively for each of the ~45
  consumers of `StubChannelDeclarationRegistry`.
- **The "control-invariant" vs "control" assessment** — per the brief's definition ("the
  invariant is taken from ALL src/ classes via reflection"), this audit also classed files that
  scan a SUBSET of src/ (e.g. `ThresholdValidatorAssignmentTest` — only `Evidence/*`), not
  literally "all" classes. The boundary is disputed, the decision belongs to the owner, as the
  brief asks.
- **"Directory" correctness was assessed by the owning class's physical path**, not by a formal
  ADR analysis (ADR 0016/0022 co-change/counterfactual-ownership were not applied to the tests) —
  for clear-cut cases (a wrong namespace, use by another domain only) the discrepancy is
  indisputable, for borderline ones (e.g.
  `Rule/LevelActivityReadsBothDisablingSpellingsTest.php` in `Rule/` instead of
  `RuleConfiguration/`) the assessment is soft ("not critical").

## Assumptions

- The "control" category was assigned by the brief's criterion literally: the test doesn't run
  product behavior in real time, it checks laid-out state (documentation, generated artifacts,
  source text via regex/AST). Borderline integration tests with an across-the-board walk of the
  class population (see "Control candidates") were left as integration with an explicit caveat.
- For the 4 Support files, "SUT" is described as the object being constructed/the measuring
  instrument rather than checked behavior — per the brief's direct instruction for this case;
  "category" is `helper (fixture)`.
- No CLAUDE.md §9 violations (`#[Test]` + the `itXxx` form) were found in any of the 84 files —
  everywhere either both markers are correctly present, or (for the Support files) the methods
  aren't tests at all. This was checked independently by all four parallel streams and none found
  a violation.
- One of the background subagents (the last eight files of group B) crashed on a 429 API rate
  limit; these 8 files were read through and analyzed directly by the orchestrating agent without
  loss of depth — noted in the group B report.
- The "correct directory" column is left blank (= "ok") where the current location inside
  `tests/Analysis/Finding/` matches subject ownership per the `src/` code, even when the category
  is control/control-invariant: the question "should a control test live in `tests/` at all" is
  separate from "is this the correct subdirectory inside `tests/`", and the first is explicitly
  moved into the "Control candidates" section per the brief's requirement, not mixed into the
  "directory" column.
