# Unrecognized configuration keys in Qualimetrix — enumeration by measurement

Measured 2026-09-08 against commit `1b225c2e` (v0.26.0) (`bin/qmx`, version
reported as `dev-main`). Black box: every row below is a pair of runs (control / experiment) on a
private probe tree, not a reading of `src/`.

## Measurement protocol

* Probe tree `<scratch>` — `composer.json` (psr-4 `ProbeNs\` → `src/`),
  `src/Probe.php` (class `ProbeNs\Probe`, methods `complex` CCN 14 and `simple` CCN 1),
  `src/Other.php` (class `ProbeNs\Sub\Other`, method `f` CCN 2).
  Second tree `<scratch>` (adds `src/Skip/Skipped.php`) only for `exclude`.
  Third tree `<scratch>` (one file) only for inline directives.
* Every run: `bin/qmx -d <probe> check src --workers=0 --no-cache --no-progress --format=json
  --fail-on=none [--config=…] [extra]`, `1>OUT 2>ERR`, `ec=$?` taken immediately, no pipe.
* **`--fail-on=none` is deliberate.** Without it every run on this probe exits 2 because npath /
  class-rank / cohesion produce errors at default thresholds, and the exit code then says nothing
  about the key under test. With it, the control exits 0 and `0 / 1 / 2 / 3` become readable.
  Rows whose exit is not 0 under `--fail-on=none` are therefore genuinely caused by the key.
* Findings compared machine-readably: `violationsMeta.byRule` plus an md5 digest over the sorted
  tuple `(channel, symbol, severity, threshold)` of every entry in `violations`. The digest is what
  settles cases where two different configurations happen to produce the same *count*.
* Verbosity: every row whose verdict is `silent` was re-run at `-vvv` together with
  `--log-level=debug --log-file=…`, and both stderr and the log file were grepped for
  `unknown|unrecogn|invalid|ignor|<the typo'd token>`. **Not one produced a diagnostic** — the only
  matches were the routine `Analysis complete {...files_analyzed...}` lines. Row 17 was additionally
  swept at `-v` and `-vv` with the same result. So "silent" and "silent without `-v`" are not two
  different rows here: the four extra streams are uniformly empty for every key in this table.
* Column "stdout said" is `—` unless noted. **No diagnostic from the option validator ever reached
  stdout**, under `--format=json` or `--format=summary` — it is stderr in both. The one class of
  position that *does* speak through stdout is inline directives (rows 69–72), which deliver their
  refusal as findings inside the report itself.

## 1. Positions I tried to measure and could not

* **`architecture` beyond the first refusal.** The section is fail-closed at every depth I could
  reach (section key, layer-entry key, `allow` key, `allow` value), so I never got to a state where
  a policy was *running* with an unknown key inside it. Whether a key inside `match:`/`exclude:`
  criteria is validated is unmeasured: my probe tree has no class-attribute or interface structure
  rich enough to build a control where those criteria demonstrably change layer membership.
* **`coverage-gap` and `max_expanded_layers` values.** Known keys of `architecture:`, but I had no
  control that makes their effect observable on a two-class tree.
* **Per-level computed formulas.** `bin/qmx rules` documents a `computed` rule and README language
  mentions per-level formulas, but every spelling I could reach either silently did nothing
  (row 35) or crashed (row 36); I never produced a *working* per-level control, so "silent" in
  row 35 means "no observable effect", not "the correct form was rejected".
* **Rule-specific shorthands other than `threshold`.** `bin/qmx rules` shows camel-cased scalar
  options (`maxCycleSize`, `excludeReadonly`, `minMethods`, `wocThreshold`, …) and one kebab-cased
  pair (`vo-warning`/`vo-error` on `code-smell.long-parameter-list`). I proved the normalizer makes
  snake/camel/kebab interchangeable for `class.max_warning` (row 22) and I have no reason to think
  those differ, but I did not build a separate control for each of them — the probe tree does not
  produce findings for most of those rules.
* **`suppressed` format / `--show-suppressed` composition.** Not used as an observer; the `byRule`
  digest was sufficient everywhere, and adding it would not have distinguished any row.
* **A second config source overriding a first.** I measured `--config` vs autodiscovered `qmx.yaml`
  (row 61) but not preset + config + CLI layered together with the *same* unknown key in two of
  them; there was no control that would tell the layers apart.

## 2. Observations I first took for a defect and then refuted

Not empty — three:

1. **"The unknown key makes the run exit 2."** My first runs, and the orchestrator's own
   pre-measured `method:` row, showed `exit 2`. Refuted by adding `--fail-on=none`: the control
   config with a perfectly valid key also exits 2, because `complexity.npath`, `coupling.class-rank`
   and `health.cohesion` produce *errors* at default thresholds on this probe. Under
   `--fail-on=none` the `method:` case exits **0**. The exit code in the orchestrator's brief is an
   artifact of finding severity, not of the unknown key.
2. **"`levels:` crashes because the key is unknown."** Row 36 aborts with a TypeError, which read
   like "unknown key → crash". Refuted twice: (a) `foo: {bar: {warning: 1}}`, `clas: {warning: 1}`
   and `formulas: {clas: "2+2"}` — equally unknown, equally nested — are silently ignored and exit 0;
   (b) `levels: {class: {warning: 1}}`, where the *inner* key is the valid level name, crashes
   identically. The crash is about the shape passed to a key the reader does know, not about the key
   being unrecognized.
3. **"`--rule-opt` in dotted form is silently ignored"** (the trap stated in my brief, and in the
   project's own `rule_opt_syntax_trap` memory). Refuted on this build:
   `--rule-opt=complexity.ccn.callable.warning=1` exits **3** with
   `Invalid --rule-opt "…". Expected RULE:OPTION=VALUE.` — a clean refusal, not silence. The silent
   `--rule-opt` shape on this build is a *different* one: a well-formed `rule:option` with **no
   `=value`** (row 48), which is accepted, dropped, and never mentioned even at `-vv`.

4. **"The `annotation.*` exit 2 cannot be switched off."** I wrote this after
   `--disable-rule=annotation` was refused. Refuted by naming the rule the way `bin/qmx rules` lists
   it: `--disable-rule=annotation.directive` exits 0 and the finding disappears, as does
   `--disable-rule=annotation.unresolved-directive`. What is actually broken is narrower and
   different — the *group prefix* form, which is what `--help` advertises (row 77).
5. **"Top-of-rule keys warn because they are top-of-rule; inner keys are silent because they are
   inner."** This is a claim about depth, and it could equally have been a claim about the names
   `warning`/`error` being unvalidated wherever they appear. Discriminated by rows 74–75: on
   `coupling.class-rank`, a rule with no levels, `warnign` and `errro` sit at the top of the rule and
   **do** warn. So the depth reading survives: the option validator runs exactly one level deep, and
   everything below a level slot is unchecked.

A further near-miss worth recording as the inverse: `enabled: false` (row 23) *prints an unknown-option
warning and works anyway*. I initially recorded it as "warn, key ignored"; the digest refuted that —
`complexity.ccn` disappears from the findings entirely. So the warning is a false alarm, and its
twin `enable:` (row 24) prints the identical sentence while doing nothing. A user cannot tell the
working key from its typo by the message.

## 3. Forms that were not in the starting list

* **A key that warns and is honoured anyway** (`enabled:`, row 23) — and its typo, which warns
  identically and is not honoured (row 24). The message does not separate them.
* **A key that is silently *accepted* under a different case** — `Callable:` (row 15) is applied,
  while `CALLABLE:` (row 16) is rejected, and rejected under a mangled name.
* **The unknown-option message echoing a normalized, not a typed, key** — `CALLABLE` is reported as
  `"c-a-l-l-a-b-l-e"` (row 16). Searching the config for the string in the warning finds nothing.
* **Case-insensitivity is asymmetric between depths.** The level slot accepts `Callable`; the inner
  keys do not accept `WARNING`/`ERROR` (row 20) — and say nothing about it.
* **Naming convention is silently free at the innermost depth** — `max_warning`, `maxWarning` and
  `max-warning` are one and the same key (row 22). "snake vs camel vs kebab" is not a defect class
  here, it is a non-distinction; the defect class is that nothing tells you which spellings are
  equivalent.
* **`--rule-opt` with a valid `rule:option` and no `=value`** (row 48) — silent no-op, while the
  malformed-without-colon form is refused. The two malformations are treated oppositely.
* **Unrecognized *values* rather than keys**: `suppress_paths` / `suppress_namespaces` / `exclude`
  entries that match nothing (rows 37–41), and `--namespace` / `--class` filters that match nothing
  (rows 55–56). The last two are the loudest silence measured: a full, clean-looking report with
  zero findings and exit 0.
* **`--format-opt` unknown key *and* unknown value** (rows 53–54) — a whole option namespace with no
  validation at all.
* **Refusal delivered as a finding rather than as a config error** — inline directives (rows 69–72)
  produce `annotation.unresolved-directive` / `annotation.invalid-threshold` channels, and the run
  exits **2 even under `--fail-on=none`**. It *can* be turned off, but only by naming the rule or the
  channel exactly: `--disable-rule=annotation.directive` and
  `--disable-rule=annotation.unresolved-directive` both work (exit 0), while the bare prefix
  `--disable-rule=annotation` is refused.
* **A CLI form the tool's own help documents and the tool does not accept** (row 77) — `--help` for
  `--disable-rule` says "a rule or group by prefix (e.g., **complexity**, size.class-count)", and
  `--disable-rule=complexity` is refused with "does not match any registered producer, group, or
  channel". Only fully-qualified rule and channel names are accepted.
* **A misspelled directive *tag*** (row 73) — invisible to both observers: `check` says nothing and
  `bin/qmx directives src` reports "No inline directives in the analysed scope". The audit command
  designed to find inert directives cannot see a directive whose tag is misspelled.
* **Baseline entry fields** (rows 62–66) as a position class: unknown *added* fields are silently
  accepted, while *renamed* fields are reported — but reported under the internal field name
  (`"count" must be an integer` for a `magnitudes` → `magnitude` rename), not the one the user wrote.
* **A refusal that names the wrong thing** — row 31 (`formulaa:`) refuses with
  "has no formula for level namespace", never mentioning the key that was actually misspelled.
* **A whole run lost to an uncaught TypeError** (row 36) — no JSON, exit 1, an internal FQCN in
  stderr as the only diagnostic.
