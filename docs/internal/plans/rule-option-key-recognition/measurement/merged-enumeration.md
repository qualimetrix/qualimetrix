## Мой протокол разрешения

Собственный пробник `<scratch>` — независимый от пробника второго
свидетеля: `composer.json` (psr-4 `RecNs\` → `src/`), `src/Probe.php` (`RecNs\Probe::complex`
CCN 15, `::simple` CCN 1), `src/Sub/Other.php` (`RecNs\Sub\Other::f`). Отдельное дерево
`<scratch>` для инлайн-директив.

Каждый прогон: `bin/qmx -d <probe> check src --workers=0 --no-cache --no-progress
--format=json --fail-on=none [...]`, `1>rec-<id>.out 2>rec-<id>.err`, `ec=$?` снят сразу, **без
пайпа**. Находки сравнивались машинно: количество + md5 по отсортированному кортежу
`(channel, symbol, severity, threshold)`. Обёртка — `<scratch>`.

## Расхождения и как разрешены

Пять точек были названы в задании; все пять разрешены собственным прогоном. Плюс три
расхождения, найденные при сведении.

1. **`--rule-opt` точечной формы — «молча игнорируется» против «exit 3».**
   Разрешено: `rec-run.sh ro-dotted --rule-opt='complexity.ccn.callable.warning=1'` → **exit 3**,
   `Invalid --rule-opt "…". Expected RULE:OPTION=VALUE.` Полностью точечная форма **отказывает**,
   не молчит. Молчит **другая** форма: корректная `rule:option` **без `=value`**
   (`--rule-opt='complexity.ccn:callable.warning'` → exit 0, опция отброшена, DEFAULT).
   Оба свидетеля по существу правы, просто про разные формы: код назвал молчаливой строку 12
   (двоеточие есть, `=` нет), измерение — строку 48, это одна и та же позиция.
   Неверна была формулировка в задании (и стоящая за ней запись памяти `rule_opt_syntax_trap`).
   Заодно установлен базис: `--rule-opt='complexity.ccn:callable.warning=1'` + `…:callable.error=2`
   даёт digest BASE, то есть точечная форма ПОСЛЕ двоеточия — рабочая и единственная.

2. **`coupling.distance:project_namespaces` — «работает и объявлен неизвестным».**
   Разрешено тремя прогонами. `--rule-opt='coupling.distance:project_namespaces=RecNs'` печатает
   `[WARNING] Unknown option "project-namespaces"`, но со значением `RecNs` предупреждение
   «no project namespaces detected among 2 namespaces» **не появляется**, а со значением
   `NoSuchNs` — **появляется**. Контроль на объявленном ключе `include_namespaces` даёт ровно ту же
   пару реакций. Ключ читается и применяется, а валидатор объявляет его неизвестным.
   Позиция кода подтверждена; измерение её не имело.
   Побочно: в одном и том же stderr «Available options» печатает `include-namespaces` (kebab), а
   подсказка внутри сообщения — `include_namespaces=` (snake).

3. **Нечисловой порог внутри уровня — exit 1 мимо обработчика конфигурации.**
   Разрешено: `{callable: {warning: "abc", error: 2}}` → **exit 1**,
   `Unexpected error: Invalid configuration for rule "complexity.ccn": option "callable.warning"
   must be numeric, got "abc".` Текст отказа корректен и точно называет ключ — но приходит под
   префиксом «Unexpected error» и с кодом 1 вместо 3. То же на верхнем уровне (`threshold: "abc"`).
   Это единственная проверка, доходящая ВНУТРЬ уровня, и она смотрит на значения, не на имена.

4. **`computed_metrics` с `levels: {class: {…}}` — неперехваченный TypeError.**
   Разрешено: **exit 1**, stdout пуст, единственная диагностика —
   `Unexpected error: …ComputedMetricOverrideReader::mapLevel(): Argument #1 ($level) must be of
   type string, array given`. Отчёта нет вовсе. Контроль `levels: [methd]` (список) даёт чистый
   refuse 3 «Invalid computed metric level». Крах — про ФОРМУ значения известного ключа, а не про
   неизвестный ключ; это подтверждает и рефутацию второго свидетеля в его §2.2.

5. **`--disable-rule=complexity` — пример из собственного `--help`.**
   Разрешено: справка дословно говорит `Disable a rule or group by prefix (e.g., complexity,
   size.class-count)`. Первый пример → **exit 3**, `Rule selector "complexity" does not match any
   registered producer, group, or channel.` Второй пример (`size.class-count`) → exit 0.
   Форма группового префикса не существует; та же строка из конфигурационного файла
   (`only_rules: [complexity]`) отказывает так же.

6. **Расхождение, найденное при сведении: код-перечисление про `BaselineCommand` (его §1) заявляло
   exit 2.** Измерено: **exit 1**, и диагностика уходит в **stdout**, а не в stderr. Хуже
   заявленного: тот, кто перенаправляет stdout, теряет сообщение целиком. Заодно измерено, что
   `rules` и `graph:export` битый `qmx.yaml` **не читают вовсе** — exit 0, обе полностью молчат.

7. **Расхождение о том, что делает `bin/qmx directives`.** Код заявлял «на unmeasured возвращает 0».
   Измерено и усилено: наблюдатели **инвертированы**. Директива с неизвестным именем правила —
   `check` exit 2, `directives` exit 0. Корректная директива, ничего не подавляющая — `check`
   exit 0, `directives` exit 2. Ни один из двух не видит обе беды.

8. **Расхождение о `suppress_namespace_channels`.** Код заявлял (его §2 п.10) отказ и корректную
   работу, измерение позиции не имело. Измерено: ключ карты **валидируется** (неадресуемый канал →
   refuse 3), но при верном канале **не подавляет ничего** ни при `["RecNs"]`, ни при `["*"]`, ни
   при `["RecNs\Probe"]`. Дискриминаторы: `suppress_namespaces` и `suppress_paths` на том же
   правиле работают (7→4), значит дефект специфичен для `_channels`, а не для пер-рульного
   подавления вообще; на корне `suppress_namespace_channels` не является ключом (refuse 3).

## Строки, которые я опроверг

Опровергнутых **между свидетелями — ноль**: там, где оба высказались, они не противоречили друг
другу ни разу; расхождения оказывались разными формулировками одной позиции либо разными
позициями. Опровергнуто три утверждения, и все три — не из перечислений:

1. **«`--rule-opt` точечной формы молча игнорируется»** — формулировка задания и запись памяти
   `rule_opt_syntax_trap`. На этой сборке форма **отказывает** с exit 3 и внятным текстом
   (см. «Расхождения» п.1). Второй свидетель уже отверг это в своём §2.3; я подтверждаю.

2. **«Неузнанный ключ опции заставляет прогон выйти с 2»** — исходная постановка задания.
   Опровергнуто протоколом: контроль с заведомо ВЕРНЫМ ключом на этом пробнике тоже выходит с 2,
   потому что npath / class-rank дают ошибки на дефолтах. Под `--fail-on=none` эти позиции выходят
   с **0**. Exit 2 был артефактом severity находок, а не ключа.

3. **«`BaselineCommand` отдаёт exit 2»** — утверждение код-перечисления (его §1, третий буллет).
   Измерено **exit 1** и вывод в stdout (см. «Расхождения» п.6). Механизм («один класс ошибки —
   разные коды в разных командах») подтверждён, конкретное значение — нет.

Отдельно: одна моя собственная серия прогонов была **артефактом моего метода**, не продукта —
первая попытка построить YAML через `printf '%s'` не разворачивала `\n`, и шесть позиций
«отказали» на ошибке парсера YAML. Перемерено через `printf '%b'`; в таблицу вошли только вторые
результаты. Записываю, потому что это ровно тот класс, который делает согласие двух свидетелей
недоказательным.

## Что осталось неизмеренным

Поимённо, с причиной:

1. **#94 `architecture.layers[].exclude` — неизвестный ключ внутри блока `exclude`.** Заявлен
   кодом как refuse 3. Не измерен: мой пробник из двух классов не даёт структуры (атрибутов,
   интерфейсов), на которой критерий `exclude` наблюдаемо менял бы состав слоя, поэтому контроля
   «ключ работает» построить не удалось, а отказ без контроля ничего не различает. То же
   ограничение назвал второй свидетель.

2. **#95 long-form ключ записи `architecture.allow.<src>[]`** и **#98 вид отношения в
   `relations:`** — по той же причине: секция fail-closed на каждой достижимой мной глубине, до
   состояния «политика работает с неизвестным ключом внутри» я не дошёл.

3. **#99 имя переменной шаблонного слоя в `exclude`.** Требует шаблонного слоя с переменными;
   на двухклассовом дереве не строится.

4. **`architecture.max_expanded_layers` — значения.** Известный ключ, но на моём дереве его эффект
   ненаблюдаем: контроля нет.

5. **Строка 21 код-перечисления — молчание при отсутствии отдельного err-потока**
   (`ErrorStream` fallback на `NullOutput` при встраивании/буферизации). Из CLI недостижимо в
   принципе: путь возникает при программном встраивании, а не при запуске `bin/qmx`. Оставлено
   как утверждение по коду.

6. **Строки 69 и 71 код-перечисления** — правило без записи в `RuleThresholdKeyGroupRegistry` и
   отсутствие `KnownRuleNamesProviderInterface`. Оба требуют изменения кода (новое правило /
   отсутствующая инъекция), то есть недостижимы на неизменённом дереве. Второе сам автор назвал
   тестовым швом.

7. **Поведение warn-строки в параллельных воркерах.** Все мои прогоны — `--workers=0`, намеренно:
   иначе порядок и адресат диагностики становятся ещё одной переменной. Вопрос «вызывается ли
   построение опций внутри worker-процесса и куда там уходит логгер» остаётся открытым у обоих
   свидетелей и у меня.

8. **Полный свип 49 классов `*Options.php` на расхождение «что читает `fromArray()`» против «что
   объявлено контрактами»** (механизм M2). Подтверждены два экземпляра — `enabled` и
   `project_namespaces`. Свип требует сопоставления по каждому классу; это объём, а не
   невозможность. **Это самый крупный неизмеренный остаток: M2 — единственный механизм, чей
   РАЗМЕР неизвестен.**

9. **Слоение трёх источников с одним и тем же неизвестным ключом сразу** (пресет + файл + CLI).
   Измерена только пара «пресет + CLI» на ИЗВЕСТНОМ ключе (#65, вытеснение подтверждено).
   Для неизвестного ключа контроля, различающего слои, построить не удалось.

10. **Порядок узнавания при нескольких дефектах сразу.** `validateStructure` отказывает на первом,
    поэтому автор с двумя опечатками увидит одну; насколько это верно для владельческих
    валидаторов — не проверял ни один из троих.
