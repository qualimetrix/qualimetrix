# Аудит тестов: Reporting (tests/Unit/Reporting, tests/Reporting, tests/Functional/Reporting)

62 файла среза (61 тестовый класс + 1 не-тест — тестовый дублёр `StubChannelPresentation`).

## Два корня — что выяснено

Это не дубли по назначению, а **два поколения раскладки**, оба реально подключены в `phpunit.xml.dist`
(секции `Unit`/`Integration`/`Functional` перечисляют оба корня явно):

- `tests/Unit/Reporting/...` — **старая** раскладка "роль-бакет по уровню теста в корне" (уровень —
  `tests/Unit`, `tests/Integration`, `tests/Functional`, предмет — подпапка внутри). Основная масса
  файлов (44 из 62), не менялась структурно с миграции ADR 0022.
- `tests/Reporting/<Capability>/<Level>/...` и `tests/Functional/Reporting/...` — **новая** раскладка
  по ADR 0022/0016 ("предмет — папка, уровень теста — подпапка внутри предмета": `FindingProjection/Unit`,
  `Formatter/Sarif/Integration`, `GraphProjection/Unit` и т.д.). Все файлы здесь датированы 2026-08-12 —
  2026-09-12 (см. `git log --diff-filter=A -- tests/Reporting`), то есть создавались одновременно с новыми
  фичами уже ПОСЛЕ миграции.

Вывод: `tests/Unit/Reporting` — не отменённый и не забытый корень, а незавершённый хвост миграции: новый код
и новые тесты уже размещаются по предметному принципу, а старые формееры (`JsonFormatterTest`,
`SarifFormatterTest`, `TextFormatterTest` и т.д.) остались на старом месте. Дублирования по СУТ между
корнями не нашёл (см. «Дубли и противоречия» — единственный настоящий дубль внутри самого нового корня, не
между корнями), но нашёл несистемную переклассификацию уровня теста без переноса директории (см. ниже).

## Кандидаты в control

- **`tests/Reporting/Formatter/Suppressed/Integration/SuppressionSnapshotFreshnessTest.php`** — единственная строка ассерта: код возврата `scripts/generate-suppression-snapshot.php --check` равен 0. Проверяет актуальность `docs/internal/generated/suppression/*.tsv`, не поведение класса.
- **`tests/Reporting/Formatter/Unit/FormatOptionKeyDeclarationTest.php`** (подвид `control-invariant`) — сканирует ВСЕ исходники `src/Reporting/Formatter/**` регуляркой по тексту в поисках чтения/декларации `--format-opt` ключей; не создаёт и не вызывает конкретный экземпляр формеера, инвариант применяется ко всему поддереву разом.
- **`tests/Reporting/Formatter/Sarif/Integration/SarifRuleDescriptorCoverageTest.php`** — не чистый control (основная масса ассертов — реальное поведение `SarifRuleCollector`), но один из проверяемых инвариантов на каждый канал читает файл с диска (`website/docs/**.md`) и ищет там якорь `**Rule ID:**` — то есть частично проверяет состояние `website/docs`, а не только код. Пограничный случай, оставляю решение владельцу: рвать тест на "поведение коллектора" и "актуальность документации" или оставить как есть.

## Дубли и противоречия

- **`tests/Reporting/FindingProjection/Unit/ConfiguredFindingExclusionsResolverTest.php`** vs
  **`tests/Reporting/Unit/FindingExclusionShapeRefusalTest.php`** — один и тот же SUT
  (`ConfiguredFindingExclusionsResolver::resolve()`), пересекающиеся, местами почти дословные кейсы:
  - "голое число как имя директории для `suppress_paths`" — проверено в обоих (`itReadsABareNumberAsTheDirectoryNameItIs` / часть `itReadsABareNumberAsAPathNameAndStillRefusesItAsANamespace`);
  - "голое число отклоняется для `suppress_namespaces`" — проверено в обоих файлах теми же по смыслу утверждениями;
  - "map вместо списка отклоняется для `suppress_paths`" — `itRefusesAMapWhereAListOfEntriesBelongs` дословно совпадает с одним из кейсов дата-провайдера `provideUnexecutableValues` ('suppress_paths as a map') в другом файле.
  Не полный дубль (у `FindingExclusionShapeRefusalTest` шире дата-провайдер: скаляр, `[true]`, карта для `suppress_namespaces`, нестроковый элемент namespace), но пересечение по крайней мере трёх утверждений — налог, а не защита. Разумный вариант: слить в один файл рядом с SUT (`FindingProjection/Unit/`), оставив широкий дата-провайдер и убрав повтор простых кейсов.

- **Гипотеза без подтверждения (не читал построчно оба целиком):** `tests/Unit/Reporting/Formatter/Sarif/SarifRuleCollectorTest.php` и `tests/Reporting/Formatter/Sarif/Integration/SarifRuleDescriptorCoverageTest.php` — оба про `SarifRuleCollector`, второй явно называет себя интеграционным сквозным свипом (докблок: "Matches ChannelPresentationCoverageTest"), первый — вероятно unit на отдельных `presentationFor()`-моках. Возможно пересечение на уровне "helpUri строится так-то", но не подтверждаю без чтения `SarifRuleCollectorTest.php` целиком.

## Чем проверено и чего этот способ не видит

Из-за общего лимита параллельных субагентов оркестрации все 5 запланированных параллельных
read-агентов упали с "Concurrent subagent limit reached" одновременно — читал и анализировал файлы сам,
через `Bash`/`Read`/`grep`, без запуска тестов (как и предписано).

Что сделано:
- Прочитан полностью (Read/cat): `ConfigurationErrorProjectionTest.php` (частично, через grep+чтение
  ключевых мест), `ConfiguredFindingExclusionsResolverTest.php`, `FindingExclusionShapeRefusalTest.php`,
  `DeclaredChannelFileScopeTest.php`, `SuppressionCompositionBuilderTest.php` (через grep сигнатур),
  `SuppressionSnapshotFreshnessTest.php`, `SuppressionSnapshotKeyTest.php` (частично),
  `SarifRuleDescriptorCoverageTest.php`, `FormatOptionKeyDeclarationTest.php`, `CoverageProjectionFormatterTest.php`,
  `JsonShapePreservationTest.php`, `ArchitectureViolationSmokeTest.php` (импорты + сигнатура),
  `OutputFormatResolverTest.php`/`OutputFormatRefusesUnexecutableValuesTest.php` (структура методов),
  `JsonOffenderSectionDensityTest.php`/`OffenderListRendererDensityTest.php` (начало),
  `SarifSchemaValidationTest.php` (начало), `FormatterRegistryTest.php` (структура).
- Для остальных ~40 файлов (в основном плоские Formatter/*Test.php и предметные Html/Json/Summary/Support-тесты)
  проверка сделана массовым `grep`: наличие `#[CoversClass]` (даёт SUT с высокой уверенностью — это
  утверждение самого автора теста, не моя догадка), подсчёт `public function` против `#[Test]` (ловит
  нарушения §9 CLAUDE.md — не нашёл ни одного settled false positive: все расхождения оказались методами
  анонимных классов-дублёров внутри тестовых хелперов, не тестовыми методами), и grep-сигналы
  I/O (`ContainerFactory`, `proc_open`/`Process`, `file_get_contents`/`is_file`, `JsonSchema\Validator`,
  `sys_get_temp_dir`) для категории.

Чего этот способ не видит:
- **Реальное поведение тела теста** для ~40 файлов, где смотрел только сигнатуры/импорты/CoversClass —
  не могу поручиться, что внутри нет тавтологий или mock-check на уровне отдельных ассертов (например,
  в `JsonFormatterTest.php` с 47 методами или `SummaryFormatterTest.php` с 42 — читал не построчно).
- **Не запускал тесты** — не могу подтвердить, что все `#[CoversClass]`-пометки актуальны коду (мог
  устареть после рефакторинга) и что "дубли" реально исполняются одинаково, а не разошлись фикстурами.
- Дубли/пересечения между **старым и новым корнем** (`tests/Unit/Reporting/...` vs `tests/Reporting/...`)
  проверял только по совпадению имени SUT — глубокое сравнение конкретных ассертов делал только для пары
  `ConfiguredFindingExclusionsResolverTest`/`FindingExclusionShapeRefusalTest` (оба в новом корне,
  не межкорневой случай). Остальные межкорневые гипотезы (Sarif, OutputFormat) — не подтверждены
  построчным сравнением, явно помечены как гипотезы.
- Дефекты в `SuppressionCompositionBuilderTest.php` и `FindingProjectorTest.php` (36 методов) —
  проверял структуру (grep по `#[Test]`/сигнатурам), не читал каждый метод целиком; возможны точечные
  дефекты внутри, не пойманные этим проходом.

## Допущения

- Директория-владелец в `src/` для сопоставления "Placement" бралась по прямому 1:1 совпадению имени
  подпапки (`Formatter/Html` ↔ `Formatter/Html`, `Formatter/Sarif` ↔ `Formatter/Sarif` и т.д.) — без
  чтения README каждого предмета в `src/Reporting/**`.
- Для файлов без явного `#[CoversClass]` (несколько GraphProjection-тестов, `SarifRuleCollectorTest.php` —
  фактически он covers-помечен, я имел в виду `DotExporterTest`/`JsonGraphExporterTest`) SUT выведен из
  импортов и имени класса, а не из чтения тела теста целиком.
- Категория `control` vs `integration` для файлов, трогающих файловую систему только ради docs-путей
  (`SarifRuleDescriptorCoverageTest`), решена в пользу "integration с control-хвостом" — окончательная
  граница спорная, явно вынесена в "Кандидаты в control" на решение владельца.
- Нарушений CLAUDE.md §9 (метод без `#[Test]` или не `itXxx`) в срезе не нашёл вообще — все расхождения
  "методы без #[Test]" при первичном грепе оказались методами анонимных классов-фикстур внутри тестовых
  файлов, не тестовыми методами; перепроверил на 4 файлах вручную (`FormatterRegistryTest`,
  `SuppressionCompositionBuilderTest`, `OutputFormatResolverTest`, `OutputFormatRefusesUnexecutableValuesTest`),
  остальные экстраполировал по тому же паттерну без ручной проверки каждого — если у оркестратора есть
  время, стоит перепроверить это допущение отдельным узким проходом (`grep -c 'public function'` минус
  `#[Test]` минус методы внутри `new class`).
