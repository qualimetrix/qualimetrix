## How this was checked and what this method cannot see

The audit was entirely read-only: files were read line by line (Read), for every test I found
the real SUT in `src/` via explicit imports and calls (not the file name), and for
control-invariant tests I read exactly what they scan (AST via nikic/php-parser, a text grep
over `src/`, the contents of `qmx-baseline.json`). For two files (`DebtCalculatorTest.php`,
`ClassRankResolverTest.php`) I personally re-checked the output of a parallel independent pass —
a full match, which is exactly the required "second witness" at the slice boundary.

What this method cannot see:
- **Not confirmed by execution.** PHPUnit was never run (forbidden by the brief) — I don't know
  whether all these tests currently pass; the conclusions about "what the test checks" rest on
  reading the code, not on observed behavior.
- **Duplicate coverage is limited to the slice.** Duplicates were searched for only inside the
  slice's three directories (Measurement, ComputedMetrics, Prioritization). The same SUT could
  be re-tested in other slices (e.g. Health formulas duplicate logic from
  src/Analysis/Evidence/Coupling — adjacent capabilities were not checked).
- **`RatchetKeyGrammarTest`** — I did not find a product class with the same key-parsing
  algorithm (`grep` returned no matches in `src/` in my sample of commands); it's possible I
  simply didn't find it in a quick grep, not that it doesn't exist — this is a hypothesis, not a
  fact.
- **The golden/invariant tests** (`GoldenFileAggregationTest`, `MetricInvariantTest`) contain
  dozens of hand-derived numbers; I checked the internal consistency of their calculations (e.g.
  recomputed part of the health.* formulas), but did not run the pipeline to confirm agreement
  with the real output.
- **Mutation coverage was not assessed** — "there's an assertion" doesn't mean "the assertion
  catches a real mutation"; per the project's memory ("Verify the check itself"), this is
  exactly the kind of assumption that regularly turns out wrong without a separate rig run.
- Some of the "duplicate/not a duplicate" and "control vs control-invariant" judgments are
  evaluative (e.g. `MetricNameVocabularyTest`, `ProjectNamespaceResolverTest`) and are explicitly
  flagged as disputed for the owner's decision.

## Assumptions

- The `unit` category was assigned to tests with real VO/DTO collaborators with no I/O and no
  DI-container build (e.g. an in-memory `InMemoryMetricRepository`) — by the letter of the brief
  such tests are not "integration", even though they're broader than a classic self-contained
  unit test.
- `ProjectNamespaceResolverTest.php` works with a real filesystem
  (`mkdir`/`file_put_contents`/`chdir`) — classed as `unit`, since exactly one class is checked
  with no container; this is a borderline reading of the brief's definition.
- Pinning error-message text was considered a defect only where the message isn't an explicitly
  documented user contract (e.g. `ConfigurationRefusal` messages in
  `ComputedMetricsConfigResolverTest` are NOT considered a defect — that's exactly what the user
  sees on a configuration error; while the internal `RuntimeException`/`LogicException` in
  `MetricBagTest`/`DebtCalculatorTest`/`RemediationTimeRegistryTest` were counted, since these
  are internal diagnostics for a developer/agent, not an end-user contract).
- The file group names (`Group 1..5` in intermediate notes) are an artifact of how the audit was
  organized, not used in the final table.
- The second independent pass (background agents) was used as material only where I either
  personally re-checked it on a sample of files (Prioritization: 2 of 5), or it agreed in
  substance with my own reading of the same files (Measurement/Integration/Aggregation,
  Measurement/Unit misc) — no discrepancies between the independent readings were found.
