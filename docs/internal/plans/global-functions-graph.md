# План: глобальные функции в графе зависимостей qmx

**Дата:** 2026-07-28
**Тип:** расширение существующего слоя (`Analysis/Collection/Dependency`), не вертикальный слайс
**Статус:** редакция 1, к ревью

---

## 0. Резюме и вердикт

**Делать стоит.** Но не в той формулировке, с которой задача пришла.

Наблюдаемый симптом («у функции не извлекается тип из сигнатуры») —
верхушка. Реальная дыра в другом: у зависимости, найденной вне класса, нет
**владельца-узла**, поэтому теряется не только сигнатура, но и всё тело
функции — `new`, `Foo::bar()`, `Foo::class`, `catch`, `instanceof`.
Диспетчерская таблица `DependencyVisitor` уже умеет обрабатывать все эти
узлы; она просто никогда до них не доходит из-за раннего `return null`.

Замер на benchmark-корпусе (`benchmarks/vendor`, 8278 файлов, 43 пакета,
исключены polyfill-пакеты) — 449 top-level функций:

| Показатель                                            | Значение  |
| ----------------------------------------------------- | --------- |
| Функций даёт **хотя бы одно ребро**                   | 385 (86%) |
| из них ребро есть **только в теле**, сигнатура пустая | 216 (48%) |
| ребро есть **только в сигнатуре**                     | 8 (2%)    |
| и там, и там                                          | 161 (36%) |
| не даёт рёбер вовсе                                   | 64 (14%)  |
| уникальных ссылок на классы                           | 563       |

То есть **починка «только сигнатур» закрывает 38% случаев и пропускает
почти половину**. Это ключевой аргумент за то, чтобы делать задачу целиком
(владелец + тело), а не точечно.

**Выбранное представление — вариант (а): собственный узел графа на функцию**
(`SymbolPath::forGlobalFunction()`, канонический ключ `func:Ns::name`).
Обоснование и разбор альтернатив — §2.

**Ключевое проектное решение по метрикам** (§4): функция участвует в графе
как **партнёр по связанности**, но **не как субъект** class-level метрик.
Одно множество рёбер, никаких graph views; разделение проходит по **виду
узла**, а не по потребителю, и применяется одинаково во всех class-level
метриках.

Следствие для совместимости: `classRank`, циклы, DIT/NOC **не сдвигаются
вообще**; сдвигаются class-level `ca`/`cbo`/`instability` у классов, которые
использует хотя бы одна функция, и namespace-level `ce`/`ca`/`cbo` →
`distance` → `health.coupling` → `health.overall`.

**Чего фича не обещает:** рёбер «вызов функции» (`helper()` из класса) — их
нет сегодня и не будет в этой итерации (§13). Граф остаётся направленным
«функция → класс», обратных рёбер «класс → функция» не появляется.

## 1. Что сломано сегодня

`Qualimetrix\Analysis\Collection\Dependency\DependencyVisitor::enterNode()`:

```
if ($this->currentClass === null || $this->currentContext === null) {
    return null;   // ← здесь теряется всё, что объявлено вне класса
}
// ... implementation details
```

`currentContext` создаётся только при входе в **именованный** `ClassLike`.
`DependencyContext` в конструкторе принимает `string $currentClass` и строит
источник ребра через `SymbolPath::fromClassFqn()` — т.е. владелец
структурно обязан быть классом.

Следствия, проверенные эмпирически (задание, повторной проверки не требуют):

- у `function globalFn(TargetF $f): TargetF` в `graph:export` нет ни узла
  `globalFn`, ни ребра на `TargetF`;
- то же для тела функции — ни `new`, ни `Foo::class` внутри функции в граф
  не попадают.

**Чем это отличается от недавно закрытого пропуска замыканий.** У замыкания
внутри класса владелец есть — им хватило добавления `Closure` /
`ArrowFunction` в таблицу диспетчеризации `FunctionLikeHandler`. Здесь
владельца нет вообще, и решение о нём — предмет этого плана.

**Асимметрия с метриками.** На уровне метрик глобальная функция —
полноценный символ: `SymbolType::Function_` существует,
`SymbolPath::forGlobalFunction()` существует,
`Metrics\CodeSmell\ParameterCountVisitor` строит для функций FQN,
`Analysis\Collection\Metric\DerivedMetricExtractor` кладёт их в репозиторий,
`Analysis\Aggregator\AggregationHelper::collectFromFunctions()` агрегирует
их в namespace, `Rules\CodeSmell\LongParameterListRule` и
`Rules\CodeSmell\UnreachableCodeRule` по ним срабатывают. **Граф —
единственная подсистема, которая функцию не видит.** Это самостоятельный
аргумент за вариант (а): он устраняет расхождение, а не создаёт новое.

## 2. Чем функция представлена в графе: выбор варианта

### 2.1 Критерии сравнения

| #   | Критерий                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------ |
| K1  | **Точность атрибуции** — на что показывает `layer-violation` и `graph:export`                                      |
| K2  | **Совместимость с контрактами `DependencyGraphInterface`** — не ломает ли смысл `getAllClasses()` / `getClassCa()` |
| K3  | **Ущерб семантике метрик** — насколько искажаются CBO / instability / ClassRank                                    |
| K4  | **Работоспособность для функций без namespace** (26% корпуса, см. §6)                                              |
| K5  | **Согласованность с метрической стороной** (`SymbolType::Function_` уже существует)                                |
| K6  | **Объём изменений и число затронутых потребителей**                                                                |

### 2.2 Сравнение

| Вариант                                     | K1                  | K2                          | K3                 | K4  | K5  | K6      |
| ------------------------------------------- | ------------------- | --------------------------- | ------------------ | --- | --- | ------- |
| **(а)** собственный узел `func:Ns::name`    | ✅ точно до функции | ⚠️ требует нового аксессора | ⚠️ управляемо (§4) | ✅  | ✅  | средний |
| **(б)** синтетический узел-владелец на файл | ❌ до файла         | ❌                          | ❌                 | ⚠️  | ❌  | средний |
| **(в)** синтетический узел на namespace     | ❌ до namespace     | ❌ опасно                   | ❌                 | ⚠️  | ❌  | малый   |
| **(г)** без узла, зависимости — namespace'у | ❌                  | ⚠️                          | ✅                 | ⚠️  | ❌  | малый   |

### 2.3 Разбор

**(б) узел-владелец на файл** — `SymbolPath::forFile($path)`.
У file-путей `namespace === null`. Это ломает ровно то, ради чего фичу
делают:

- `DependencyGraphBuilder::computeNamespaceCe()` / `computeNamespaceCa()`
  явно пропускают источники с `namespace === null` («Skip file-level
  symbols») — namespace-level связанность не улучшится вообще;
- `Architecture\Domain\Layer\ClassContextFactory::fqnFor()` вернёт `null`
  для file-пути → `LayerRegistry::resolveAll()` вернёт пустой список → ни
  одно правило слоёв никогда не классифицирует такой источник. Рёбра будут
  существовать и при этом гарантированно молчать, зато шумя в
  `architecture.coverage`.

Плюс: все функции файла схлопываются в один узел, атрибуция теряется.
**Строго хуже (а) по всем критериям, кроме K4.** Отвергнут.

**(в) синтетический узел на namespace.** Технически опасен: в
`DependencyGraphBuilder::build()` источник ребра безусловно попадает в
`$classMap`, а значит в `getAllClasses()`. Namespace-путь в списке «классов»
приводит к тому, что `Metrics\Coupling\CouplingCollector::computeClassMetrics()`
запишет **class-level** `cbo`/`ca`/`ce`/`instability` в тот же `MetricBag`,
куда `computeNamespaceMetrics()` пишет **namespace-level** значения тех же
метрик. Репозиторий мержит бэги — получим тихую порчу namespace-метрик без
падения теста. Плюс атрибуция до namespace и произвольный `Location`.
Отвергнут.

**(г) без узла, зависимости приписываются namespace'у как агрегату.**
Единственный вариант с нулевым ущербом class-level метрикам. Но:

- он **не решает основную задачу**. Ради чего фича делается (§3.6):
  `architecture.layer-violation` строит нарушения из
  `graph->getAllDependencies()` и классифицирует **оба конца ребра** через
  `registry->resolveAll($dependency->source)`. Если источника-символа нет,
  правило нечему классифицировать. Пришлось бы подменять источник на
  namespace-путь — это и есть вариант (в) со всеми его проблемами, только
  спрятанный;
- сообщение нарушения будет «слой X не должен зависеть от слоя Y
  (`App\Support` → `App\Domain\Order`)» — пользователь не узнает, какая
  именно функция виновата, и `Location` укажет в никуда.

Отвергнут как «дешёвый, но не решающий задачу».

### 2.4 Решение

**Вариант (а).** Функция — собственный узел, ключ
`SymbolPath::forGlobalFunction($namespace, $name)`, канонический вид
`func:App\Support::helper` / `func::globalHelper` (для глобального
namespace). Это:

- единственный вариант, дающий точную атрибуцию (K1) — а точность
  сообщений это то, чем `architecture.*` в проекте отличается от deptrac
  (ADR 0005, ADR 0011);
- единственный, согласованный с уже существующим представлением функции на
  метрической стороне (K5);
- работает для функций без namespace (K4): `forGlobalFunction('', 'name')`
  даёт корректный `SymbolType::Function_`, а `namespace === ''` (не `null`)
  проходит через namespace-агрегацию так же, как классы в глобальном
  namespace проходят сегодня.

Цена — K2 и K3, они разбираются в §3 и §4 и **являются основным
содержанием этого плана**.

## 3. Потребители графа: по каждому

Потребителей шесть. Ниже — что происходит с каждым и как исключается
бессмысленное участие функции **без введения параллельных представлений
графа**.

Механизм ровно один и общий: **функция не попадает в множество
узлов-субъектов** (`getAllClasses()`), но её рёбра остаются в общем
`getAllDependencies()` / `bySource` / `byTarget`. Все class-level метрики
итерируют по субъектам, поэтому ни одна из них не начнёт считать метрику
«для функции». См. §5 — почему это не graph views.

### 3.1 CBO (`Metrics\Coupling\CouplingCollector`)

- **Субъект:** нет. Функция не в `getAllClasses()` → цикл
  `computeClassMetrics()` её не видит → `cbo` на функцию не пишется.
  Это важно ещё и потому, что `Reporting\Formatter\MetricsJsonFormatter`
  выводит `SymbolType::Function_` — иначе в `--format=metrics` появились бы
  бессмысленные `cbo`/`instability` у функций.
- **Партнёр:** да. `getClassDependents($class)` вернёт ребро с
  источником-функцией → `cbo` класса, который используется хелпером,
  вырастет на 1. Это осознанное расширение области определения — §4.
- **Производные:** `cbo_app` (функция не во framework-namespace → попадёт в
  «app»-множество), `ca`, `instability` — сдвигаются вместе с `cbo`.
  `ce_framework` и `ce_packages` считаются только по **исходящим** рёбрам
  класса → не меняются.

### 3.2 ClassRank (`Metrics\Coupling\ClassRankCollector`)

Осмысленно ли участие? Нет. PageRank отвечает на вопрос «какой класс
структурно центральный». Функция не имеет входящих рёбер вообще (рёбер
«класс → функция» в графе нет и не появится в этой итерации), т.е. её ранг
всегда был бы околобазовым, а её присутствие в множестве узлов **разбавляет
ранги всех классов** (`baseRank = (1 - d) / n`, плюс вклад dangling-узлов).
Это чистый шум.

**Исключение:** бесплатное. Коллектор строит `$projectClasses` из
`getAllClasses()` с фильтром `$repository->has()`. Функции нет в
`getAllClasses()` → нет в `$projectClasses` → и её исходящие рёбра
игнорируются при построении `$outLinks`. **ClassRank не меняется ни на
один знак.** Правки в коллекторе не требуются.

### 3.3 Instability / Distance / Abstractness

- **Class-level `instability`** — производная от `ca`/`ce`, сдвигается вместе
  с §3.1.
- **Namespace-level `ce`/`ca`** (`DependencyGraphBuilder::computeNamespaceCe/Ca`)
  — **должны** включать рёбра функций, и включат автоматически: обе функции
  пропускают только `namespace === null`, а у функции namespace — строка
  (возможно пустая). Это семантически верно: Ce пакета по Мартину — это то,
  от чего зависит **содержимое пакета**, а функция в пакете лежит.
  Здесь никакого расширения области определения нет.
- **`distance`** (`Metrics\Coupling\DistanceCollector`) и
  **`abstractness`** (`Metrics\Coupling\AbstractnessCollector`) итерируют
  `repository->all(SymbolType::Namespace_)`; `abstractness` считается из
  счётчиков типов и функцию не увидит. `distance = |A + I - 1|` сдвинется
  через `I`.
- **Родительские namespace'ы** (`computeParentNamespaceCouplings`) —
  пропускают пары с `namespace === null` с обеих сторон; функция проходит.

### 3.4 Детектор циклов (`Analysis\Collection\Dependency\CircularDependencyDetector`)

Осмысленно ли участие? Формально безвредно, фактически бесполезно: Tarjan
итерирует `getAllClasses()`, а функция — чистый источник без входящих рёбер,
поэтому её SCC всегда размера 1 и в цикл она попасть не может **даже если бы
была узлом**.

**Исключение:** бесплатное, тем же механизмом (нет в `getAllClasses()`).
**Результаты `architecture.circular-dependency` не меняются.**

### 3.5 DIT / NOC (`Metrics\Structure\DitGlobalCollector`, `NocCollector`)

Итерируют `repository->all(SymbolType::Class_)` и читают только рёбра
`extends`. Функция не порождает `extends`. **Не меняются.** Правок нет.

### 3.6 `architecture.layer-violation` / `coverage` (`Architecture\Rules\LayerViolationRule`)

**Это единственный потребитель, ради которого фича делается.** Он итерирует
`graph->getAllDependencies()`, а не `getAllClasses()`, поэтому рёбра функций
увидит сразу.

Здесь есть **обязательная правка, без которой фича даёт отрицательный
эффект**. `Architecture\Domain\Layer\ClassContextFactory::fqnFor()` строит
FQN из `namespace` + `type`. У функции `type === null`, поэтому метод
вернёт **голый namespace**. Дальше:

- `Core\Util\NamespaceMatcher::matchesSingle('App\Support\**', 'App\Support')`
  → `fnmatch` требует литеральный `App\Support\` перед `**` → **false**;
- значит функция не классифицируется ни в один слой →
  `LayerViolationRule::collectEdgeViolations()` увеличит `sourceEdges` и
  добавит FQN в множество `classes` → **вырастет шум
  `architecture.coverage`, а нарушения не появятся**;
- вдобавок все функции одного namespace схлопнутся в один ключ
  `contextCache`.

**Требуется:** `fqnFor()` должен для `SymbolType::Function_` возвращать
`Ns\funcName` (или `funcName` при пустом namespace). Тогда `App\Support\**`
матчится, `suffix:` работает по имени функции, а `attributes:` /
`implements:` / `extends:` естественно не срабатывают (у функции их нет) —
`build()` уже корректно короткозамыкает на минимальный контекст при
`type === null`.

`collectClassEvidence()` (счётчик `layerHits`, shadow-evidence) итерирует
`metrics->all(SymbolType::Class_)` — функции туда не попадут, и это верно:
`unreachable-layer` уже досчитывает попадания по концам рёбер
(`edgeLayerHits`), так что слой, матчащий только функции, «достижимым»
считаться будет. Правок в правиле не требуется.

### 3.7 `graph:export` (`Infrastructure\Console\Command\GraphExportCommand`)

Оба экспортёра (`Export\DotExporter`, `Export\JsonGraphExporter`) строят
множество узлов из `getAllClasses()` и отфильтровывают рёбра, у которых хотя
бы один конец вне этого множества. Если ничего не делать, **функции и их
рёбра пропадут из экспорта** — а это ровно та команда, которой пользователь
диагностирует граф.

**Требуется:** экспортёры строят множество узлов из объединения
`getAllClasses()` и нового `getAllFunctions()`.

Два краевых момента:

1. **Коллизия идентификаторов.** Оба экспортёра используют `toString()` как
   идентификатор узла (DOT node id, JSON `fqn`). Для функции
   `App\Utils\helper` `toString()` даёт `App\Utils\helper` — **байт-в-байт
   то же, что у класса `App\Utils\helper`**. В PHP это разные таблицы
   символов, такая пара легальна. Узлы схлопнутся.
   **Решение:** для function-узлов рендерить суффикс `()` —
   `App\Utils\helper()`. Дёшево, читаемо, снимает коллизию, попутно делает
   экспорт самодокументируемым.
2. **Фильтрация по namespace** (`--namespace` / `--exclude-namespace`)
   работает по `$path->namespace` — для функции это корректная строка,
   правок не требует.

## 4. Смысл метрик: допустимо ли трогать CBO

### 4.1 Что именно меняется

Функция как **субъект** class-level метрик — не вводится (см. §3). Меняется
только одно: у класса `Foo`, который используется глобальной функцией,
множество «связанных сущностей» пополняется этой функцией, т.е.
`cbo(Foo) += 1`, `ca(Foo) += 1`, `instability(Foo)` пересчитывается.

### 4.2 Разбор по Metrics Policy проекта

CLAUDE.md, раздел Metrics Policy, перечисляет **допустимые** расширения, и
среди них дословно:

> Scope adaptation for PHP realities (e.g., RFC including global functions)

То есть прецедент «включить глобальные функции в область метрики, изначально
описанной для классов» в проекте **уже принят и документирован** — для RFC.
Форма адаптации там та же, что предлагается здесь: измеряемый субъект
остаётся классом, расширяется множество считаемых партнёров.

Недопустимым по той же политике было бы: (1) сменить формулу CBO без
переименования метрики, (2) заявлять «follows the original spec», (3)
оставить отклонение недокументированным. Ни одного из трёх здесь нет.

**Вердикт: допустимо.** Условия:

- докблок `Metrics\Coupling\CouplingCollector` явно говорит, что CBO считает
  партнёрами и глобальные функции, со ссылкой на прецедент RFC;
- на сайте (`website/docs/metrics/coupling/cbo.md` + `.ru.md`) появляется
  блок `!!! info "Deviation from original spec"` с формулировкой
  «semantic interpretation», а не «follows the original»;
- `src/Metrics/README.md` — строка в таблице отклонений.

### 4.3 Рассмотренная и отклонённая альтернатива

**«Исключить функции из CBO, оставив их только для архитектурных правил.»**
Технически это означает: при подсчёте `cbo`/`ca` пропускать рёбра, у которых
`source->getType() === SymbolType::Function_`.

Отклонено по двум причинам:

1. **Внутренняя противоречивость.** Класс `Foo`, используемый
   исключительно из `helpers.php`, получил бы `ca = 0`, `instability = 1.0`
   («от меня никто не зависит»), тогда как namespace-уровень и
   `layer-violation` одновременно утверждали бы обратное. Отчёт бы сам себе
   противоречил — ровно тот класс дефекта, который правило
   `unreachable-layer` в проекте специально лечит (см. докблок
   `LayerViolationRule::collectEdgeViolations()`).
2. Это **фильтрация по потребителю**, а не по виду узла — то есть именно то,
   что отвергнуто решением B соседнего плана (§5).

### 4.4 Почему функция всё-таки не субъект class-level метрик

Симметричный вопрос: раз функции — партнёры, почему не считать `cbo` и **для**
функции? Потому что здесь адаптация уже не «scope», а подмена субъекта:
CBO — «Coupling Between **Objects**», и число «связанность функции» не имеет
ни порога, ни интерпретации, ни агрегации (`AggregationHelper::collectFromFunctions()`
читает только определения с `collectedAt === SymbolLevel::Method`, так что
class-level метрика на функции осталась бы висеть неагрегированной), зато
немедленно протекла бы в `--format=metrics`. Отказ от субъектности — не
компромисс, а корректная граница.

## 5. Отношение к принятому решению «без graph views»

Раздел обязателен: задача прямо требует не протаскивать graph views, а при
необходимости вынести противоречие.

**Противоречия нет, и вот почему — с явным указанием, где проходит граница.**

Отвергнутое (решение B соседнего плана, `phpdoc-dependencies.md` §0):
*consumer-specific фильтрация* — «учитывать канал X в `architecture.*`, но
не в CBO». Вред: два расходящихся представления **одного и того же множества
рёбер**, отчёт всю жизнь продукта показывает CBO по одному множеству, а
`layer-violation` по другому; комбинаторика тестов на каждого потребителя.

Предлагаемое здесь: **одно** множество рёбер `getAllDependencies()`, которое
все потребители читают целиком. Ограничение проходит по **множеству
узлов-субъектов**: class-level метрика итерирует узлы вида «класс», потому
что её определение — «метрика класса». Это свойство определения метрики, а
не настройка под потребителя: **все** class-level метрики применяют одно и
то же правило, и оно неизменяемо (нет флага, нет опции, нет второго графа).

Прецедент в кодовой базе уже есть, и он не считался view:

- `DependencyGraphBuilder::build()` отфильтровывает рёбра на PHP-builtin
  классы, кроме `extends` — потому что «coupling to stable standard library
  types is not architectural risk»;
- `CouplingCollector` и `ClassRankCollector` пропускают символы, которых нет
  в репозитории (`$repository->has()`) — vendor-классы не становятся
  субъектами метрик, хотя рёбра на них в графе есть;
- `DitGlobalCollector` / `NocCollector` читают только рёбра `extends`.

То есть граф **уже** не «сырая истина», и потребители **уже** читают из него
разные подмножества — при этом граф остаётся один. Добавление вида узла
`func:` эту картину не меняет качественно.

**Где я обязан быть честным.** Формально при подсчёте `cbo` класса
партнёр-функция **не** исключается (§4.1) — то есть ни один потребитель не
делает `if (source is Function) skip`. Если бы решение §4.3 было принято в
обратную сторону (исключать функции из CBO), это **был бы** consumer-specific
фильтр и потребовал бы пересмотра решения B. Именно поэтому §4.3 отклонён
не только по семантике, но и по этому основанию.

## 6. Границы и краевые случаи

Эмпирика по benchmark-корпусу (8278 файлов) даёт распределение форм, а не
догадки:

| Форма                                              | Доля (non-polyfill, N=449) |
| -------------------------------------------------- | -------------------------- |
| объявлена внутри `if (!function_exists(...))`      | 396 (88%)                  |
| в глобальном namespace (без `namespace`)           | 115 (26%)                  |
| вложенная функция (`function` внутри `function`)   | 0                          |
| дубли одного FQN в разных файлах (полифилы и т.п.) | 110 по всему корпусу       |

Концентрация крайне длиннохвостая: 234 из 449 — один файл
`phpunit/phpunit/src/Framework/Assert/Functions.php`; далее
`laravel/framework/.../Foundation/helpers.php` (64),
`laravel/prompts/src/helpers.php` (30), `Illuminate/Support/helpers.php` (23).
То есть фича на практике работает по небольшому числу
`helpers.php`-подобных файлов — но это ровно тот сценарий, который задача и
называет.

### 6.1 Условно объявленные функции (`if (!function_exists(...))`) — 88%

Доминирующая форма. Узел `Stmt\Function_` находится внутри `Stmt\If_`;
`NodeTraverser` в него заходит, поэтому обработка не требует ничего
особенного. **Решение:** обрабатывать как обычную функцию, условие
игнорировать (статически неразрешимо). Документировать как известное
ограничение: qmx считает функцию объявленной, даже если в рантайме ветка не
исполнится. Это то же допущение, что уже сделано в
`Metrics\CodeSmell\ParameterCountVisitor`, — расхождения не вносим.

### 6.2 Дубли FQN в разных файлах — 110

Полифилы объявляют одну функцию в нескольких пакетах. Граф мержит по
каноническому ключу, поэтому рёбра из разных файлов схлопнутся в один узел,
а `Location` ребра укажет на тот файл, где ребро было найдено. **Решение:**
принять как есть (та же семантика, что у одноимённых классов сегодня),
задокументировать. Отдельного диагностического канала не вводим.

### 6.3 Функции без namespace — 26%

`SymbolPath::forGlobalFunction('', 'name')` → `namespace === ''`, канонический
ключ `func::name`. Проходит через namespace-агрегацию так же, как классы в
глобальном namespace сегодня (`SymbolPath::fromClassFqn('GlobalClass')` даёт
`namespace === ''`).

Важное следствие для §7 задачи (архитектурная ценность): **слой,
объявленный через `patterns:` по namespace, такую функцию не поймает** —
матчить нечего. Пользователю доступны `patterns: ['*']` или `suffix:`.
Это ограничение обязано попасть в документацию: «глобальные функции без
namespace видны в графе и в `graph:export`, но namespace-паттерны их не
классифицируют».

### 6.4 Вложенные функции — 0 в корпусе, но легальны

`function outer() { function inner() {} }`. PHP регистрирует `inner` в том же
глобальном пространстве, что и `outer`. **Решение:** стек владельцев (§7.1);
`inner` получает собственный узел `func:Ns::inner`, а не становится частью
`outer`. Тест обязателен, несмотря на нулевую частоту.

### 6.5 Именованный класс, объявленный внутри функции

Легально. Сейчас `currentClass`/`currentContext` — один слот, очищаемый при
выходе из именованного `ClassLike`; при наивной реализации выход из
вложенного класса обнулил бы владельца-функцию, и остаток тела функции
потерял бы рёбра. **Решение:** стек владельцев, а не слот (§7.1).

### 6.6 Анонимные классы

Текущая ветка `Class_ && name === null && currentContext !== null` относит
`extends`/`implements` анонимного класса к охватывающему контексту. С
владельцем-функцией это заработает автоматически и даст ребро
«функция → базовый класс анонимного класса» — семантически верно (функция
действительно зависит от этого типа). Методы внутри анонимного класса
продолжают атрибутироваться охватывающему контексту (текущее поведение), т.е.
для анонимного класса внутри функции — функции. **Решение:** оставить как
есть, покрыть тестом.

### 6.7 Замыкания и стрелочные функции на верхнем уровне файла

Сегодня их сигнатуры теряются (докблок `DependencyVisitor` это фиксирует).
После введения владельца-функции ситуация меняется только внутри функций;
замыкание, лежащее на верхнем уровне файла **вне** функции, владельца
по-прежнему не получает. **Решение:** вне рамок (§13), но докблок
`DependencyVisitor` обязан быть обновлён — сейчас он утверждает, что это
поведение зеркалит обработку top-level `function`, а после этой задачи
утверждение станет ложным.

### 6.8 Функции в файле, попавшем в `exclude_paths` / фильтры

Никакой специальной логики: фильтрация происходит на уровне discovery и
`ViolationFilterPipeline`, до и после графа соответственно. Отдельного кейса
нет.

### 6.9 `Location` ребра

`DependencyContext` уже принимает `?RelativePath $file` и строку. Для функции
ничего не меняется — строка берётся с узла, где найдена зависимость.

## 7. Контракты

Только сигнатуры, без реализации.

### 7.1 `Analysis\Collection\Dependency\DependencyVisitor`

Ключевое изменение: **один слот владельца → стек владельцев**.

```
private array $ownerStack = [];        // list<DependencyContext>
private ?DependencyContext $currentContext = null;   // вершина стека

// enterNode: именованный ClassLike  → push(context of class)
// enterNode: Stmt\Function_         → push(context of function)
// leaveNode: тот же узел            → flush deps, pop, currentContext = top|null
// ... implementation details
```

Публичный API (`setFile()`, `reset()`, `getDependencies()`, `enterNode()`,
`leaveNode()`) — **без изменений сигнатур**.

Инвариант, который обязан пиниться тестом: `reset()` очищает стек; после
обработки файла стек пуст (нет утечки владельца между файлами — визитор
переиспользуется и в `CompositeCollector`, и в `GraphExportCommand`).

### 7.2 `Analysis\Collection\Dependency\Handler\DependencyContext`

```
public function __construct(
    DependencyResolver $resolver,
    ?RelativePath $file,
    SymbolPath $owner,          // было: string $currentClass
);

public function addDependency(string $resolvedTargetClass, DependencyType $type, int $line): void;
public function getOwner(): SymbolPath;      // было: getCurrentClass(): string
```

Замечания:

- `getCurrentClass()` в текущем коде **не вызывается ни одним хендлером**
  (проверено grep'ом) — переименование безопасно, но по факту это удаление
  мёртвого API. Решение: переименовать в `getOwner()`, а не удалять (может
  понадобиться диагностике).
- Логика «пропустить self-reference» сейчас сравнивает строки FQN. С
  owner-`SymbolPath` сравнение должно идти по `toCanonical()`, иначе
  функция `App\helper` и класс `App\helper` считались бы одним символом.
- Все шесть хендлеров (`ClassLikeHandler`, `TraitUseHandler`,
  `InstantiationHandler`, `StaticAccessHandler`, `CatchInstanceofHandler`,
  `PropertyHandler`, `FunctionLikeHandler`) вызывают только
  `addDependency()` / `getResolver()` / `getFile()` — их сигнатуры **не
  меняются**.

### 7.3 `Analysis\Collection\Dependency\Handler\FunctionLikeHandler`

```
public static function supportedNodeClasses(): array;   // + Stmt\Function_
```

`Stmt\Function_` реализует `PhpParser\Node\FunctionLike`, поэтому тело
`handle()` не меняется. Но: хендлер вызывается из таблицы диспетчеризации
**после** проверки владельца, а владельца для `Function_` создаёт сам
визитор — значит `Function_` обрабатывается визитором дважды (создание
контекста + диспетчеризация в хендлер). Порядок обязан быть: сначала push
контекста, затем диспетчеризация. Это точка, где легко посадить баг —
явный тест обязателен.

### 7.4 `Core\Dependency\DependencyGraphInterface` + `Analysis\...\DependencyGraph`

```
public function getAllFunctions(): array;   // list<SymbolPath>, SymbolType::Function_
```

`getAllClasses()` **сохраняет текущий смысл** («все уникальные class-level
SymbolPath») — это и есть механизм ограничения из §3. Docblock обязан быть
уточнён: «функции сюда не входят, см. `getAllFunctions()`».

Конструктор `DependencyGraph` получает дополнительный параметр
`array $functions`.

### 7.5 `Analysis\Collection\Dependency\DependencyGraphBuilder`

Изменение в `build()`: при индексации разделять `$classMap` и `$functionMap`
по `SymbolPath::getType()`. Всё остальное (`$bySource`, `$byTarget`,
`$dependencies`, namespace Ce/Ca, `classCe`/`classCa`) считается **по всему
множеству рёбер** без изменений.

Проверить (тестом): `isPhpBuiltinClass()` смотрит только на `target->type`,
у ребра «функция → класс» target — класс, поэтому builtin-фильтрация
работает как раньше.

### 7.6 `Architecture\Domain\Layer\ClassContextFactory`

```
private function fqnFor(SymbolPath $class): ?string;   // + ветка SymbolType::Function_
```

Для `Function_`: `Ns\funcName`, либо `funcName` при пустом namespace.
`build()` уже короткозамыкает на минимальный контекст при `type === null` —
поведение (нет attributes/implements/extends у функции) корректно и правок
не требует.

### 7.7 Экспортёры

```
// DotExporter, JsonGraphExporter
// множество узлов = getAllClasses() ∪ getAllFunctions()
// идентификатор function-узла = toString() . '()'
// ... implementation details
```

`DotExporterOptions` и CLI-опции `graph:export` — **без изменений**.

### 7.8 Что НЕ меняется (важно для ревью)

`CouplingCollector`, `ClassRankCollector`, `CircularDependencyDetector`,
`DitGlobalCollector`, `NocCollector`, `AbstractnessCollector`,
`DistanceCollector`, `LayerViolationRule`, `MetricAggregator` и его фазы,
`AggregationHelper`, `Core\Symbol\SymbolPath`, сериализация для параллельных
воркеров — **ни строчки**. Это прямое следствие выбора «функция не в
`getAllClasses()`». Если по ходу реализации выяснится, что правка в одном из
этих файлов всё-таки нужна, — это сигнал, что дизайн разошёлся с планом, и
повод остановиться, а не «дописать».

## 8. Совместимость и масштаб сдвига

Проект в `0.x`; по SemVer 2.0 §4 ломающее едет в **минорной** версии с
записью в разделе `Breaking` файла `CHANGELOG.md`. Мажорный релиз не нужен.

### 8.1 Что сдвинется

| Метрика / вывод                                 | Сдвиг                      | Кого касается                                    |
| ----------------------------------------------- | -------------------------- | ------------------------------------------------ |
| class `cbo`, `cbo_app`, `ca`, `instability`     | вверх                      | классы, используемые глобальными функциями       |
| namespace `ce`, `ca`, `cbo`, `instability`      | вверх                      | namespace'ы с глобальными функциями              |
| `distance`, `health.coupling`, `health.overall` | ±                          | те же namespace'ы                                |
| `architecture.layer-violation`                  | новые нарушения            | конфиги со слоями                                |
| `architecture.coverage`                         | ±                          | зависит от §3.6 (без правки `fqnFor` — вырастет) |
| `graph:export` (dot/json)                       | новые узлы и рёбра         | все                                              |
| `--format=metrics`                              | без новых ключей у функций | —                                                |
| `classRank`, циклы, DIT, NOC, `abstractness`    | **не меняются**            | —                                                |

Порог «сколько именно» без замера назвать нельзя. Порядок величины из
корпуса: 563 новых ребра на 8278 файлов при 6595 классах — т.е. ~8,5%
прироста к числу рёбер только от функций... но распределены они крайне
неравномерно: проект без `helpers.php` не почувствует ничего, проект
Laravel-типа получит заметный сдвиг в 2–3 namespace'ах.

### 8.2 Замер на benchmark-корпусе — обязателен

**Да, обязателен, и до релиза.** Причины:

1. Собственный `src/` проекта содержит **ноль** глобальных функций
   (проверено). Значит `composer check` / selfcheck **не дадут никакого
   сигнала** — ни регрессии, ни подтверждения. Вся доказательная нагрузка
   переносится на тесты и benchmark.
2. `composer benchmark:check` сравнивает health-скоры с ожидаемыми
   диапазонами; сдвиг `health.coupling` может вывести проекты за диапазон и
   красная сборка будет выглядеть как баг формулы.

Процедура: снять `composer benchmark:check` **до** изменений, применить
изменения, снять **после**, задиффить. По результату — либо
`composer benchmark:update` (перекалибровка диапазонов) с объяснением в
коммите, либо расследование, если сдвиг больше ожидаемого.

Отдельно: `tests/Fixtures/GoldenMetrics/` **уже содержит** глобальные
функции (`App/Repository/functions.php`, `global_helper.php`). Ни у одной из
них нет классовых типов в сигнатуре, но тело нужно перепроверить —
`tests/Integration/Metrics/GoldenFileAggregationTest.php` и
`tests/Integration/Metrics/MetricInvariantTest.php` являются первым рубежом
обнаружения сдвига.

## 10. Тестовый план

Что тестируем (без самих тестов).

### 10.1 Юнит: `DependencyVisitorTest`

1. функция с классовым типом параметра → ребро `TypeHint`;
2. функция с классовым типом возврата → ребро `TypeHint`;
3. `new Foo()` в теле функции → ребро `New_`;
4. `Foo::bar()` / `Foo::$p` / `Foo::CONST` в теле → соответствующие рёбра;
5. `catch (FooException)` / `instanceof Foo` в теле → рёбра;
6. атрибут на параметре функции → ребро `Attribute`;
7. импорты (`use`) корректно резолвятся внутри функции — короткое имя типа
   разворачивается в FQN;
8. функция в глобальном namespace → источник `func::name`;
9. **вложенная функция** → два независимых узла, рёбра не смешиваются;
10. **именованный класс внутри функции** → рёбра класса идут классу, рёбра
    остатка тела функции — функции (регрессия на стек владельцев);
11. **анонимный класс внутри функции** → `extends`/`implements` относятся к
    функции;
12. **условно объявленная функция** (`if (!function_exists)`) → обрабатывается;
13. self-reference: класс `App\h` и функция `App\h` в одном файле — ребро
    между ними **не** отбрасывается как self;
14. `reset()` / `setFile()` очищают стек — рёбра не текут между файлами.

### 10.2 Юнит: `DependencyGraphBuilderTest` / `DependencyGraphTest`

15. функция в `getAllFunctions()`, не в `getAllClasses()`;
16. `getClassCa(target)` учитывает источник-функцию;
17. namespace `Ce` namespace'а функции включает её цель;
18. функция в глобальном namespace попадает в бакет `ns:`;
19. builtin-фильтрация: `function f(): \DateTimeImmutable` — ребро
    отфильтровано (как у класса).

### 10.3 Регрессионные (доказывают отсутствие сдвига)

20. `ClassRankCollector`: набор фикстур с функциями и без — ранги классов
    **побитово равны**;
21. `CircularDependencyDetector`: функции не появляются ни в одном `Cycle`;
22. `AbstractnessCollector` / DIT / NOC: значения не меняются;
23. `MetricsJsonFormatter`: у символов `type: "function"` **нет** ключей
    `cbo` / `classRank` / `instability`.

> Важно (по опыту проекта, [[verify_the_check_itself]]): тесты 20–23 обязаны
> быть прогнаны против **сломанной** версии — т.е. проверить, что если
> функции всё-таки попадут в `getAllClasses()`, эти тесты покраснеют. Тест,
> который зелёный в обоих случаях, ничего не доказывает.

### 10.4 Интеграционные: архитектура

24. `layer-violation` ловит нарушение из функции, сообщение содержит имя
    функции;
25. `allow`-запись разрешает такое ребро → нарушения нет;
26. функция без namespace: поведение зафиксировано (не классифицируется);
27. `architecture.coverage` не растёт из-за функций, которые слои покрывают.

### 10.5 Экспорт

28. DOT: function-узел присутствует, идентификатор с `()`;
29. JSON: то же + ребро;
30. коллизия «класс и функция с одинаковым FQN» → два узла;
31. `--namespace` / `--exclude-namespace` фильтруют function-узлы.

### 10.6 Golden / инварианты

32. `GoldenFileAggregationTest` — перепроверить, изменились ли значения; если
    да, обновлять только после ручной верификации корректности новых чисел
    (процедура из CLAUDE.md, «Self-Analysis: Interpreting Results»);
33. `MetricInvariantTest` — зелёный без правок ожиданий (если красный —

## 13. Вне рамок первой итерации

- **Рёбра «класс → функция»** (вызов `helper()` из метода). Их нет сегодня
  вообще; добавление создало бы входящие рёбра у функций и немедленно
  вернуло бы функции в ClassRank/циклы — т.е. заново открыло бы весь §4.
  Отдельная задача с отдельным решением.
- **Замыкания и стрелочные функции на верхнем уровне файла** (вне функции и
  вне класса) — владельца по-прежнему нет (§6.7).
- **`use function` / резолвинг импортов функций** — `DependencyResolver`
  сознательно игнорирует `Use_::TYPE_FUNCTION`. Пока рёбер «на функцию»
  нет, это не нужно.
- **Отдельный порог/правило «функция слишком связана»** — метрики на
  функции как субъекте не вводятся (§4.4).
- **Диагностика дублирующихся FQN функций** (§6.2).

## 14. Открытые вопросы к пользователю

**Q1 (главный). Функция как партнёр в class-level CBO — принять или
исключить?**
План рекомендует **принять** (§4.2): прецедент «scope adaptation for PHP
realities (e.g., RFC including global functions)» уже зафиксирован в
Metrics Policy проекта, а исключение породило бы внутренне противоречивый
отчёт (§4.3) и было бы consumer-specific фильтрацией, т.е. пересмотром
решения B. Цена — `cbo`/`ca`/`instability` классов сдвинутся, и это надо
описать как отклонение в докблоке + на сайте.
Альтернатива, если ответ «исключить»: сдвиг class-level метрик станет
нулевым, но появится расхождение «класс говорит ca=0, namespace и
layer-violation говорят обратное», и §5 придётся переписывать как
противоречие с решением B.

**Q2. Достаточно ли `getAllFunctions()` как способа не пускать функции в
class-level метрики, или нужно поднять вопрос отдельно?**
План считает это свойством определения метрики, а не graph view (§5). Но
это единственное место, где кто-то может увидеть «фильтрацию», и решение
стоит подтвердить явно, а не постфактум на ревью.

**Q3. Идентификатор function-узла в `graph:export` — суффикс `()`?**
Нужен для снятия коллизии «класс и функция с одинаковым FQN» (§3.7).
Альтернатива — префикс `func:` (канонический вид) — уродливее в DOT-метках.
Формат экспорта версионирован (`meta.version: 1.0.0`) — стоит ли бампать?

**Q4. Функции без namespace (26% корпуса) — фиксируем «не классифицируются
namespace-слоями» как ограничение, или это неприемлемо?**
Если неприемлемо — единственный выход, который я вижу, это разрешить слоям
критерий по файлу/пути, а это отдельная фича с собственным дизайном.

**Q5. Замер на benchmark — блокирует релиз или идёт параллельно?**
План ставит его блокирующим (§8.2), потому что собственный `src/` даёт
нулевой сигнал (ноль глобальных функций) и `benchmark:check` — единственный
механизм, который поймает неожиданный сдвиг health-скоров.

**Q6. Объём этапа 1: чинить только сигнатуры или сразу тела?**
План настаивает на «сразу тела» — иначе закрывается 38% случаев вместо 86%
(§0), а тела не требуют ни строчки нового кода извлечения (диспетчерская
таблица уже готова), только владельца. Если по каким-то причинам нужен
минимальный шаг — это надо решить сейчас, потому что тестовый план и
пакеты работ построены под полную версию.
