## 2. Silent addresses

These are the load-bearing findings — a build that stays green while asserting something false.

**A. `classifyOwner()`'s prefix ladder can silently swallow a *new* path into the wrong (coarser) owner bucket instead of failing.**
Established by reading code (lines 693-1003), not by running the generator against the moved tree (moving files is out of scope for a read-only task).
- The ladder is ordered, first-match-wins. Several catch-all branches are broad enough to match paths the CSV creates that were never intended for them, e.g. line 962:
  `str_starts_with($path, 'tests/Infrastructure/')` — this matches **any** new Infrastructure-owned target path (e.g. `tests/Infrastructure/DependencyInjection/Integration/RulesCommandWiringTest.php`), classifying it into the coarse `['Infrastructure', 'permanent'|'P6'|'P7']` bucket *before* the narrower, correct regex at line 972 (`^tests/Infrastructure/(Ast|Cache|Console|DependencyInjection|Logging|Parallel|Profiler|Rule|Serializer)/`) ever gets a chance to run.
  Why this is silent, not loud: the function never reaches `fail('Unclassified test artifact: ...')` for these paths — it returns a plausible-looking (if wrong) owner tuple, and the generator completes and writes a TSV that a fresh diff (the freshness check in `composer architecture:check`) will find internally self-consistent, because the freshness check only asks "does a re-run reproduce the committed file", never "does the committed file's owner/target column correspond to where the CSV plan actually put the file". Confirmed no such semantic check exists: `git grep -n "target_path\|targetPath(" governance scripts/modular-architecture` returns nothing outside the generator itself.
- **B. `dispositionFor()` / `targetPath()` compute a stale or wrong target for files that already sit at a path matching one of the "materialized, retain in place" regexes** (e.g. `^tests/Infrastructure/(Unit|Integration)/`, lines 1264 and 1311). Before the move, `tests/Infrastructure/Unit/RulesCommandTest.php` matches this regex and both functions correctly treat it as already-settled. After the move to `tests/Infrastructure/Console/Unit/Command/RulesCommandTest.php`, the same regex **no longer matches** (the file no longer sits directly under `tests/Infrastructure/Unit/`), so the ladder falls through to the generic formula at line 1329-1331:
  `$targetRoot . '/' . $targetSuite . '/' . basename($path)` → produces `tests/Infrastructure/Console/Unit/RulesCommandTest.php` — **one directory level shallower than the file's real, already-final location** (missing the `Command/` segment), and `dispositionFor()` reports `'Move atomically with the named owner and closure package.'` for a file that has already moved. Nothing downstream ever compares this claim to the CSV or to disk reality, so the generated `test-ownership.tsv` would permanently assert an incorrect pending move for these rows, and `composer architecture:check` stays green regardless (it only checks the TSV against its own regeneration, not against ground truth).
  Confidence: **hypothesis from code reading**, not from executing the generator against the actually-moved tree (forbidden here) — I traced the regex and formula by hand and re-derived the two example paths above from the relocation-map CSV; I did not run the script to confirm the exact printed TSV row.

## 3. What this method produces, and what it does not see

Tools used per channel, explicitly:
1. **Path-literal channel** — `git grep -n <literal>` over the whole tracked tree (`git ls-files` implicitly, since `git grep` only sees tracked files), filtered by hand to drop generated TSVs and the excluded stage-03 plan directory.
2. **Namespace-literal channel** — same `git grep`, searching `Tests\\Unit` etc. (escaped backslash), then read each hit's surrounding code by hand.
3. **Relative-path-inside-moving-file channel** — `grep -n "dirname(__DIR__\|__DIR__ *\." ` restricted to the 114 CSV `current` paths (built via `python3 csv.DictReader` → a scratch file, then `xargs grep -l`), then a small Python script computing `posixpath.dirname` N times against both `current` and `target` to compare resolved depth.
4. **External-relative-path-into-moving-file channel** — `git grep -n "dirname(__DIR__" -- 'tests/*'` diffed against the 114-path list, plus a `require|include` grep; both came back empty.
5. **Baked-value-over-generated-artifact channel** — targeted `grep -n "assertCount"` inside `governance/`, then manually inspected the two hits that reference TSV files owned by the same generator this move touches, and read `dispositionFor()`/`targetPath()` for value-correctness rather than count-correctness (see §2.B, which is this channel's headline finding, discovered by *reading the generator*, not by grepping for a magic number, since there is no test asserting the generator's *semantic* output — only its byte-for-byte reproducibility).
6. **Baked-command-string channel** — `grep -n "tests/Unit\|tests/Integration\|tests/Functional"` in `composer.json`, `scripts/*.sh`, `scripts/*.py`; empty.
7. **Root-enumeration/existence-guard channel** — read `assertPathLiteralsResolve()`, `TestTree::autoloadDevRoots()`, `testSuitePrefixTable()` bodies directly; cross-checked which named constants it guards against `is_file()`.
8. **PHPUnit-suite channel** — read `phpunit.xml.dist` in full, cross-referenced every `<directory>` whose file-set is exactly the moving files (via `find <dir> -type f`) against the CSV.

**What stayed uncovered by this pass (named explicitly, not silently dropped):**
- I did not run `bin/qmx` or PHPUnit itself against a scratch copy of the moved tree — every "loud vs silent" call for the generator (`classifyOwner`/`dispositionFor`/`targetPath`) is derived from static reading of the PHP source, not from executing it post-move. A second, execution-based witness (move the files in a throwaway worktree, run `composer architecture:check`) would either confirm or refute §2 empirically; I did not do this because the task is read-only.
- I did not enumerate every literal inside the ~330-line `classifyOwner()` prefix ladder individually — I read the whole function and its ordering, but the address table above cites the function as one unit (with the two specific silent sub-cases in §2) rather than one row per `str_starts_with` call. A full per-branch enumeration would need to symbolically evaluate all 114 target paths against the ladder's exact branch order; I did this by hand only for the two examples in §2 (`RulesCommandTest.php`, `RulesCommandWiringTest.php`), not for all 114.
- I did not check `docs/internal/generated/modular-architecture/*.tsv` row-by-row for other stale owner/target claims beyond the two hand-traced examples — there may be more of the 23 "already-relocated-once" rows that hit the same silent-drift bug in §2.B; I did not re-derive all 23.
- Governance suites outside `TestSuiteHygiene`, `ModularOwnership`, and `Channel` were not individually opened; I relied on `grep` across all of `governance/` for the specific literals/patterns in each channel, which would miss a governance test that computes a suite/path/namespace fact *indirectly* (e.g., via reflection over loaded classes rather than a string literal) without matching any of my grep patterns.
- website docs (`website/docs/**`) were not searched for stale test-path examples; out of scope per the brief's focus on "what breaks the build", and `composer docs:check` does not read `tests/`.
- I did not verify whether any of the 114 target paths collides with an *existing* file already at that path (a different, non-listed hazard); the brief scopes this task to registration/reference addresses, not to move-collision detection.
