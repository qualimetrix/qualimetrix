## Кандидаты в control

- Строгих "control" (документация/сгенерированные артефакты/qmx.yaml/composer.json и т. п.) в этой группе нет.
- `RuleThresholdKeyGroupRegistryCompletenessTest.php` и `RuleThresholdKeyGroupRegistryDriftTest.php` — **control-invariant по механизму** (полное сканирование всего `src/` рефлексией/AST), но проверяют не раскладку/документацию, а корректность конкретного продуктового реестра (`RuleThresholdKeyGroupRegistry`) относительно реального кода — то есть служат ровно цели «не дать ИИ сломать код» (обнаружение дрейфа реестра при добавлении/удалении вызовов `ThresholdParser::parse()`). Формально попадают под спорную границу владельца (сканирование `src/` рефлексией ради инварианта раскладки), но по содержанию — не про раскладку, а про полноту хендмейд-структуры данных. Решение владельца: оставить как integration/regression, не выносить в control.

## Дубли и противоречия

- **`RuleThresholdKeyGroupRegistryCompletenessTest` vs `RuleThresholdKeyGroupRegistryDriftTest`** — два отдельных файла (793 + 513 строк), оба сканируют `src/` целиком и сверяют `RuleThresholdKeyGroupRegistry` с реальными вызовами `ThresholdParser::parse()`. Названия методов почти идентичны (`itMakesEveryRegistryEntryCorrespondToARealCallSite` / `...RealThresholdParserCallSite`; `itAgreesWithEveryCallSitesLiteralKeys` / `itGivesEveryThresholdParserCallSiteAMatchingRegistryEntry`). Разница по факту: Drift проверяет количество вызовов на `(rule, path)` и поведенческий дифф-проб через реальную фабрику; Completeness проверяет литеральные АРГУМЕНТЫ каждого вызова через AST и форму значений. Авторы сами документируют разницу в докблоках — не слепой дубль, но кандидат на объединение с точки зрения стоимости прогона (оба гоняют парсер по всему `src/`).
- **`RuleConfigurationIsolationTest`** (сброс `RuleOptionsRegistry`) частично пересекается с `itResetsState()`/`itResetsClearsAllState()`/`itDoesNotLeakCliOptionsIntoTheNextRunAfterReset()` в `RuleOptionsFactoryTest.php` — тот же SUT (`RuleOptionsRegistry::resetRuntimeState()`/сброс состояния), разные поля под проверкой (namespace exclusions/CLI options vs RuleSelection/capturesExcludedFindings). Не строгий дубль, но стоит рассмотреть слияние в один файл про изоляцию состояния реестра.
- **`RuleNamespaceExclusionProviderTest`** — первые два теста фактически принадлежат `RuleOptionsRegistry` (делегирование), не заявленному SUT `RuleNamespaceExclusionProvider`; по предмету близки к `RuleOptionsFactoryTest`'ным `itExtractsSuppressNamespacesWritten...`/`itExtractsCodeScopedNamespaceExclusions` тестам, но проверяют другой слой (после парсинга конфигурации, не сырые ключи) — не дубль, но смешение SUT внутри одного файла нарушает «один файл — один предмет».

## Допущения

- Из-за объёма (`RuleOptionsFactoryTest.php` — 2194 строки/~150 тестов, `RuleExecutorTest.php` — 1504 строки/~45 тестов) не каждая строка прочитана посимвольно: заголовок, структура каждого метода и наиболее рискованные с точки зрения задачи участки (границы исключений, threshold-shorthand, сброс состояния) прочитаны полностью; середина `RuleOptionsFactoryTest.php` (строки ~300–1300, ~1700–2000) просмотрена по названиям методов и выборочным блокам, не построчно — не исключены точечные дефекты (лишний дубль ассерта, слишком узкая проверка), не пойманные при таком просмотре.
- Нарушений CLAUDE.md §9 (`#[Test]` + `itXxx`) в прочитанных фрагментах не найдено — везде выдержан паттерн.
- Соответствие "SUT ↔ каталог" проверено по физическому пути найденного класса (`find`), не по глубокому анализу владения предметной областью (ADR 0016/0022) — расхождений не выявлено.
- Оценка "дефект" ограничена вопросами из брифа (дубль/тавтология/противоречие/лживое имя/формулировка вместо поведения/нарушение §9); архитектурные вопросы (правильно ли вообще место класса в `src/`) вне рамок этой группы файлов.
