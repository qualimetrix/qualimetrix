## Duplicates and contradictions

- **`YamlConfigLoaderTest.php` × `YamlNormalizationCharacterizationTest.php` ×
  `YamlKeyReachabilityTest.php`** (all three — Configuration): each file's docblock claims "we're
  about different things" (behavior vs snapshot vs reachability), but the cases almost literally
  repeat for the same root keys: `cache.dir`/`cache.enabled`, `parallel.workers`,
  `coupling.framework_namespaces`, the `rules`/`computedMetrics` identifier section (name
  preservation + option normalization), `architecture.layers`/`allow`/`coverage-gap`/
  `max_expanded_layers`. Three files guard the same `YamlConfigLoader` behavior with three
  almost-identical sets of assertions. A reasonable goal (the ADR 0009 migration) doesn't erase
  the fact that the specific rows are duplicated.
- **`DeadConfigurationKeysTest.php` × `YamlConfigLoaderTest.php`**: the refusal for the
  `namespace` root is checked in both files (`itRejectsTheRemovedNamespaceRoot`,
  `itRejectsTheRemovedNamespaceRootRegardlessOfItsChildren` in `YamlConfigLoaderTest`;
  `'namespace strategy'`/`'namespace composer json'` in `DeadConfigurationKeysTest`) — the same
  SUT, the same assertion.
- **`AnalysisConfigurationCacheDirResolutionTest.php` × `AnalysisConfigurationTest.php`**: one
  SUT (`ConfigurationDocument`), both are small files about
  `workingDirectory()`/`contributions()`. Reasonable to merge into one class.
- **`Run/Unit/Discovery/FinderFileDiscoveryTest.php` × `FinderFileDiscoveryAbsolutePathTest.php`**:
  not a strict duplicate (the second file targets the `AbsolutePath`-key contract introduced by
  ADR 0015 Phase 2), but the coverage is heavily adjacent — both run the same
  `FinderFileDiscovery` on identical scenarios (a single file, a directory, deduplication, a
  nonexistent path). The difference is justified by migration history, but today it's double
  protection of one behavior.
- **`AnalysisConfigurationTest::itDoesNotExposeAMergedGenericConfigurationBag`** and
  **`ConfigurationHolderTest::itDoesNotProvideMutableReplacementOperations`** — not a duplicate
  in content (different lists of forbidden methods), but the same weak pattern: reflection
  checking "method X is absent" instead of behavior. See the section below.
- No contradictions (two tests asserting incompatible things about the same behavior) were found
  in this slice.

## How this was checked and what this method cannot see

The audit was done by reading only: the full content of all 63 files plus the relevant README
(`src/Analysis/Configuration/README.md`) were read in full; the SUT was inferred from `use`
imports and actual calls in the test body, not the file name. For control candidates, what
`require_once` points to was checked (`scripts/...` vs `src/...`), rather than relying on the
namespace — the `Qualimetrix\PromiseEffect` namespace could mislead a name-only search.

What this method cannot see:
- **Tests and `composer check` were never run** (per the brief's direct prohibition) — no
  conclusion is confirmed by execution. In particular, the guess about the
  `AnalysisPipelineIntegrationTest` docblock ("tests must fail") is not verified by a run — the
  conclusion was made by reading the code (the test bodies clearly check fixed, not broken,
  behavior) and could diverge from reality if some `markTestSkipped`/conditional path survived
  that I didn't notice.
- **Real mutation coverage was not measured** — "not a duplicate" or "a duplicate" was
  determined by a text comparison of assertions and fixtures, not by running a mutation tester.
  Both false duplicates are possible (two tests look alike but actually catch different mutants)
  and missed duplicates (different code shape, the same mutant).
- **The currency of `@covers`/`#[CoversClass]` was not checked** programmatically — it was
  taken on faith that the attribute matches the actual import; in the overwhelming majority of
  files it did.
- The conclusion "the SUT is `scripts/`, not `src/`" rests on the current location of
  `scripts/promise-effect/*.php` and `scripts/directive-audit*/*.php` files in this working
  tree; if the owner decides to physically move these classes under `src/` (e.g. into
  `src/Infrastructure/Tooling/`), the `control` category conclusion would need revisiting — it's
  currently correct for this state of the tree.
- Long/large files (`CollectionOrchestratorTest` 1190 lines, `FileProcessorTest` 847,
  `AnalysisPipelineIntegrationTest` 964, `YamlConfigLoaderTest` 1179,
  `ThresholdPopulationAgreementTest` 705) were read in full, but at this volume a single missed
  subtle defect at the level of one assertion line cannot be ruled out.

## Assumptions

- The `unit` category was assigned to a single-class SUT regardless of whether the test writes
  temp files via `sys_get_temp_dir()`/`tempnam()` — this kind of filesystem access is typical for
  config loaders and physically sits next to other unit tests in this project (the `Unit/`
  folder). A stricter reading of the brief ("integration = several classes OR a filesystem")
  would have given `integration` to almost every loader/reader test (`YamlConfigLoaderTest`,
  `ComposerReaderTest`, `PresetResolverTest`, `ConfigFileStageTest`, `DeadConfigurationKeysTest`,
  `ProjectScopeCoverageTest`, the discovery tests in `Run/`) — that would flip ~10 table rows
  from `unit` to `integration`; the softer reading chosen is made explicit here so the owner can
  reject it.
- `MultiNamespaceAnalysisTest` is marked "functional (2 tests) / integration (1 test)" — the
  file as a whole is categorized as functional, since that's the dominant and more
  representative mode (a real binary via `Process`).
- For the control files, "correct directory" does not name a specific directory: the decision
  on whether such tests should live under `tests/` at all (or move to
  `scripts/promise-effect/tests/`, `scripts/directive-audit/tests/`, a separate
  `tests/Tooling/`) is left to the owner, as the brief's item 4 asks ("a separate owner
  decision").
- The `YamlConfigLoader` duplicate group (3 files) was assessed as a "tax", not a penalty on any
  one file: without a mutation-tester run there's no reliable way to say which of the three is
  redundant and which catches a unique mutant; the "merge" recommendation is a hypothesis, not a
  fact.
