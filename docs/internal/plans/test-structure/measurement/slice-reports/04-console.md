## Control candidates

- `tests/Infrastructure/Console/Integration/ErrorStreamSoleOwnerTest.php` — scans `src/` and
  `bin/qmx` as text/tokens for "nothing except `ErrorStream` writes to STDERR" — this is a
  layout/ownership invariant, not product input-output behavior.
- Borderline **control-invariant** (not pure control, but uses reflection/text scanning over
  multiple classes for an invariant):
  - `tests/Infrastructure/Console/Integration/CommandRegistrationTest.php` — walks every command
    class in `src/Infrastructure/Console/Command` via reflection to check registration
    completeness.
  - `tests/Infrastructure/Console/Integration/ErrorStreamContainerIdentityTest.php` — walks a
    hardcoded list of container consumers to check singleton identity.
  - `tests/Infrastructure/Console/Unit/DrillDownBindingTest.php`, the case
    `itRanksOffendersForExactlyTheLevelsTheUniverseTrustsWithACanonicalName` — reads the source
    text of `HealthSummaryBuilder.php` with a regex for a cross-module check of one constant.

The decision on these belongs to the owner; they don't read as "documentation duplicates", but
they don't check the product's behavior on real input either — they hold layout/link
completeness.

## Duplicates and contradictions

1. **Exact duplicate (high confidence).**
   `tests/Infrastructure/Console/Functional/Command/CheckCommandTest.php::itHandlesNonExistentPath`
   (lines 137-152) and
   `tests/Infrastructure/Console/Functional/Command/CheckCommandPathInputTest.php::itRejectsNonExistentPath`
   — an identical fixture and three identical assertions (exit 3, empty stdout, "does not exist"
   in stderr). `CheckCommandPathInputTest` is the specialized file for paths, `CheckCommandTest`
   is the general smoke test; the duplicate should be removed from the smoke file.
2. **A strong SUT overlap (integration vs. so-called unit).**
   `tests/Infrastructure/Console/Unit/RuntimeConfiguratorTest.php` and
   `tests/Infrastructure/Console/Integration/RuntimeConfigurationIsolationTest.php` — both check
   `RuntimeConfigurator` state reset/isolation between sequential runs in one process (cache,
   parallel workers, LCOM exclusions, the profile). Possibly a legitimate split (different
   specific state owners), but `RuntimeConfiguratorTest` physically lives in `Unit/` while
   behaving like `Integration/` — the two files should be lined up side by side to see whether
   they literally cover the same fact twice under different names.
3. **An overlap by mechanism, not by individual case.**
   `tests/Infrastructure/Console/Unit/RuleOptionKeyDoorSymmetryTest.php` and
   `tests/Infrastructure/Console/Unit/TranslatedRefusalVocabularyTest.php` — both run
   `CheckCommand` through a real container with broken rule configs and check the refusal text;
   there are partially repeating fixtures ("callable" + a typo like `max_warnign`/`warnign`).
   Different specific invariants (a "file vs flag" symmetry versus "the wording names the
   correct subject"), but both physically live in `Unit/`, though both are full CLI runs; a
   candidate for merging/reconsidering the boundaries.
4. **A possible cross-level overlap.**
   `tests/Infrastructure/Console/Unit/ResultPresenterTest.php` (cases
   `itRefusesANamespaceThatSelectsNothingInTheRun`, `itRefusesAClassThatSelectsNothingInTheRun`,
   etc.) re-checks drill-down refusal behavior via `ResultPresenter`, while
   `tests/Infrastructure/Console/Unit/DrillDownBindingTest.php` checks the same
   `DrillDownBinding` class at a lower level. This could be a deliberate "wiring vs logic" split
   (as explicitly documented for the `RuleExclusionStatsWiringTest`/`FindingFilterOrchestratorTest`
   pair in the Integration group), but no such docblock exists here — worth an explicit
   decision, and if this is a wiring test, it should be labeled as one.
5. **A structural, not a substantive, problem.** `tests/Functional/Console/` and
   `tests/Infrastructure/Console/Functional/` both exist in the tree — two parallel "homes" for
   console functional tests. No content overlap was found (Hook commands exist only in the
   first, the other functional Console tests only in the second), but the mere coexistence of
   two directories with the same purpose is a layout defect worth fixing (e.g. move
   `tests/Functional/Console/*` under `tests/Infrastructure/Console/Functional/*`, since all
   their SUTs are `Infrastructure/Console/Command/*`).
6. **Not a duplicate, but the proximity should be reconciled.**
   `tests/Infrastructure/Integration/RulesCommandWiringTest.php` and
   `tests/Infrastructure/Integration/SharedRuleOptionsContainerTest.php` sit directly in
   `tests/Infrastructure/Integration/`, while every other Console-related integration test is in
   `tests/Infrastructure/Console/Integration/`. For `RulesCommandWiringTest` (SUT —
   `RulesCommand`, the Console domain) this is probably the wrong place; for
   `SharedRuleOptionsContainerTest` (SUT — a DI compiler pass) the current location is
   justified.

## How this was checked and what this method cannot see

Checked (4 parallel passes + direct reading): every file's SUT — by actually reading the test's
code and the corresponding class in `src/`, not the file name; category — by the presence of a
container/filesystem/CLI run versus plain stubs; `#[Test]`+`itXxx` compliance — by line-by-line
grep/reading over all 51 files (no violations found); the test directory matching the owning
domain in `src/` — by comparing namespaces; explicit duplicates within and between files in the
same slice — by matching specific assertions and fixtures.

What this method cannot see:
- The tests were not run (per the task's terms) — it isn't verified that they actually pass,
  whether the pty test (`ErrorStreamPseudoTerminalTest`) or the process test
  (`ApplicationRefusalTest`) flakes on CI, or whether the `chdir()` leak (the Hook tests) catches
  a real state corruption in a full run — this is a hypothesis from reading the code, not a
  measured fact.
- Duplicates/contradictions with files OUTSIDE this slice (`tests/Analysis/...`,
  `tests/Reporting/Formatter/...`, etc.) were not checked systematically — only via docblocks
  that reference them themselves (e.g. `RuleExclusionStatsWiringTest` explicitly names
  `Unit/FindingFilterOrchestratorTest` as its pair; `CheckCommandConfigurationErrorGateTest`
  explicitly references the unit-level `ConfigurationErrorProjectionTest`, which was not read).
- The 1300+-line `DirectivesCommandTest.php` was read by method signatures and the
  beginning/end, not line by line in full — more subtle internal duplicates could have gone
  unnoticed.
- The executable value of the control/control-invariant candidates was not assessed
  quantitatively (how many real regressions they ever caught) — only a structural classification
  per the brief's rubric.
- Threshold/numeric values (memory_limit, pty timeouts, columns=120, etc.) were not checked for
  currency against the current CI infrastructure.

## Assumptions

- The four files in `tests/Infrastructure/Console/Support/` (`PseudoTerminalRun.php`,
  `RestoresShellVerbosityEnvironment.php`, `SplitStreamConsoleOutput.php`, `TerminalScreen.php`)
  are test doubles/helpers, contain no test methods and don't fit the "SUT/category/defects"
  rubric from the brief; excluded from the main table and explicitly listed here so the file sum
  matches 51 test files + 4 helpers = 55 PHP files total in the slice.
- "Correct directory" is stated as a recommendation based on the test's actual behavior
  (presence of a container/filesystem/CLI), not as a hard mandate — the decision on moving files
