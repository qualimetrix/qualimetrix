# Audit: tests/Analysis/Policy/Architecture, tests/Integration/Architecture, tests/TestSupport, tests/System

Slice: 113 files (50 `*Test.php` files, the rest are fixtures, support helpers, python runner
tests). The owning product subject for most of the slice is `src/Analysis/Policy/Architecture/`
(the declared-layer policy capability, see `src/Analysis/Policy/Architecture/README.md`).

Method: `Unit/*.php` files were parsed by a line scan (`use` statements, the list of `#[Test]`
methods, full reading of suspicious files); every `Integration/*.php` and `Support/*.php` was
read in full; `System/*` and `TestSupport/*` were read in full; `Fixtures/*` fixtures were
classified by class/package name and by a cross-referencing grep for consumer files in
`Integration/`.

## How this was checked and what this method cannot see

The check was done by reading: a full line-by-line reading of every `Integration/*.php`,
`Support/*.php`, `System/*`, `TestSupport/*` (except the `Fixtures/` inside `TestSupport`, which
were opened in full but without a deep line-by-line parse — they're short, unambiguous fixtures)
and a structural grep scan (the class, `use` statements, the list of `#[Test]` methods, a search
for methods without `itXxx`) over all 30 `Unit/*.php` files, with a targeted full read of the ones
the grep scan flagged as suspicious (`ArchitectureInternalTopologyTest.php`,
`LayersValidatorMembershipRefusalGuardTest.php`, `ArchitectureProcessorTest.php`). The fixtures
under `Fixtures/Architecture/*` were classified by class name/docblock and by a grep tie to the
integration test that uses them, without running any tests.

What this method cannot see:
- **Actual behavior** of no test was verified by running it — per the task's boundaries PHPUnit
  was never run. Every conclusion that a test "checks X" is drawn from reading the test's code
  and the SUT's signatures, not from observing a real pass/fail. Subtle assertions (e.g. on
  element order, boundary numbers) were not verified by execution.
- Of the 30 `Unit/*.php` files, only 3 were fully read line by line (the topology test, the guard
  test, the processor test) — for the other 27 the category/defect decision was made by a
  structural scan (`use` imports + the method list), without line-by-line reading of the
  assertion bodies. Subtle defects inside a method body (e.g. a tautology 5–10 lines deep into
  one specific case) could have remained invisible — the risk is concentrated in the largest
  files (`AllowValidatorTest.php` 1059 lines, `LayerDefinitionTest.php` 1065,
  `LayersValidatorTest.php` 1230, `LayerViolationRuleTest.php` 1644), where method headers were
  fully checked but not every body.
- A full line-by-line reading of every duplicated fixture was not performed — a fixture's
  ownership by a specific test was established via `grep -rl <FolderName>` over the integration
  tests, which finds a direct path mention but doesn't guarantee the fixture is actually used by
  every method inside the found file (it could be a dead remnant of one deleted case).
- A second agent, who analyzed `Integration/*.php` and `Support/*.php` independently, found no use
  of `Support/LayerVerdicts.php` and `Support/ProcessorBuilder.php` in any of the 11 Integration
  files reviewed; their real consumers (presumably unit tests) are outside this task's slice and
  were not checked.
- The `control` / `control-invariant` boundary for `DocumentationConsistencyTest.php` had to be
  drawn manually by method within one file (rather than by the whole file) — the owner's decision
  may not match this split, especially for `itRecognizesPlanningChronologyOnlyInsideComments`,
  which formally unit-tests the same file's private helper but physically lives inside a control
  class.

## Assumptions

- The "owning subject" for most files in the slice was assumed to be
  `src/Analysis/Policy/Architecture/` per its README; for `TestSupport/ArchitectureStaticAnalysis/*`
  — `tools/phpstan/Rules/` (found via `find`, outside `src/`); for
  `ModularArchitectureGovernanceIntegrationTest.php` — `scripts/` (the manifest generators) plus
  `docs/internal/`.
- The `control-invariant` category was applied only where the invariant is literally taken via
  reflection/AST/grep over EVERY file/class of one module or repository (zone topology, the full
  rule list, the full list of `tests/`+`scripts/` PHP files); tests scanning 3 named files for
  one specific, docblock-justified invariant (`LayersValidatorMembershipRefusalGuardTest`) were
  not classed as control-invariant — the boundary was drawn between "the entire input class" and
  "a named input list justified by a specific threat".
- Some Unit files testing `ArchitecturePolicy`/`LayerDeclarationValidator`/`UnassignedClassRule`
  together with several VO collaborators (`CoverageDiagnosticsTest`, `PendingLayerDiagnosticsTest`,
  `UnassignedClassDiagnosticsTest`) were classed as `integration`, not `unit`, strictly per the
  brief's definition ("several classes") — even in the absence of a DI container and filesystem.
  `ArchitectureProcessorTest.php` was left `unit`, since it has an explicit
  `#[CoversClass(ArchitecturePolicy::class)]` and its collaborators act only as constructor data,
  not as separately checked behavior.
- `tools/phpstan/` in the brief's control definition was read as "checking tooling
  content/configuration", not "checking the behavior of code that just physically happens to
  live in tools/" — hence the decision not to class `BannedStringPathPropertyRuleTest*` as
  control. If the owner meant literally any test physically inside/about `tools/phpstan/`, both
  files need reclassifying.
- Fixtures and golden-file JSON were counted as separate table rows (every file in the slice is
  one row), even though they aren't tests themselves; the DoD "as many table rows as `*Test.php`
  files" is satisfied as a special case (50 of the 113 rows are test files), not as the table's
  ceiling.
