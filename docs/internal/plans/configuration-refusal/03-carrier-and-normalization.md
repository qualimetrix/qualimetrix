# Этап 03. Тип-носитель отказа и нормализация в местах броска

База — `1513bf67`. Сквозное решение и его развилки — в `00-overview.md`, здесь не

## 1. Где живёт носитель

**`Qualimetrix\Analysis\Configuration\Contract\Refusal\ConfigurationRefusal`**,
файл `src/Analysis/Configuration/Contract/Refusal/ConfigurationRefusal.php`,
владелец `Analysis.Configuration`, `visibility: contract`.

Довод — владение контрактом, а не число импортов. Поля носителя (позиция ключа, набранное
написание, допустимое в этой позиции, источник) — словарь конфигурации, и он уже есть в
`Analysis/Configuration`: `ConfigurationLayer::$source` — то самое перечисление источников,
из которого носитель берёт свой словарь (`defaults`, `composer.json`, базовое имя файла,
`preset:<имена>`, `cli` — 5 мест конструирования, снято `grep` по `new ConfigurationLayer(`;
слепое пятно способа — слой, собранный фабрикой или рефлексией; проверено, таких нет).
В перечисление носителя входят не все пять: два источника отказов не производят и потому
случая не получают — довод в §2.

Проверка на цикл сделана, иначе размещение было бы незаконным: `src/Analysis/Configuration`
не импортирует ничего из `Analysis\Policy`, `Analysis\Finding`, `Analysis\Evidence`,
`Infrastructure`, `Reporting` (`grep` по `use Qualimetrix\…` — пусто).

**Отвергнуто: `Core`.** Довод «бросают многие владельцы, а `Core` всем разрешён» — ровно
тот, который CLAUDE.md §1 и ADR 0022 отклоняют дословно: «many imports do not make a type
neutral». Семантика носителя вне конфигурации пуста: `Core` пришлось бы завести понятие
«источник конфигурации», то есть принять жизненный цикл `Analysis/Configuration` — каждый
новый слой конфигурации менял бы `Core`. Условие пересмотра: отказ по вводу без ключа и
без источника конфигурации — второй предмет, он заводится своим типом у своего владельца,
а не переездом этого в `Core`.

**Отвергнуто: маркерный интерфейс поверх пяти существующих классов.** Довод за — минимум
правок. Против, решающее: правило 1 обзора требует наружу **один род носителя**, а пять
классов с разными полями оставляют потребителю ветвление по типу — та же маршрутизация по
таксономии, переехавшая из команды в интерфейс. Живой образец —
`src/Infrastructure/Console/ConfigurationFailure.php`.

**Отвергнуто: `Contract/Exception/` как каталог.** Его имя — роль, а не предмет.
`Contract/Refusal/` называет предмет. Старый каталог удаляется вместе с
`ConfigLoadException` (пакет P6).

## 2. Контракт носителя

Сигнатуры без тел. Четыре типа, все в `src/Analysis/Configuration/Contract/Refusal/`.
Контракт даёт **обе стороны**: как носитель читают и как его строят. Сторона создания
обязательна, потому что бросают его четыре владельца, и трое из них — не мой набор
(`Infrastructure.Console`, `Analysis.Evidence.ComputedMetrics`, `Analysis.Policy.*`);
контракт, дающий только геттеры, замораживает половину и вынуждает потребителя лезть в
реализацию.

```php
final class ConfigurationRefusal extends RuntimeException
{
    // Публичного конструктора нет: каждый отказ — одна из названных форм.
    private function __construct(/* ... */);

    /** Отказ, адресуемый позицией ключа: неизвестный ключ, негодная форма значения. */
    public static function at(
        ConfigurationOrigin $origin,
        RefusedPosition $position,
        string $summary,
        ?Throwable $previous = null,
    ): self;

    /** Отказ о документе целиком: файл не найден, не разобран, версия конверта чужая. */
    public static function aboutDocument(
        ConfigurationOrigin $origin,
        string $summary,
        ?Throwable $previous = null,
    ): self;

    /** Отказ о значении, у которого нет позиции в документе: аргумент, селектор, путь. */
    public static function aboutInput(
        ConfigurationOrigin $origin,
        string $summary,
        ?Throwable $previous = null,
    ): self;

    public function origin(): ConfigurationOrigin;

    /** null у форм aboutDocument/aboutInput — там позиции нет по построению. */
    public function position(): ?RefusedPosition;

    /**
     * Одно предложение, без рамки, без префикса «Configuration error:» и без кода.
     * Обрамление принадлежит предъявлению (этап 01) — здесь его быть не должно.
     */
    public function summary(): string;
}
```

```php
final readonly class RefusedPosition
{
    /**
     * Замкнутая позиция: перечень допустимых написаний исчерпывающий.
     *
     * @param list<string> $segments  путь ключа сверху вниз
     * @param string       $written   последний сегмент в том виде, в каком его получил шов
     * @param list<string> $accepted  непустой; пустой перечень у замкнутой позиции — LogicException
     */
    public static function closed(array $segments, string $written, array $accepted): self;

    /**
     * Открытая позиция: перечня нет по построению (пространство, куда пользователь
     * заводит собственные имена; значение, у которого есть грамматика, а не список).
     * Грамматику и допустимые слова называет `summary()` носителя.
     *
     * @param list<string> $segments
     */
    public static function open(array $segments, string $written): self;

    public function segments(): array;          // list<string>

    /** Тот же путь для печати, точками. */
    public function display(): string;

    /** Последний сегмент — то, что отвергнуто, в том виде, в каком его получил шов. */
    public function written(): string;

    /** Канонические написания, допустимые в этой позиции, отсортированы; пуст у open(). */
    public function accepted(): array;          // list<string>

    /** true у closed(), false у open(). Читается, а не задаётся отдельно от формы. */
    public function isClosed(): bool;
}
```

**Необязательная причина есть у всех трёх фабрик, и это не украшение.** Сегодня цепочка
живёт: `ConfigLoadException::parseError($path, $e->getMessage(), $e)`
(`YamlConfigLoader.php:30-31`) несёт Symfony `ParseException` с позицией в YAML,
`ArchitectureConfigurationException` принимает `$e` третьим аргументом в четырёх
перезаворотах §3, `ArchitecturePreparationException` — в `LayerInstantiator:68`. Контракт
без `previous` терял бы её на конверсии, и восстановить исходное исключение под `-vvv`
или в логе стало бы нечем. Что с ней делает предъявление: **в `summary()` она не
попадает** (там одно предложение), в конверт — тоже (схема из двух полей,
`01-refusal-envelope.md` §2.1); её печатает трасса под повышенной громкостью
(`01-refusal-exit-ladder.md` §3), то есть ровно там же, где её печатал Symfony до раунда.
Отвергнуто **сознательно оборвать цепочку**: диагностика места разбора YAML — единственное,
что отличает «файл не разобран» от «файл не разобран на строке 14», и заменить её было бы
нечем, кроме переписывания текста `summary()` в каждом шве.

Двух фабрик достаточно, потому что после §2.1 не остаётся ни одной позиции с непустым
`accepted()` при открытом пространстве: смешанные случаи разводятся по разным позициям,
а не по третьему состоянию флага. **Отвергнуто: одна фабрика с булевым параметром** —
она допускает конструкцию «замкнуто, перечень пуст», то есть «здесь нельзя написать
ничего», а такой позиции в продукте нет; форма, отвергающая невозможное на построении,
дешевле теста, который это же проверяет.

```php
enum ConfigurationSource { case ConfigFile; case Preset; case CommandLine;
                           case BaselineFile; case Resolved; }

final readonly class ConfigurationOrigin
{
    /** Единственный способ построить: источник плюс его локатор. */
    public static function of(ConfigurationSource $source, ?string $locator = null): self;

    public function source(): ConfigurationSource;

    /** Путь файла, имя пресета, имя опции CLI. null у Resolved. */
    public function locator(): ?string;
}
```

**Пять случаев, а не семь: у `Defaults` и `ComposerJson` нет производителя.**
`DefaultsStage::apply()` возвращает `new ConfigurationLayer('defaults', [])` и не
отказывает ни на каком вводе — умолчания пишем мы, а не пользователь.
`ComposerReader::extractAutoloadPaths()` на любой негодности `composer.json` возвращает
`[]` без единой диагностики (`:23-34`: нет файла — `[]`, не читается — `[]`, не
разбирается как JSON — `[]`). Случай перечисления без производителя — то, что проект ловит
стражами в других местах, и заводить его здесь значит писать перечисление, которое нечем
проверить. Молчаливое принятие негодного `composer.json` **измерено и осознанно
отложено**: оно меняет анализируемый набор путей при exit 0, это четвёртый маршрут
молчаливого принятия рядом с четырьмя из `01-refusal-verdicts.md` §5.6, и его починка — новый
отказ на входе, который сегодня работает у всех, то есть отдельное решение с отдельной
записью `Breaking`. Условие пересмотра: первое же место броска с этим источником
возвращает свой случай в перечисление.

### 2.1. Как читается род отказа и чем это НЕ является

**`catch (ConfigurationRefusal)` — первичный признак кода 3, а не единственный.** Род
отказа выражен тождеством типа, и это остаётся главным решением; но обзор (правило 1)
называет и вторичные признаки, потому что множество мест броска открыто:

| признак                                                          | где                                       | чей                                  |
| ---------------------------------------------------------------- | ----------------------------------------- | ------------------------------------ |
| **первичный:** тождество `ConfigurationRefusal`                  | четыре командные лестницы и `Application` | 03 объявляет, 01 ловит               |
| вторичный: общий `catch (InvalidArgumentException)`              | те же лестницы и `Application`            | 01, названный долг обзора            |
| вторичный: `ConsoleExceptionInterface` (разбор командной строки) | `Application`                             | 01, `01-refusal-exit-ladder.md` §2.5 |

Вторичные признаки — не оговорка задним числом, а цена, названная обзором: продуктовый
дефект, бросивший `InvalidArgumentException`, получит 3 вопреки правилу 2. Раунд не
сокращает множество вторичных признаков, он делает их одинаковыми во всех командах и
**считает остаток числом** (§6).

Это же снимает соблазн завести поле рода. **Отвергнуто: поле `kind` со значениями
«ввод»/«внутренняя ошибка».** Поле разрешило бы бросить носитель на дефекте продукта и
получить код 3 — ровно то, что запрещает правило 2 обзора («пакет, маршрутизирующий
`TypeError` в 3, не закрывает крах, а прячет его»). Ошибку вида «бросил не тот род» тип с
одним смыслом сделать невозможно, тип с полем — нет.

**Что обязан уметь потребитель, не заглядывая в реализацию.** Предъявление (01) и
`computed_metrics` (02) строят своё сообщение из `origin()` + `position()` + `summary()`.
**Форму машинного конверта этот файл не описывает** — она одна и живёт в
`01-refusal-envelope.md` §2.1; здесь про неё сказано ровно то, что нужно носителю: конверт
несёт `summary()` уже обрамлённым и код возврата, а `origin()`/`position()` в него
структурно **не** попадают. Условие пересмотра — в `01-refusal-external-contracts.md` §12.

**Случай `Resolved` и почему он есть.** Валидаторы `Policy/Architecture` и
`Finding/RuleConfiguration` работают на **слитом** документе:
`ConfigurationDocument::contributions()` (`…/Contract/ConfigurationDocument.php:19`) отдаёт
вклады без метки источника, а `appliedSources()` уникализирован и с вкладами не
сопоставляется. Честно атрибутировать они не могут — сегодня это видно как
`ArchitectureConfigurationException` с `configPath = 'architecture'` (46 мест броска, 13
проверок в тестах) и `ConfigLoadException('', …)` в `RuleOptionKeyRecognition` (3 места).
`Resolved` называет это вслух вместо пустой строки, притворяющейся путём. Тот же ответ по
`written()`: `RuleOptionRefusalWording` документирует, что ключ приходит уже свёрнутым
(`ConfigKeySpelling::normalize`), поэтому контракт — «в том виде, в каком его получил шов».

**Отвергнуто: протянуть попарную провенанс-метку через `ConfigurationDocument` и
`ConfigurationMerger`.** Технически это мой набор, и тогда `Resolved` был бы не нужен.
Против: метод меняет контракт, который читают 23 кросс-владельческих импорта, и окупается
только если его начнёт использовать **каждый** валидатор — то есть работа в `Architecture`,
`ComputedMetrics` (не мой набор) и `Finding`. Это отдельный заход. Условие пересмотра:
первое же требование «покажи, из какого файла пришёл ключ» закрывает вопрос в пользу
провенанса.

**`BaselineConflictException`: почему откладывается, и чем прежний довод был неверен.**
Обзор называет его исходом, который таблица двух кодов не классифицирует, и оставляет
код 1. Довод «конфликт принятых записей — законное состояние документа» **не проверяем и
потому не используется как основание**. Проверяемое основание: все четыре места броска
лежат в `BaselineDocumentWriter.php:84,171,179,187` под удерживаемым локом и требуют
гонки (файл изменился между чтением и записью) — **достижимого входа не показал никто**.
Отдельно исправлена атрибуция: `baseline:generate` в существующий файл к этому исключению
не относится вовсе (`BaselineGenerateCommand::doExecute` печатает своё сообщение и
возвращает `self::FAILURE`) — это отдельный отказ по вводу, владелец — 01/P01-4.
Следствие для тестов: страж «`BaselineConflictException` не превращается в носитель»
обязан быть рукотворным, потому что естественного входа у него нет.
