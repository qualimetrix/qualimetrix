# `bin/qmx rules` reports what a rule accepts, not what has a flag

## The defect, measured

`bin/qmx rules` builds its per-rule body out of `RuleMetadata->aliases` alone.
An option without a CLI alias is therefore not printed at all, while the
refusal path — `RuleOptionKeyRecognition` — names the true set from
`acceptedOptionKeys()`. Two readers, two answers, and the one the product sends
users to (`check --help`: "Run bin/qmx rules to see all available rules and
their options") is the incomplete one.

Instruments, counts, and what they cannot see: `measurement/README.md`. Every
number below is regenerated by a committed instrument and checkable from the
tables beside it.

**132 substantive options across 54 producers; 78 have an alias; 54 are
invisible.** `duplication.clone` and `code-smell.boolean-argument` print zero
options while having five and two. The two witnesses — declarations read
through the production container, and the shipped binary's own refusal — agree
on all 64 (rule, depth) pairs.

Two further facts from the same join, both in scope because they are the same
join:

- **34 of the 80 alias lines** print their target in a spelling no refusal uses
  — `class.max_warning`, `excludeDataClasses` against canonical kebab.
- All 80 aliases resolve to an accepted key. Nothing checks that they still
  will.

## Decision

**One declaration, two readers, and neither reader owns the derivation.** Today
the derivation is private to `RuleOptionKeyRecognition` — `optionsHere()`, the
`FRAMEWORK_KEYS` constant, the walk into `levelOptionsClasses()`. It moves into
`Analysis\Finding\Contract\Rule`, the place ADR 0022 reserves for a type a named
external owner-consumer reads; here that consumer is `RulesCommand`.

Three boundaries the review forced, each stated so P1's diff can be held to it:

1. **The recognition half does not move.** `knows()` and `shapeOf()` stay on
   `RuleOptionKeySet`: judging a key is about one class's declaration, not
   about the two-depth shape. What moves is *addressing* — which declaration
   answers at which depth — and the composition with the framework keys.
2. **The framework keys are not part of any class's declaration**, and the new
   type must not absorb them as if they were. They are Finding's own policy:
   `RuleOptionsFactory` takes them out of the user's config before
   `fromArray()` is called.
   **They also already have a named owner, and revision 3 did not.** A sweep for
   literal spellings inside `src/Analysis/Finding/` — not for the word, which
   appears in prose throughout — finds four sites, and one of them declares
   itself the single enumeration: `Exclusion\ConfiguredSuppression` holds the
   three as constants under a docblock saying "a fourth option is added here,
   and the applying, judging and reporting sides gain it in the same edit", with
   a guard keeping it the only *reader*. Introducing a `FrameworkOptionKeys`
   beside it would be a second owner of a fact that already has one — the defect
   this boundary exists to prevent, committed while claiming to fix it.
   So the enumeration is **relocated, not duplicated**: it moves to a value in
   `Contract\Rule` that both the surface and `ConfiguredSuppression` read, and
   `ConfiguredSuppression` keeps its reader guard and its author-facing
   spellings by deriving them from that one list.
   The four sites and what happens to each:

| Site                                         | Today                                                                      | P1                                                                                                             |
| -------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `Exclusion\ConfiguredSuppression`            | declares the three as snake constants, calls itself the shared enumeration | derives them from the relocated owner; stays the only reader                                                   |
| `RuleConfiguration\RuleOptionKeyRecognition` | `FRAMEWORK_KEYS`, kebab                                                    | reads the owner                                                                                                |
| `RuleConfiguration\RuleOptionsFactory`       | three camel/snake literal pairs                                            | reads the owner                                                                                                |
| `Exclusion\RuleNamespaceExclusionProvider`   | names two keys inside refusal sentences                                    | **stays** — a refusal naming a key is wording, and the class already answers about those keys in its own words |

3. **The surface states facts; each reader shapes them.** Revision 1 gave the
   type one method per output shape of each reader (`optionsHere()`,
   `optionsAt()`, `allowedAtTopLevel()`), which names the subject "what my two
   callers print" — a role, not a subject, and the thing ADR 0016 forbids. The
   subject is *where an option key may be written and which declaration answers
   there*. The listing's subtraction of slot names is the listing's own
   presentation choice and stays in the command.

Rejected: letting the command read `acceptedOptionKeys()` and
`levelOptionsClasses()` itself with only a test bridging the two — it leaves
the framework keys declared in one place and re-listed in another, the defect
class this change exists to close.

Rejected: a machine format for `rules`. No consumer asked; the gate compares
the human snapshot.

## Contract

```
/**
 * The keys Finding consumes before any options class sees them — the
 * enumeration relocated out of `Exclusion\ConfiguredSuppression`, which keeps
 * its author-facing spellings by deriving them from here.
 */
final readonly class FrameworkOptionKeys
{
    /** canonical kebab, sorted */
    public static function all(): list<string>;
    public static function contains(string $normalizedKey): bool;
}

/** Where a rule option key may be written, and which declaration answers there. */
final readonly class RuleOptionSurface
{
    public static function of(class-string<RuleOptionsInterface> $optionsClass): self;

    /** the level slots, in declaration order; empty for a non-hierarchical rule */
    public function levels(): list<string>;

    /** the declaration answering at this depth; null when $level names no slot */
    public function keySetAt(?string $level): ?RuleOptionKeySet;

    /**
     * Every key writable at this depth, canonical kebab, sorted.
     * At depth 1 that includes the slot names and the framework keys;
     * inside a slot it is that level class's accepted set and nothing else.
     */
    public function writableAt(?string $level): list<string>;

    /**
     * Where a freely authored alias target lands.
     *
     * Null covers two cases on purpose, because an alias join has no use for
     * the difference: a key nothing here knows, and a key the class recognises
     * only to answer about in its own words. An alias may not target either —
     * the first names nothing, and the second is the class's to speak for.
     */
    public function locate(string $aliasTarget): ?RuleOptionAddress;
}

/** A located option: the depth, and the canonical spelling of the key there. */
final readonly class RuleOptionAddress
{
    public ?string $level;
    public string $key;
}
```

`writableAt(null)` **is** the refusal's "Options here" — one operation, not a
second list shaped like it. `locate()` takes the **raw** target, so the split
on the first `.`, the fold, the slot lookup and the canonicalisation happen
once, inside the owner of the spelling fold. Revision 1's `resolve(?level, key)`
left the split with the caller while claiming to have taken the join.

## Consumers, enumerated

Obtained by grepping `src/` **and** `tests/` for `acceptedOptionKeys`,
`levelOptionsClasses`, `acceptedForDisplay`, `withLevelSlots`, `FRAMEWORK_KEYS`
and `->aliases`. Blind spot: a consumer reaching these through a string class
name and reflection would not appear. None does today, and
`RuleOptionsInterface` is only ever named as a `class-string` generic, which
this grep does see.

**Production — these change.** The right-hand column also names who reads each
new operation; an operation with no reader is not in the contract.

| Consumer                            | Today                                                  | After                                                                             | Reads                                  |
| ----------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------- |
| `RuleOptionKeyRecognition`          | owns addressing, the display list and `FRAMEWORK_KEYS` | addresses through `RuleOptionSurface`; keeps `knows()`/`shapeOf()` on the key set | `keySetAt()`, `writableAt(null)`       |
| `RulesCommand`                      | reads `->aliases` only                                 | reads `RuleOptionSurface` + `->aliases`                                           | `levels()`, `writableAt()`, `locate()` |
| `RuleOptionsFactory`                | spells the framework keys itself                       | reads them from one place                                                         | `FrameworkOptionKeys::all()`           |
| `ConfiguredSuppression`             | declares the enumeration                               | derives it; keeps its reader guard                                                | `FrameworkOptionKeys::all()`           |
| `ThresholdParser`, `CliAliasReader` | read attributes, not key sets                          | unchanged                                                                         | —                                      |

**Invariant tests — these must stay green *without being edited*.** They pin
the declarations the new type reads, so an edit to any of them means P1 moved a
boundary it should not have. Named rather than assumed:
`RuleOptionKeyDeclarationCoverageTest`, `RuleOptionKeySetTest` (including the
guard that keeps `levelOptionsClasses()` the single source of a slot),
`DeclaredOptionKeysCoverReadKeysTest`, `RuleOptionWordSetDeclarationAgreementTest`,
`RuleThresholdKeyGroupRegistryCompletenessTest`, `UnknownRuleOptionKeyRefusalTest`.

## Output format

Per rule, after the `judges` lines and before the alias lines:

```
    options: enabled, error, min-lines, min-tokens, threshold, warning
    options at callable: enabled, error, threshold, warning
    options at class: enabled, max-error, max-warning, threshold
```

A rule with no substantive option at depth 1 prints no `options:` line. A slot
always prints its line: the slot name is itself the information that a level may
be addressed, and suppressing it would hide the depth rather than tidy it. Every
slot accepts at least one key today, and test 5 pins that, so an empty slot is a
failure rather than a blank line. Alias lines keep their position
and their shape, with the target restated in canonical kebab. The footer names
the three framework keys once, and only those:

```
Every rule also takes: suppress-paths, suppress-namespaces, suppress-namespace-channels
```

**`enabled` is printed inline and is not in the footer**, and the measurement is
why. A footer claiming "every rule takes `enabled`" would be false about
`architecture.unassigned-class`, whose `mode` is the real switch and whose
`enabled` is declared answered-by-the-class — its refusal reads
`Options here: mode, suppress-*` with no `enabled`. A footer would therefore
contradict the refusal for that one rule, which is this change's own defect
class reintroduced one line lower. The three framework keys carry no such
counterexample: no options class declares them, and the refusal adds all three
at depth 1 for all 54 producers.

The listing names options and never says what one reaches. For `threshold` — 32
of the 54 hidden options — what it reaches is the unsettled subject of
`docs/internal/plans/shorthand-scope/`, whose cure is unimplemented. Printing
the name is safe now; printing its scope would have to be rewritten by that
round.

## Test plan

1. **Agreement, on the live population** (`tests/Infrastructure/Integration/`).
   For every producer and every level slot, the set `RulesCommand` renders —
   its `options` lines plus the footer plus the slot lines — equals the set the
   refusal names. The refusal side is obtained by *running the recognition*
   (`RuleOptionKeyRecognition::refuseUnknownKeys(['zzNotAnOption' => 1], ...)`
   and its level form) and reading `$refusal->position()->accepted()`, which is
   structural; no sentence is parsed. Derived per run from `allRules()`, never
   from a committed table — a committed table greens as the product grows. The
   docblock must say what the test is for: both sides read one declaration, so
   the *set* is near tautological; what it catches is wiring — a forgotten
   level slot, a skipped classless producer, a footer that stops matching
   `FrameworkOptionKeys`, a rule whose `enabled` is not accepted.
2. **Every alias resolves.** For each of the 80 aliases, `locate()` on the raw
   target returns an address. A guard, not a repair: all 80 pass today.
3. **Spelling.** A rule whose alias target is authored in snake and one in camel
   both print kebab — `complexity.ccn` and `complexity.wmc`.
4. **Unit, from stubs** (`RulesCommandTest`): a hierarchical stub prints both
   depths; a stub accepting only framework keys prints no `options:` line.
5. **`RuleOptionSurface` unit**: a non-hierarchical class has no levels; a slot
   name appears in `writableAt(null)` and is what the command subtracts;
   framework keys appear at depth 1 and never inside a slot; a key in the
   answered-by-the-class state appears in neither; `locate()` answers for a
   dotted target, a bare target, and returns null for a target nothing accepts.
6. **`RuleOptionSurface` against an independent witness.** The unit tests above
   are written against the same declarations the type reads. The witness that
   is not is `measurement/sweep-refusal.sh` — the shipped binary's answer — and
   `check-agreement.php` compares them. It is part of P1's DoD rather than the
   test suite: it runs the binary 64 times and belongs in a package gate, not
   in `composer check`.
