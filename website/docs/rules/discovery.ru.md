# Правила обнаружения файлов (Discovery)

Правила этой группы сообщают о выборе файлов самим прогоном, а не о коде, который он проанализировал. Фильтр, который ничего не убрал, выглядит ровно как отсутствие фильтра: отчёт покрывает файлы, которые автор собирался исключить, и каждое число в нём посчитано по набору, о котором никто не просил.

---

## Непривязанное исключение

**Rule ID:** `discovery.unmatched-exclude`

### Что измеряется

Каждое значение `--exclude` и каждая запись `exclude:` в `qmx.yaml` сверяется с каталогами, которые прогон действительно обошёл. Значение, не убравшее ни одного каталога, сообщается.

На канале **две находки**, потому что у селектора три возможных судьбы и молчание — только одна из них:

| Судьба селектора                                            | Что говорит прогон                                         |
| ----------------------------------------------------------- | ---------------------------------------------------------- |
| Он убрал каталог                                            | ничего — конфигурация работает                             |
| Он не убрал ничего нигде в проекте                          | селектор устарел                                           |
| Обход не смог заглянуть всюду, где селектор мог бы совпасть | селектор не осуждён, и каталог, остановивший обход, назван |

Третий случай существует потому, что каталог, который процессу нельзя перечислить, скрывает своё содержимое, и селектор, способный совпасть внутри него, устаревшим не называется. Промолчать о нём значило бы сделать «с вашей конфигурацией всё в порядке» и «вашу конфигурацию никто не проверил» одним и тем же выводом.

### Почему это важно

Без этого канала промахнувшееся исключение и его отсутствие дают побайтно одинаковый вывод. В отчёте нет ничего, что сказало бы автору: `--exclude=subtree:vendor` не сработал, потому что прогон и так начинался ниже `vendor/`, а `exclude: [{subtree: tests}]` перестал совпадать, когда каталог переименовали в `test/`. Исключаемые файлы анализируются, дают находки, а исключение остаётся в конфигурации и выглядит работающим.

### Область и severity

Канал сообщается на **уровне проекта**, severity `warning`.

Он судится только на прогоне, чьи пути покрывают всё, что `composer.json` проекта объявляет в `autoload`, — корни `psr-4` и `psr-0`, записи `classmap` и `files` наравне, — а с [`--include-autoload-dev`](../usage/cli-options.ru.md#--include-autoload-dev) и всё, что объявлено в `autoload-dev`. На более узком прогоне — по одному подкаталогу, по git-срезу — паттерн не привязывается просто потому, что названный им код лежит вне среза. Это выбор вызывающего, а не ошибка автора, поэтому правило молчит, а не пересказывает вызывающему его же сужение. Проект, чей манифест ничего не объявляет в секциях, которые учитывает прогон, — нет `composer.json`, он не парсится или в нём нет ни одной такой секции, — не даёт проверке знаменателя, и там правило тоже молчит.

Селектор судится по **всему дереву проекта**, а не по анализируемым путям. `exclude: [{subtree: tests}]`, написанный для `qmx check .`, ничего не убирает под `qmx check src/`, но названный им каталог на месте — и правило молчит. Сообщается только селектор, который не убрал бы ни одного каталога нигде в проекте. Discovery использует тот же полнообъектный язык путей `exact | subtree | regex`, что и подавление, и не заходит внутрь совпавшего каталога.

Обе находки подчиняются описанным выше воротам и одной опции `enabled`, но их идентичности в baseline разные: принять устаревший селектор — не значит принять неосуждённый, и проект, принявший первое, про второе услышит.

| Правило                  | ID                            | Что обнаруживает                                                                |
| ------------------------ | ----------------------------- | ------------------------------------------------------------------------------- |
| Непривязанное исключение | `discovery.unmatched-exclude` | Паттерн исключения, не убравший ни одного каталога либо не проверенный прогоном |

### Пример

```bash
bin/qmx check src/ --exclude=subtree:Generated
```

Когда каталога `Generated` нигде в проекте нет:

```
[project] discovery.unmatched-exclude
  The exclude pattern "Generated" matched no directory anywhere in the project,
  so nothing was left out for it. Every file it was written to skip was
  measured, and this report covers them.
```

Когда каталог, внутри которого паттерн мог бы совпасть, перечислить не удалось — недоступное монтирование, каталог, права которого запрещают доступ этому процессу, — тот же канал сообщает, что паттерн не был осуждён:

```
[project] discovery.unmatched-exclude
  The exclude pattern "Generated" could not be checked: the directory
  "vendor/private" could not be listed, and a directory the pattern would have
  matched may sit inside it. This report says nothing about whether that
  pattern is still needed.
```

Это `warning`, поэтому при `--fail-on=warning` прогон завершается ненулевым кодом. Так задумано: CI-задача, смонтировавшая каталог, который не может прочитать, меряет дерево, которое видит не целиком, — и зелёная сборка утверждала бы обратное. Дайте процессу право перечислить каталог или исключите его, чтобы обход перестал спрашивать.

### Опции

| Опция     | По умолчанию | Описание                       |
| --------- | ------------ | ------------------------------ |
| `enabled` | `true`       | Включает или выключает правило |

### Конфигурация

```yaml
# qmx.yaml
rules:
  discovery.unmatched-exclude:
    enabled: true
```

```bash
bin/qmx check src/ --disable-rule=discovery.unmatched-exclude
```
