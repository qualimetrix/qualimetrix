# M6. Маршруты отказа конфигурации в CLI — перечисление по коду

Дерево: `1513bf67`. Второй свидетель: всё выведено **чтением кода**, отчёт свидетеля-измерителя не открывался.
Строк «подтверждено прогоном» нет: `bin/qmx` не запускался ни разу (см. слепые пятна).

## 0. Метод

1. Точка входа `bin/qmx` → `src/Infrastructure/Console/Application.php` → `vendor/symfony/console/Application.php`
   и `vendor/symfony/console/Command/Command.php` (оба читаны напрямую).
2. Список команд снят машинно из карты `ContainerCommandLoader` в `bin/qmx:57-71` и сверен с регистрациями
   в `src/Infrastructure/DependencyInjection/Configurator/OutputConfigurator.php:367-533` и
   `ArchitectureConfigurator.php:31,81` (строковый канал: имя класса `LayerAssignmentCommand` задано строкой).
3. Для каждой команды найдены все `catch` (`grep -rn "catch ("` по `src/Infrastructure/Console/`),
   определён диапазон `try` и то, какие вызовы чтения конфигурации в него **не** попадают —
   включая те, что происходят до `execute()` (конструктор → `configure()`).
4. Классы исключений разобраны по иерархии (`extends`), а не по имени файла; места броска —
   `grep -n "throw "` (не `throw new`: именованные конструкторы `ConfigLoadException::fileNotFound()`
   иначе невидимы), затем `grep -rn "throw new <Class>\|throw <Class>::"` покласово.
5. Коды возврата взяты из констант (`Command::SUCCESS/FAILURE/INVALID` = 0/1/2, локальные
   `EXIT_CONFIG_ERROR`=3, `EXIT_INVALID_INPUT`=`INVALID`=2) и — для исключений, вылетающих наружу, —
   из `$e->getCode()` в `vendor/symfony/console/Application.php:203-211`.

### Развилки, решённые самостоятельно

- **Гранулярность маршрута.** Один маршрут = одна пара (класс исключения или вид отказа) × (обработчик).
  Одно исключение, обрабатываемое четырьмя командами по-разному, — это четыре маршрута, потому что
  различаются код возврата и поток. Перечисление измерением будет заведомо грубее.
- **`CommandNotFoundException` включена**: это «неизвестное значение CLI» в смысле границ предмета.
- **Исключено по границам предмета:** ошибки покрытия разбора (`IncompleteAnalysisException`,
  `BaselineRun.php:92`, код 4; `DirectivesCommand` `EXIT_INCOMPLETE_RUN`=4; `GraphExportCommand`
  `EXIT_ANALYSIS_INCOMPLETE`=4) — это «часть дерева не разобрана», то есть ошибка анализа кода.
  Из-за этого код **4 в таблице ниже не встречается**; он существует, но вне предмета.
- **Исключено:** git-скоуп (`ScopeWarningChecker`) и ошибки записи отчёта. Но отказ `graph:export`
  по `--format` включён: это разбор пользовательского ввода, а не запись.

## 1. Ключевой факт каркаса

`Application` **не вызывает** `setCatchExceptions()` / `setCatchErrors()` (проверено grep по `src/` и `bin/`).
Действуют умолчания `vendor/symfony/console/Application.php:79-80`:
`catchExceptions = true`, **`catchErrors = false`**.

Следствие 1: любой `Error`/`TypeError`, вылетевший из команды, **перебрасывается** из `run()`
(`vendor/symfony/console/Application.php:200`).

Следствие 2 (главное): к моменту переброса собственного обработчика уже нет. В `finally`
(`vendor/symfony/console/Application.php:213-225`) при отсутствии предшествующего PHP-обработчика
выполняется `set_exception_handler($renderException) === $renderException` → два `restore_exception_handler()`,
и `$renderException` снят. Значит escaping `Error` печатает **не** `Application::renderThrowable`
(и, следовательно, не через `ErrorStream`), а нативный вывод PHP про uncaught Error, с кодом **255**.
Поток этого вывода задают `display_errors`/`log_errors` в php.ini — это факт об окружении, а не о коде.

Следствие 3: `autoExit = true`, поэтому `exit($application->run())` в `bin/qmx:74` — мёртвый код:
Symfony завершает процесс сам и зажимает код в 0..255.

Следствие 4: `Command::__construct()` вызывает `$this->configure()`
(`vendor/symfony/console/Command/Command.php:116`), а конструирование команды происходит внутри
`ContainerCommandLoader::get()` внутри `Application::find()` — то есть внутри `try` на
`vendor/symfony/console/Application.php:295-299`, но **до** любого `try` самой команды.
Всё, что бросает `configure()`, недостижимо ни для одного `catch` в команде.

### Про `ValueError`

`GroupBy::from` бросает `ValueError`, но он перехвачен в `FormatterContextFactory.php:38` и **переоформлен**
в `InvalidArgumentException` (`:40`). Отдельного маршрута для `ValueError` нет — он всегда сливается в #13.

### Про достижимость #36-#37

`BaselineConfiguredThresholds::resolve()` (`:99`) итерирует `$this->rules->getClasses()` — **все**
объявленные классы правил, независимо от того, включила ли их конфигурация прогона. Поэтому правило,
чьи опции не строятся под текущей конфигурацией, попадает в проглатывание даже если сам прогон его
не собирал и потому не отказал раньше на `BaselineCommand.php:48`. Маршрут достижим; какой именно
пользовательский вход туда доходит, чтением кода не устанавливается.

### Заметные расхождения по коду возврата и потоку (зафиксировать, не чинить)

- Неверная форма `--memory-limit`: **3** в `check` (#13) и `directives` (#22), **1** в baseline (#20)

### Где чтение конфигурации не покрыто `catch (Throwable)`

- `directives`: `AnalysisPreflight.php:55` внутри `try`, но клауза `catch (Exception)` — `Error` уходит в #9.
- `debug:layer-assignment`: `:135` внутри `try`, клауза `catch (Exception)` — `Error` уходит в #9.
- `check` и пять baseline-команд закрыты `catch (Throwable)` целиком: `TypeError` там даёт 1, а не 255.
- `CheckCommand::configure()` (через конструктор) выполняется **вне** всех `try` самой команды —
  см. #8.
- Конструирование контейнера (`bin/qmx:52`, `ContainerFactory::create()`) идёт **до** `Application::run()`,
  то есть вне всякого `try`. Проверено: `ContainerFactory` только регистрирует определения и сканирует
  каталоги `src/`; пользовательская конфигурация там не читается — маршрута «отказ конфигурации
  до входа в Symfony» нет.

## 4. Маршруты, недостижимые из CLI

1. **`CheckCommand.php:163` — `catch (ConflictingCliAliasException)` мёртв.**
   Исключение бросается в `RuleRegistry.php:59`, вызванном из `CheckCommandDefinition.php:325`
   ← `CheckCommand::configure()` (`CheckCommand.php:65`) ← `Command::__construct()`
   (`vendor/symfony/console/Command/Command.php:116`). Конструирование происходит в
   `ContainerCommandLoader::get()` внутри `Application::find()`, то есть до `CheckCommand::run()`
   и тем более до `execute()`. Реальный маршрут — #8, код 1, stderr; клауза на `:163` не исполнится
   никогда. (Строго говоря это дефект инструмента, а не пользовательской конфигурации, но
   недостижимый `catch` относится сюда по определению раздела.)
2. **Мёртвых `catch` по иерархии не найдено.** Все восемь проектных классов —
   `ConfigLoadException`, `ArchitectureConfigurationException`, `ArchitecturePreparationException`,
   `ComputedMetricConfigurationException`, `BaselineLoadException`, `ConflictingCliAliasException`,
   `IncompleteAnalysisException`, `BaselineConflictException` — **наследуют `RuntimeException`**.
   Поэтому `catch (InvalidArgumentException)` в `CheckCommand.php:190` не затеняет `:194`
   (`InvalidArgumentException` — потомок `LogicException`, ветвь-сестра), а в `BaselineCommand`
   клауза `:54 InvalidArgumentException|RuntimeException` стоит **после** всех специфичных — порядок верен.
3. **Мёртвый код `bin/qmx:74`:** `exit($application->run())` недостижим как выражение выхода —
   `autoExit = true` завершает процесс внутри `run()`.
4. **`ValueError` как самостоятельный маршрут недостижим** — единственный источник в границах предмета
   обёрнут и переоформлен (`FormatterContextFactory.php:38-45`).
5. **Все 13 зарегистрированных в DI команд присутствуют в карте `bin/qmx`** — команд,
   зарегистрированных, но недостижимых по имени, нет.

**Чего этот способ не видит — поимённо:**

1. **`TypeError`/`Error` статически не перечисляются.** Мест их возникновения в коде как синтаксиса нет.
   Маршрут #9 охарактеризован не списком мест, а признаком «команда не закрыта `catch (Throwable)`
   вокруг чтения конфигурации». Какие входы туда попадают, даст только измерение.
2. **Поток нативного вывода PHP при uncaught `Error` (#9)** зависит от `display_errors`/`log_errors`
   в php.ini, а не от кода. Прогонами не подтверждалось.
3. **Рефлексия и автоконфигурация по тегу/интерфейсу не перебирались.** `CompilerPass`-ы
   (`CollectorCompilerPass`, `FormatterCompilerPass`, `ConfigurationStageCompilerPass`, правиловые)
   собирают сервисы по тегам. Отказ из автоматически зарегистрированной стадии конфигурации я вижу
   по классу исключения (все они — `ConfigLoadException`), но **не по полному списку стадий**:
   стадию, бросающую класс вне моего списка восьми, я не увижу.
4. **Тесты как канал не перебирались.** `tests/` не читались вовсе; они могли бы назвать маршруты,
   которых нет в production-коде, или показать ожидание, расходящееся с кодом.
5. **`vendor` дальше `symfony/console` не читался.** `symfony/yaml` бросает `ParseException`,
   перехваченную в `YamlConfigLoader.php:31` — это видно; но исключения
   `symfony/expression-language` (формулы computed-метрик) и `symfony/finder` классифицированы
   по тому, чем их ловят команды, а не по их собственным иерархиям.
6. **Цена отказа во времени измерена только для #35.** Видно, что `graph:export --format=bogus`
   отказывает после полного построения графа; для остальных маршрутов «что успевает произойти
   до отказа» не проверялось. Для #13 (неизвестный `--format` в `check`) есть основание подозревать
   то же самое — `FormatterRegistry` спрашивается в `presentResults`, после анализа, — но это
   не проверено пошагово.
7. **Ни одного прогона `bin/qmx`.** Все строки таблицы — «код»; ни один код возврата не подтверждён
   эмпирически. Расхождение с измерением, если оно будет, разрешается в пользу измерения по кодам
   и потокам, и в пользу этого документа — по достижимости и по наличию обработчика.
