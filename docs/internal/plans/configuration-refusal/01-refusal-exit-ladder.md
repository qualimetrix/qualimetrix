### 2.4. Отмена кода 255 — и почему `setCatchErrors(true)` её не заканчивает

`setCatchErrors(true)` в `bin/qmx` рядом с созданием `Application` отменяет PHP-фатал.
Измерено на копии `bin/qmx` в пробнике (единственная правка — вставка вызова):

| вход                                       | сегодня                      | с `setCatchErrors(true)` |
| ------------------------------------------ | ---------------------------- | ------------------------ |
| `directives src` (крах `computed_metrics`) | `ec=255, out=5210, err=5785` | `ec=1, out=0, err=563`   |
| то же `--format=json`                      | `ec=255, out=5210, err=5785` | `ec=1, out=0, err=563`   |
| `debug:layer-assignment RecNs\Probe`       | `ec=255, out=4708, err=5107` | `ec=1, out=0, err=458`   |
| `check src`                                | (маршрут 16)                 | `ec=1, out=0, err=163`   |

**Но код 1 в этой таблице — свойство четырёх измеренных входов, а не механизма.**
Прочитано `vendor/symfony/console/Application.php:204-212`: поймав исключение, Symfony
берёт код процесса из `$e->getCode()` и приводит к 1 **только** неположительное или
нечисловое значение. У `TypeError`/`Error` код 0, поэтому все четыре измерения дали 1;
исключение с ненулевым кодом отдало бы свой (в дереве 24 места `JSON_THROW_ON_ERROR`, а
коды `JsonException` — это коды `json_last_error`, в частности 4 = `JSON_ERROR_SYNTAX` и
5 = `JSON_ERROR_UTF8`). Код 4 у `bin/qmx directives` документирован как «run incomplete»
и читается `composer directives:audit` внутри `check:self` — то есть внутренняя ошибка
стала бы неотличима от исхода анализа.

**Решение: код назначаем мы, а не Symfony.** `Application::doRun()` (наш, он уже
перекрыт — `src/Infrastructure/Console/Application.php:51`) оборачивается собственной
лестницей, и она возвращает число явно, игнорируя `getCode()` пойманного.

**Лестница оборачивает ВСЁ тело нашего `doRun()`, а не вызов родителя.** Проверки
`--working-dir` (`Application.php:53-70`) бросают **выше** `parent::doRun()`, и обёртка
вокруг одного лишь вызова родителя пропустила бы их мимо себя — `-d <файл>` ушёл бы в
`Application::run()`, где Symfony взял бы код из `getCode()` (у `InvalidArgumentException`
он 0 → 1) и отрендерил бы исключение сам, вопреки строке ниже и вопреки DoD P01-6
(`-d <файл>` даёт `ec=3`). Псевдокод поэтому такой:

```
public function doRun(InputInterface $input, OutputInterface $output): int
{
    try {
        // проверки --working-dir: chdir, они же бросают носителя
        // ... implementation details
        return parent::doRun($input, $output);
    }
    catch (ConfigurationRefusal $r)      { return $presenter->refusal($output, null, $r); }       // 3
    catch (ConsoleExceptionInterface $e) { return $presenter->fallbackRefusal($output, null, $e); } // 3, §2.5
    catch (InvalidArgumentException $e)  { return $presenter->fallbackRefusal($output, null, $e); } // 3, вторичный признак §2.6
    catch (Throwable $e)                 { return $presenter->internalError($output, null, $e); }   // 1
}
```

**Что делает третья клауза — переписано третьим раундом.** Прежняя редакция называла её
«тем, чем `rules` получает единообразный fallback». Это было неверно дважды: `rules` на
неизвестной `--group` не бросает вовсе (`01-refusal-verdicts.md` §5.7), а после раунда
она бросает **носителя** и попадает в первую клаузу, а не в третью. Третья клауза
обслуживает то, что действительно долетает сюда `InvalidArgumentException`-ом и не имеет
носителя:

* отказ, брошенный **до** `execute()` — из `configure()` и из конструктора команды
  (команды грузятся лениво через `ContainerCommandLoader`), где никакая лестница команды
  ещё не стоит;
* `InvalidArgumentException` из ~145 мест вне Console, которые раунд **считает**, а не
  конвертирует (§2.6), поднявшийся в команде без своей лестницы;
* всё, что раунд не перечислил: множество мест броска открыто (обзор, правило 1), и эта
  клауза — названный вторичный признак кода 3, а не недосмотр.

`graph:export` из этого списка ушла: по §2.1 у неё появляется своя клауза в команде,
потому что здесь формат неизвестен.

Следствие, которое надо назвать: исключение больше не долетает до `Application::run()`,
значит Symfony его **не рендерит** — печатаем мы, через предъявителя с `format: null`
(формат на этом уровне неизвестен, §2.2). Отсюда два обязательства, переезжающие на
предъявителя, — см. §3: остановка прогресс-фрейма и судьба трассы.

**Окно `configureIO` описано точно, а не «новое».** `configureIO()` и `doRun()` лежат
внутри одного `try` в `Application::run()`
(`vendor/symfony/console/Application.php:191-193`), а `catchExceptions` по умолчанию
**истинно** (`:79`) — значит для `Exception` сеть там была и до раунда, и код в ней
брался из `getCode()` уже сегодня. `setCatchErrors(true)` добавляет к этому **только**
не-`Exception` `Throwable` (ветка `:200`), то есть отменяет фатал и код 255. Внутри окна
`configureIO` код по-прежнему берётся из `getCode()`, и это признаётся вторичным:
достижимого входа в него с ненулевым кодом не показано, записано как ограничение, а не
как гарантия.

**Жёсткая граница обзора соблюдена: `TypeError` остаётся кодом 1.** Ловля не
переклассифицирует род — она отменяет 255 и второй поток. Крах `computed_metrics`
лечится этапом 02 в источнике; после него этот вход перестанет доходить сюда вовсе, а
сеть останется под тем, чего никто не предвидел.

**Отвергнуто: полагаться на умолчание Symfony.** Довод за — меньше кода. Против:
гарантия «внутренняя ошибка = 1» стала бы утверждением о двух измеренных входах вместо
утверждения о механизме, а цена ошибки — код 4, неотличимый от исхода анализа.

**Отвергнуто: перекрывать `Application::run()`.** Довод за — поймать и `configureIO`.
Против: пришлось бы дублировать всю работу с обработчиком исключений и `SHELL_VERBOSITY`
(`vendor/…/Application.php:180-235`).

**Отвергнуто: `set_exception_handler` в `bin/qmx`.** Symfony снимает свой обработчик в
`finally` и восстанавливает предыдущий; чужой обработчик поверх этого — гонка за право
печатать, а не решение.

### 2.5. `ConsoleExceptionInterface` — код 3, один раз в `Application`

Маршруты 3, 4, 6, 7 — это «нет такой команды», «нет такой опции», «слишком много
аргументов»: ключ, который написал пользователь. По таблице обзора это код 3, а сегодня
1. `CheckCommand::run()` уже сегодня спускает один такой случай на 3 (маршрут 5) — и его
докблок (`CheckCommand.php:126-133`) формулирует довод за меня: код 1 читается обёрткой
CI как «прогон упал», а не «есть что поправить во вводе».

**Решение: `ConsoleExceptionInterface` → 3, один раз, в лестнице §2.4.** Частный случай
маршрута 5 остаётся там, где он есть: он меняет **текст**, а не код. Это **вторичный**
признак кода 3, названный таковым в `03-carrier-and-normalization.md` §2.1: носителем эти
исключения не становятся, потому что бросает их Symfony, а не наш шов.

**Отвергнуто: оставить разбор опций на коде 1.** Довод за — так делает всякое
symfony-приложение. Против: тогда «неизвестный `--format`» даёт 3 у `check` и 1 у
`graph:export` не по роду, а по тому, кто первым его увидел, — дефект, который раунд
называет своим предметом.

**Не трогаем:** интерактивный вопрос «Do you want to run "check" instead?» (маршрут 4)
остаётся на stdout — это диалог, а не диагностика; меняется только код.

### 2.6. Единообразный fallback: что раунд с ним делает

Обзор оставил общий `catch (InvalidArgumentException) → 3` как названный вторичный
признак и названный долг и потребовал сделать его **одинаковым во всех командах**.
Утверждение «одинаковым» — про пять лестниц, поэтому лестницы перечислены, а не
подразумеваются (снято чтением пяти файлов на `1513bf67`):

| команда                  | сегодня                                                                                                                                                  | после раунда                                                                                                                                                                                                              | пакет                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `check`                  | `catch (InvalidArgumentException)` → 3 (`CheckCommand.php:189`)                                                                                          | без изменений по коду; поток и конверт — через предъявителя                                                                                                                                                               | P01-3                                                                           |
| `baseline:*`             | `catch (InvalidArgumentException\|RuntimeException)` → `fail()` → **1** (`BaselineCommand.php:54`)                                                       | клауза **расщепляется**: `InvalidArgumentException` → 3, `RuntimeException` → 1                                                                                                                                           | P01-4                                                                           |
| `directives`             | `catch (InvalidArgumentException)` → 3 (`:142`); ниже `catch (Exception)` → `ConfigurationFailure::message()` → 3, иначе 1                               | код без изменений; ветка `ConfigurationFailure` умирает вместе с классом (P01-7)                                                                                                                                          | P01-5                                                                           |
| `debug:layer-assignment` | клаузы на `InvalidArgumentException` **нет**; `catch (Exception)` → `self::FAILURE` = **1** даже для распознанного конфигурационного текста (`:160-174`) | добавляется `catch (InvalidArgumentException)` → 3 перед `catch (Exception)`                                                                                                                                              | P01-5                                                                           |
| `graph:export`           | своей лестницы нет — уходит в `Application`                                                                                                              | **заводит свою лестницу** (§2.1): без неё её `--format=json` получил бы код 3 и ноль байт на stdout                                                                                                                       | P01-5                                                                           |
| `rules`                  | своей лестницы нет; **и отказ по `--group` до лестницы не доходит** — команда печатает и делает `return self::FAILURE` (маршрут 37, `ec=1`, измерено)    | проверка `--group` **бросает носителя на месте** (P01-5); код 3 даёт **первая** клауза лестницы `Application` (P01-6). Своей лестницы команда по-прежнему не заводит и конверта не получает — машинного формата у неё нет | правка команды — **P01-5**; лестница и сквозной кейс — **P01-6**, ребро названо |

**Порядок клауз — корректность, а не стиль.** `ConfigurationRefusal extends RuntimeException`,
поэтому в `BaselineCommand` он обязан стоять **выше** расщеплённой пары, иначе носитель
уедет в ветку `RuntimeException → 1`. То же в `DirectivesCommand` (выше `catch (Exception)`)
и в `CheckCommand` (выше `catch (Throwable)`).

**Лестниц становится шесть, а не пять**: `check`, `baseline:*` (одна на все пять команд,
`BaselineCommand::execute()`), `directives`, `debug:layer-assignment`, `graph:export`
(новая) и `Application`. Счёт назван, потому что «одинаково во всех командах» — утверждение
о множестве, и множество перечислено.

**Цена названа обзором и повторяется здесь как условие приёмки, а не как сноска:**
продуктовый дефект, бросивший `InvalidArgumentException`, получит 3 вопреки правилу 2.
Сегодня `check` уже так делает примерно для 145 мест вне Console
(`grep -rn 'throw new InvalidArgumentException\|extends InvalidArgumentException' src/ | grep -v '^src/Infrastructure/Console/'`
→ 145 строк: `Analysis/Policy` 49, `Analysis/Evidence` 30, `Analysis/Finding` 20,
`Core/Symbol` 14, `Core/Path` 12, `Infrastructure/Git` 3, `Infrastructure/Rule` 1). Это
статус-кво, а не регрессия раунда: раунд ничего из этого не ломает и ничего не чинит, он
**считает** остаток числом (`scripts/enumerate-refusal-fallback.php`, владелец 03/P1).
`src/Infrastructure/Rule/`, `src/Infrastructure/Git` и три места `--report=git:*` в нём —
внутри этого числа; пакетов на них раунд не заводит.

### 2.7. Один владелец кода отказа

Число 3 живёт сегодня в трёх местах (`CheckCommand.php:106`, `DirectivesCommand.php:61`
и как «не 3» в `BaselineCommand.php:37`). Владельцем становится
`Qualimetrix\Infrastructure\Console\Refusal\ConsoleExitCode` — enum с двумя случаями
раунда (`Refusal = 3`, `InternalError = 1`) и ничем больше.

`ExitCodeResolver` владельцем **не** становится и не трогается: он считает исходы
анализа (0/1/2/4), и его `hasConfigurationError()` (`:116`) — про находки правил, а не
про отказ по вводу. Смешать их значило бы вернуть маршрутизацию, только в другой класс.

## 3. Контракты, которые заводит этап

Сигнатуры без тел; каталог `src/Infrastructure/Console/Refusal/`.

```php
enum ConsoleExitCode: int { case Refusal = 3; case InternalError = 1; }
```

```php
/** Куда и в каком виде уходит сообщение, завершающее прогон. */
final class RefusalPresenter
{
    public function __construct(private readonly ErrorStream $errorStream) {}

    /** Отказ по вводу: конверт на stdout для JSON-форматов, иначе одно предложение на stderr. */
    public function refusal(OutputInterface $output, ?string $format, ConfigurationRefusal $refusal): int;

    /**
     * Вторичный признак кода 3 (§2.6): пойманный общий InvalidArgumentException,
     * у которого носителя нет. Отдельный метод, чтобы «сколько входов идут этим путём»
     * было видно счётчиком вызовов, а не рассуждением.
     */
    public function fallbackRefusal(OutputInterface $output, ?string $format, Throwable $failure): int;

    /** Внутренняя ошибка: та же развилка, код 1, шапка «Internal error». */
    public function internalError(OutputInterface $output, ?string $format, Throwable $failure): int;

    // Обрамление живёт здесь и только здесь: summary() приходит без рамки и префикса.
    // Все записи идут уровнем VERBOSITY_QUIET (§2.3).
    // Каждый из трёх методов ПЕРВЫМ делом зовёт ErrorStream::stopProgress() — иначе
    // сообщение печатается поверх живого прогресс-фрейма и затирается им.
    // ... implementation details
}
```

**Две обязанности переезжают сюда из `Application::renderThrowable()`, и это следствие
лестницы §2.4, а не побочный эффект.** Переопределённый `renderThrowable`
(`Application.php:32-49`) существует ради двух вещей: `stopProgress()` до печати и печать
через `boundWriter()`, чтобы диагностику не затёрли. Лестница ловит раньше `run()`, значит
на всех перехваченных путях `renderThrowable` **не вызывается**, и обе обязанности
остались бы бесхозными.

* **Прогресс-фрейм.** `stopProgress()` становится первой строкой каждого метода
  предъявителя; DoD P01-6 получает кейс «отказ при живом прогресс-фрейме читается
  целиком».
* **Трасса.** Раньше её печатал Symfony под `-v`/`-vvv`. **Решение: предъявитель печатает
  трассу при `VERBOSITY_VERBOSE` и выше — и только для `internalError()`.** Довод: трасса
  отказа по вводу пользователю не адресована (чинит он конфигурацию, а не наш стек), а
  трасса внутренней ошибки — единственное, с чем заводят баг. Отвергнуто **не печатать
  трассу вовсе**: это регрессия против сегодняшнего `-vvv` и ровно та потеря диагностики,
  которую раунд объявил дефектом на другой оси. Отвергнуто **печатать её и для отказа**:
  тогда `-v` возвращает пользователю стек вместо предложения.

`Application::renderThrowable` **остаётся** — он ещё нужен на путях, лестницей не
накрытых (окно `configureIO`, §2.4), и его удаление было бы снятием сети без замены.

**Метода `refusalText(string $summary)` в контракте нет, и это решение.** Он был нужен,
пока у команды не было способа построить носителя; после того как контракт носителя
получил сторону создания (`ConfigurationOrigin::of()`, `ConfigurationRefusal::aboutInput()`
— `03-carrier-and-normalization.md` §2), проверка внутри команды бросает носителя ровно
так же, как валидатор. Отвергнуто **оставить его для удобства**: он был бы третьим
признаком кода 3, а раунд тем и занят, что их пересчитывает и сокращает.

```php
/** Один вопрос: пишется ли stdout этого формата как JSON. Список — §2.1. */
final class MachineReadableFormats { public static function carriesJson(?string $format): bool; }
```

**Как предъявитель попадает в `Application`.** Он не может прийти в неё DI-конфигуратором:
`Application` конструируется руками в `bin/qmx` (`new Application($container->get(ErrorStream::class))`).
**Решение: вторым аргументом конструктора, из того же контейнера.** Довод — утверждение
«обрамление живёт в предъявителе и только в нём» иначе неверно: лестница §2.4 печатает
сама, и в дереве появился бы второй экземпляр обрамления, расходящийся с первым молча.
Правка `bin/qmx` и конструктора — пакет P01-6, и в его наборе оба файла уже есть.
Отвергнуто **дать `Application` печатать своими средствами**: это второй диалект отказа,
то есть предмет раунда, воспроизведённый на уровне приложения.

Псевдокод предъявления в команде — один и тот же во всех пяти, порядок клауз обязателен
(§2.6):

```
try { … }
catch (ConfigurationRefusal $refusal)   { return $presenter->refusal($output, $format, $refusal); }
catch (InvalidArgumentException $input) { return $presenter->fallbackRefusal($output, $format, $input); }
catch (Throwable $failure)              { return $presenter->internalError($output, $format, $failure); }
```

`BaselineCommand` сохраняет между первой и второй клаузами свои `IncompleteAnalysisException`
(код 4) и `BaselineConflictException` (код 1) — их раунд не трогает.
