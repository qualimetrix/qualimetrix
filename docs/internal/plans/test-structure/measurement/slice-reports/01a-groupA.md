## Control candidates

- There are no strict "control" files (documentation/generated artifacts/qmx.yaml/composer.json
  etc.) in this group.
- `RuleThresholdKeyGroupRegistryCompletenessTest.php` and `RuleThresholdKeyGroupRegistryDriftTest.php`
  — **control-invariant by mechanism** (a full scan of all of `src/` via reflection/AST), but they
  check not layout/documentation but the correctness of a specific product registry
  (`RuleThresholdKeyGroupRegistry`) against real code — i.e. they serve exactly the purpose of
  "don't let an AI break the code" (detecting registry drift when `ThresholdParser::parse()` calls
  are added/removed). Formally they fall under the disputed owner boundary (scanning `src/` via
  reflection for a layout invariant), but by content it's not about layout, it's about the
  completeness of a hand-made data structure. Owner's decision: keep as integration/regression, do
  not move to control.

## Duplicates and contradictions

- **`RuleThresholdKeyGroupRegistryCompletenessTest` vs `RuleThresholdKeyGroupRegistryDriftTest`**
  — two separate files (793 + 513 lines), both scan all of `src/` and check
  `RuleThresholdKeyGroupRegistry` against real `ThresholdParser::parse()` calls. Method names are
  nearly identical (`itMakesEveryRegistryEntryCorrespondToARealCallSite` /
  `...RealThresholdParserCallSite`; `itAgreesWithEveryCallSitesLiteralKeys` /
  `itGivesEveryThresholdParserCallSiteAMatchingRegistryEntry`). The actual difference: Drift checks
  the call count per `(rule, path)` and a behavioral diff probe via the real factory;
  Completeness checks the literal ARGUMENTS of every call via AST and the value shape. The authors
  themselves document the difference in the docblocks — not a blind duplicate, but a candidate for
  merging on run-cost grounds (both run the parser over all of `src/`).
- **`RuleConfigurationIsolationTest`** (resetting `RuleOptionsRegistry`) partially overlaps with
  `itResetsState()`/`itResetsClearsAllState()`/`itDoesNotLeakCliOptionsIntoTheNextRunAfterReset()`
  in `RuleOptionsFactoryTest.php` — the same SUT (`RuleOptionsRegistry::resetRuntimeState()`/state
  reset), different fields under check (namespace exclusions/CLI options vs
  RuleSelection/capturesExcludedFindings). Not a strict duplicate, but worth considering merging
  into one file about registry state isolation.
- **`RuleNamespaceExclusionProviderTest`** — the first two tests actually belong to
  `RuleOptionsRegistry` (delegation), not the declared SUT `RuleNamespaceExclusionProvider`; by
  subject they are close to `RuleOptionsFactoryTest`'s `itExtractsSuppressNamespacesWritten...`/
  `itExtractsCodeScopedNamespaceExclusions` tests, but they check a different layer (after config
  parsing, not raw keys) — not a duplicate, but mixing SUTs inside one file violates "one file —
  one subject".

## Assumptions

- Because of the volume (`RuleOptionsFactoryTest.php` — 2194 lines/~150 tests,
  `RuleExecutorTest.php` — 1504 lines/~45 tests), not every line was read character by character:
  the header, each method's structure, and the sections riskiest for this task (exclusion
  boundaries, threshold shorthand, state reset) were read in full; the middle of
  `RuleOptionsFactoryTest.php` (lines ~300–1300, ~1700–2000) was skimmed by method name and
  sampled blocks, not line by line — point defects (a stray duplicate assertion, an overly narrow
  check) not caught by this kind of pass are not ruled out.
- No CLAUDE.md §9 violations (`#[Test]` + `itXxx`) were found in the sections read — the pattern
  is followed everywhere.
- "SUT ↔ directory" correspondence was checked by the physical path of the found class (`find`),
  not by a deep subject-ownership analysis (ADR 0016/0022) — no discrepancies found.
- The "defect" assessment is limited to the questions from the brief
  (duplicate/tautology/contradiction/lying name/wording instead of behavior/§9 violation);
  architectural questions (whether the class's place in `src/` is even correct) are outside the
  scope of this file group.
