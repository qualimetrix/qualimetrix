# Violation Magnitude Inventory

Collected 2026-08-05. Mechanical enumeration, not analysis: every `new
Violation(` call site under `src/` (found via `grep -rn "new Violation("
src/`, 43 matches across 31 files), read directly to record the literal
expression passed as `metricValue`, whether it is a real measured magnitude
or a fixed marker, which direction is worse (with a file:line citation of the
actual comparison in code), and whether `threshold:` is passed to the
`Violation` constructor at all.

**Unit of enumeration** is the physical `new Violation(` occurrence (one row
per grep match), not the logical channel. Three call sites are reused by
multiple subclasses/branches with a computed `ruleName`/`violationCode`
(`AbstractCodeSmellRule.php:90`, `AbstractSecurityPatternRule.php:102`,
`TypeCoverageRule.php:178`) — per task instructions these stay one row each,
with every value the computed expression can take listed in the Channel
column. Two call sites in the same file (`LongParameterListRule.php:115` and `:139`)
are kept as two separate rows even though they resolve to the same literal
channel and report the same magnitude — `MetricName::CODE_SMELL_PARAMETER_COUNT`,
read once at `:96` ahead of the branch. They are split because each carries an
independent threshold pair (`voWarning`/`voError` vs `warning`/`error`),
selected by the symbol, not because the magnitude differs.

*(Corrected 2026-08-05 after a review spot-check: the original wording claimed
the VO branch reported a distinct promoted-property count. It does not — the
rule's message says "promoted parameters", but no such metric is read.)*

Row count: 43, matching the grep count exactly (see the running total in the
`Counts` implied by the table below).

## Emission points outside the rule layer

Two groups emit `Violation` objects without going through a `RuleInterface`
implementation's normal `analyze()` contract in the conventional
`src/Rules/**` sense:

1. **`src/Analysis/Pipeline/AnalysisPipeline.php`** — two private methods,
   `buildUnsupportedOverrideViolations()` (`:237-272`, emission at `:256`)
   and `buildDiagnosticViolations()` (`:363-388`, emission at `:375`),
   convert `ThresholdOverride`/`ThresholdDiagnostic` data (produced upstream
   during annotation parsing in the Collection phase, not by any rule) into
   `Violation` objects with `ruleName`/`violationCode` prefixed
   `annotation.*`. Both are called directly from `analyze()` (`:183`,
   `:186-188`) and merged into the rule-produced `$violations` array
   (`:190-193`) before the `AnalysisResult` is built. Neither carries a
   `metricValue`. These are the only two `Violation`-emitting call sites in
   the entire codebase that live outside `src/Rules/` and
   `src/Architecture/Rules/` altogether.

2. **`src/Architecture/Rules/LayerViolationRule.php`** — technically inside
   `src/Architecture/Rules/` (so it is a normal rule class from a
   directory-layout standpoint), but its `analyze()` method (`:153-199`)
   fans out into **five** distinct diagnostic builders, four of which use a
   `ruleName`/`violationCode` other than the class's own `self::NAME`:
   - `buildEmptyTemplateDiagnostics()` → `EMPTY_TEMPLATE_DIAGNOSTIC_NAME`
     (`:222-253`, emission `:232`)
   - `buildViolation()` → `self::NAME` itself (`:400-438`, emission `:419`)
     — the only one of the five that matches the class's own name.
   - `buildCoverageDiagnostic()` → `COVERAGE_DIAGNOSTIC_NAME` (`:586-641`,
     emission `:632`)
   - `buildUnreachableLayerDiagnostics()` → `UNREACHABLE_LAYER_DIAGNOSTIC_NAME`
     (`:659-690`, emission `:678`)
   - `buildPotentialShadowDiagnostics()` → `POTENTIAL_SHADOW_DIAGNOSTIC_NAME`
     (`:711-784`, emission `:768`)

   All five channels carry `metricValue: absent` — none of them, including
   the primary `architecture.layer-violation` edge-level channel, report a
   measured magnitude on the `Violation` object. Any counts that exist
   (`$total` evidence entries, `$unmatchedEnds`, `$size` of a criteria list)
   surface only inside free-text `message`/`recommendation` strings.

## Compound rules reporting fewer axes than they judge

Two rules gate emission on more than one measured value but report only one
of them in `metricValue`:

- **`DataClassRule`** (`src/Rules/Design/DataClassRule.php:116`) — the
  trigger predicate is a conjunction: `$wocValue >= $effectiveOptions->wocThreshold`
  **and** `$wmcValue <= $effectiveOptions->wmcThreshold` (coded as the
  negated early-return `if ($wocValue < ... || $wmcValue > ...) return null;`).
  Both `WOC` and `WMC` are real measured metrics
  (`MetricName::STRUCTURE_WOC`, `MetricName::STRUCTURE_WMC`) fetched at
  `:107` and `:113`. Only `$wocValue` reaches `metricValue` (`:133`); `$wmcValue`
  is visible solely inside the `message` string (`:126-131`) and is
  otherwise lost once the `Violation` object exists.

- **`GodClassRule`** (`src/Rules/Design/GodClassRule.php:105-119`) — judges
  4 independent criteria via `GodClassCriteriaEvaluator::evaluate()`: WMC
  (`>= 47`), LCOM4 (`>= 3`), TCC (`< 0.33`), class LOC (`>= 300`) — see the
  thresholds documented at `GodClassOptions.php:18-21`. `metricValue` reports
  only `$matchedCount` (`:139`), the tally of how many of the (up to 4)
  evaluable criteria matched — not which ones, and not any of their
  individual values. The per-criterion messages (`$result->message`) are
  concatenated into the free-text `message` string (`:129-137`) but do not
  reach `metricValue`.

Other rules that combine multiple inputs into one number
(`CboRule` — `Ca`/`Ce` → single `CBO` value; `DistanceRule` — `A`/`I` →
single `D` value; `InstabilityRule`'s own `Ca`/`Ce` → single `I` value) are
**not** classified as "fewer axes than judged" here: in those cases the
combined value itself *is* the one thing the rule's threshold judges (`Ca`
and `Ce` are not independently thresholded), so there is no separate,
independently-gating axis left unreported — unlike `DataClassRule`'s WOC+WMC
conjunction or `GodClassRule`'s 4-criterion tally.

## Discrepancies against channel-trait-inventory.md

`docs/plan/channel-trait-inventory.md` was **not** edited; differences below
are recorded for reference, not corrections to that file (it answers a
different question — per-channel trait classification — with its own
"channel" as the unit of enumeration, whereas this inventory's unit is the
physical emission point).

1. **Missing scope, not an error**: `channel-trait-inventory.md` states its
   own scope as `src/Rules/**/*Rule.php` + `src/Architecture/Rules/*Rule.php`
   (its header, line 3-4). Both `annotation.unsupported-threshold` and
   `annotation.invalid-threshold[.code]` channels, emitted from
   `src/Analysis/Pipeline/AnalysisPipeline.php`, fall outside that scope by
   the old inventory's own definition and are consequently absent from it
   entirely — not a factual gap in that document, just a boundary this task
   was specifically asked to also cover.

2. **Row-count convention differs for `code-smell.long-parameter-list`**:
   the old inventory lists it as **one** row (its CodeSmell section header
   says "14 channels / 11 rule classes", and the table has a single
   `code-smell.long-parameter-list` row noting the VO-dependent threshold
   selection in its "Threshold source" cell). This inventory lists it as
   **two** rows (`LongParameterListRule.php:115` and `:139`) because they are
   different physical `new Violation(` call sites with different threshold
   pairs (`voWarning`/`voError` vs. `warning`/`error`) selected by the symbol —
   per this task's explicit instruction not to collapse emission points that
   differ in form. Their magnitude is identical, so for any consumer that cares
   about the magnitude rather than the threshold, the two rows are one channel. Reconciling the two unit
   conventions: old inventory's 52 channel-rows for `src/Rules/**` +
   `src/Architecture/Rules/**` become 53 emission-point-rows here once this
   one channel is split (43 total emission points − 2 Pipeline rows = 41
   Rules/Architecture rows... but 3 of those 41 rows expand internally to
   multiple channels: `AbstractCodeSmellRule` 1→9, `AbstractSecurityPatternRule`
   1→3, `TypeCoverageRule` 1→3 — net channel count = 41 − 3 + 9 + 3 + 3 = 53,
   which is the old inventory's 52 plus exactly the one extra
   `long-parameter-list` row this inventory does not collapse).

3. **A fact this inventory adds that the old one's dimension vocabulary
   does not track**: whether the `Violation` object's `threshold:`
   constructor parameter is actually populated. The old inventory's
   "1. Threshold source" column records whether a threshold **exists and
   drives severity** (e.g. "configured tiers" for
   `architecture.circular-dependency`, `design.data-class`, `design.god-class`,
   `duplication.code-duplication`, `code-smell.unreachable-code`,
   `code-smell.unused-private`), but does not distinguish that from whether
   the threshold value **reaches the `Violation` object**. This inventory
   found all six of those channels omit the `threshold:` argument entirely
   at their emission call sites (see each row's "threshold param" column
   above) — a strictly finer-grained fact than what `channel-trait-inventory.md`
   captures, not a contradiction of it.

4. **Additional dead-code `getSeverity()` instances not listed in the old
   inventory's "Observations" section**: that section calls out
   `HardcodedCredentialsOptions`/`SensitiveParameterOptions` (unreachable-false
   `> 0` guard) and "several CodeSmell Options classes" (`BooleanArgumentOptions`,
   `ErrorSuppressionOptions`, `CodeSmellOptions`) as having a working but
   never-called `getSeverity()`. Reading the Design domain for this
   inventory surfaced three more instances of the same pattern not
   mentioned there: `DataClassOptions::getSeverity()` (`:66`, always returns
   fixed `Warning`, but `DataClassRule` hardcodes `Severity::Warning` inline
   at `DataClassRule.php:132` instead of calling it),
   `GodClassOptions::getSeverity()` (`:76`, its own comment says "Severity
   is determined inline in analyze()"), and `TypeCoverageOptions::getSeverity()`
   (`:92`, always returns `null`; `TypeCoverageRule::checkCoverage()`
   computes severity inline instead).

No channel present in `channel-trait-inventory.md`'s Rules/Architecture
table was found to be missing from the actual code, and no channel found in
the code (within that same `src/Rules/**` + `src/Architecture/Rules/**`
scope) was found absent from the old inventory — the only differences are
the two items above (Pipeline scope, and the long-parameter-list row-split
convention) plus the finer-grained `threshold`-param and dead-`getSeverity()`
facts this inventory happened to record in passing while reading the same
code for a different purpose.
