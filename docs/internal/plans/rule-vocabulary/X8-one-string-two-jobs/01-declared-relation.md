# Э1 — связь «канал судит эту метрику» объявлена, а не написана

Закрывает записи 90 и 108. Этап не переименовывает ничего: он делает ссылку на
метрику типизированной там, где строка означает метрику, и объявленной там, где
канал судит метрику.

## Что сегодня

Три разных способа сказать про одну связь, и ни один не проверяется:

1. `RuleInterface::requires()` — 57 различных строк в 36 классах правил. **Ни
   одного производственного потребителя**: `->requires()` в `src/` вызывается в
   `GlobalCollectorSorter` и `DerivedCollectorRunner`, и оба работают с
   коллекторами — одноимённый метод другой иерархии. Читают 37 юнит-тестов,
   каждый сверяя список своего правила сам с собой.
2. 17 строк из 57 приходят из **другого словаря**: `codeSmell.boolean_argument`,
   `security.sql_injection` — это живые ключи фактов коллектора в старом
   написании, а не несуществующие метрики. Дефект не в том, что они мертвы, а в
   том, что один список смешивает два пространства имён и ничто не проверяет,
   какое из них имелось в виду.
3. Совпадение написаний: 18 кодов каналов из 52 равны ключу метрики. Оно
   заставило стража вычитать пересечение из карты владения, из-за чего часть
   production-мест не судится вовсе; точный размер снимает П4a оптикой самого
   стража — подстрочный счёт даёт другое множество (см. П4a).
4. Расхождение написаний: `complexity.cyclomatic` судит `complexity.ccn`,
   `maintainability.index` — `maintainability.mi`, `design.inheritance` —
   `design.dit`, `code-smell.constructor-overinjection` —
   `code-smell.parameter-count`, `code-smell.unused-private` —
   `code-smell.unused-private.total`. Связь не выражена нигде.

## Решение

`requires()` у правил удаляется целиком; `ChannelDeclaration` получает фабрику,
называющую метрики каталога, из которых может прийти `metricValue` канала.

```
// Величина канала берётся из каталога метрик.
ChannelDeclaration::judging(
    WorseDirection $direction,
    JudgedMetrics $metrics,
    SymbolLevel $level,
    SymbolLevel ...$moreLevels,
): self

// Непустота — по арности, а не по проверке в теле:
JudgedMetrics::of(string $metricKey, string ...$moreKeys): self

// Существующие фабрики сохраняются:
ChannelDeclaration::magnitude(WorseDirection, SymbolLevel, SymbolLevel ...): self   // величина собственного изготовления
ChannelDeclaration::occurrence(SymbolLevel, SymbolLevel ...): self                  // без направления
```

Почему `JudgedMetrics`, а не `list<string>`: у `ChannelDeclaration` уровни
вариадические, поэтому вторую вариадику в ту же сигнатуру не поставить, а
`list<string>` делает пустой список **выразимым** — против принципа ADR 0031 и
против собственного докблока класса («a caller cannot express the empty list at
all»). Первая редакция предлагала `list<string>` и была на этом поймана ревью.

**Чем это НЕ является.** `JudgedMetrics::of(string, string ...)` принимает
строки, и назвать это «типизированной ссылкой на метрику» нельзя: тип даёт
непустоту по арности, существование ключа даёт сборка, а от опечатки в значении
константы не защищает ни то, ни другое. Типизирует здесь только **место
вызова** — `MetricName::COMPLEXITY_CCN` вместо литерала, что и нужно стражу,
читающему токены. Второй раунд ревью поймал первую редакцию на этой подмене
слов; она исправлена здесь, а не в докблоке будущего класса.

**Четвёртое поле в `ChannelDeclaration` спорит с закрытым перечнем.** Докблок
класса перечисляет, что там лежит, и заканчивается «Nothing else belongs here»;
ADR 0031 объясняет, почему форма ушла из этого класса. Поле `judges` — законное
исключение из обоих текстов, и этап **обязан** выпустить errata к ADR 0031 либо
новый ADR, а не молча дописать поле. Без этого следующий читатель найдёт
докблок, спорящий с кодом.

Форма канала при этом остаётся свойством продюсера (ADR 0031): `judging` и
`magnitude` обе дают форму `magnitude`, объявленную через `RuleInterface::shape()`.
Новой формы не заводится.

Почему валидация живёт в сборке: `ChannelDeclaration` принадлежит
`Analysis\Finding`, а `MetricName` — `Analysis.Evidence.Measurement`. Проверка
«строка есть значение константы `MetricName`» ставится в
`ChannelDeclarationCompilerPass` (`Infrastructure`), который уже композирует обе
стороны, — так `Analysis.Finding` не заводит ребра на `Measurement`.

### Три проверки, и третья — единственная новая работа

| проверка                                                                | где                | что ловит                                                            |
| ----------------------------------------------------------------------- | ------------------ | -------------------------------------------------------------------- |
| ключ есть значение константы `MetricName` или её агрегатное написание   | сборка реестра     | объявление несуществующей метрики; переименование метрики без канала |
| `judging` только у формы `magnitude`                                    | сборка реестра     | канал без направления, назвавший судимую величину                    |
| `metricValue` находки выводится из объявленной метрики того же субъекта | наблюдённый прогон | объявление, разошедшееся с телом правила                             |

**Третья проверка в первой редакции была неисполнима, и это подтвердили оба
ревьюера.** Строгое равенство ломается на трёх измеренных классах:

| класс                  | пример                                                                  | почему равенство неверно                          |
| ---------------------- | ----------------------------------------------------------------------- | ------------------------------------------------- |
| округление             | `MaintainabilityRule.php:130` публикует `round($miValue, 1)`            | опубликованное значение не равно сырому           |
| агрегатное написание   | `ClassCountRule.php:102` судит `MetricName::agg(SIZE_CLASS_COUNT, Sum)` | судится `size.class-count.sum`, а не базовый ключ |
| выбор ключа по конфигу | `CboRule.php:160`                                                       | судимый ключ зависит от `scope`                   |

Отсюда форма проверки: объявляется **точное написание, включая агрегатную
стратегию**; сравнение идёт с допуском, покрывающим объявленное округление;
для канала с несколькими кандидатами достаточно совпадения с одним. И главное —
**множество каналов, которое проверка не покрывает, объявляется списком с
числом**, иначе оно молча вырастет: сегодня это **шесть** позиций: четыре канала формы `magnitude` без метрик
каталога (`architecture.circular-dependency`, `architecture.unassigned-class`,
`duplication.code-duplication`, `design.god-class`), плюс `coupling.class-rank`
— он остаётся occurrence по ADR 0017, но `metricValue` публикует из каталожной
метрики (`ClassRankRule.php:103,134`), то есть проверка на нём молчит при живом
значении, — плюс всё семейство computed-metric, разрешаемое в рантайме. Пакет,
который не может назвать это множество поимённо, не сдан.

### Раскладка по каналам

Из `enumeration-channels.tsv` (52 строки), колонка `judged_metric_key`:

| группа                                                                                         | сколько | что объявляет                                                                                                                                      |
| ---------------------------------------------------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| magnitude, одна метрика каталога (в их числе `coupling.cbo` — он один объявляет два кандидата) | 19      | `judging`                                                                                                                                          |
| magnitude, оба судят `code-smell.parameter-count`                                              | 2       | `judging`; many-to-one законно                                                                                                                     |
| magnitude, композитный гейт, публикует `design.woc` (`design.data-class`)                      | 1       | `judging(JudgedMetrics::of('design.woc'))`                                                                                                         |
| magnitude, величина собственного изготовления                                                  | 4       | `magnitude` без изменений: `architecture.circular-dependency`, `architecture.unassigned-class`, `duplication.code-duplication`, `design.god-class` |
| occurrence                                                                                     | 26      | `occurrence` без изменений                                                                                                                         |

Итого объявляют `judging` — **22 канала**; 19 + 2 + 1 + 4 + 26 = 52.

**`coupling.class-rank` развилки не имеет.** Первая редакция отдавала
исполнителю решение «неверное объявление или неверная форма»; решение уже
принято и записано: [ADR 0017](../../../adr/0017-baseline-ceiling.md), пункт 5 —
проектно-нормализованный `coupling.class-rank` **намеренно** сделан occurrence-
каналом, потому что величина может сменить смысл при неизменном канале и дать
над-принятие в baseline. Канал остаётся occurrence и `judging` не объявляет; это
записывается в докблок, чтобы следующий читатель не переоткрывал вопрос.

## Пакеты работ

Порядок: П1 → П2 → П3 → П5, затем П4a → П4b. **П4b не параллелен**: он
добавляет импорты `MetricName`, а манифест ведёт точные импорты поимённо —
параллельно с П2 это дало бы два пакета на одном
`modular-architecture-manifest.json`. П4a параллелен чему угодно: он только
читает и пишет свой артефакт.

### П1 — снять `requires()` у правил

**Файлы:** `src/Analysis/Finding/Rule/RuleInterface.php`; 36 классов правил,
объявляющих `requires()` (`git grep -l "public function requires(): array" -- src`
даёт 46, из них 10 — коллекторы, их не трогать); 37 тестов в `tests/`.

**Не трогает:** `GlobalContextCollectorInterface`, `DerivedCollectorInterface` и
их реализации — там метод живой и потребляемый.

**Что теряется намеренно.** `requires()` перечислял и метрики, которые правило
читает для гейтинга, но не публикует (`LcomRule`, `WmcRule`,
`AbstractCodeSmellRule`), — `judging` их не несёт по определению, он называет
источник `metricValue`. Этот факт не исчезает, а переезжает в докблок правила
одной строкой; пакет обязан перенести его для каждого правила, где список
`requires()` был длиннее одного ключа, и назвать их число в отчёте.

**DoD:** `git grep -n "->requires()" -- src tests` возвращает только строки
коллекторов — **`tests` в grep обязателен**: метод объявляют и дублёры правил в
тестах, и набор пакета их включает; ни один класс правила не объявляет метод; `composer check:code` и
`composer architecture:check` зелёные. Пакет начинается с перепроверки
утверждения «у правил нет производственного потребителя»: нашёлся — возврат
оркестратору, план неверен.

### П2 — `JudgedMetrics`, фабрика `judging` и 22 объявления

**Файлы:** `src/Analysis/Finding/Contract/ChannelDeclaration.php`, новый
`JudgedMetrics` рядом с ним,
`src/Infrastructure/DependencyInjection/CompilerPass/ChannelDeclarationCompilerPass.php`,
**35 классов, объявляющих `channelDeclarations()`** (множество не совпадает с П1:
четыре из них `requires()` не объявляют — `AbstractTypeCoverageRule`,
`ConfigurationValidatorInterface`, `LayerDeclarationValidator`,
`InlineDirectiveValidator`), `tests/Analysis/Finding/Unit/ChannelDeclarationTest.php`.

**DoD:** пустой список метрик невыразим (проверяется сигнатурой, тест на арность);
объявление с несуществующим ключом отвергается сборкой; `judging` на форме
`occurrence` отвергается; число каналов с `judging` равно 22 и совпадает с TSV;
`composer check:code` зелёный. Строку манифеста, если она нужна, пакет **называет
в отчёте, а не вносит** — манифест принадлежит владельцу этапа.

### П3 — пришпилить объявление прогоном

**Файлы:** тест сноса уровней (найти по докблоку `ChannelDeclaration`), фикстуры.

**DoD:** подмена объявленного ключа на другую существующую метрику роняет тест
(проверяется руками, результат в отчёте); каналы вне покрытия перечислены
поимённо в докблоке теста с их числом; `composer check:code` зелёный.

### П5 — печатать пару там, где стоит читатель

**Файлы:** вывод `qmx rules`, сообщение об ошибке порога; набор страниц
задаётся командой, а не описанием — страницы, называющие любой из каналов с
`judging`, по `git grep -l` их кодам в `website/docs/`, EN и RU парами.

**DoD:** `bin/qmx rules` показывает судимую метрику у всех каналов с `judging`;
`composer check:docs` зелёный; `composer gate --reference=<коммит начала П5>` —
вывод `qmx rules` входит в сравниваемые поверхности, изменение объявляется.

### П4a — снять популяцию оптикой стража и классифицировать её

Первая редакция назвала десять файлов и предписала им одно лечение. Вторая
сняла предписание, но оставила популяцию, снятую **не тем методом**: «62 места в
10 файлах» получены счётом подстрок по тексту файла
(`str_contains($src, "'$code'")`), а страж читает токены
`T_CONSTANT_ENCAPSED_STRING` (`RuleIdentifierLiteralGuardTest.php:489-508`).
Множества не совпадают, и совпадение итогов это скрывало: по токенной оптике
`MetricHintCatalog.php` даёт **36** вхождений, а подстрочный счёт приписал ему
14; при этом три файла держат ключ в комментарии или докблоке
(`GlobalCollectorSorter.php:180`, `HealthContributor.php:18`,
`MetricDefinition.php:26`), где стража нет вовсе, а в
`ComputedMetricDefaults.php` значением литерала является вся формула целиком.

**Отсюда правило пакета: популяция снимается тем же читателем, что и у
механизма.** Скрипт переиспользует `stringLiterals()` стража и его вычисление
владельца, а не повторяет их своими словами.

**Работа:** получить множество мест и разложить каждое по тому, **что означает
строка**. Артефакт `enumeration-overlap-sites.tsv`: `file`, `line`, `literal`,
`meaning`, `cure`, `evidence`, и — как у остальных четырёх перечислений — блок
«чем получено и чего этот способ не видит». Затравка классов (проверить и
дополнить): `metric-read` — заменить константой; `rule-name` — не трогать, это
другой универсум (`RuleThresholdKeyGroupRegistry` держит имена правил, а не
ключи метрик); `format-field` — не трогать (`JsonFormatter.php:133`,
`JsonOffenderSection.php:117`); `dsl-string` — константа невыразима;
`declaration-site` — сам `MetricName.php`.

**DoD:** число строк артефакта равно тому, что вернул читатель стража, — **а не
числу из этого плана**; ни одной пустой ячейки; у каждой строки `evidence` с
путь:строка; блок «чем получено» присутствует; число мест каждого класса
названо в отчёте; названо расхождение с подстрочным счётом, если оно есть.

**Чем П4a может сдаться зелёным, не дав П4b пригодного входа, и что это
закрывает.** Классификацию судит тот же, кто её делает: неверная строка `cure`
выглядит как работа. Цена ошибки не локальна — `ALLOWED_FILES` пропускает
**файл целиком** (`RuleIdentifierLiteralGuardTest.php:158`), поэтому одна
неверная строка по `MetricHintCatalog` уводит из-под проверки все 36 его мест, и
оба пакета остаются зелёными. Поэтому:

- файл, где хоть одно место классифицировано как `metric-read`, разрешительной
  записи получить **не может** — он лечится, а не освобождается;
- разрешение допустимо только для файла, у которого *все* места неизлечимы, и
  пакет обязан это показать построчно;
- П4b проверяет каждую новую запись на обе стороны: мета-страж зелёный с ней и
  красный без неё.

### П4b — применить лечение и снять исключение стража

**Файлы:** те из десяти, которым П4a назначил лечение, плюс файл стража, плюс
манифест.

**Работа:** применить назначенное; снять `metricKeys()` и её вычитание из
`ownerByOwnedLiteral()`; для мест, где лечение невозможно, завести запись в
`ALLOWED_FILES` **с аргументом**, а не с упоминанием.

**Утверждение первой редакции «покрытие вернётся с 34 до 52 само» неверно.**
Возврат покрытия стоит новых разрешительных записей, и каждая обязана
зарабатываться `everyNamedFileStillEarnsItsEntry` — а этот мета-страж падает,
если разрешённый файл перестал держать чужой литерал. Пакет, добавивший запись,
обязан показать, что мета-страж на ней зелёный **и** краснеет при её удалении.

**DoD:** `metricKeys()` в файле стража отсутствует; страж и его мета-страж
зелёные; число кодов каналов под половиной владения равно 52 (печатается
скриптом, число в отчёте); `composer architecture:check` зелёный после правки
манифеста.

## Тестовый план

- Отказ сборки: несуществующий ключ метрики; `judging` у `occurrence`; пустой
  список (невыразим — проверяется тем, что код не компилируется/не типизируется).
- Снос: подменённый ключ роняет тест наблюдённого прогона.
- Округление и агрегация: `maintainability.index` и `size.class-count` проходят
  проверку, не будучи равными сырому значению базового ключа.
- Страж: файл, копирующий код канала чужой капабилити, краснеет — включая коды
  из бывшего пересечения; файл, читающий чужую **метрику** через константу,
  остаётся зелёным.
