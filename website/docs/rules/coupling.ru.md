# Правила связанности

Правила связанности измеряют, насколько тесно ваши классы зависят друг от друга. Когда классы тесно связаны, изменение одного класса может сломать множество других. Слабо связанный код легче тестировать (можно изолировать класс), легче изменять (меньше побочных эффектов) и легче переиспользовать.

Тот же анализ связанности классифицирует зависимости от настроенных framework-пространств имён для метрик `coupling.cbo-app` и `coupling.ce-framework`. Более поздний источник конфигурации заменяет предыдущий список пространств имён; явный пустой список отключает эту классификацию для запуска.

Представьте связанность как провода, соединяющие коробки. Чем больше проводов между двумя коробками, тем труднее передвинуть одну, не потревожив другую.

---

## CBO -- Связанность между объектами

**Rule ID:** `coupling.cbo`

**Судимые метрики:** `coupling.cbo`, `coupling.cbo-app`

<!-- llms:skip-begin -->
### Что измеряет

CBO считает общее количество **других классов, с которыми связан данный класс**. "Связь" означает либо:

- Этот класс **использует** другой класс (исходящая зависимость, называемая "эфферентная связанность" или Ce), либо
- Другой класс **использует** этот класс (входящая зависимость, называемая "афферентная связанность" или Ca)

CBO = |Ca ∪ Ce| (количество уникальных классов в объединении обоих множеств).

Например, если `UserService` использует `UserRepository`, `Logger`, `Validator` и `Mailer` (Ce = 4), а его используют `UserController` и `AdminController` (Ca = 2), то CBO = 6 (без пересечений).

**Как читать значение:**

| CBO    | Интерпретация                          |
| ------ | -------------------------------------- |
| 0--7   | Нормальная связанность                 |
| 8--14  | Умеренная                              |
| 15--20 | Высокая -- стоит уменьшить зависимости |
| 20+    | Очень высокая связанность              |

**На уровне пространства имён CBO считает пространства имён, а не классы.** CBO пространства имён -- это число различных пространств имён, в которых лежит класс на другой стороне зависимости, пересекающей границу этого пространства имён, в любом направлении. Граница -- всё поддерево пространства имён, та же область, по которой считаются его `coupling.ca` и `coupling.ce`, поэтому родительское пространство имён связано с тем, что лежит вне его, и никогда -- со своими вложенными пространствами имён. `coupling.ca` и `coupling.ce` на пространстве имён по-прежнему считают классы, поэтому CBO пространства имён обычно меньше каждой из них, и сообщение находки пишет его как `CBO: N namespaces`.

Другая сторона называется пространством имён, объявившим класс, поэтому число зависит от того, насколько мелко разбит окружающий код: разделение соседнего каталога на вложенные пространства имён поднимает CBO этого пространства имён при неизменных Ca и Ce. Родительское пространство имён у корня проекта связано со многими такими пространствами имён и обычно имеет самый высокий CBO. Пороги уровня пространства имён ниже повторяют числа уровня класса; для этой величины отдельно они не калибровались.

**Пространство имён судится по собственным классам.** Правило читает `coupling.cbo-own` -- тот же счёт, взятый по классам, объявленным непосредственно в пространстве имён, где вложенное пространство имён -- такое же пространство имён, как любое другое. У пространства имён без вложенных область одна, и оба ключа там равны. У родителя они расходятся, и значение по поддереву не судится: оно растёт вместе с поддеревом, а его область зависит от того, какие вложенные пространства имён есть в запуске, так что суженный и полный запуски разошлись бы в оценке одного и того же кода. Собственная область от этого не зависит, и вердикт тоже. Входящие и исходящие связи в сообщении находки -- тоже из собственной области (`coupling.ca-own`, `coupling.ce-own`). Пространство имён, не объявляющее ни одного собственного типа, не публикует `coupling.cbo-own` и не судится; `coupling.cbo` по поддереву публикуется на каждом пространстве имён (`--format=metrics`).

### Пример

```php
class ReportGenerator
{
    public function __construct(
        private UserRepository $userRepo,      // +1
        private OrderRepository $orderRepo,    // +1
        private ProductRepository $productRepo, // +1
        private Logger $logger,                // +1
        private CacheInterface $cache,         // +1
        private EventDispatcher $dispatcher,   // +1
        private TemplateEngine $templates,     // +1
        private PdfGenerator $pdf,             // +1
        private CsvExporter $csv,              // +1
        private EmailService $email,           // +1
        private TranslatorInterface $translator, // +1
        private ConfigProvider $config,        // +1
        private MetricsCollector $metrics,     // +1
        private SecurityChecker $security,     // +1
        private AuditLogger $audit,            // +1
    ) {}
    // Ce = 15, и если ничего не зависит от этого класса, CBO = 15 -> WARNING
}
```

<!-- llms:skip-begin -->
### Как исправить

- **Разделите класс.** Класс с 15+ зависимостями делает слишком много. Выделите группы связанных зависимостей в отдельные сервисы (например, `ReportDataProvider`, `ReportExporter`).
- **Используйте интерфейсы** вместо конкретных классов. Это не снижает CBO напрямую, но делает связанность слабее и гибче.
- **Применяйте внедрение зависимостей.** Избегайте создания зависимостей внутри класса через `new`. Внедряйте их через конструктор, чтобы их можно было заменить.
- **Рассмотрите паттерн Facade.** Оберните группы связанных сервисов за единым интерфейсом.

### Особенности реализации

Qualimetrix реализует **двунаправленную связанность** в соответствии с Chidamber & Kemerer (1994): CBO = |Ca ∪ Ce|, подсчитывая количество **уникальных** классов, которые появляются во входящих или исходящих зависимостях. Если класс A одновременно использует и используется классом B, B считается один раз (семантика объединения множеств), а не два.

- **Расширенные типы связанности:** Qualimetrix обнаруживает 14 типов связанности, выходя за рамки исходного определения C&K "методы или переменные экземпляра". Учитываются: создание экземпляров, вызовы статических методов, подсказки типов (параметры, типы возврата, свойства), блоки `catch`, проверки `instanceof`, константы классов, атрибуты, `extends`/`implements` и использование трейтов (`use`).
- **Union- и intersection-типы:** Каждый тип в union (`A|B`) или intersection (`A&B`) подсказке типа считается отдельной связью.
- **Само-ссылки исключены:** Обращения к `self`, `static` и `parent` внутри того же класса не считаются связанностью.
- **Встроенные PHP-классы исключены:** Зависимости от классов из дистрибутива PHP (php-src) исключаются из CBO, Ca и Ce — включая базовые классы (`Exception`, `DateTime`, `Closure`), SPL (`ArrayIterator`, `SplFileInfo`) и встроенные расширения (`PDO`, `DOMDocument`, `Random\Randomizer`, `CurlHandle` и др.). Связанность со стабильными PHP-типами не увеличивает архитектурный риск. Классы из PECL-расширений (например, `Redis`, `Memcached`, `MongoDB\Driver\Manager`) **не** исключаются и учитываются в CBO как обычные зависимости. Исключение не зависит от способа упоминания: `extends \RuntimeException` учитывается в CBO, Ca и Ce не больше, чем `implements \Countable` или подсказка типа `\DateTimeImmutable`. Само ребро `extends` сохраняется, потому что DIT и NOC читают из него наследование.

!!! info "Deviation from original spec"
    Вселенная графа включает каждый именованный класс, интерфейс, trait и enum
    проекта, даже если у него нет рёбер. CBO, Ca и Ce дедуплицируют логические
    endpoints и сохраняют необъявленные внешние цели; поэтому декларации с
    нулевой степенью получают известные нули вместо отсутствующих метрик.
    Логическая оценка класса проецируется на каждую точную принадлежащую
    декларацию, чтобы controls, baseline identities и fingerprints оставались
    независимыми.

### Настройка

```yaml
# qmx.yaml
rules:
  coupling.cbo:
    suppress_namespaces:
      - App\Core\ValueObject
    scope: application  # 'all' (по умолчанию) или 'application' (использует CBO_APP)
    class:
      warning: 18
      error: 25
    namespace:
      enabled: true
      min_class_count: 5
```

Сокращённая запись с `threshold` для одного уровня:

```yaml
rules:
  coupling.cbo:
    class:
      threshold: 18   # warning=18, error=18
```

```bash
bin/qmx check src/ --rule-opt="coupling.cbo:class.warning=18"
bin/qmx check src/ --rule-opt="coupling.cbo:class.error=25"
bin/qmx check src/ --rule-opt="coupling.cbo:namespace.min_class_count=5"
bin/qmx check src/ --rule-opt="coupling.cbo:namespace.enabled=false"
bin/qmx check src/ --rule-opt="coupling.cbo:scope=application"
```

**Плоский ярлык `threshold` (сразу для обоих уровней):** голый `threshold`
на верхнем уровне правила — НЕ вложенный в `class:`/`namespace:` — задаёт
`warning`/`error` одним и тем же значением сразу **на обоих** измерениях,
class и namespace. Это отличается от `complexity.ccn`, где верхний
`threshold` применяется только к уровню callable: у CBO дефолты class и
namespace уже совпадают (14/20), поэтому нет одного «основного» уровня,
которому стоило бы отдавать предпочтение.

```yaml
rules:
  coupling.cbo:
    threshold: 15   # class И namespace: warning=15, error=15
```

```bash
bin/qmx check src/ --rule-opt="coupling.cbo:threshold=15"
```

!!! warning "Плоский threshold побеждает вложенную секцию class:/namespace:"
    Если для `coupling.cbo` одновременно заданы и `threshold` на верхнем
    уровне, и вложенная секция `class:`/`namespace:`, побеждает плоский
    `threshold` целиком — вложенная секция игнорируется, а не сливается с
    ним. Используйте одну форму или другую, но не обе сразу для одного и
    того же правила.

**Верхнеуровневые `warning:` / `error:` — тоже опции этого правила.** В отличие
от правил сложности, `coupling.cbo` читает их на собственном верхнем уровне: они
открывают ту же плоскую форму, что и `threshold`, и задают оба измерения сразу.
Здесь они работали всегда; документируются сейчас потому, что необъявленный ключ
опции отвергается, а отвергать работающий ключ было бы неверно.

```yaml
rules:
  coupling.cbo:
    warning: 12     # class И namespace
    error: 18
```

### Разделение фреймворк/приложение

По умолчанию CBO считает **все** зависимости одинаково: импорт 50 типов `PhpParser\Node\*` весит столько же, сколько зависимость от 50 сервисов приложения. Но фреймворковая связанность — структурная (нельзя убрать без смены фреймворка), а прикладная — архитектурная (должна минимизироваться).

Qualimetrix предоставляет две дополнительные метрики:

| Метрика                 | Формула                                            | Назначение                    |
| ----------------------- | -------------------------------------------------- | ----------------------------- |
| `coupling.cbo-app`      | Ca_app + Ce_app (зависимости фреймворка исключены) | Только прикладная связанность |
| `coupling.ce-framework` | Количество исходящих зависимостей на фреймворк     | Информационная                |

**Настройка:**

```yaml
# qmx.yaml
coupling:
  framework-namespaces:
    - subtree: Symfony
    - subtree: PhpParser
    - subtree: Psr
    - subtree: Amp
```

Это явные namespace-селекторы. `subtree: Psr` совпадает с `Psr\Log\LoggerInterface`, но не с `PsrExtended\Custom`; также доступны `exact` и полнообъектный `regex`.

**Использование с правилом CBO:**

Установите `scope: application`, чтобы правило CBO проверяло `coupling.cbo-app` вместо `coupling.cbo`:

```yaml
rules:
  coupling.cbo:
    scope: application
    class:
      warning: 10   # более строгие пороги для прикладной связанности
      error: 15
```

Если `framework-namespaces` не указаны, `coupling.cbo-app` равен `coupling.cbo` (без эффекта).

## Непривязанный неймспейс фреймворка { #unmatched-framework-namespace }

**Rule ID:** `coupling.unmatched-framework-namespace`

**Severity:** warning (фиксированная)

### Что измеряет

Селектор из `framework-namespaces`, с которым не совпало ни одно имя прогона.

Селектор писали, чтобы вынести классы из `coupling.cbo-app` в
`coupling.ce-framework`. Промахнувшийся не выносит ничего, и любой вывод о
прикладной связанности делается по более широкому множеству, чем вы просили.
Больше об этом ничто в прогоне не говорит: промах даёт ровно тот же отчёт, что
и прогон вообще без селектора.

```
The framework namespace "Symfony\Bundle" matched no class the run analysed or
depends on. Nothing was moved out of the application scope for it, so
"coupling.cbo-app" still counts every class it was written to exclude and
"coupling.ce-framework" counts none of them.
```

Обычные причины: вендорный неймспейс переименовали; написали ведущий обратный
слэш (`\Symfony` не совпадает никогда — пишите неймспейс так, как он выглядит
в `use`); зависимость убрали при рефакторинге, а префикс остался в `qmx.yaml`.

Одна находка на каждый непривязанный селектор, на уровне проекта. Селектор
сверяется с обоими концами каждого ребра зависимостей — с целями, где живут
внешние классы фреймворка, и с источниками, — потому что именно это множество
классифицируют сами метрики.

### Когда молчит

- **`framework-namespaces` не заданы.** Ничего не утверждали — нечему и
  промахиваться.
- **Селектор совпал.** В том числе если он совпал только с вашими же
  анализируемыми классами: они всё равно выносятся из прикладной области, а это
  и есть действие опции.
- **Граф зависимостей прогона пуст.** Проверьте один файл, который ни от чего
  не зависит, — классифицировать было нечего, и верный общий `qmx.yaml` не
  получает находок из-за такого запуска.
- **Граф зависимостей не построен.** Тогда не с чем сверять, и прогон молчит,
  а не обвиняет разом все префиксы.

### Настройка

```yaml
rules:
  coupling.unmatched-framework-namespace:
    enabled: true   # по умолчанию
```

Это обычная находка правила, а не ошибка конфигурации: она подчиняется
`fail_on`, `--disable-rule=coupling.unmatched-framework-namespace`,
`@qmx-ignore coupling.unmatched-framework-namespace` и baseline. Общий
`qmx.yaml`, законно называющий фреймворк, которого в одном из репозиториев нет,
— тот самый случай, ради которого это не отказ.

## Нестабильность

**Rule ID:** `coupling.instability`

**Судимая метрика:** `coupling.instability`

<!-- llms:skip-begin -->
### Что измеряет

Нестабильность измеряет **направление зависимостей** класса или пространства имён. Она отвечает на вопрос: "Этот класс в основном зависит от других, или другие в основном зависят от него?"

Формула:

```
I = Ce / (Ca + Ce)
```

Где:

- **Ca (Афферентная связанность)** = сколько других классов зависят от ЭТОГО класса (входящие)
- **Ce (Эфферентная связанность)** = от скольких классов зависит ЭТОТ класс (исходящие)

Результат -- число от 0.0 до 1.0:

- **I = 0.0 (максимально стабильный)** -- много классов зависят от этого, но он ни от чего не зависит. Как фундамент: его нельзя подвинуть, не сломав всё, что сверху. Стабильные классы должны быть абстрактными (интерфейсы, абстрактные классы), чтобы от них было безопасно зависеть.
- **I = 1.0 (максимально нестабильный)** -- класс зависит от многих, но никто не зависит от него. Как лист на дереве: легко изменить, не затронув ничего. Конкретные реализации обычно должны быть нестабильными.

**Как читать значение:**

| I (Instability) | Интерпретация                                                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 0.0             | Максимально стабильный -- или вовсе не связанный: при Ca = Ce = 0 отношение не определено и по соглашению сообщается как 0 |
| 0.0--0.3        | Стабильный -- много зависимых классов                                                                                      |
| 0.3--0.7        | Сбалансированный                                                                                                           |
| 0.7--1.0        | Нестабильный -- легко менять                                                                                               |
| 1.0             | Максимально нестабильный                                                                                                   |

!!! note "Почему высокая нестабильность -- это плохо?"
    Нестабильность близкая к 1.0 означает, что у класса много исходящих зависимостей и никто от него не зависит. Хотя это звучит как "свобода для изменений," это также означает, что класс очень чувствителен к изменениям в его зависимостях. Если любая из зависимостей изменится, этот класс может сломаться.

<!-- llms:skip-end -->

### Пример

```php
// Сильно нестабильный класс (I = 1.0): зависит от 5 вещей, никто не зависит от него
class DailyReportJob
{
    public function __construct(
        private UserRepository $users,
        private ReportGenerator $generator,
        private EmailService $email,
        private Logger $logger,
        private Clock $clock,
    ) {}
    // Ca = 0 (ничто не зависит от этого)
    // Ce = 5 (зависит от 5 классов)
    // I = 5 / (0 + 5) = 1.0 -> ERROR
}
```

<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Как исправить

- **Сокращайте исходящие зависимости.** Меньше `use` и параметров конструктора означает меньше Ce.
- **Вводите абстракции.** Если класс -- сервис, который могут использовать другие, выделите интерфейс. Это увеличивает Ca (другие классы будут зависеть от интерфейса) и снижает I.
- **Принимайте нестабильность, когда она оправдана.** Точки входа -- консольные команды, контроллеры, cron-задачи -- естественно нестабильны (высокий Ce, низкий Ca). Рассмотрите отключение правила для них или повышение порога.

!!! info "Deviation from original spec"
    Robert C. Martin (1994) изначально определял Instability только на уровне **пакетов** (пространств имён). Qualimetrix расширяет её на уровень классов для более детального анализа. Instability на уровне пространств имён — каноническая метрика по спецификации Martin; на уровне классов — расширение Qualimetrix.

<!-- llms:skip-end -->

### Настройка

```yaml
# qmx.yaml
rules:
  coupling.instability:
    suppress_namespaces:
      - App\Core\ValueObject
    class:
      max_warning: 0.9
      max_error: 1.0
      min_afferent: 1    # по умолчанию: 1
    namespace:
      min_class_count: 5
      min_afferent: 1    # по умолчанию: 1
```

**`min_afferent`** -- минимальное афферентное сцепление (Ca), необходимое для проверки класса или пространства имён. По умолчанию: `1` (символы с Ca = 0 пропускаются). Установите `0`, чтобы проверять все символы, или `2`, чтобы также пропускать символы с единственным зависимым. Символы с малым числом зависимых имеют высокую нестабильность по определению, что архитектурно ожидаемо для конкретных классов-реализаций.

Сокращённая запись с `threshold` для одного уровня:

```yaml
rules:
  coupling.instability:
    class:
      threshold: 0.9   # warning=0.9, error=0.9
```

```bash
bin/qmx check src/ --rule-opt="coupling.instability:class.max_warning=0.9"
bin/qmx check src/ --rule-opt="coupling.instability:class.max_error=1.0"
bin/qmx check src/ --rule-opt="coupling.instability:class.min_afferent=0"
bin/qmx check src/ --rule-opt="coupling.instability:namespace.min_class_count=5"
bin/qmx check src/ --rule-opt="coupling.instability:namespace.min_afferent=2"
```

**Плоский ярлык `threshold` (сразу для обоих уровней):** голый `threshold`
на верхнем уровне правила — НЕ вложенный в `class:`/`namespace:` — задаёт
`max_warning`/`max_error` одним и тем же значением сразу **на обоих**
измерениях, поскольку их дефолты уже совпадают (0.8/0.95).

```yaml
rules:
  coupling.instability:
    threshold: 0.9   # class И namespace: warning=0.9, error=0.9
```

```bash
bin/qmx check src/ --rule-opt="coupling.instability:threshold=0.9"
```

!!! warning "Плоский threshold побеждает вложенную секцию class:/namespace:"
    Правило то же, что и у `coupling.cbo` выше: если верхнеуровневый
    `threshold` и вложенная секция `class:`/`namespace:` заданы
    одновременно, плоский `threshold` побеждает целиком, а не сливается со
    вложенной секцией.

**Верхнеуровневые `max_warning:` / `max_error:` — тоже опции этого правила.**
Как и `warning`/`error` у `coupling.cbo`, они открывают плоскую форму на
собственном верхнем уровне правила и задают оба измерения сразу. Здесь они
работали всегда и документируются сейчас по той же причине.

```yaml
rules:
  coupling.instability:
    max_warning: 0.85   # class И namespace
    max_error: 0.95
```

## Расстояние от главной последовательности { #distance-from-main-sequence }

**Rule ID:** `coupling.distance`

**Судимая метрика:** `coupling.distance`

<!-- llms:skip-begin -->
### Что измеряет

Это правило проверяет **баланс между абстрактностью и стабильностью** пространства имён (группы классов). Оно основано на идее:

- **Стабильные пакеты должны быть абстрактными.** Если от вашего пакета зависят многие классы, он должен состоять из интерфейсов и абстрактных классов. Тогда при необходимости изменить поведение вы добавляете новую реализацию, а не модифицируете то, от чего зависят другие.
- **Нестабильные пакеты должны быть конкретными.** Если ваш пакет зависит от многих, но ничто не зависит от него, он должен содержать конкретные реализации. Нет смысла делать его абстрактным, если никто не будет реализовывать эти абстракции.

Формула:

```
D = |A + I - 1|
```

Где:

- **A (Абстрактность)** = `(абстрактные классы + интерфейсы) / (классы + трейты + интерфейсы + енумы, реализующие интерфейс)` в пространстве имён (0.0 = все конкретные, 1.0 = все абстрактные)
- **I (Нестабильность)** = метрика нестабильности, описанная выше

Результат -- число от 0.0 до 1.0:

- **D = 0.0** -- пространство имён находится на "главной последовательности," что означает сбалансированное сочетание абстрактности и стабильности.
- **D = 1.0** -- пространство имён далеко от идеального баланса.

Есть две проблемные зоны:

- **Зона боли** (внизу слева): стабильный + конкретный. От пакета зависят многие классы, но весь код конкретный. Любое изменение расходится волной. Решение: добавить интерфейсы.
- **Зона бесполезности** (вверху справа): нестабильный + абстрактный. Пакет полон абстракций, которые никто не реализует. Мёртвый груз.

**Как читать значение:**

| Distance | Интерпретация                            |
| -------- | ---------------------------------------- |
| 0.0--0.1 | На главной последовательности            |
| 0.1--0.3 | Приемлемый баланс                        |
| 0.3+     | Дисбаланс -- зона боли или бесполезности |

!!! info "Deviation from original spec"
    Robert C. Martin (1994) определял Abstractness только через абстрактные и
    конкретные классы, поэтому каждый появившийся позже конструкт PHP приходится
    отображать на эту модель. Qualimetrix считает **голый енум нейтральным** и
    полностью исключает его из знаменателя, а не относит к конкретике:
    перечисление литералов не даёт ни одной точки подстановки -- его нельзя
    расширить, у него не бывает подтипов и реализаций. **`enum X implements Y`
    считается конкретным** и остаётся в знаменателе: это конкретная реализация
    объявленного контракта, и без этой оговорки пространство имён с одним
    интерфейсом и N реализующими его енумами показывало бы `A = 1.0`, хотя
    реализации лежат рядом. Учитываются только явные `implements`; интерфейсы
    `UnitEnum` / `BackedEnum`, которым удовлетворяет любой енум, не учитываются.
    Форма формулы не меняется -- это адаптация скоупа под реалии PHP, а не другая
    метрика. Пространство имён, где объявлены только голые енумы, имеет пустой
    знаменатель и сохраняет прежний результат для случая «нет типов» -- `A = 0.0`;
    такие пространства имён и так пропускаются по `minClassCount`.

<!-- llms:skip-end -->

### Две области у пространства имён и проектное число

Пространство имён, которое одновременно объявляет собственные классы и содержит
вложенные пространства имён, имеет две области связанности, и публикуются обе:

| Ключ                                                                                                                       | Область                                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `coupling.ca` / `coupling.ce` / `coupling.instability` / `coupling.abstractness` / `coupling.distance`                     | Всё поддерево с корнем в этом пространстве имён — величина, которую судит правило и которую показывает отчёт уровня пространства имён |
| `coupling.ca-own` / `coupling.ce-own` / `coupling.instability-own` / `coupling.abstractness-own` / `coupling.distance-own` | Только типы, объявленные непосредственно здесь; те, что держат вложенные пространства имён, остаются за ними                          |

`coupling.cbo` и `coupling.cbo-own` делятся так же, но здесь правило судит
собственную область: см. [CBO](#cbo----связанность-между-объектами).

У пространства имён без вложенных областей обе совпадают. Пространство имён, не
объявляющее ни одного собственного типа, вовсе не несёт собственной
абстрактности и не получает ключей `-own` для абстрактности и distance:
насколько пакет удалён от главной последовательности — вопрос, не определённый
там, где пакета нет, и молчание говорит это, а `0.0` не сказал бы.

**Проектное число сворачивается по собственным областям.**
`coupling.distance-own.avg` — невзвешенное среднее `coupling.distance-own` по
всем пространствам имён, которые её публикуют; проектный ключ называется
`coupling.distance-own.avg`, а `coupling.distance.avg` не существует. Свёртка
роллапов поддерева считала бы объявления родителя один раз за родителя и ещё по
разу за каждого ребёнка. Прежняя свёртка избегала этого двойного счёта, беря
только листовые пространства имён, — и тем самым выбрасывала каждое родительское
пространство имён с собственными классами: в дереве, где промежуточные
пространства имён держат настоящий код, изрядная доля классов не была
представлена в проектном среднем ни одним значением.

Популяция, по которой идёт свёртка, — это же и то, долей чего является строка
покрытия здоровья; см. [Что именно покрывает оценка](../reference/health-scores.ru.md#what-a-score-covers).

<!-- llms:skip-begin -->
### Пороговые значения

| Уровень | Порог  | Серьёзность |
| ------- | ------ | ----------- |
| Warning | >= 0.3 | Warning     |
| Error   | >= 0.5 | Error       |

Правило судит величину поддерева `coupling.distance`, а не `coupling.distance-own`.

Анализируются только пространства имён с минимум 3 классами (настраивается через `minClassCount`).

Пространство имён без зависимостей в обе стороны (Ca = Ce = 0) тоже не судится. Его нестабильность равна 0 по соглашению, а не по измерению, поэтому конкретное пространство имён, которое никто не использует и которое ничего не использует, получило бы D = 1.0 и было бы названо зоной боли -- а она требует многих зависимых, которых у него нет. Значение по-прежнему публикуется и входит в `health.coupling`.

Пространство имён, которому не хватает входа, не публикует расстояние вовсе, а не считает его от 0. Пространство имён, объявляющее только функции, не входит в граф зависимостей классов, поэтому у него нет нестабильности и нет `coupling.distance`.
<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Пример

Рассмотрим пространство имён `App\Payment` с 10 классами:

- 0 интерфейсов или абстрактных классов (A = 0.0)
- Много входящих зависимостей из других модулей (I = 0.2, довольно стабильный)
- D = |0.0 + 0.2 - 1| = 0.8 -- далеко от главной последовательности (Error)

Это пространство имён в **Зоне боли**: оно стабильно (трудно изменить, не сломав других), но не имеет абстракций (каждое изменение требует модификации конкретного кода).

<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Как исправить

- **Для пакетов в Зоне боли:** Добавьте интерфейсы. Выделите контракты, от которых могут зависеть другие модули, оставив реализации как детали.
- **Для пакетов в Зоне бесполезности:** Удалите неиспользуемые абстракции или сделайте их конкретными. Абстрактные классы, которые никто не расширяет -- это накладные расходы.
- **Стремитесь к главной последовательности:** Стабильные пакеты должны быть абстрактными; нестабильные -- конкретными.

<!-- llms:skip-end -->

### Настройка

```yaml
# qmx.yaml
rules:
  coupling.distance:
    max_distance_warning: 0.4
    max_distance_error: 0.6
    min_class_count: 5
    include_namespaces:
      - subtree: App\Domain
      - subtree: App\Infrastructure
    suppress_namespaces:
      - subtree: App\Tests
```

Сокращённая запись с `threshold`:

```yaml
rules:
  coupling.distance:
    threshold: 0.4   # warning=0.4, error=0.4
```

```bash
bin/qmx check src/ --rule-opt="coupling.distance:max_distance_warning=0.4"
bin/qmx check src/ --rule-opt="coupling.distance:max_distance_error=0.6"
bin/qmx check src/ --rule-opt="coupling.distance:min_class_count=5"
```

**`min_class_count`** — минимальное число классов в пространстве имён, при
котором оно вообще проверяется. По умолчанию `3`, сравнение строгое: пространство
из одного или двух классов пропускается и не сообщает ничего, как бы далеко от
главной последовательности оно ни находилось. Пространство из двух классов с
D = 1.00 и сбалансированное выглядят в отчёте одинаково, потому что тишина здесь
означает «не измерено», а не «чисто». Ограничение существует потому, что A и I —
доли: на горстке классов перемещение одного класса бросает D через весь диапазон.
Значение `0` включает проверку для каждого пространства имён. Следствие для
рефакторинга: дробление каталога на меньшие пространства имён может включить это
правило для частей, причём сообщать оно начинает с третьего класса, а не со
второго.

По умолчанию пространства имён проекта автоматически определяются из `composer.json` (`autoload.psr-4`).

`include_namespaces` — список явных namespace-селекторов `exact`, `subtree`
или `regex`; bare scalar отвергается. Универсальная дверь `--rule-opt`
использует ту же scalar-форму `kind:value`, поэтому
`--rule-opt="coupling.distance:include_namespaces=subtree:App\Domain"` выбирает
это поддерево; несколько селекторов пишутся списком в `qmx.yaml`.

## ClassRank

**Rule ID:** `coupling.class-rank`

<!-- llms:skip-begin -->
### Что измеряет

ClassRank использует алгоритм **PageRank на графе зависимостей** для определения наиболее "важных" классов в кодовой базе. Принцип работы: если A зависит от B, это означает, что A "голосует" за B. Классы с большим количеством зависящих от них (или с важными зависимыми) получают более высокий ранг.

Высокий ClassRank означает, что класс является критическим узлом -- изменения в нём имеют широкое влияние на всю систему.

**Как читать значение:**

| ClassRank  | Интерпретация                                 |
| ---------- | --------------------------------------------- |
| Ниже 0.01  | Периферийный класс                            |
| 0.01--0.02 | Умеренная важность                            |
| 0.02--0.05 | Важный узел -- изменения имеют широкий эффект |
| 0.05+      | Критическая точка связанности                 |

<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Пороговые значения

| Уровень | Порог   | Серьёзность |
| ------- | ------- | ----------- |
| Warning | >= 0.02 | Warning     |
| Error   | >= 0.05 | Error       |

Оба порога делятся на коэффициент размера проекта, описанный в особенностях реализации. Класс, от которого не зависит ни один другой класс (`coupling.ca` = 0), не сообщается никогда, каким бы ни был его ранг: он не хаб, а на маленьком проекте минимальный ранг, который получает каждый класс, может сам по себе превысить масштабированный порог.
<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Пример

```php
// Этот класс используется (прямо или косвенно) большей частью проекта
class DatabaseConnection
{
    public function query(string $sql, array $params = []): Result { /* ... */ }
    public function beginTransaction(): void { /* ... */ }
    public function commit(): void { /* ... */ }
    public function rollback(): void { /* ... */ }
}

// UserRepository зависит от DatabaseConnection -> голосует за него
// OrderRepository зависит от DatabaseConnection -> голосует за него
// PaymentService зависит от DatabaseConnection -> голосует за него
// ReportGenerator зависит от DatabaseConnection -> голосует за него
// AuditLogger зависит от DatabaseConnection -> голосует за него
//
// Если эти зависимые классы сами важны (имеют высокий ранг),
// ClassRank DatabaseConnection растёт ещё сильнее.
// ClassRank = 0.06 -> ERROR (против порога, отмасштабированного по числу классов проекта)
```

<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Как исправить

- **Извлеките интерфейс.** Создайте `DatabaseConnectionInterface` и зависьте от него. Это применяет принцип инверсии зависимостей: модули высокого уровня зависят от абстракций, а не от конкретных классов.
- **Разделите ответственности god-класса.** Если класс делает слишком много, разбейте его. Например, разделите `DatabaseConnection` на `QueryExecutor`, `TransactionManager` и т. д.
- **Снизьте транзитивную важность.** Если зависимые от этого класса сами являются узлами, рефакторинг их в сторону абстракций снизит и ClassRank этого класса.

<!-- llms:skip-end -->

<!-- llms:skip-begin -->
### Особенности реализации

- **Алгоритм PageRank** с коэффициентом демпфирования 0.85 и максимумом 100 итераций. Сходимость определяется порогом epsilon = 1e-6.
- **Ранги суммируются до 1.0** -- каждый ранг представляет долю "важности" класса в общем графе.
- **Vendor-классы исключены** -- анализируются только классы проекта (присутствующие в репозитории метрик).
- **Dangling-узлы** (классы без исходящих зависимостей внутри проекта) распределяют свой вес равномерно между всеми узлами -- так сумма и остаётся равной 1.0. Поэтому каждый класс получает не меньше `(1 - d) / N + d · S / N`, где `d` -- коэффициент демпфирования, `N` -- число классов, `S` -- суммарный ранг dangling-классов. Изолированный класс (без входящих и исходящих зависимостей) получает ровно этот минимум, а не `(1 - d) / N`: в проекте совсем без зависимостей все классы dangling, `S = 1`, и ранг каждого -- `1 / N`. Минимум растёт с долей dangling-классов, поэтому правило не сообщает класс, от которого никто не зависит.
- **Масштабирование sqrt для размера проекта:** Поскольку ранги суммируются до 1.0, индивидуальные значения ClassRank естественно уменьшаются с ростом количества классов (эффект разбавления). Для сохранения осмысленности порогов при разных размерах проекта Qualimetrix применяет масштабирующий коэффициент `sqrt(classCount / 100)`: оба порога делятся на него, поэтому они остаются неизменными для проекта из 100 классов, ниже для более крупных проектов (где каждый ранг разбавлен) и выше для меньших.

Каждая вершина графа — логический класс. Его единственная оценка ClassRank
проецируется на каждую точную декларацию этого логического класса: оценка и
граф остаются логическими, а controls, findings, baseline identity и
fingerprints — declaration-scoped.

<!-- llms:skip-end -->

### Настройка

```yaml
# qmx.yaml
rules:

    warning: 0.03
```
