## Кандидаты в control

- `tests/Analysis/Evidence/CodeSmell/Unit/DebugCodeDocumentationConsistencyTest.php` — сверяет `DebugCodeRule::SEVERITY` с текстом `website/docs/rules/code-smell.md` регэкспом; не выполняет ни строчки продуктового поведения.
- `tests/Analysis/Evidence/CodeSmell/Integration/CodeSmellRuleContractTest.php` (первый метод, `itRequiresEverySubclassToDeclareMandatoryConstants` / `itMakesTheDirectoryScanAgreeWithTheRuleRegistry`) — рефлексия-скан директории `src/Analysis/Evidence/CodeSmell/*Rule.php` ради инварианта раскладки/контракта. Второй метод файла — полноценный integration-тест (поднимает DI-контейнер), поэтому控-часть смешана с обычной в одном классе, а не вынесена отдельно.

Из Security и Complexity ни один файл не тестирует состояние репозитория, доку или сгенерированные артефакты;
`SecurityPatternFindingTest::itKeepsTheApprovedInternalSurfaceClosed` рефлексией проверяет ровно один класс
(`SecurityPatternFinding`), это не control/control-invariant по определению задания (снимается не со ВСЕХ
классов `src/`), а точечный architecture-pin — оставлен как `unit`.

## Дубли и противоречия

1. **CognitiveComplexityCollectorTest ↔ CognitiveComplexityVisitorTest** (Complexity). Оба гоняют один и тот
   же PHP-код через один и тот же движок (`CognitiveComplexityVisitor` внутри `NodeTraverser`), различаясь
   только точкой входа (через `Collector::collect()` vs напрямую через visitor). Кейсы `single if`/`if-else`/
   `nested if`/`and chain`/`switch`/`ternary`/`null coalescing`/`try-catch`/`recursion` в data-provider'е
   `CognitiveComplexityVisitorTest::provideComplexityCases` буквально повторяют одноимённые именованные тесты
   `CognitiveComplexityCollectorTest` (`itCountsSingleIfAsOnePoint`, `itCountsNestedIfWithNestingBonus`,
   `itCountsLogicalOperators`, `itCountsSwitchAsOnePoint`, `itCountsEachCatchClause`, `itCountsTernaryAsOnePoint`,
   `itCountsNullCoalescingAsOnePoint`, `itCountsRecursiveCall`) — те же входные сниппеты, те же ожидаемые
   значения. Аналог CyclomaticComplexity этой проблемы не имеет: там `CyclomaticComplexityVisitorTest` проверяет
   совсем другой аспект (scoping/metadata через `VisitorMethodContext`, всего 3 теста), а не decision-point
   подсчёт — вся decision-point матрица живёт только в `CyclomaticComplexityCollectorTest`. Отсюда видно, что
   расхождение — не системный стиль проекта, а конкретная избыточность именно в паре Cognitive-файлов.

2. **WmcIntegrationTest: тесты 1/2/4 внутри одного файла** (Complexity). `itMakesWmcMetricAvailableAfterAggregation`,
   `itVerifiesWmcEqualsCcnSum` и `itComputesWmcForMultipleClasses` конструируют разные наборы методов/классов,
   но проверяют один и тот же факт: `complexity.wmc` класса равен сумме `complexity.ccn` его методов. Тест 3
   (`itHandlesClassWithoutMethodsGracefully`) — единственный, проверяющий действительно другой угол (пустой
   класс).

3. **LongParameterListVoPropagationTest ↔ LongParameterListRuleTest (VO-секция) ↔ ParameterCountCollectorTest**
   (CodeSmell). Все три покрывают один и тот же исторический баг — флаг `isVoConstructor` не пробрасывался через
   `getCallablesWithMetrics()` в `LongParameterListRule`. Сценарии (VO ниже порога / VO warning / non-VO на
   обычных порогах) структурно совпадают на трёх уровнях глубины (реальный AST / стаб MetricBag / чистый
   collector-output) без явной ссылки друг на друга — читателю не очевидно, что это один и тот же регрессионный
   сюжет, размазанный по трём файлам.

4. **EvalRuleTest::itReportsAnErrorForEachEvalUsage ↔ CodeSmellLinePrecisionTest::itCreatesASingleFindingWithTheCorrectLineForASingleOccurrence**
   (CodeSmell). Оба проверяют один finding, error severity, конкретную строку для `eval()`; разница — источник
   входа (стаб vs реальный парсер). Частичное, не полное пересечение.

5. **IdenticalSubExpressionCollectorTest ↔ IdenticalSubExpressionVisitorTest** (CodeSmell) — не дубль, а
   неверное распределение: файл, названный по имени коллектора, содержит один тривиальный тест
   (`itDeliberatelyDoesNotProvideCallableMetrics`), тогда как реальные тесты коллектора
   (`itIntegratesWithCollectorCorrectly`, `itProducesNoCollectorFindingsForCleanCode`, `itReturnsCollectorName`,
   `itProvidesExpectedMetricKeys`) находятся в файле `*VisitorTest` под чужим `#[CoversClass]`.

6. **CredentialLiteralsTest ↔ HardcodedCredentialsVisitorTest** (Security). Классификационная семантика
   (`SensitiveNameMatcher` + форма значения → `CredentialLocation`) проверена дважды: сначала на голых
   AST-узлах (`CredentialLiterals::locations()` напрямую), затем через полный парсер+traverser+visitor, который
   является тонкой обёрткой над той же `CredentialLiterals` (`HardcodedCredentialsVisitor.php:40`). ~15 из ~30
   кейсов `provideDetectionCases` повторяют кейсы `CredentialLiteralsTest` почти дословно ("password hash",
   "token storage", "cache key", "bare token/key", "option password constant", dot-notation). Обоснованный
   остаток у Visitor-теста — только wiring (declaration index, reset, subject-присвоение).

7. **SensitiveNameMatcherTest ↔ (CredentialLiteralsTest, HardcodedCredentialsVisitorTest)** (Security) —
   non-sensitive набор имён (`passwordHash`, `tokenStorage`, `cacheKey`, bare `token`/`key`, `OPTION_PASSWORD`)
   протестирован на уровне матчера, а затем повторно обёрнут в полные объявления и заново прогнан как отдельные
   сценарии ещё в двух файлах — легитимная тестовая пирамида, но с большим объёмом копипасты входных данных.

8. **SqlInjectionDetectorTest / XssDetectorTest / CommandInjectionDetectorTest ↔ SecurityPatternVisitorTest**
   (Security) — крупнейший дубль в срезе. `SecurityPatternVisitor` — документированный тонкий диспетчер поверх
   трёх Detector-классов. `provideSqlInjectionCases`/`provideXssCases`/`provideCommandInjectionCases` в
   `SecurityPatternVisitorTest` воспроизводят 30+ сценариев один-в-один с тремя `*DetectorTest`
   ("$_SESSION not dangerous", "exec with escapeshellarg", "concat with SELECT",
   "echo htmlspecialchars", int-cast сценарии и т.д.), различаясь лишь тем, что код теперь парсится, а не
   строится вручную. Оправданный остаток у Visitor-теста — собственно диспетчерская логика
   (`itGetsLocationsByType`, `itResetsClearsState`, отсутствие двойного счёта вложенного `Concat` через
   `concatDepth`).

Не найдено (не дефект, а системный, осознанно задокументированный паттерн, не заслуживающий отдельной строки
дефекта в таблице): восемь rule-тестов в CodeSmell (`BooleanArgumentRuleTest`, `EvalRuleTest`, `ExitRuleTest`,
`GotoRuleTest`, `EmptyCatchRuleTest`, `DebugCodeRuleTest`, `CountInLoopRuleTest`, `SuperglobalsRuleTest`)
повторяют один и тот же паттерн `itKeysOccurrenceToItsOwnSmellType` с одинаковым поясняющим комментарием —
каждый пинит литерал своего `SMELL_TYPE`, что и есть цель паттерна (анти-тавтология против случайного
копирования константы). Аналогично три *RuleTest в Security (`CommandInjectionRuleTest`, `SqlInjectionRuleTest`,
`XssRuleTest`) и три *RuleTest в Complexity (`ComplexityRuleTest`, `CognitiveComplexityRuleTest`,
`NpathComplexityRuleTest`) структурно идентичны друг другу — но SUT в каждом свой (разные Rule-классы),
это ожидаемая форма для правил, реализующих общий контракт, а не копипаста одного и того же утверждения.

Найдено противоречий (два теста утверждают несовместимое про одно и то же поведение) — ни одного.
Нарушений CLAUDE.md §9 (testXxx / без `#[Test]` / голая глагольная фраза) — ни одного во всех 70 файлах.

## Чем проверено и чего этот способ не видит

- **Полнота чтения.** CodeSmell (38 файлов) и Security (18 файлов) прочитаны полностью двумя параллельными
  субагентами, каждый читал файл целиком инструментом Read, а не грепом; проверка §9 и SUT — по факту
  прочитанного кода (импорты + что реально инстанцируется), а не по имени файла. Complexity (14 файлов)
  прочитан мной: часть файлов (`WmcIntegrationTest`, `*OptionsTest`, `ComplexityRuleTest`, `WmcRuleTest`,
  `NpathExpressionCalculatorTest`) — целиком; часть крупных файлов (`CognitiveComplexityCollectorTest`,
  `CognitiveComplexityVisitorTest`, `CyclomaticComplexityCollectorTest`, `CyclomaticComplexityVisitorTest`,
  `NpathComplexityCollectorTest`, `NpathComplexityRuleTest`) — через список `grep`-ом извлечённых имён методов
  и `use`-импортов плюс выборочное глубокое чтение конкретных секций (там, где список имён намекал на
  дублирование или control-подозрение). Это значит: для крупных Complexity-файлов таблица дефектов опирается
  на сверку ИМЁН тестов и структуры data-provider'ов, а не построчное чтение каждого assert. Для
  `CognitiveComplexityCollectorTest`/`CognitiveComplexityVisitorTest` дубль подтверждён прямым сравнением кода
  (не только имён) — там я прочитал оба фрагмента целиком. Для `CyclomaticComplexityCollectorTest`,
  `NpathComplexityCollectorTest`, `NpathComplexityRuleTest` вывод "нет дублей между файлами" базируется на
  списке имён методов + отсутствии одноимённого "сестринского" Visitor/Collector файла — риск пропустить
  внутрифайловую избыточность (несколько тестов внутри ОДНОГО файла, покрывающих один и тот же кейс) в этих
  трёх файлах выше, чем в файлах, прочитанных целиком.
- **SUT определялся по импортам и по факту инстанцирования**, а не по имени файла — там, где это разошлось
  (`IdenticalSubExpressionCollectorTest`, `WmcIntegrationTest`), это явно названо дефектом или уточнением места.
- **Не запускался ни один тест и ни один статический анализатор** (по прямому запрету брифа) — все выводы о
  поведении опираются на чтение кода теста и (где нужно было установить формулу) — на чтение соответствующего
  класса в `src/`. Следствие: если тест на самом деле падает или всегда проходит из-за бага в самом тесте
  (например, недостижимый assert, неверно расставленный mock-ожидание), этот аудит такое не поймает — только
  PHPUnit-прогон с покрытием мог бы это показать.
- **Понятие "дубль" в этом отчёте — эвристическое**: сравнивались входные PHP-сниппеты/значения и итоговые
  assert'ы по смыслу, а не побайтово. Часть отмеченных "дублей" технически проверяет разные уровни абстракции
  (стаб MetricBag vs реальный AST, голые AST-узлы vs полный traversal) — это осознанно НЕ приравнено к
  тавтологии (описано отдельно), но экономически это всё равно повторный прогон одного и того же продуктового
  вывода, что и просил искать бриф.
- **Не проверялась историческая git-связь** (кто, когда и зачем добавил каждый тест) — некоторые пересечения
  могут быть намеренным регрессионным дублированием после конкретного инцидента (см. докблоки-объяснения типа
  "Regression: ..." в ряде файлов Complexity/CodeSmell) — там, где такой докблок был явно виден, это учтено
  при классификации (не помечено как случайная копипаста).
- **Оценка "правильного каталога"** опиралась на сопоставление namespace теста с деревом `src/Analysis/Evidence/
  {CodeSmell,Security,Complexity}/`, а не на полный обход соседних доменов (`Policy/Inline`, `Run`) — для
  `NamespaceExclusionOccurrenceTest` и `PropertyHookControlPrecedenceTest` названо "не тот домен", но точный
  целевой каталог внутри `Policy/Inline`/`Run` не проверен структурно (только по духу теста).

## Допущения

- Разделение unit/integration/functional/control следовало определению из брифа буквально: наличие реального
  `NodeTraverser`+`Parser` без DI-контейнера классифицировано как `unit`, если проверяется поведение одного
  явного SUT-класса (даже когда парсер и visitor реальны) — это соответствует практике проекта (`CoversClass`
  на одном/двух классах). Файлы, где Collector оборачивает Visitor и тестируется их совместная работа с
  `DeclarationRegistrarFactory`, размечены как `integration`, т.к. это минимум два кооперирующих класса с
  разделяемым состоянием (declaration index).
- `CodeSmellRuleContractTest.php` размечен смешанно (`control-invariant` + `integration` в одном файле) вместо
  выбора одной категории на файл — брифом это не запрещено (категория даётся "по файлу", но файл внутри
  неоднороден), решение по объединению или разделению файла оставляю владельцу.
- Для `Unit/RepeatedConditionsTest.php`/`Unit/RepeatedExpressionsTest.php` (тонкое покрытие, один-два теста)
  не считаю дефектом само по себе — VO выглядит как узкий делегат, а не как недотестированная логика; итоговое
  решение о достаточности покрытия — за владельцем.
- Строки "Дефекты" в таблице для файлов без find явных проблем помечены "нет" — это означает "не найдено
  дубля/тавтологии/противоречия/нарушения §9/лжи в имени", а не "тест идеален по составу кейсов" — полнота
  покрытия домена (все ли важные кейсы предусмотрены) вне периметра этого аудита.
- Директории `Integration`/`Unit` в самих тестах совпадают с категорией лишь частично: несколько файлов лежат
  в `Unit/`, но по факту используют реальный `Parser`+`NodeTraverser`+`DeclarationRegistrarFactory` (то есть
  по моей категоризации — `integration`); это несоответствие имени каталога и категории не считаю дефектом
  "места" в смысле брифа (предметная папка верна — `Security`/`CodeSmell`/`Complexity`), только сама метка
  `Unit` vs `Integration` внутри домена не всегда точна.
