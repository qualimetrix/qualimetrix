# Запись для FOLLOWUPS.md — пакет F захода Х9

## Х9 (2026-09-05) — хвост Х6 (рост CPU под параллелизмом): наблюдение не согласуется с P/E-гипотезой в заявленной форме, открыто с новым фактом

Пакет измерительный (production-код не менялся). Таблица —
`X9-gate-holes/x6-cpu-measurement.tsv`: `bin/qmx check src/ --format=json`,
`--workers=0,2,4,8`, три повтора на точку, `/usr/bin/time -l`, машина без
конкурирующей нагрузки (фон в шапке таблицы), кэш AST прогрет один раз и не
чистился между точками — все 12 прогонов на одном тёплом кэше, все дали
`filesAnalyzed=900` и exit code 2.

Медианы (полные числа — в таблице):

| workers | wall-clock, медиана | CPU total (user+sys), медиана |
| ------- | ------------------- | ----------------------------- |
| 0       | 18.89 с             | 18.88 с                       |
| 2       | 12.46 с             | 19.41 с                       |
| 4       | 9.18 с              | 19.94 с                       |
| 8       | 7.65 с              | 20.95 с                       |

### Новый факт: машина этой сессии — 10 P-ядер, не меньше

`sysctl hw.perflevel0.physicalcpu`=10, `hw.perflevel1.physicalcpu`=4,
`hw.ncpu`=14 (Apple M4 Pro). Х6-гипотеза формулирует наблюдаемый рост CPU как
«воркеры расселяются на E-ядра **за пределом числа P-ядер**» — то есть
ожидаемая форма кривой: плоско (или почти плоско) до тех пор, пока число
процессов (воркеры + главный) не превысит 10, и рост начинается только после
этой границы. Ни одна из тестируемых точек (`--workers=0,2,4,8`, то есть до 9
процессов включая главный) эту границу не пересекает — вся серия целиком
внутри бюджета P-ядер.

### Наблюдение не той формы, которую предсказывает гипотеза

CPU total растёт **плавно и заметно ещё до границы**: 18.88 → 19.41 → 19.94 →
20.95 (+11% суммарно от 0 до 8 воркеров), без видимого перегиба между
соседними точками — прирост примерно одинаков на каждом шаге (+0.53, +0.53,
+1.01). Если бы механизм был «E-ядра включаются только за пределом P-ядер»,
рост в этом диапазоне (0-8, все точки под бюджетом 10) должен был быть
пренебрежимо мал, а не монотонно накапливаться с каждым удвоением воркеров.

Дополнительно wall-clock даёт сублинейное ускорение уже на малых числах
воркеров: `--workers=2` даёт speedup ×1.52 от `--workers=0` (не ×2),
`--workers=4` — ×2.06 (не ×4), `--workers=8` — ×2.47 (не ×8). Эффективность
падает монотонно (76% → 51% → 31%) далеко не доходя до 10 P-ядер — это форма,
типичная для оверхеда координации/сериализации между процессами и
последовательных фаз пайплайна (Aggregation/RuleExecution/Reporting,
CLAUDE.md раздел «Pipeline Phase Separation»), а не для конкретно
P/E-throttling.

### Вердикт: не согласуется в заявленной форме, открыто с новым фактом

Уровень уверенности — умеренный, не факт. Наблюдаемый рост CPU и деградация
эффективности параллелизма **воспроизводимы** (одинаковы по трём повторам на
каждую точку), но их форма (плавный монотонный рост от самой первой
параллельной точки) не соответствует форме, которую предсказывает P/E-гипотеза
Х6 (цена начинается только за пределом P-ядер). Наблюдаемое лучше объясняется
обычным оверхедом межпроцессной координации/сериализации и
последовательными фазами пайплайна — эффект, который гипотеза Х6 не
называла и который не требует обращения к E-ядрам вовсе.

Сама P/E-гипотеза при этом **не опровергнута** — она просто не была проверена
в релевантной точке: `powermetrics` недоступен (root, вне пакета), а
`--workers=8` на этой машине не превышает бюджет в 10 P-ядер, так что граница,
предсказанная гипотезой, лежит за пределами протестированного диапазона.
Проверка самой гипотезы потребовала бы точки `--workers` заметно выше 10
(или доступа к `powermetrics`/`Instruments` для прямого наблюдения P/E-
занятости) — это новый факт для следующей сессии, если вопрос снова станет
актуален, а не повод отменять решение о ёмкости пакета F в этом заходе.
