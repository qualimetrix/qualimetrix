# M5 — перечисление ключей секции `computed_metrics:`

Съёмка на коммите `1513bf67`. Строки, установленные **прогоном**, помечены `[прогон]`;
остальные — **чтением кода** (`[код]`). Протокол прогона — в конце документа.

## 0. Топология секции

Секция читается ровно одной цепочкой, и это установлено Serena, а не впечатлением:

```
ConfigurationDocument
  → ComputedMetricContributionReader::read()            (единственный вызов: ComputedMetricAnalysis:28)
  → ComputedMetricsConfigResolver::resolve()            (единственный вызов: ComputedMetricAnalysis:31)
      ├── ComputedMetricOverrideReader::merge()         (единственный вызов: ComputedMetricsConfigResolver:79)
      └── ComputedMetricOverrideReader::create()        (единственный вызов: ComputedMetricsConfigResolver:87)
  → ComputedMetricDefinition (конструктор: validateName + validateLevels)
  → ComputedMetricFormulaValidator::validate()
  → ChannelUniverse::assertRuntimeNamesUnclaimed()      (src/Infrastructure/Rule/ChannelUniverse.php:246)
```

Второго читателя сырой карты `computed_metrics` в дереве нет (проверено
`find_referencing_symbols` по всем четырём точкам входа и грепом по литералу
`'computedMetrics'` — 4 попадания, все в этой цепочке плюс константа схемы).

Глубин у секции **три**, не четыре:

- глубина 0 — имя записи (`health.*` / `computed.*`);
- глубина 1 — ключи записи метрики (9 имён);
- глубина 2 — ключи внутри `formulas:` (слова уровней) и **элементы списка**
  `levels:` (это значения, не ключи).

**«Блока уровня» в этой секции не существует.** `levels:` — список слов, порогов
на уровень здесь нет: `ComputedMetricRuleOptions::acceptedOptionKeys()` объявляет
единственный ключ `enabled` (`ComputedMetricRuleOptions.php:41-44`), а
`levelOptionsClasses()` эта секция не реализует вовсе. Известный крах
`levels: {class: {warning: 1}}` — это пользователь, принёсший форму из секции
`rules:` в секцию, где её нет. Это факт, на котором придётся строить план: лечение
не может «починить блок уровня», ему придётся **отказать** в нём.

## 1. Таблица ключей

Столбец «Форма» различает три состояния, потому что иначе счёт врёт:
**отказ** — прогон падает с сообщением; **тихий игнор** — значение отброшено,
поведение как без ключа; **тихая смена поведения** — значение отброшено, но это
меняет результат (порог снимается).

## 3. Замкнуто ли множество

**Глубина 1 замкнута.** Девять имён, все девять — литералы или константы в двух
файлах цепочки; новый ключ здесь — правка `ComputedMetricOverrideReader`. Ничего не
порождается динамически: ни рефлексии по конструктору, ни ключей из
пользовательских данных. Объявить набор декларацией можно **сразу**, без
предварительной работы.

**Глубина 2 замкнута.** Ключи `formulas:` — те же три слова уровней, уже объявленные
`REPORTING_LEVELS:44`; элементы `levels:` — тот же список. Декларация здесь — не
новое утверждение, а второй читатель уже существующего.

**Глубина 0 не замкнута и замкнутой быть не может.** `computed.*` — открытое
пространство имён по построению: имя выбирает пользователь. Но это не значит, что
множество не описано: оно описано **грамматикой плюс пятью запретами**
(см. §1). Половина `health.*` при этом замкнута на шесть имён.

**Вывод о применимости решения X13.** Декларация в форме `RuleOptionKeySet` /
`acceptedOptionKeys()` применима к глубинам 1 и 2 и неприменима к глубине 0 по
построению — там нужен не набор, а грамматика, которая уже есть. Два условия
применимости проверены:

- X13 сравнивает ключи после `ConfigKeySpelling::normalize()` с обеих сторон
  (`RuleOptionKeySet` docblock, `src/Analysis/Finding/Contract/Rule/RuleOptionKeySet.php:29-33`),
  поэтому камелизация глубины 2 и ниже политикой `PRESERVE_IMMEDIATE_CHILDREN`
  (`ConfigSchema.php:236`, `SectionNormalizationPolicy:51`) отказу не мешает — но
  **сообщение должно называть авторскую орфографию**, потому что до читателя
  `bogus_key` доезжает как `bogusKey`. Это здесь та же политика, что в `rules:`.
- Третье состояние X13 («ключ, о котором класс отвечает сам») здесь тоже нужно:
  `threshold` в паре с `warning`/`error` уже имеет собственный отказ
  `ComputedMetricOverrideReader.php:235-239`, и генерический «unknown option» не
  должен его перебивать.

Одна оговорка, которой в `rules:` нет: у `computed_metrics` **отсутствует
класс-носитель**. `ComputedMetricRuleOptions` описывает `rules: { health.*: … }`
(один ключ `enabled`), а не эту секцию. Носителя декларации придётся выбрать или
завести — это развилка для плана, не факт измерения.

1. **Пресеты.** Ключи, которые встроенные пресеты (`--preset=strict|legacy|ci`)

   которого нет в таблице, отказ ударит по продукту, а не по пользователю.
2. **Порядок вкладов.** `ContributionReader:32` берёт **последний** вклад целиком
   (README `:107-108`). Как ведут себя ключи при нескольких документах (пресет +
   `qmx.yaml` + `-c`), не измерялось.
3. **Пути помимо `check`.** Прогоны сделаны только через `bin/qmx check`.
   `baseline:generate`, `baseline:explain`, `rules`, `directives` читают ту же
   цепочку по коду (второго читателя нет), но их exit-коды на дефектной секции
   не снимались.
4. **YAML-типы вне проверенных.** Не проверялись якоря/мержи YAML (`<<:`),
   многострочные скаляры и `~` вместо `null` для каждого ключа по отдельности.
5. **Правая половина `qmx.yaml`.** Секция `rules: { health.*: … }` — соседняя
   поверхность с теми же именами; её ключи здесь не перечислены (это предмет X13).
6. **Отказ на глубине 0 через `ChannelUniverse:246`** прочитан, но прогоном не
   воспроизведён.

Два пути к exit 3 с разной формой сообщения: `ComputedMetricConfigurationException`
печатается с префиксом «Configuration error:» (`CheckCommand.php:194`), а
`InvalidArgumentException` — без префикса (`CheckCommand.php:190`). В таблице это
`[прогон p5]` и `[прогон p12]`. Разнобой сообщений — отдельная строка для плана.

- **Всего ключей: 13** — 1 слот имени записи (глубина 0) + 9 ключей записи
  (глубина 1) + 3 ключа уровня внутри `formulas:` (глубина 2). Элементы списка
  `levels:` — значения, а не ключи, и в счёт не входят.
- **Читаются по имени без объявления принимаемого набора: 12** — все 9 ключей
  глубины 1 и все 3 глубины 2. Четыре из девяти (`threshold`, `warning`, `error`,
  `enabled`) адресуются через константы `RuleOptionKey`, но константа — это
  словарь, а не утверждение «здесь принимается именно этот набор».
- **Имеют проверку формы значения: 9** — все ключи глубины 1 (значения глубины 2
  проверяются `is_string`, но сами ключи не проверяются ничем).
- **Из них действительно отказывают: 2** — `levels:` через `mapLevel()`
  (для строкового элемента) и взаимоисключение `threshold` с `warning`/`error`.
  Остальные 7 при неверной форме молчат: пять — тихим игнором, два (`warning`,
  `error`) — тихой сменой поведения, снимая порог.

## Протокол прогона

```
$WT/bin/qmx -d <probe> check src --workers=0 --no-cache --no-progress \
    --format=json --fail-on=none 1>out 2>err; ec=$?
```

Пробник: два класса (`P\A` — типизированный, `P\B` — нетипизированный, низкая
когезия), `qmx.yaml` собирается `printf '%b'`. Exit-код снимается сразу и без
пайпа. Идентификаторы прогонов (`p1`…`p18`, `qA`…`qF`, `r1`…`r3`) — ссылки на
случаи внутри этой съёмки.
