### Структурное доказательство чтением кода — почему порог не может подействовать

`ClassCountRule::analyze()` (`src/Analysis/Evidence/Size/ClassCountRule.php:92`):

```php
if ($namespace !== null && $context->namespaceTree !== null && !$context->namespaceTree->isLeaf($namespace)) {
    continue;
}
```

Правило анализирует только листовые пространства имён. `NamespaceTree`
строится один раз на весь прогон, до применения любой rule-scoped
suppression (`Analysis\Run\Pipeline\AnalysisPipeline.php:238`,
`:269`, `:292`) — порог правила `size.class-count` не может ни изменить
дерево, ни обойти этот `continue`.

А `.sum` начинает расходиться с базой ровно там, где пространство имён
перестаёт быть листом:

- `ClassToNamespaceAggregator` и провайдер `ClassCountCollector::getNamespacesWithMetrics()`
  пишут базу и `.sum` листа из **одного и того же** набора собственных
  файлов пространства имён — по построению совпадают.
- `TreeAwareNamespaceAggregator` (`src/Analysis/Evidence/Measurement/Aggregation/TreeAwareNamespaceAggregator.php:57-60`)
  перезаписывает `.sum` **только** для нелистовых («parent») пространств,
  собирая его рекурсивно по всем потомкам дерева (`$tree->getDescendants($parentNs)`).
  Базовое `size.class-count` при этом не трогается: оно остаётся
  собственным значением родителя (2 — свои файлы), а `.sum` становится
  суммой по поддереву (5 = 2 свои + 2 `Excluded` + 1 `GloballyExcluded`).

Значит: субъект, где база ≠ `.sum`, — **всегда** нелистовой, а нелистовой
субъект `size.class-count` **всегда** пропускает. Это не порог и не
конфигурация конкретного кейса — это инвариант архитектуры при текущей
однонамспейсовой (один блок `namespace` на файл) форме корпуса. Утверждение
ADR 0046 «объявлено `.sum`» остаётся истинным по коду, но неотличимо от
«объявлена база» никаким прогоном корпуса для этого правила, пока правило
пропускает ровно те субъекты, где отличие могло бы проявиться.

### Единственная найденная лазейка — сама дефект, не легитимная основа для фикстуры

`NamespaceMetricContributions::mapFilesToNamespaces()` собирает **все**
пространства имён, которых касается файл, а
`mapNamespacesToFileSymbols()` затем приписывает **целиком** файловый
уровень метрики (`getClassCount()` — сумму по всему файлу) каждому из этих
пространств. Файл с двумя блоками `namespace` (два листовых, братских
пространства в одном файле) получил бы `.sum` для каждого блока,
раздутый на класс из чужого блока, при том что база (собранная
`ClassCountVisitor::getNamespaceCounts()` — точно по блокам) осталась бы
корректной. Это дало бы различимый лист — но ценой построения кейса на
атрибуционном дефекте: работает только пока эта не задокументированная
особенность агрегации не починена, и утверждение кейса тогда покраснеет по
чужой причине. Не эксплуатируется здесь; называю владельцу отдельно.

### Что закрывает запись Х8

Запись Х8 «Агрегатное написание объявлено, но корпусным прогоном не
различается» **не закрыта фикстурой** — предписанное в брифе лечение
(порог в конфиге кейса на уже существующем различающем субъекте)
опровергнуто измерением (оба свидетеля выше). Уточнённая формулировка,
которой запись заменяется: **утверждение неотличимо by construction** для
`size.class-count` при текущей форме правила и корпуса — доказательство
выше даёт и число (2 vs 5), и механизм (`continue` на nonleaf), и почему ни
один существующий или добавимый однонамспейсовый лист не может воспроизвести
расхождение.

Пути, которые сделали бы отличимость возможной (решение владельца, вне
объёма E5):

1. Продуктовая правка `ClassCountRule`: анализировать и нелистовые
   пространства (изменение поведения правила, не только гейта).
2. Другой канал-свидетель для «объявлена агрегатная форма, а не база»:
   не корпусный прогон, а юнит/golden-тест на `ClassCountRule`, читающий
   `.sum` при явно расходящихся метриках в тестовом `MetricBag` —
   ADR 0046 проверяется на уровне контракта, а не на уровне корпуса.
3. Почтить как отдельный дефект атрибуцию `NamespaceMetricContributions`
   (файл с несколькими блоками `namespace` раздувает `.sum` каждого блока
   на чужой класс) и только после его починки — или намеренной фиксации
   как поведения — решать, годится ли он в основу нового кейса.
