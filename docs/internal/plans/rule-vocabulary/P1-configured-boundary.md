# П1. Границу называет тот, кто её держит

План одного шага захода `rule-vocabulary`. Журнал захода — `PLAN.md`; сюда
вынесен отдельным файлом, потому что журнал уже 5828 строк.

Версия 4, после двух раундов ревью плана и раунда ревью исполнения (native,
Codex), который нашёл в исполнении два пропущенных канала и один ложный оракул. Разбор обоих раундов — в конце
файла; текст переписан целиком, а не пропатчен, поэтому читать надо его, а не
дельту к предыдущим версиям.

## Дефект

`src/Infrastructure/Console/Command/BaselineConfiguredThresholds.php` отвечает
на вопрос «какую границу предупреждения канал получил из `qmx.yaml`» — это одна
из колонок `baseline:explain`. Ответ он **угадывает перебором имён свойств**:
`GENERIC_PROPERTIES = ['warning', 'maxWarning', 'minWarning']` (строка 100),
плюс вывод имени свойства из суффикса канала (`axisOf`/`axisProperty`), плюс
подсчёт свойств с суффиксом `Warning` как детектор неоднозначности
(`countsWarningBoundaries`).

Перебор — не приближение к истине, а другой вопрос: он спрашивает, **как
названо** свойство, тогда как ответ зависит от того, **что решает** объект
опций. Три следствия, все измерены:

1. **Ложный отрицательный.** `coupling.distance` держит `maxDistanceWarning`.
   Имени нет в списке из трёх — `explain` печатает «not resolvable» о канале, у
   которого граница настроена и работает. Единственная строка населения, где
   сегодняшний ответ неверен.
2. **Список не закрывается.** Четвёртое имя чинится только дописыванием в
   список: новый класс опций либо попадает туда руками, либо молча теряет ответ.
3. **Отказы выглядели честными и не были.** `null` для `god-class` и
   `data-class` первые три версии этого плана называли правильным ответом. Он
   неправильный: `GodClassRule` репортит `matchedCount` и предупреждает от
   `minCriteria`, `DataClassRule` репортит WOC и эмитит при
   `woc <= wocThreshold`. Обе величины настраиваемы и обе — границы на той оси,
   которую канал отчитывает. Перебор их не находил, а объяснение, почему их и не
   надо находить, занимало в докблоке абзац. Объём этого объяснения и есть цена
   угадывания: оно звучало убедительно и было ложным.

Задача — не сделать перебор точнее, а **убрать вопрос об именах**: класс опций
называет свою границу сам, потребитель её читает.

## Два перечисления, и почему одного мало

- `enumeration-configured-boundary-population.tsv` — 49 пар «канал × уровень»
  над 39 классами опций, по два независимых свидетеля на строку: имена числовых
  членов и точки переключения `getSeverity()`, снятые пробой по сетке.
- `enumeration-boundary-contract-implementors.tsv` — 55 конкретных реализаций
  затронутых интерфейсов (45 в `src/`, 10 дублей в `tests/`).

Первое перечисляет **пути**, второе — **классы**, и разность непуста: пять
иерархических родителей и `ComputedMetricRuleOptions` не встречаются как
`resolved_options` ни в одной строке путей. Версия 1 этого плана рассуждала о
классах по таблице путей и потеряла ровно эти шесть; оба перечисления теперь
лежат рядом, генераторы к ним — тоже, и каждое называет, чего его способ не
видит. Шесть анонимных классов в тестах не видит рефлексия — они сняты grep'ом и
названы поимённо в шапке второго файла.

Свидетели расходятся в пяти строках, все пять разобраны в шапке первого файла:
`coupling.distance` — дефект, остальные четыре — правильный сегодняшний отказ.

## Решение

**Обязательство ложится на `ThresholdAwareOptionsInterface`, а не на
`RuleOptionsInterface`.** Основание — измерение, а не вкус: в таблице путей нет
ни одной строки, где границу держит класс вне этого интерфейса (обе проверки
`awk` дают 0). Держатели границы уже внутри — их 27 в `src/` плюс один дубль в
тестах.

```
enum NoConfiguredBoundary        // Analysis\Finding\Contract\Rule
    case MoreThanOneBoundary     // границ несколько, запрос не говорит, какая
    // «границы нет вовсе» говорится невхождением в интерфейс, а не случаем

interface ThresholdAwareOptionsInterface           // + этот метод
    public function warningBoundary(): int|float|NoConfiguredBoundary;
```

Три решения, каждое с ценой:

- **`warningBoundary()`, а не `configuredWarningBoundary()`.** Объект отвечает о
  границе, которую держит **сейчас**; после `withOverride()` это уже
  переопределённая величина. «Настроенная» — рамка потребителя, который
  оверрайдов не применяет, а не свойство метода. Имя, обещающее «настроенную»,
  лгало бы на копии после оверрайда. Семантика закрепляется тестом на
  `withOverride()`, а не докблоком.
- **Без аргументов.** Уровень уже выбран через `forLevel()`, канал не решает
  ничего: три класса обслуживают больше одного канала (`CodeSmellOptions` — 7,
  `SecurityPatternOptions` — 3, `TypeCoverageOptions` — 3), и ни один не держит
  при этом двух разных границ — первые два не держат никакой, третий создаётся
  по экземпляру на правило. Это снятие возможности: ветка `axisOf`/`axisProperty`
  удаляется.
- **`MoreThanOneBoundary`, а не «неоднозначно без оси».** У
  `LongParameterListOptions` выбор между `warning` и `voWarning` делает
  `LongParameterListRule` по свойству субъекта — конструктор ли это value
  object, — через отдельный `getVoSeverity()`. Это не ось канала, и имя случая
  не должно утверждать, что ось.

Потребитель после правки:

```
thresholdFor(options, level):
    target = options is Hierarchical ? levelOptions(options, level) : options
    if target is not ThresholdAware: return null
    b = target->warningBoundary()
    return b is number ? b : null       // обе причины отсутствия -> "not resolvable"
```

Удаляются целиком: `GENERIC_PROPERTIES`, `readProperty`, `axisOf`,
`axisProperty`, `countsWarningBoundaries`, импорты `ReflectionObject` и
`ReflectionProperty`, и та часть докблока, которая объясняла угадывание.

**Молчание не-`ThresholdAware`-класса ловится проверкой, а не типом.** `null`
для класса вне интерфейса — умолчание, и само по себе оно того же рода, что
перебор. Его закрывает отрицательная ветка проверки 2, и область её действия
задаётся точно: она применяется к объектам, объявившим `NotAThresholdDecision`,
и к объектам вне интерфейса, но **не** к объявившим `MoreThanOneBoundary` — у
тех член-переключатель есть по определению случая, и без этой оговорки страж
краснеет на `LongParameterListOptions`, ради которого случай и заведён. Это
измерено, а не предположено: прогон по всем не-объявляющим классам даёт 14 из 15
чистыми и ровно одну сработку — на `LongParameterListOptions`.

**Чего эта ветка не видит, сказано здесь, а не обнаружится потом.** Публичные
члены пяти иерархических родителей — объекты уровней, а не числа, так что страж
сквозь них не смотрит. Числа родителей покрыты тем, что обход доходит до самих
объектов уровней; сверх этого пинуется структурный факт, на котором стоит всё
решение: **ни один иерархический родитель не входит в
`ThresholdAwareOptionsInterface`**. Этот пин сегодня зелен и ловит не дефект, а
будущее изменение — так он и записан в тесте.

**Трейта нет.** Метод пишется явно в каждом из 27 классов: трейт `return
$this->warning;` подошёл бы 19 из них, а остальным восьми всё равно нужен свой
текст — экономия не окупает второго способа сказать одно и то же.

### Одно определение «точки переключения»

Нормативное определение одно, и оно принадлежит проверке: **число `b` есть точка
переключения объекта, если `getSeverity()` не постоянна на окрестности
`b`.** Окрестность для целого `b` — `{b-1, b, b+1}`, для дробного —
`{b-δ, b, b+δ, b+1}`. Хвост `b+1` не украшение: сравнение со строгим `>` и
приведением `(int)$value` сдвигает переключение на `b+1`, и окрестность из
`b∓δ` такую границу пропускает. Колонка `severity_switch_points` в перечислении
снята грубым проходом по сетке и служит **чтению**, а не проверке; в шапке
перечисления это сказано теми же словами, чтобы два определения не разошлись.

### Отвергнутая альтернатива: выводить границу из поведения

Проба `getSeverity()` по сетке даёт правильный ответ на 47 из 49 строк вообще
без правки классов, и её стоит отвергнуть текстом, а не молчанием. Отвергается
по трём причинам: результат зависит от сетки (0.02 у `class-rank` первая сетка
потеряла — это уже случилось); «границы нет» неотличимо от «граница вне сетки»;
и продукт начинает зависеть от оракула, написанного для тестов. Проба остаётся
тем, чем она хороша, — **вторым свидетелем в проверке**, а не источником ответа.

## Что меняется в наблюдаемом поведении

**Три строки** `baseline:explain` вместо «not resolvable» печатают границу:
`coupling.distance` (член зовётся `maxDistanceWarning`, перебор знал три имени),
`design.god-class` (`minCriteria`) и `design.data-class` (`wocThreshold`).
Остальные 46 строк дают то же, что сегодня, — это проверяется золотой картой, а
не заявляется.

Версии 1–3 обещали одну строку. Обещание держалось на том, что отказ для
`god-class` и `data-class` правилен, и ревью исполнения это опровергло.

Корпус гейта видит две из трёх (третья, `coupling.distance`, ни одним кейсом
`explain` не покрыта) и требует объявленной дельты на каждую: обе объявлены с
причиной в `finding-gate/declared-delta.tsv`. Заодно derive-прогон снёс
`declared-delta/case-health-format-health.diff` — сироту, на которую индекс не
ссылался ни одной строкой.

Величина зависит от конфигурации, и числа в перечислении — **дефолты классов**,
а не то, что судит этот репозиторий: контейнер, поднятый одним
`ContainerFactory`, `qmx.yaml` не читает, поэтому там 0.3, тогда как `qmx.yaml`
ставит `max_distance_warning: 0.5`. Золотая карта снимается тем же способом и
потому проверяет дефолты.

## Тестовый план

Правило шага: **каждая проверка предъявляет, на чём она краснеет.** Проверка, не
прогнанная против неисправного кода, ничего не доказывает.

1. **Золотая карта `resolve()` через настоящий контейнер.** Ожидание — 25
   сегодняшних пар плюс `coupling.distance`. Ломается на сегодняшнем коде
   отсутствием ключа; доказательство — прогон на неисправленном дереве с
   сохранённым выводом.
2. **Перекрёстный свидетель: объявление против поведения.**

   *Положительная ветка.* Если объект объявил число `b`, то `b` — точка
   переключения, причём **ровно один** из соседей `b∓δ` даёт `null`.
   Формулировка «в самой точке `b` severity не `null`» была бы неверна:
   `MaintainabilityOptions` и три `TypeCoverageOptions` сравнивают строго и в
   точке `b` дают именно `null`. Оракул в исправленном виде **проверен на всех
   26 строках с числом** (`enumeration-boundary-oracle-check.php` рядом с
   планом: 26 OK, 0 отказов) — до того, как попал в план.

   *Отрицательная ветка.* Область — объекты с `NotAThresholdDecision` и объекты
   вне интерфейса: ни один их публичный числовой член не есть точка
   переключения в смысле определения выше. Измерено: 14 из 15 чисты, сработка
   одна и она на `MoreThanOneBoundary`, который из области исключён.

   Исключение из `getSeverity()` — отдельный исход, а не `null`; генератор уже
   исправлен, тест наследует правило.

   *Чем доказывается краснота.* Тест новый, на сегодняшнем коде его нет, поэтому
   каждая ветка снимается **отдельной мутацией на hardlink-клоне**, поштучно:

| Мутация                                                                                | Ветка         | Почему краснеет                                                       |
| -------------------------------------------------------------------------------------- | ------------- | --------------------------------------------------------------------- |
| `DistanceOptions` объявляет `maxDistanceError` (0.5) вместо `maxDistanceWarning` (0.3) | положительная | у 0.5 оба соседа не `null` (`warning`\|`error`)                       |
| `LcomOptions` объявляет `error` (5) вместо `warning` (3)                               | положительная | то же; проверяет ровно ту путаницу, которой класс не должен допускать |
| класс-детектор заводит настроенную границу, не входя в интерфейс                       | отрицательная | член становится точкой переключения                                   |

   Мутация «`LcomOptions` объявляет `minMethods`», стоявшая в версии 2, **снята
   как мёртвая**: `minMethods = 3` и `warning = 3` — одно и то же число, так что
   мутация объявляет истинную границу и проверка остаётся зелёной. Это ровно тот
   класс дефекта, который проверки и ловят, и он был в собственном тестовом
   плане.
3. **`MoreThanOneBoundary` — там и только там, где решений о величине два.**
   Свидетель не именной: у `LongParameterListOptions` вторая граница выражена
   отдельным методом `getVoSeverity()`, и проверка считает методы, решающие о
   severity, а не свойства с подходящим именем. Именной свидетель здесь
   воспроизвёл бы удаляемый `countsWarningBoundaries` и объявил бы его эталоном.
4. **Перебор не возвращается.** `BaselineConfiguredThresholds` не читает членов
   объекта опций по имени. Проверка на отсутствие импортов `Reflection*` —
   дешёвый сторож на токен, и он краснеет на сегодняшнем коде немедленно, но
   поведение стережёт проверка 2, а не он; это записано в самом тесте, чтобы его
   зелёный цвет не читался как гарантия.
5. **Оверрайд, и противоречие внутри интерфейса.**
   `withOverride(W, E)->warningBoundary() === W` для однограничных классов:
   закрепляет, что метод отвечает о текущем состоянии объекта, и что `explain`
   получает настроенную величину лишь потому, что сам оверрайдов не применяет.

   Три класса из 27 требуют обратного утверждения, и оно проверяется, а не
   обходится: у `GodClassOptions` половина `warning` документированно ложится в
   `minCriteria`, у `DataClassOptions` — в `wocThreshold`, у
   `LongParameterListOptions` — в `warning` при второй паре `voWarning/voError`.
   То есть один интерфейс одним методом принимает число «по оси warning», а
   другим отвечает «границы у меня нет». Противоречие не мнимое, и тест
   закрепляет его явно: для этих трёх `withOverride(W, E)->warningBoundary()`
   обязан остаться `NotAThresholdDecision` либо `MoreThanOneBoundary` и никогда
   не стать `W`. Членство в интерфейсе означает «принимаю оверрайд», а не
   «держу границу».
6. **Существующие тесты.** Один именованный дубль (`SubjectControlOptions`)
   реализует `ThresholdAwareOptionsInterface` и получает метод. Шесть анонимных
   дублей реализуют только `RuleOptionsInterface` и не затронуты. Потребители
   (`BaselineExplainCommandTest`, `BaselineRunBeforeLoadTest`) не меняются.
7. **Измерение унаследованной слепоты.** Память `threshold-override-design-flaw`
   фиксирует, что 27 интеграционных тестов `ThresholdAware` звали
   `withOverride()` напрямую, минуя экстрактор. Пакет П1.4 обязан **измерить**,
   все ли 27 классов покрыты путём парсера сегодня, и назвать непокрытые.
   Расширение покрытия в этот шаг не входит — входит измерение и запись факта.

## Definition of Done

Полная цепочка, без сокращений:

- `composer architecture:generate`, затем `composer check` — включает
  `check-leaks`, `cs-check`, `docs:check`, `test`, `test:cross-tool`, `phpstan`,
  три `enumeration:*:check`, `gate:self-test`, `selfcheck`
  (→ `architecture:check`, `suppression-snapshot:check`);
- `php scripts/finding-gate.php --reference=1c17ed63`;
- предъявленные логи прогонов проверок 1, 2 и 4 **против неисправного кода**
  (мутации на клоне, не в рабочем дереве);
- `selfcheck` смотрится отдельно на предмет когезии: три класса
  (`DataClassOptions`, `GodClassOptions`, `LongParameterListOptions`) получают
  метод-константу, не трогающий полей, что давит TCC. Гипотеза с механизмом, не
  измерение; если `health.cohesion` шевельнулся — это разбирается, а не
  ратчетится в `qmx-baseline.json`;
- ревью исполнения — обязательное: контракт меняется.

## Что дали два раунда ревью плана

### Раунд 1: native, Codex, Qwen

Три ревьюера, все три вернули NO-GO для версии 1, и сошлись на трёх находках из
своих; каждая проверена мной по коду до правки.

- **Обязательство стояло не на том интерфейсе** (native, единолично). Версия 1
  вешала метод на `RuleOptionsInterface` и `LevelOptionsInterface` — 45 классов
  в `src/` плюс дубли. Проверка native: держателей границы вне
  `ThresholdAwareOptionsInterface` нет ни одного. 27 классов вместо 55, пять
  иерархических родителей не получают объявления, которого у них не бывает,
  ~17 детекторов не получают метода-константы, шесть анонимных дублей в тестах
  не ломаются. Довод версии 1 против «маркерного интерфейса» («молчание
  нераспознаваемо») снят её же проверкой 2.
- **Перечисление было не тем населением** (native, Qwen). Таблица путей
  использовалась как таблица классов; разность — шесть классов. Заведено второе
  перечисление, и связь между ними названа в шапках обоих.
- **Оракул проверки 2 был ложен** (Qwen, Codex независимо). «В точке `b`
  severity не `null`» неверно для четырёх существующих классов со строгим
  сравнением. Переформулирован и проверен на 26 строках до внесения в план.
- **Семантика после `withOverride()` не была определена** (Qwen, Codex).
  Привело к переименованию метода и к отдельной проверке 5.
- **`AmbiguousWithoutAxis` называл не то** (Qwen, Codex). У
  `LongParameterListOptions` ветвление по свойству субъекта, а не по оси канала.
- **Генератор глотал `Throwable` как `null`** (Qwen). Исправлен: исключение —
  отдельный исход. Сегодня им ничего не маскируется, проверено.
- **Утверждение об исчерпанности расхождений было неверно** (native).
  Пятое — `architecture.circular-dependency`; и «18 детекторов» на деле 17.
  На этой исчерпанности держится вывод «сегодня неверна ровно одна строка».
- **Доказательство ключевого вывода противоречило данным** (native). «Только
  `TypeCoverageOptions` встречается при трёх каналах» — на деле `CodeSmellOptions`
  при семи и `SecurityPatternOptions` при трёх. Вывод выжил, цитата была ложной.
- **Второй нескомпенсированный интервал** (native). Манифест рукописный; записи
  переехали в П1.1.
- Трейт снят (native: применим к 19 из 45, теперь из 27 — экономия не окупает);
  альтернатива «выводить границу пробой» получила явный отказ вместо молчания;
  проверка 4 переписана так, чтобы её зелёный цвет не читался как гарантия
  поведения.

Отклонена одна находка: риск «трейт укажет на поле, не участвующее в решении»
(Qwen-07, Codex-05) снят вместе с трейтом, а остаточная его форма — расхождение
объявления с реальным решением — это ровно то, что ловит проверка 2.

### Раунд 2: native, узко по изменённому решению

Версия 2 сменила интерфейс-носитель, и это материал, которого раунд 1 не видел.
Вердикт — GO с обязательными правками; вопрос раунда был поставлен так: «найди
класс, на котором отрицательная ветка даст ложную тревогу или окажется вакуумно
зелёной». Он нашёл и то, и другое.

- **Мутация была мертва.** «`LcomOptions` объявляет `minMethods`» не могла
  покраснеть: `minMethods = 3` и `warning = 3` — одно число. Проверено чтением
  класса. Заменена на объявление `error` вместо `warning`; заодно снято
  заявление «три мутации, три падения», которое было ложным на второй.
- **Страж не видел исключающих сравнений.** При `(int)$value` и строгом `>`
  переключение лежит на `член+1`, а окрестность из `b∓δ` туда не достаёт.
  Определение точки переключения расширено и вынесено в отдельный раздел одним
  нормативным текстом — раунд 2 отдельно отметил, что план и шапка перечисления
  определяли её двумя разными способами.
- **Область отрицательной ветки не была задана.** Узкое чтение снимает ложную
  тревогу на `MoreThanOneBoundary`, но делает стража вакуумным; область теперь
  названа поимённо, и её измерение приложено.
- **Иерархические родители стражу не видны** — их публичные члены объекты.
  Названо прямо, плюс заведён структурный пин «ни один родитель не
  `ThresholdAware`», на котором стоит всё решение.
- **Противоречие внутри интерфейса.** На трёх из 27 классов `withOverride()`
  документированно кладёт `warning` в реальное число, тогда как
  `warningBoundary()` отвечает «границы нет». Версия 2 обходила эти классы
  исключением из проверки 5 — теперь противоречие названо и закреплено
  обратным утверждением.
- **ADR обязана сослаться** на `ThresholdOverrideSupportReader`.

Раунд 2 подтвердил и то, ради чего затевался: утверждение о населении держится
при независимом сканировании дерева, а `RuleValidatorMapFactory`,
`WorkerBootstrap`, компиляторный проход и статический `getOverrideValidator()`
новым instance-методом не затронуты.

Одну ложную тревогу отрицательной ветки я нашёл сам, до отчёта раунда 2, тем же
измерением; раунд 2 нашёл её независимо и добавил три, которых у меня не было.

## Что дал раунд ревью исполнения

Двое (native, Codex); Codex — три находки, ни одной выше MEDIUM; native — HIGH,
который переписал часть решения.

- **Два «честных отказа» оказались пропущенными границами** (native). Разобрано
  выше и в шапке перечисления. Проверено мной по коду правил до правки:
  `GodClassRule.php` репортит `$matchedCount` и warn'ит от `minCriteria`,
  `DataClassRule.php` репортит WOC и эмитит при `woc <= wocThreshold`.
- **Мой оракул был самоподтверждающимся** (native, и это главное).
  `enumeration-boundary-oracle-check.php` строил ожидания как
  `$expected = $current` — из вывода **старого** читателя — и пропускал строки,
  которых там нет. Каналы, которые старый читатель терял, были невидимы по
  построению. Шапка перечисления называла этот режим отказа и тут же разрешала
  его в неверную сторону.
- **Положительная ветка стража отвергла бы правильное объявление** (native):
  у обоих классов `getSeverity()` — заглушка, и XOR-условие на ней ложно. То
  есть оракул был не слеп, а инвертирован. Теперь эти два класса вынесены в
  пин `DECIDES_INSIDE_THE_RULE`, их свидетель — `withOverride()`, а новый страж
  проверяет, что пин совпадает с множеством классов, чьё объявление поведение не
  подтверждает. Снят мутацией: подмена `minCriteria` на `wmcThreshold` красит
  ровно свидетеля-оверрайд.
- **`NotAThresholdDecision` остался без носителей** и снят. «Границы нет вовсе»
  выражается невхождением в `ThresholdAwareOptionsInterface` — так говорят все
  детекторы; внутри интерфейса единственная оставшаяся причина — «границ
  несколько». Случай добавляется, когда найдётся причина, а не заранее.
- **`NotAThresholdDecision` не имел population-pin** (Codex, независимо от
  native, с другой стороны: он указал, что ошибочное объявление этого случая для
  будущего инлайн-правила не поймается ничем). Находка закрыта тем же пином —
  ирония в том, что оба существовавших носителя случая как раз и были такой
  ошибкой.
- **README Finding и лишняя пустая строка** (Codex, LOW) — поправлены.
- Отвергнута одна гипотеза (Codex): ковариантность сужённых возвращаемых типов
  ничего не ломает — все 27 классов `final readonly`, наследника быть не может,
  а расширение поля до `float` даст громкую ошибку в том же файле.

**Что это говорит о методе, а не об этих двух классах.** Свидетель по поведению
`getSeverity()` действителен только для правил, которые ему делегируют. Для
правила, решающего в `analyze()`, отсутствие точки переключения не есть
свидетельство отсутствия границы — надо читать условие эмиссии. Это записано и в
шапке перечисления, потому что переживёт эти два класса.
