## Кандидаты в control

- **`Baseline/Integration/MemoryCeilingManifestTest.php`** — единственный метод целиком сверяет JSON-манифест (`Fixtures/BaselineV10/memory-ceiling.json`) с `benchmarks/composer.lock`: имя пакета, версия, дата измерения, формат команды. Ни строки продуктового кода не исполняется. Собственный докблок прямо говорит: «deliberately a verification command, not a PHPUnit test» — сам автор теста признаёт его нештатность.
- **`Baseline/Integration/ResidualLimitationsCoverageTest.php`** — регексом парсит секцию «Residual limitations» `docs/adr/0017-baseline-ceiling.md`, затем рефлексией проверяет, что на каждый пронумерованный пункт документа есть публичный `#[Test]`-метод где-то в кодовой базе тестов. Это контроль состояния документации/индекса, а не поведения `src/`.
- **`Baseline/Unit/ChannelRenameTsvGateAgreementTest.php`** — SUT (`QmxFindingGate\RenameMaps`) физически лежит в `scripts/finding-gate/` и не подключён к продуктовому автозагрузчику (классы `require_once` вручную). Тест проверяет вспомогательный скрипт гейта эквивалентности находок, а не `src/`.
- **`Baseline/Functional/BaselineCommandOptionSurfaceTest.php::itKeepsRepositoryEntrypointsOnTheBaselineLifecycleSurface`** — не весь файл, а один метод: читает содержимое `action.yml`, `docker-compose.yml`, `scripts/pre-commit-hook.sh` и ищет в них подстроки. Контроль состояния репозитория внутри иначе функционального файла.
- (пограничный, не выделен отдельной строкой) **`Baseline/Unit/ChannelRenameMapTest.php::itReadsTheRepositorysOwnDeclaredChannelMap`** — читает трекаемый `finding-gate/maps/channels.tsv`, но через продуктовый класс `ChannelRenameMap`; не чистый control, упомянут для полноты.

Control-invariant (рефлексия по ВСЕМ классам одного контракта, не по одному классу) в этом срезе — ближе всего:
- `Inline/Unit/ThresholdOverrideIntegrationTest.php::itPreservesAllFieldsViaReflectionForAllThresholdAwareOptions` — рефлексией проверяет ВСЕ классы, реализующие `ThresholdAwareOptionsInterface` (не весь `src/`, но весь класс контрактов). Решение по границе — за владельцем; здесь это один метод внутри теста, категоризированного как integration за счёт остальных 12 методов, поэтому отдельной строкой в control не вынесен.

## Дубли и противоречия

Настоящих дублей (тот же SUT + то же утверждение) и противоречий (два теста утверждают несовместимое про одно поведение) в срезе не найдено. Названы структурные параллели, которые выглядят как дубли по имени метода, но таковыми не являются:

- **`Baseline/Unit/BaselineCeilingStageAcceptanceTest.php` vs `Baseline/Unit/GroupAcceptanceTest.php`** — оба проверяют «правило приёмки группы» ADR 0017 на похожих кейсах (например, `itAcceptsWhenTheBestStoredMemberWasRepaired` / `itAcceptsAGroupWhoseBestMemberWasRepaired`). Не дубль: `GroupAcceptanceTest` бьёт по чистому примитиву `GroupAcceptance`, `BaselineCeilingStageAcceptanceTest` — по `BaselineCeilingStage`, который оборачивает тот же примитив в `Finding`-шейпед сценарий и обязан реально его вызывать (это явно объяснено в докблоке `BaselineUpdaterTest`: «GroupAcceptanceTest already pins the primitive; this pins that BaselineUpdater actually calls it»). Двухслойное покрытие — намеренное и оправданное.
- **`Baseline/Unit/ChannelRenameMapTest.php` vs `Baseline/Unit/ChannelRenameTsvGateAgreementTest.php`** — оба используют один и тот же провайдер данных `ChannelRenameTsvCorpus::cases()` и оба метода называются `itAnswersTheSharedCorpusAsDeclared`. Не дубль: SUT разный (`ChannelRenameMap` из `src/` против `QmxFindingGate\RenameMaps` из `scripts/finding-gate/`) — это намеренная проверка **согласия двух независимых читателей** одного формата (докблок второго теста прямо это объясняет). Смысл пары — в расхождении SUT, а не в совпадении.
- **`Inline/Unit/IndependentAxisValidatorTest.php`, `InvertedOverrideValidatorTest.php`, `StandardOverrideValidatorTest.php`, `WarningOnlyValidatorTest.php`** — совпадающая структура кейсов (`itIsASharedSingleton`, `itAccepts...`, `itRejects...`, `itAcceptsNullsAsNoOpHalves`). Не дубль: это четыре разных класса-валидатора одной стратегии (вероятно `OverrideValidatorInterface`), с разными и местами противоположными правилами (`StandardOverrideValidator` требует warning ≤ error, `InvertedOverrideValidator` — наоборот). Параллельная структура — правильный способ тестировать симметричное семейство.

## Чем проверено и чего этот способ не видит

Метод разведки был двухуровневым и не эквивалентен построчному ревью каждого файла:

1. **Скриптовая проверка §9** (регэксп по `#[Test]` + следующая сигнатура `public function`) прогнана по всем 71 файлам без исключений — нарушений (отсутствие атрибута, имя не в форме `itXxx`) не найдено. Это надёжно: проверка синтаксическая, ложноположительных срабатываний после ручной перепроверки не осталось.
2. **Полное чтение исходного кода** (докблок класса + докблок каждого метода + сигнатура, без тела метода) — сделано для всех 71 файлов. Тела методов полностью прочитаны примерно для 15 файлов из 71 (в основном Baseline/Functional/* в первой трети работы, плюс все файлы, отмеченные как control-кандидаты или с дефектом категории).
3. Для оставшихся ~56 файлов решение о категории/SUT/дублях опирается на: `#[CoversClass]`, докблок класса (в этой кодовой базе докблоки исключительно содержательны и сами называют, что тест проверяет и почему кейс не избыточен — что подтвердилось на всех проверенных вручную файлах), имена и докблоки методов, и точечные grep-проверки (например, поиск `flock(`, `proc_open`, `symlink(` для решения вопроса unit/integration).

**Что этот способ не видит:**
- Тонкие тавтологии внутри тела метода (assert на переменную, которую сам же тест только что вычислил тем же способом, что и SUT) — такое видно только при чтении тела, а тела прочитаны не все. Риск занижен тем, что докблоки в этой кодовой базе systematически называют, ПОЧЕМУ кейс не тривиален (см. многочисленные «without this, an implementation that X would still pass» — сама культура написания тестов ориентирована против тавтологий), но гарантии нет.
- Скрытые дубли утверждений, различающиеся только именем метода и докблоком, но не найденные grep’ом по одинаковым именам — не исключены на непрочитанных телах.
- Фактическая работоспособность тестов не проверялась: `composer check`, PHPUnit и `bin/qmx` запускать было прямо запрещено брифом. Всё сказанное — вывод из чтения кода, не из прогона.
- Родственные файлы вне среза (`src/Analysis/Policy/Baseline/*`, `src/Analysis/Policy/Inline/*`) читались только выборочно (для проверки SUT по `#[CoversClass]` и природы I/O в спорных файлах), не целиком — соответствие теста поведению SUT принято на веру докблоков и сигнатур там, где не было прямого сомнения.

## Допущения

- «Правильный каталог» оценивался только на уровне `Unit`/`Integration`/`Functional`/`control` внутри `tests/Analysis/Policy/{Baseline,Inline}/` — вопрос о переносе между `Baseline/` и `Inline/` не возникал: расположение по предмету (baseline vs inline-директивы) везде совпадает с владеющим `src/`-предметом.
- Классификация control/control-invariant — рекомендация, не факт: по инструкции брифа решение остаётся за владельцем. Где я привожу тест как control-кандидат, я исхожу из буквального критерия брифа («проверяет не поведение продуктового кода, а состояние репозитория... либо сканирует src/ рефлексией... scripts/, finding-gate/»).
- Для `ChannelRenameTsvGateAgreementTest` и `ChannelRenameMapTest` я не переношу в отдельную папку и не предлагаю конкретный «правильный каталог» — институционально они образуют пару, проверяющую согласие двух читателей одного контракта; если control-тест вообще стоит выносить из test-suite (как того требует бриф-контекст «по требованию владельца»), то только вместе с объяснением, зачем эта пара существует, а не изолированно.
- Не проверялось, актуальны ли числа/версии в `MemoryCeilingManifestTest` (например, реально ли текущий `laravel/framework` в `benchmarks/composer.lock` совпадает с зафиксированным) — задача была классифицировать тест, а не валидировать его данные.
