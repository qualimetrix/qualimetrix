## Q1 — nested PSR-4 roots and `expectedNamespace()`

`governance/TestSuiteHygiene/NamespacePathAllowList.php::expectedNamespace()` (`:156-177`) resolves a path against every declared root and keeps the **longest matching root directory string**:

```php
foreach ($roots as $prefix => $root) {
    if (!str_starts_with($relativePath, $root . '/')) {
        continue;
    }
    if ($bestRoot === null || \strlen($root) > \strlen($bestRoot)) {
        $bestRoot = $root;
        $bestPrefix = $prefix;
    }
}
```

For a hypothetical `scripts/promise-effect/tests/` nested inside a hypothetical `scripts/promise-effect/` PSR-4 root, the **nested (deeper/longer) root wins** — this mirrors Composer's own PSR-4 autoloader resolution, which also picks the most specific (longest) matching prefix. `TestTree::testFiles()` (`:153-177`) independently guards against double-counting such a file under both roots: it accumulates results into an associative array keyed by path (`$files[$file] = true`) before flattening, so a file inside both a nested and an enclosing root is judged exactly once, not twice, per the docblock at `:156-159` ("A root nested inside another is a shape `NamespacePathAllowList` already resolves, so it reaches here too, and a file under both would otherwise be counted twice").

**Confirmation without a repo-modifying probe**: `governance/TestSuiteHygiene/TestNamespacesFollowTheirPathTest.php::itRefusesEachWayOnTheDeclarationsItIsGiven` (`:86-133`) already exercises exactly this nested-root case with a synthetic root map (`'Acme\Tests' => 'probe', 'Acme\Tests\Deep' => 'probe/deep'`), asserting `expectedNamespace($roots, 'probe/deep/Unit/ThreeTest.php') === 'Acme\Tests\Deep\Unit'` with the comment "The longest root wins, the way the autoloader resolves a nested one." I ran this test in isolation:

```
vendor/bin/phpunit --no-coverage --filter TestNamespacesFollowTheirPathTest \
  governance/TestSuiteHygiene/TestNamespacesFollowTheirPathTest.php
# OK (4 tests, 14 assertions)
```

No tracked file was modified for this; the test already encodes the nested-root scenario against a synthetic map, so a live registration probe against `composer.json` was unnecessary and would have added risk (an autoload-dev edit requiring `composer dump-autoload`) for no additional evidence — `git status --porcelain` was empty before and after.

## Q2 — `DEVELOPMENT_NAMESPACE_PREFIXES` and the silent-failure mechanism

`scripts/generate-modular-architecture-production-inventory.php:993-996`:

```php
const DEVELOPMENT_NAMESPACE_PREFIXES = [
    'Qualimetrix\\Tests\\',
    'Qualimetrix\\Governance\\',
];
```

This list is checked at `:1000-1013`: for every production dependency edge, if it `str_starts_with()` one of these two prefixes, it is collected into `$productionToTestRows` and the whole run `fail()`s naming every offence. **Any dependency on a development namespace whose prefix is not in this array is invisible to the check — it is neither collected nor reported, and the run exits 0.**

Two things follow directly from reading `composer.json:56-61`:

1. **This is already a live gap, not a hypothetical one for the planned move.** `Qualimetrix\PhpStan\` (mapped to `tools/phpstan/`) is a third `autoload-dev` PSR-4 root today, and it is absent from `DEVELOPMENT_NAMESPACE_PREFIXES`.
