# v0.26 — renamed published names

Five channel codes, one metric key and one configuration key change in this
release. Nothing else moves: severities, thresholds, subject keys, occurrence
keys and every other published field are unchanged.

| old                            | new                         | where you meet it                         |
| ------------------------------ | --------------------------- | ----------------------------------------- |
| `architecture.coverage`        | `architecture.coverage-gap` | channel code and rule name                |
| `complexity.cyclomatic`        | `complexity.ccn`            | channel code and rule name                |
| `design.inheritance`           | `design.dit`                | channel code and rule name                |
| `duplication.code-duplication` | `duplication.clone`         | channel code and rule name                |
| `maintainability.index`        | `maintainability.mi`        | channel code and rule name                |
| `design.type-coverage.pct`     | `design.type-coverage.all`  | metric key                                |
| `coverage:`                    | `coverage-gap:`             | configuration key, inside `architecture:` |

`v0.26-rename-map.tsv` beside this file is the same table in the format
`bin/qmx baseline:rename-channels` reads. It carries the five channel codes,
which is the only class a command can migrate.

## The four things that change for you

**Migration is not one command.** One class has a command; the other three do
not, and one of them is silent.

### 1. Your baseline file — a command, but two steps

An accepted entry whose `channel` is an old name stops suppressing anything:
the finding it covered comes back at its own severity. The stale entry is not
itself a refusal — it prints `N baseline entries could not be applied` and does
not fail the run on its own. Whether the run then passes is decided by the
finding that came back and by your `--fail-on`, not by the stale entry.

For CI that is the worst shape: the build can stay green while a suppression
evaporates, or redden for a reason its own output never names.

```bash
# 1. bring the file to the current baseline version first — the carry
#    substitutes a name and converts nothing, and refuses an older version
bin/qmx baseline:generate qmx-baseline.json src/     # or your existing upgrade step
# 2. then carry the names
bin/qmx baseline:rename-channels qmx-baseline.json v0.26-rename-map.tsv
```

### 2. Your configuration and command line — loud, exit 3

`qmx.yaml` (`rules:`, `only_rules:`, and the `architecture:` section's
`coverage:` key), `--rule-opt=`, `--disable-rule=`, and any `computed_metrics`
formula reading `m["design.type-coverage.pct"]`. An old name is an unknown rule,
an unknown option owner, an unknown key or an unknown metric: the run refuses
with **exit 3** and does not fall back to a default.

Where the refusal names the allowed keys it lists the new one, e.g.

```
Configuration error: architecture: unknown key "coverage".
Allowed keys: "layers", "allow", "coverage-gap", "max_expanded_layers".
```

Rename by the table above. There is no command for this class.

### 3. `@qmx-ignore` / `@qmx-threshold` in your own source — silent loss of suppression

A directive naming an old channel becomes `annotation.unresolved-directive`.
It is reported, so you will see it — but the finding it used to suppress comes
back at the same time. Rename these by hand; there is no command.

### 4. Anything that stored our output — silent, and the only unannounced class

SARIF `ruleId` and `rules[].name`, GitLab `check_name` and `fingerprint`,
Checkstyle `source`, the JSON and metrics field values, and any dashboard column
keyed on a channel code. The old spelling simply stops appearing. Nothing fails;
your history splits in two unless you migrate the store by the table above.
