files), `tests/Analysis/Evidence/Complexity/` (14 files). Total 70 files — matches the number of
rows in the table.

Method: CodeSmell and Security were read and analyzed in full by two parallel agents (a full
reading of every file + a check against `src/`); Complexity was read and analyzed directly by me
(a full reading of every file, plus a look at the `CallableToClassAggregator`,
`CyclomaticComplexityCollector` sources in `src/` to establish the real SUT where the import
doesn't give it directly).

## Duplicates and contradictions

1. **CognitiveComplexityCollectorTest ↔ CognitiveComplexityVisitorTest** (Complexity). Both run
   the same PHP code through the same engine (`CognitiveComplexityVisitor` inside
   `NodeTraverser`), differing only in the entry point (via `Collector::collect()` vs directly
   through the visitor). The `single if`/`if-else`/`nested if`/`and chain`/`switch`/`ternary`/
   `null coalescing`/`try-catch`/`recursion` cases in
   `CognitiveComplexityVisitorTest::provideComplexityCases`'s data provider literally repeat the
   identically named tests in `CognitiveComplexityCollectorTest`
   (`itCountsSingleIfAsOnePoint`, `itCountsNestedIfWithNestingBonus`, `itCountsLogicalOperators`,
   `itCountsSwitchAsOnePoint`, `itCountsEachCatchClause`, `itCountsTernaryAsOnePoint`,
   `itCountsNullCoalescingAsOnePoint`, `itCountsRecursiveCall`) — the same input snippets, the
   same expected values. The CyclomaticComplexity counterpart doesn't have this problem: there
   `CyclomaticComplexityVisitorTest` checks a completely different aspect (scoping/metadata via
   `VisitorMethodContext`, only 3 tests), not decision-point counting — the entire decision-point
   matrix lives only in `CyclomaticComplexityCollectorTest`. This shows the divergence is not a
   systemic project style, but a specific redundancy in the Cognitive file pair specifically.

2. **WmcIntegrationTest: tests 1/2/4 inside one file** (Complexity).
   `itMakesWmcMetricAvailableAfterAggregation`, `itVerifiesWmcEqualsCcnSum` and
   `itComputesWmcForMultipleClasses` construct different sets of methods/classes, but check one
   and the same fact: a class's `complexity.wmc` equals the sum of its methods'
   `complexity.ccn`. Test 3 (`itHandlesClassWithoutMethodsGracefully`) is the only one that
   really checks a different angle (an empty class).

3. **LongParameterListVoPropagationTest ↔ LongParameterListRuleTest (the VO section) ↔
   ParameterCountCollectorTest** (CodeSmell). All three cover the same historical bug — the
   `isVoConstructor` flag wasn't propagated through `getCallablesWithMetrics()` into
   `LongParameterListRule`. The scenarios (VO below the threshold / a VO warning / non-VO at the
   usual thresholds) structurally coincide at three levels of depth (real AST / a stub MetricBag
   / plain collector output) with no explicit cross-reference — it isn't obvious to a reader that
   this is one and the same regression story, spread across three files.

4. **EvalRuleTest::itReportsAnErrorForEachEvalUsage ↔
   CodeSmellLinePrecisionTest::itCreatesASingleFindingWithTheCorrectLineForASingleOccurrence**
   (CodeSmell). Both check one finding, error severity, a specific line for `eval()`; the
   difference is the input source (a stub vs a real parser). Partial, not complete, overlap.

5. **IdenticalSubExpressionCollectorTest ↔ IdenticalSubExpressionVisitorTest** (CodeSmell) —
   not a duplicate, but a misdistribution: the file named after the collector contains one
   trivial test (`itDeliberatelyDoesNotProvideCallableMetrics`), while the collector's real
   tests (`itIntegratesWithCollectorCorrectly`, `itProducesNoCollectorFindingsForCleanCode`,
   `itReturnsCollectorName`, `itProvidesExpectedMetricKeys`) live in the `*VisitorTest` file
   under someone else's `#[CoversClass]`.

6. **CredentialLiteralsTest ↔ HardcodedCredentialsVisitorTest** (Security). The classification
   semantics (`SensitiveNameMatcher` + the value shape → `CredentialLocation`) is checked twice:
   first on bare AST nodes (`CredentialLiterals::locations()` directly), then through a full
   parser+traverser+visitor, which is a thin wrapper over the same `CredentialLiterals`
   (`HardcodedCredentialsVisitor.php:40`). ~15 of ~30 `provideDetectionCases` cases repeat
   `CredentialLiteralsTest`'s cases almost verbatim ('password hash', 'token storage', 'cache
   key', 'bare token/key', 'option password constant', dot-notation). The Visitor test's
   justified remainder is only the wiring (the declaration index, reset, subject assignment).

7. **SensitiveNameMatcherTest ↔ (CredentialLiteralsTest, HardcodedCredentialsVisitorTest)**
   (Security) — the non-sensitive name set (`passwordHash`, `tokenStorage`, `cacheKey`, bare
   `token`/`key`, `OPTION_PASSWORD`) is tested at the matcher level, then wrapped again into full
   declarations and re-run as separate scenarios in two more files — a legitimate test pyramid,
   but with a large amount of copy-pasted input data.

8. **SqlInjectionDetectorTest / XssDetectorTest / CommandInjectionDetectorTest ↔
   SecurityPatternVisitorTest** (Security) — the largest duplicate in the slice.
   `SecurityPatternVisitor` is a documented thin dispatcher over three Detector classes.
   `provideSqlInjectionCases`/`provideXssCases`/`provideCommandInjectionCases` in
   `SecurityPatternVisitorTest` reproduce 30+ scenarios one-for-one with the three
   `*DetectorTest` files ('$_SESSION not dangerous', 'exec with escapeshellarg', 'concat with
   SELECT', 'echo htmlspecialchars', int-cast scenarios, etc.), differing only in that the code
   is now parsed rather than hand-built. The Visitor test's justified remainder is the dispatch
   logic itself (`itGetsLocationsByType`, `itResetsClearsState`, the absence of double-counting
   a nested `Concat` via `concatDepth`).

Not found (not a defect, but a systemic, deliberately documented pattern that doesn't deserve
its own defect row in the table): eight rule tests in CodeSmell (`BooleanArgumentRuleTest`,
`EvalRuleTest`, `ExitRuleTest`, `GotoRuleTest`, `EmptyCatchRuleTest`, `DebugCodeRuleTest`,
`CountInLoopRuleTest`, `SuperglobalsRuleTest`) repeat the same `itKeysOccurrenceToItsOwnSmellType`
pattern with an identical explanatory comment — each pins the literal of its own `SMELL_TYPE`,
which is exactly the pattern's purpose (an anti-tautology against accidentally copying the
constant). Similarly, three *RuleTest files in Security (`CommandInjectionRuleTest`,
`SqlInjectionRuleTest`, `XssRuleTest`) and three *RuleTest files in Complexity
(`ComplexityRuleTest`, `CognitiveComplexityRuleTest`, `NpathComplexityRuleTest`) are structurally
identical to each other — but each has its own SUT (different Rule classes), which is the
expected shape for rules implementing a shared contract, not copy-pasting the same assertion.

Contradictions found (two tests asserting incompatible things about the same behavior) — none.
CLAUDE.md §9 violations (testXxx / no `#[Test]` / a bare verb phrase) — none across all 70 files.

## How this was checked and what this method cannot see

- **Reading completeness.** CodeSmell (38 files) and Security (18 files) were read in full by
  two parallel subagents, each reading the whole file with the Read tool, not a grep; the §9
  check and the SUT were established from the code actually read (imports + what is actually
  instantiated), not from the file name. Complexity (14 files) was read by me: part of the files
  (`WmcIntegrationTest`, `*OptionsTest`, `ComplexityRuleTest`, `WmcRuleTest`,
  `NpathExpressionCalculatorTest`) — in full; part of the large files
  (`CognitiveComplexityCollectorTest`, `CognitiveComplexityVisitorTest`,
  `CyclomaticComplexityCollectorTest`, `CyclomaticComplexityVisitorTest`,
  `NpathComplexityCollectorTest`, `NpathComplexityRuleTest`) — via a `grep`-extracted list of
  method names and `use` imports plus a targeted deep read of specific sections (where the name
  list hinted at duplication or raised a control suspicion). This means: for the large
  Complexity files, the defect table rests on matching test NAMES and data-provider structure,
  not on a line-by-line reading of every assertion. For
  `CognitiveComplexityCollectorTest`/`CognitiveComplexityVisitorTest` the duplicate is confirmed
  by a direct code comparison (not just names) — both fragments were read in full there. For
  `CyclomaticComplexityCollectorTest`, `NpathComplexityCollectorTest`,
  `NpathComplexityRuleTest`, the conclusion "no duplicates between files" rests on the method
  name list + the absence of a same-named "sibling" Visitor/Collector file — the risk of missing
  intra-file redundancy (several tests inside ONE file covering the same case) is higher in
  these three files than in the files read in full.
- **The SUT was determined by imports and actual instantiation**, not by the file name — where
  this diverged (`IdenticalSubExpressionCollectorTest`, `WmcIntegrationTest`), it is explicitly
  named as a defect or a location clarification.
- **No test and no static analyzer was ever run** (per the brief's direct prohibition) — every
  conclusion about behavior rests on reading the test's code and (where the formula needed
  establishing) reading the corresponding class in `src/`. Consequence: if a test actually fails
  or always passes because of a bug in the test itself (e.g. an unreachable assertion, a
  misplaced mock expectation), this audit won't catch it — only a PHPUnit run with coverage
  could show that.
- **The notion of "duplicate" in this report is heuristic**: the input PHP snippets/values and
  the final assertions were compared by meaning, not byte for byte. Some flagged "duplicates"
  technically check different levels of abstraction (a stub MetricBag vs real AST, bare AST
  nodes vs a full traversal) — this is deliberately NOT equated with a tautology (described
  separately), but economically it's still a repeated run of the same product output, which is
  exactly what the brief asked to look for.
- **The git history connection was not checked** (who added each test, when and why) — some
  overlaps could be deliberate regression duplication after a specific incident (see
  "Regression: ..."-style explanatory docblocks in several Complexity/CodeSmell files) — where
  such a docblock was clearly visible, it was accounted for in the classification (not flagged
  as accidental copy-paste).
- **The "correct directory" assessment** rested on matching the test's namespace against the
  `src/Analysis/Evidence/{CodeSmell,Security,Complexity}/` tree, not on a full walk of
  neighboring domains (`Policy/Inline`, `Run`) — for `NamespaceExclusionOccurrenceTest` and
  `PropertyHookControlPrecedenceTest` "the wrong domain" is named, but the exact target
  directory inside `Policy/Inline`/`Run` is not verified structurally (only by the spirit of the
  test).

## Assumptions

- The unit/integration/functional/control split followed the brief's definition literally: the
  presence of a real `NodeTraverser`+`Parser` without a DI container was classed as `unit` if
  the behavior of one explicit SUT class is checked (even when the parser and visitor are real)
  — this matches the project's practice (`CoversClass` on one/two classes). Files where a
  Collector wraps a Visitor and their joint work with `DeclarationRegistrarFactory` is tested are
  marked `integration`, since that's at least two cooperating classes with shared state (the
  declaration index).
- `CodeSmellRuleContractTest.php` is marked mixed (`control-invariant` + `integration` in one
  file) instead of choosing one category per file — the brief doesn't forbid this (the category
  is given "per file", but the file is heterogeneous inside), leaving the decision to
  merge/split the file to the owner.
- For `Unit/RepeatedConditionsTest.php`/`Unit/RepeatedExpressionsTest.php` (thin coverage, one
  or two tests) I don't consider this a defect by itself — the VO looks like a narrow delegate,
  not undertested logic; the final decision on coverage sufficiency belongs to the owner.
- The "Defects" rows in the table for files with no found explicit problems are marked "none" —
  this means "no duplicate/tautology/contradiction/§9 violation/lying name was found", not "the
  test is ideal in its case composition" — domain-coverage completeness (whether all important
  cases are provided for) is outside this audit's perimeter.
- The `Integration`/`Unit` directories in the tests themselves match the category only
  partially: several files live in `Unit/`, but actually use the real
  `Parser`+`NodeTraverser`+`DeclarationRegistrarFactory` (i.e. by my categorization —
  `integration`); I don't consider this directory-name/category mismatch a "placement" defect
  in the brief's sense (the subject folder is correct — `Security`/`CodeSmell`/`Complexity`),
  only the `Unit` vs `Integration` label itself within the domain isn't always accurate.
