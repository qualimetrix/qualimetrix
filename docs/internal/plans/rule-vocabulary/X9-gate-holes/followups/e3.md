# Запись для FOLLOWUPS.md — пакет E3 захода Х9

## Х9 (2026-09-05) — разрешение стража стало парой `файл:литерал`

### Закрыта запись Х8 «Разрешительная запись стража освобождает файл целиком, а мета-страж проверяет непустоту»

`ALLOWED_FILES` (`array<string, string>`, файл → причина) заменена на
`ALLOWED_LITERALS` (`array<string, array<string, string>>`, файл →
[литерал → причина]) в `RuleIdentifierLiteralGuardTest`. Основной страж
(`noProductionFileOutsideARuleOrChannelsOwningCapabilityHoldsItsLiteral`)
пропускает теперь не файл целиком, а ровно те литералы, что перечислены для
этого файла; новый литерал в разрешённом файле судится как любой другой.
Мета-страж (`everyNamedFileStillEarnsItsEntry`) переписан под пары: для
каждой пары проверяется существование файла, присутствие литерала среди
строковых литералов файла и то, что владелец литерала всё ещё отличается от
владельца файла — стухшая пара (файл удалён, литерал больше не встречается,
или перестал быть чужим) считается находкой.

### Перенос из `enumeration-overlap-sites.tsv` был неполным для одного файла — нашёл второй свидетель

Таблица Х8 (`docs/internal/plans/rule-vocabulary/X8-one-string-two-jobs/enumeration-overlap-sites.tsv`)
даёт 20 строк `cure=allow-file`: 18 для `MetricName.php`, по одной для
`JsonFormatter.php` и `JsonOffenderSection.php`. Механический перенос этих 20
плюс 16 строк `cure=none-already-allowed` для
`RuleThresholdKeyGroupRegistry.php` (тот же файл был разрешён целиком и в
Х8 не редактировался — 16 литералов из его собственного файлового
разрешения) дал 36 пар. Вторым свидетелем стал сам страж: прогон против 36
перенесённых пар покраснел на `RuleThresholdKeyGroupRegistry.php` с шестью
литералами, которых нет ни в одном из двух списков TSV
(`complexity.cyclomatic`, `code-smell.long-parameter-list`,
`code-smell.constructor-overinjection`, `maintainability.index`,
`design.inheritance`, `duplication.code-duplication`).

Причина расхождения: `enumeration-overlap-sites.tsv` — таблица Х8 —
перечисляла места пересечения написания метрики и канала (её собственный
предмет), а не каждый литерал, ради которого файл был разрешён целиком.
`RuleThresholdKeyGroupRegistry.php` держит 22 литерала правил
(`ThresholdParser::parse()` ключи), из которых лишь 16 совпадают по
написанию с метрикой и потому попали в артефакт Х8; оставшиеся 6 — чисто
`rule-name`-литералы без метрического двойника, вне предмета той таблицы.
Итоговый список — все 22 (сверено вторым прогоном стража, зелёный).

**Итог счёта:** 18 (`MetricName.php`) + 22 (`RuleThresholdKeyGroupRegistry.php`)
+ 1 (`JsonFormatter.php`) + 1 (`JsonOffenderSection.php`) = 42 пары, вместо
36 механически перенесённых из TSV.

### Асимметрия «снятие пары красит основной страж, а не мета-страж» подтверждена по построению и мутацией

Мета-страж итерируется по `ALLOWED_LITERALS`, поэтому снятая пара для него
просто не существует — он не может о ней ничего утверждать. Основной страж
теряет пропуск ровно для этого литерала и красит его как чужой. Названо в
докблоке `ALLOWED_LITERALS`; проверено мутацией на одной паре
(`JsonFormatter.php` → `coupling.class-rank`): снятие покраснило только
`noProductionFileOutsideARuleOrChannelsOwningCapabilityHoldsItsLiteral` с
единственной находкой по этому файлу и литералу, `everyNamedFileStillEarnsItsEntry`
остался зелёным. Возврат пары — снова три теста зелёных (317 assertions).

### Что закрыто

Запись Х8 «Ещё одна асимметрия, найденная ревью» и «Что закроет: разрешение,
чей предмет — место, а не файл» — закрыты. Дальнейшего хвоста нет: новый
литерал ни в одном из четырёх разрешённых файлов больше не наследует чужое
разрешение.
