## Control candidates

- **`Baseline/Integration/MemoryCeilingManifestTest.php`** — its single method checks the JSON
  manifest (`Fixtures/BaselineV10/memory-ceiling.json`) against `benchmarks/composer.lock`
  entirely: package name, version, measurement date, command format. Not a line of product code
  executes. The docblock itself says outright: "deliberately a verification command, not a
  PHPUnit test" — the test's own author admits its non-standard nature.
- **`Baseline/Integration/ResidualLimitationsCoverageTest.php`** — parses the "Residual
  limitations" section of `docs/adr/0017-baseline-ceiling.md` with a regex, then checks via
  reflection that every numbered item in the document has a public `#[Test]` method somewhere in
  the test codebase. This is a check on documentation/index state, not on `src/` behavior.
- **`Baseline/Unit/ChannelRenameTsvGateAgreementTest.php`** — the SUT
  (`QmxFindingGate\RenameMaps`) physically lives in `scripts/finding-gate/` and is not wired into
  the product autoloader (classes are `require_once`d manually). The test checks the
  finding-equivalence gate's helper script, not `src/`.
- **`Baseline/Functional/BaselineCommandOptionSurfaceTest.php::itKeepsRepositoryEntrypointsOnTheBaselineLifecycleSurface`**
  — not the whole file, just one method: it reads the contents of `action.yml`,
  `docker-compose.yml`, `scripts/pre-commit-hook.sh` and searches them for substrings. A
  repository state check inside an otherwise functional file.
- (borderline, not given its own row)
  **`Baseline/Unit/ChannelRenameMapTest.php::itReadsTheRepositorysOwnDeclaredChannelMap`** —
  reads the tracked `finding-gate/maps/channels.tsv`, but through the product class
  `ChannelRenameMap`; not pure control, mentioned for completeness.

Control-invariant (reflection over EVERY class of one contract, not over a single class) — the
closest fit in this slice:
- `Inline/Unit/ThresholdOverrideIntegrationTest.php::itPreservesAllFieldsViaReflectionForAllThresholdAwareOptions`
  — checks EVERY class implementing `ThresholdAwareOptionsInterface` via reflection (not all of
  `src/`, but the entire contract class). The boundary decision belongs to the owner; here it's
  one method inside a test categorized as integration because of its other 12 methods, so it
  isn't given a separate row under control.

## Duplicates and contradictions

No real duplicates (the same SUT + the same assertion) and no contradictions (two tests
asserting incompatible things about the same behavior) were found in this slice. Named below are
structural parallels that look like duplicates by method name but are not:

- **`Baseline/Unit/BaselineCeilingStageAcceptanceTest.php` vs
  `Baseline/Unit/GroupAcceptanceTest.php`** — both check ADR 0017's "group acceptance rule" on
  similar cases (e.g. `itAcceptsWhenTheBestStoredMemberWasRepaired` /
  `itAcceptsAGroupWhoseBestMemberWasRepaired`). Not a duplicate: `GroupAcceptanceTest` targets
  the plain primitive `GroupAcceptance`, `BaselineCeilingStageAcceptanceTest` targets
  `BaselineCeilingStage`, which wraps that same primitive in a `Finding`-shaped scenario and must
  actually call it (this is explicitly explained in `BaselineUpdaterTest`'s docblock:
  "GroupAcceptanceTest already pins the primitive; this pins that BaselineUpdater actually calls
  it"). Two-layer coverage — deliberate and justified.
- **`Baseline/Unit/ChannelRenameMapTest.php` vs `Baseline/Unit/ChannelRenameTsvGateAgreementTest.php`**
  — both use the same data provider `ChannelRenameTsvCorpus::cases()` and both methods are named
  `itAnswersTheSharedCorpusAsDeclared`. Not a duplicate: the SUT differs (`ChannelRenameMap` from
  `src/` versus `QmxFindingGate\RenameMaps` from `scripts/finding-gate/`) — this is a deliberate
  check of **agreement between two independent readers** of one format (the second test's
  docblock explicitly explains this). The point of the pair is the divergence of SUT, not the
  coincidence.
- **`Inline/Unit/IndependentAxisValidatorTest.php`, `InvertedOverrideValidatorTest.php`,
  `StandardOverrideValidatorTest.php`, `WarningOnlyValidatorTest.php`** — matching case structure
  (`itIsASharedSingleton`, `itAccepts...`, `itRejects...`, `itAcceptsNullsAsNoOpHalves`). Not a
  duplicate: these are four different validator classes for one strategy (probably
  `OverrideValidatorInterface`), with different and in places opposite rules
  (`StandardOverrideValidator` requires warning ≤ error, `InvertedOverrideValidator` the
  reverse). Parallel structure is the right way to test a symmetric family.

## How this was checked and what this method cannot see

The recon method was two-tiered and not equivalent to a line-by-line review of every file:

1. **A scripted §9 check** (a regex for `#[Test]` + the following `public function` signature)
   was run over all 71 files without exception — no violations (a missing attribute, a name not
   in `itXxx` form) were found. This is reliable: the check is syntactic, no false positives
   remained after a manual re-check.
2. **A full reading of the source code** (the class docblock + every method's docblock +
   signature, without the method body) was done for all 71 files. Method bodies were fully read
   for approximately 15 of the 71 files (mostly Baseline/Functional/* in the first third of the
   work, plus every file flagged as a control candidate or with a category defect).
3. For the remaining ~56 files, the category/SUT/duplicate decision rests on: `#[CoversClass]`,
   the class docblock (in this codebase the docblocks are exceptionally substantive and
   themselves state what the test checks and why the case isn't redundant — confirmed on every
   manually checked file), method names and docblocks, and targeted grep checks (e.g. searching
   for `flock(`, `proc_open`, `symlink(` to settle the unit/integration question).

**What this method cannot see:**
- Subtle tautologies inside a method body (an assertion on a variable the test itself just
  computed the same way as the SUT) — this is visible only by reading the body, and not every
  body was read. The risk is lessened by the fact that this codebase's docblocks systematically
  state WHY a case isn't trivial (see the numerous "without this, an implementation that X would
  still pass" — the test-writing culture itself is oriented against tautologies), but there is no
  guarantee.
- Hidden assertion duplicates that differ only by method name and docblock, and were not found by
  a grep for matching names — not ruled out in the unread bodies.
- The tests' actual functioning was not verified: running `composer check`, PHPUnit and
  `bin/qmx` was directly forbidden by the brief. Everything said here is inferred from reading
  the code, not from a run.
- Related files outside the slice (`src/Analysis/Policy/Baseline/*`,
  `src/Analysis/Policy/Inline/*`) were only sampled (to check the SUT via `#[CoversClass]` and
  the nature of the I/O in disputed files), not read in full — the test's correspondence to the
  SUT's behavior was taken on faith from docblocks and signatures wherever there was no direct
  doubt.

## Assumptions

- "Correct directory" was assessed only at the `Unit`/`Integration`/`Functional`/`control` level
  inside `tests/Analysis/Policy/{Baseline,Inline}/` — moving between `Baseline/` and `Inline/`
  was never a question: placement by subject (baseline vs inline directives) everywhere matches
  the owning `src/` subject.
- The control/control-invariant classification is a recommendation, not a fact: per the brief's
  instruction the decision remains with the owner. Where I cite a test as a control candidate, I
  go by the brief's literal criterion ("checks not product-code behavior but repository state...
  or scans src/ via reflection... scripts/, finding-gate/").
- For `ChannelRenameTsvGateAgreementTest` and `ChannelRenameMapTest` I don't move them into a
  separate folder or propose a specific "correct directory" — institutionally they form a pair
  checking agreement between two readers of one contract; if a control test should be moved out
  of the test suite at all (as the brief's "at the owner's request" context requires), it should
  be moved only together with an explanation of why this pair exists, not in isolation.
- Whether the numbers/versions in `MemoryCeilingManifestTest` are current (e.g. whether the
  current `laravel/framework` in `benchmarks/composer.lock` really matches the pinned one) was
  not checked — the task was to classify the test, not validate its data.
