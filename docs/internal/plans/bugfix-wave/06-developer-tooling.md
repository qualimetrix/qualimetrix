## Item 1 — `check-code-parallel.py` holds all output until every child exits

**Facts.** Children write to per-child temporary files (chosen to avoid pipe
blocking); `publish()` prints every child's labelled blocks once, after all
children finish and cleanup. After Ctrl-C, output appears only after the
30-second shutdown grace. Tests in `test_check_code_parallel.py` pin the held,
fixed-order output, and the README describes it. `.github/workflows/qmx.yml`
imports this module (`importlib.import_module('check-code-parallel')`); read what
it calls before changing any function signature. Session 05's governance test
reads the `COMMANDS` tuple from this file.

**Decision.** Publish each child's labelled blocks as soon as that child exits
(completion order), from the same temporary files. Do not stream line by line:
it would need pipes or file tailing, which the design avoided on purpose. The
exit-code rule does not change (the first failing child in `COMMANDS` order
decides). On interrupt, a child that exits during the grace period is
published when it exits. Keep `COMMANDS` a tuple literal with the same two
entries.

**Tests.** Rewrite the pinned-order tests to assert what still holds: each
child's stdout and stderr blocks are complete, contiguous and labelled; a child
that exits first is published first (two fake children with different sleeps);
the interrupt test still sees both blocks. Keep the umask, launch-failure,
group-refusal and TERM-ignoring-grandchild tests green.
Run: `python3 -m unittest discover -s scripts/check-code-parallel/tests -p 'test_*.py'`.
Update the README's sentences about held output. ADR 0112 states that the
output is "published in command order": append an amendment
(`## Amendment, <date>: output is published as each command exits`, overview
rule 7) and the `amended <date>: ...` clause on its line in `docs/adr/README.md`.
The ADR's other decisions (the cheap code tests run before `check:parallel`;
the exit-code rule) stay.

## Item 2 — one functional test shares a container across tests

**Facts.** `CheckCommandBaselineTest` keeps `private static ?ContainerBuilder $container`
and reuses it across its nine tests; `beginInvocation()` resets per-invocation
state. Several tests run `runGenerate()` and then `runCheck()` and rely on the
same container inside one test, on purpose. One test already builds its own
container. A container build costs about 0.3–0.7 s.

**Change.** One container per test method (an instance property built lazily),
still shared by all invocations inside that test. Remove the static property
and `tearDownAfterClass()`.

## Item 3 — two integration tests leave `tempnam()` files behind

**Facts.** `CheckFindingProjectionBaselineReportingTest::writeBaseline()` and
`CheckFindingProjectionTest::writeBaseline()` call `tempnam()`, append
`.json`, and unlink only the `.json` path. Both tests already create
`$this->tempRoot` in `setUp()` and remove it recursively in `tearDown()`.

**Change.** Write the baseline inside `$this->tempRoot` (random suffix via
`bin2hex(random_bytes(...))`) and drop the `tempFiles` bookkeeping. Check
first that nothing in the tests assumes the baseline lives outside the analysed
paths.

## Item 4 — the d3 export list is hand-written twice

**Facts.** `html-report/scripts/bundle-d3.js` re-exports a hand-written list
of d3 names into `dist/d3.min.js`; `html-report/vite.config.js` keeps a second
hand list (`rollupOptions.external` and `output.globals`) for
`report.min.js`. `html-report/src` imports ten names from six `d3-*` modules
(`d3-hierarchy`, `d3-scale`, `d3-axis`, `d3-shape`, `d3-selection`,
`d3-format`; in `main.js` and `martin-diagram.js`). `composer html-bundle:check`
rebuilds only `report.min.js`, so a new d3 import passes every check and then
throws in the browser.

**Change.**
- New module `html-report/scripts/d3-imports.mjs` exporting one function that
  reads every `.js` file under `html-report/src` and returns the named imports
  from `d3-*` modules as `{ module: [sortedNames] }`. It handles multi-line
  import lists and `name as alias` (the export is `name`), and throws on a
  default or namespace import from a `d3-*` module (the IIFE bundle only
  re-exports names).
- `bundle-d3.js` builds its entry from that function; `vite.config.js` derives
  `external` and `globals` from it. Neither keeps a list of its own.
- `composer build:js` regenerates both bundles. `d3.min.js` gets smaller:
  the names nothing imports (`selectAll`, `create`, `scaleDiverging`, `rgb`,
  `hsl`, `interpolateRgb`, `transition`) disappear. Before accepting that,
  confirm nothing reaches them through the global:
  `grep -rn "d3\.\|\.transition(" html-report/src html-report/dev.html`.

**Tests.** New `html-report/tests/d3-imports.test.js` (vitest): the scanner on
fixture strings or a temporary directory — multi-line list, alias, non-d3 import
ignored, default import refused — and one assertion that on the real
`html-report/src` it returns exactly the ten current names in six modules.

## Item 5 — a refusal-test template links the live `src/`

**Facts.** `createProjectTemplate()` in `ModularArchitectureGeneratorRefusalTest`
symlinks the checkout's `src` and `vendor` into the scratch project, with a
comment that probes never write production sources. No current probe writes
there (they write `tests/`, `phpunit.xml.dist`, a script copy), but nothing
enforces it. Copying `src` per probe would multiply the cost.

**Change.** Keep the symlinks. In `setUpBeforeClass()` record a snapshot of the
live `src` tree — every entry's relative path, its type (file, directory,
symlink), the content hash of every file (`sha1_file`) and the target of every
symlink — and in `tearDownAfterClass()` assert the snapshot is unchanged, with a
message that names the changed paths. Size and mtime are not enough: a write of
the same size within one second keeps both. Reword the comment to point at the
guard.

Planted defect (revert, do not commit): make one probe overwrite a file under
the project's `src` with different bytes of the same length → the class fails
in `tearDownAfterClass()`. Restore the file before reverting.

cover those rules. `CaseDefinition` refuses unknown keys, so the reason can go
only into `description`.

**Change.** Extend `description` with one sentence: which rules the overrides
silence and that dedicated cases cover them. Change nothing else in the case.
